## 来源支持的机制与定义

固定 README 的 Metrics 表以请求、响应和 benchmark 历时定义指标。它把 TTFT 写为请求发出到首个响应收到的经过时间；request latency 的终点是最终响应。表中文字并未逐一规定空角色、心跳或其他非内容响应的过滤，因此不能只凭这个名字认定它等于本库“首个有效内容”的边界。接入工具时需要核验实际导出事件与计数映射。

| 文档中的量 | 归约对象与分母 | 提炼时必须保留的区别 |
|---|---|---|
| TTFT | 每请求一个发出到首响应的时间 | 首响应、首有效内容、服务端首 token 是不同候选事件 |
| Time to Second Token | 每请求第一与第二个 streaming response 的间隔 | 名称含 token，文字定义使用 response；多 token chunk 时不能推断逐 token 轨迹 |
| ITL | 每个相邻响应间隔除以后一个响应中的生成 token 数 | 这是响应级归一化观测，不是已经观测到全部真实 token 间隔 |
| 每用户输出速率 | 每请求不含第一个 token 的输出量除以该请求生成阶段历时 | 每请求速率的平均、合并间隔的倒数与系统总输出速率不同 |
| Request latency | 每请求发出到最终响应 | 最终协议响应可以晚于最后一个内容 token |
| 输入/输出序列长度 | 每请求 token 数 | 分词器、模板、特殊 token 和输出过滤共同影响计数 |
| 输出 token 吞吐 | benchmark 中输出 token 总数除以 benchmark 历时 | 必须保留输出人口和实际计时窗，不能用各请求速率求和替代 |
| 请求吞吐 | benchmark 中最终响应数除以 benchmark 历时 | 最终响应、质量合格完成与满足联合时延条件的完成并非同一个集合 |

README 的测量区间说明按区间内完成的请求收集观测；这一完成窗口可以包含窗前到达者，并排除窗末尚未完成者。它与固定到达 cohort 加排空截止的设计不同。工具依据最近若干测量的变化执行的稳定性规则，也不证明生产队列已经稳定或尾部概率已被充分估计。

goodput 文档将其定义为每秒满足指定指标约束的已完成请求数，并以 TTFT、ITL 约束作例。这里的工具约束不包含一个自动成立的任务质量证明；必须另行确定质量评价、完整 offered 人口、失败与拒绝规则。特定例子的阈值不是本库默认 SLO。

GPU telemetry 表提供功率、能量、显存、时钟和利用率等观测入口。指标可被采集不等于其分子、单位、采样率、设备范围和实验边界已经与服务计数对齐；它们也不能单独解释吞吐瓶颈。

## InfraAgents 如何据此推导

本库依据这些文档建立明确的指标合同：事件起止、时钟、单位、请求人口、输出计数、统计单位、窗口和未定义原因。逐 token 可见时间已知时，TPOT 使用首末内容时间与 N−1 个间隔；若改用协议最终响应，其多出的尾部必须单列。对照实验还需明确实际发送与计划到达的差、每用户速率与系统吞吐、成功条件与联合 SLO，以及离线质量判定和服务完成的两个截止。这些是本库在固定资料上的推导，不能归称为工具已经实现的全部审计功能。

具体算法与反例见[服务指标](../workloads/metric-events.md)；负载、区组、估计对象和确认实验见[评测设计](../workloads/measurement-comparability.md)；联合资格和容量边界见[Goodput](../workloads/slo-goodput.md)。
