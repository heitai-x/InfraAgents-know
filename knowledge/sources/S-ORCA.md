## 来源支持的机制与定义

Orca 把生成迭代作为调度边界，调度器要求引擎只推进当前批的一次迭代；结束的请求退出，后来请求可在后续边界进入。它改变的是跨请求的等待与批组成，同一请求的下一生成 token 仍依赖前一 token 的结果。§3–4 的选择性聚批将不同历史长度请求的线性操作合并执行，对论文中狭义 Attention 操作则按请求分开。狭义 Attention 不包含 QKV 与输出投影，后两者仍属于有权重的线性操作。

这个历史选择不能推出“变长 Attention 在数学上不可聚批”：现代 ragged 或分页 kernel 可以在同次提交中处理多个独立段。其合法性要求每个段保持自身的 head、位置和可见集合，成本取决于工作划分与布局。ORCA 说明的是把共享权重的线性操作与请求状态访问区别组织的价值，并非限制后续引擎只能逐请求调用 Attention。

§4.2 的 Algorithm 1 按到达顺序选择至多给定数量的请求，在首次调度时为该请求的最大 token 上限预留 KV 槽。每槽对应一个 token 的 K/V 容量；预留充分时，之后增长不致因其他请求占满全部槽而无法推进。该做法付出保守预留的机会成本，是论文的容量选择。逐轮按需分配同样合法，但必须另行处理页不足、准入与恢复进度，不能把论文的无后续分配阻塞保证直接带过去。

论文还让多个批在不同 worker 中流水推进，在达到相应在途批数量后等待完成。它不能使同一请求越过未生成 token 的依赖；调度器要知道一个请求何时可以再次进入。批次 ID、执行顺序与 KV 责任需要保持一致，不能仅凭 host 已发出调用认为上一迭代已完成。

## InfraAgents 如何据此推导

[连续批处理正文](../algorithms/iteration-batching.md)从这些机制推导已知 token 与已完成 KV 的不同边界、压紧行映射，以及预留/提交/完成/取消的完整算法。正文选择每请求最多一轮在途，并按实际近期增量预留页；这是便于说明正确性的独立设计，不是 ORCA Algorithm 1 的复刻。时间预算、轮转公平、数值系数、迟到通知负对照和诊断数据也属于本库设定推导。

检验批处理收益时，应使用同一请求到达与输入输出条件，分别记录开始等待、有效模型工作和交付；更早让一条请求进入批不等于其 ITL 一定更低。原论文的吞吐与延迟结论绑定其模型、并行设置和实验流量，不能当作目标系统可直接达到的指标。
