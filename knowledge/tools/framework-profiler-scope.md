# K-TOOLS-004：框架 Profiler：算子归属、内存与图边界

框架 profiler 把高层操作、主机提交、设备执行、shape、调用栈和内存活动连接起来。它提供的是特定版本、采集配置和窗口内的观测记录。解释性能时，需要先恢复执行实例及其依赖，再讨论耗时和资源；算子名称、时间接近或累计计数本身不足以建立因果归属。

## 观测对象、身份与证据边界

设采集窗口为 `W=[T0,T1)`，配置为 `C`，观测结果为 `O(W;C)`。`C` 包括模型与框架版本、执行模式、负载阶段、启用的活动、shape/stack/memory 选项及硬件条件。事件表示为 `x=(kind,domain,scope,id,[s,e),attrs)`：`domain` 指时钟或计数域；`scope` 保存采集运行、进程、设备、agent、队列等身份；`attrs` 保存 shape、字节、调用栈和关联字段。区间使用半开约定，结束于某时刻的对象与该时刻开始的对象不因此发生重叠。

输入不仅包括事件，还包括字段语义、窗口覆盖情况、编译产物身份和时钟映射。输出包含实例关联、逻辑归属、区间统计、内存账本和未决记录。没有匹配的记录也是输出的一部分，不能因为它没有可用 correlation 就删除。

| 证据 | 成立条件 | 能支持什么 | 仍不能推出什么 |
|---|---|---|---|
| 明确身份关联 | 字段语义已确认，关联键在对应作用域和代次内无歧义 | 某次提交与某些 dispatch 对应 | kernel 内每个融合子操作分别花了多少时间 |
| 范围、包含与顺序 | 范围身份或时钟可比较，依赖与队列顺序有依据 | 父范围、候选集合或先后约束 | 仅凭时间接近建立精确归属 |
| 聚合计数 | 采集对象、事件类型和运行范围明确 | 该范围的资源活动 | 无依据地拆成各 kernel 的贡献 |
| 缺失或截断 | 未启用、未覆盖、无权限或记录不完整 | 当前证据不足 | 零工作、零耗时或某个独有的 stall 原因 |

correlation 连接身份，时钟校准连接时间坐标，两者不能互相替代。即使已经知道某个 API 提交了某个 kernel，也不能直接对两个未校准时钟的时间戳相减。完成时间映射后仍须保留误差界限；若间隔与误差同量级，应保留先后未知。

作用域字段不是一套跨平台固定键。实际工具可能提供进程内 correlation、外部范围 ID、dispatch ID 或编译映射，API 记录未必直接携带设备队列。必须先解释字段如何连接；不能用缺失队列的默认值伪造身份。下文的完整键连接是一个字段齐全、提交键唯一的保守模型。

## 算子、提交与 kernel 的多对多关系

令 `L` 为逻辑算子实例集合，`A` 为提交实例集合，`K` 为设备 dispatch 集合。`P⊆L×A` 表示框架范围与提交的联系，`E⊆A×K` 表示提交与设备工作的联系，逻辑归属为 `R={(l,k) | 存在 a，(l,a)∈P 且 (a,k)∈E}`。关系通常不是一一函数。

一个高层算子可能产生多个 kernel、复制或同步；多个算子可能融合进一个 kernel。一个算子也可能没有设备 dispatch：纯主机计算、惰性结果未求值、优化消除、工作被融合或采集缺失都可能产生这种现象。eager 与 compiled trace 的命名粒度变化不表示工作凭空消失，需要沿输入输出、生成计划和实际执行解释。

同名重复调用必须保留调用实例。嵌套 host 范围中，父模块和叶算子都可能包含同一个提交：父范围的 inclusive 时间用于解释层级，不能与子范围相加成为独立资源成本。真正的融合共享归属也应与这种祖先包含关系区分。只有编译映射、明确标注或其他支持多算子关系的证据，才能把一个 kernel 记为多个逻辑操作共同实现。

host operator duration 与设备持续时间不同。主机范围可能包含参数准备、锁、图构造、入队和等待；设备区间描述所选 dispatch 的执行。异步 API 提前返回，只能证明提交边界发生变化，不能单独证明输出更早完成。设备 kernel 通常也不要求被短暂的入队 API 时间区间包含。

shape 可以暴露历史重算、padding、KV 展开和非连续复制，但需要回到张量的轴、布局、存储身份、产生者与消费者。名为 concatenate 的操作可能真实复制，也可能先形成惰性描述或被后续融合；名称不能替代字节和执行证据。

## 定义、求值、执行与消费的边界

一个结果至少有五个不同边界：定义 `D` 创建操作或图描述；提交 `S` 请求执行；执行 `R` 表示实际设备工作；完成 `C` 表示相关依赖结束；消费 `U` 表示下游设备算子或主机取得结果。设备消费者可以通过依赖继续推进，主机读取则可能需要等待可访问的结果。

MLX 固定惰性求值资料说明，操作先记录计算图，显式 eval 或访问结果才触发实际计算。打印、转换为数组、memoryview、保存和 scalar item 等访问可能触发求值；用标量数组决定控制流也会求值。未使用的输出可以不计算，但它的图构造仍有成本。过密求值支付多次固定开销，过大的未求值图又增加图级管理成本。这份资料的编译描述限于其固定文本，不能据此推断其他版本的全部编译能力。

因此，计时图定义、计时提交和计时输出可消费回答不同问题。把读取移到后面，可能只是转移等待位置。合并求值可能减少提交和图处理次数，也可能延长中间状态生存期，改变峰值和并发供给，必须同时观察。

编译、autotune、图捕获、可执行产物加载与图重放还会引入准备边界。首次调用和稳定调用应分别说明；shape 相同而 stride、dtype、guard 或 executable 不同，不能视为同一执行实例。设备指令 trace 依赖编译映射时，必须使用对应产物，不能拿另一版 NEFF 或生成计划解释当前时间线。

## 采集窗口怎样推进

采集从待裁决问题反推。先写竞争解释及不同预测，再选择能观察这些预测的活动。解释设备空洞需要主机准备、提交、同步和设备事件；解释临时复制需要 shape、布局和内存生命周期；片上资源解释才进一步需要对应计数器或指令 trace。

以下状态是抽象采集协议，不是某一框架枚举或回调时机的逐字复制。实际接口可能把最后记录与保存合为一个动作，应保持其语义。

```pseudocode
输入：负载；按步定义的采集计划；所需活动；作用域；窗口
输出：记录事件、覆盖区间、截断标记、采集配置与扰动说明
初始化：步号为0；记录集合为空；覆盖集合为空
对每个负载步：
    按计划确定本步为等待、预热或记录
    在执行本步工作前建立相应采集边界
    执行工作；保持请求、批次、线程和执行实例身份
    若为等待：将本步标为未观测
    若为预热：初始化采集路径；样本不进入正式统计
    若为记录：保存启用活动的事件和实际覆盖区间
    在步边界推进计划；若结束一段记录，刷新已有记录
结束时：
    记录保存是否成功，以及仍在途、截断或缺失的事件
    对每个持续事件与覆盖区间求交，保留原始身份和截断标记
    点事件按其自身时间戳规则处理，不冒充持续区间
    输出覆盖与未决状态；不把无记录区间填成零工作
```

记录窗口结束不等于异步工作完成。开始前已经提交的工作可能在窗口内执行；窗口内提交的工作也可能在结束后才执行。若问题涉及这些跨界工作，应扩大窗口，或保留连接到窗口外的身份及不完整标记。不能只按 API 是否落在窗口内决定所有设备工作是否属于该窗口。

采集预热与模型预热也不同。前者初始化采集路径，后者可能初始化编译、算法选择、内存池和模型状态。丢弃采集预热样本不能证明模型已经稳定；短代表窗口仍须覆盖待解释的触发和完成转换。

## 精确连接、候选连接与未决集合

在字段齐全的模型中，定义提交键 `q=(run,pid,device,queue,correlation)`。假设一次采集运行内，此键唯一标识一个提交实例；一个提交可以对应多个 dispatch。若工具复用 correlation，必须增加能消除歧义的提交代次或其他明确身份，不能任意挑一个时间最近的 API。

```pseudocode
输入：框架范围、提交记录A、dispatch记录K、字段语义及可选编译映射
输出：精确连接E、逻辑归属R、候选关系、未决集合U及原因
初始化：每个提交的dispatch列表为空；E为空；U为空
1. 规范化运行、进程、设备和队列身份；保留原字段和缺失标记
2. 检查实例ID唯一性；检查非空提交键是否存在复用或歧义
3. 对可精确解释且唯一的提交键建立索引
4. 逐个处理所有dispatch：
       若关联字段缺失：加入U，原因是缺少关联证据
       否则若完整作用域键没有对应提交：加入U，原因是未找到同域提交
       否则：连接到对应提交，保留一对多拆分关系
5. 用框架父范围或明确编译映射组合出逻辑归属；标注祖先包含与融合共享
6. 对未决记录，仅在字段、时钟和顺序允许时生成候选关系
       候选不删除未决状态，也不提升为精确连接
7. 验证：精确匹配过的dispatch与U不相交，两者并集恰好覆盖全部K
8. 输出关联、候选、未决原因、截断及采集条件
```

关键不变量是完整分区。令 `M={k | 存在a使(a,k)∈E}`，则 `M∩U=∅` 且 `M∪U=K`。未决不只包括 correlation 为空的记录，也包括 correlation 存在但没有同域提交的记录。一个记录不能因被拒绝精确关联而从账本消失。缺失标记也不能用一般的真假判断代替：若字段契约允许数值0或空字符串作为有效 ID，它们仍是有效键。

设 L1 在进程1、设备0、队列0提交 correlation c1，产生 K1、K5；另有 K7 的 correlation 也是 c1，但队列为1，且没有该队列的匹配提交；K4 则缺少 correlation。此模型下，L1 精确关联 K1、K5，未决集合应包含 K7 与 K4。只保留 K4 会丢失 K7；只按 c1 连接则会把 K7 错接给 L1。若之后取得明确的跨队列提交映射，可以修订 K7 的证据状态，但不能靠放宽键完成修复。

主机父范围的包含关系可以恢复调用层级；设备区间相对 API 的包含与时间邻近通常只能提供弱候选。异步排队、多个线程和多队列使最近邻规则尤其容易出错。聚合计数应连接到其真实采集范围；跨多个 dispatch 的计数器没有额外拆分依据时仍是聚合量。

## 重叠时间与共享归属怎样列账

对同一可比较时钟域、同一设备和窗口，先裁剪 `Jk=Ik∩W`。定义 kernel 区间和 `S=Σk|Jk|`、并集长度 `B=|⋃k Jk|`，以及覆盖重数 `m(t)=Σk 1[t∈Jk]`。于是 `S=∫W m(t)dt≥B`。

区间并集通过排序扫描计算：按起点排序，维护当前合并段；与当前段相交或相接就扩展终点，否则结算旧段并开始新段，最后结算剩余段。空集合与零长度区间贡献零。相接区间没有正长度的重叠。多队列并发时，区间和可能超过墙钟；仅逐队列求并集后再相加，也会重复计算跨队列重叠。需要设备级 kernel 并集时，应在可比较时间轴上再次合并各队列区间。

`B` 只代表已采集 kernel 的覆盖。未记录的 copy、通信、其他引擎或其他进程不能自动包含在其中，因此不能无条件称为整个设备的忙碌时间。不同设备通常分别报告；即使时钟可对齐，跨设备并集也有不同统计含义，不能替代各设备资源账。

主机等待与设备执行可能重叠，不能直接相加成为请求延迟。请求延迟来自相应依赖路径上的经过时间；主机范围并集也不等于 CPU 服务时间，因为范围内可能正在等待。

对于融合 kernel k，若声明逻辑分摊权重 `w(l,k,t)≥0`，并在每个时刻满足 `Σl w(l,k,t)=1`，则分摊量为 `Al=Σk∫Jk w(l,k,t)dt`，总和为 `Σl Al=S`。这里守恒的是 kernel 区间和。若不同 kernel 同时执行，分摊总和仍可大于并集 `B`；不能要求它等于墙钟。权重可以来自声明的 token、字节或计算量口径，它是报告选择，不是对融合内部真实耗时的测量。

## 观测与分析的条件化成本

详细记录增加主机指令、元数据访存、缓冲写入和保存成本。shape 追踪可能延长张量引用，改变引用计数相关优化和内存表现；同步、counter replay、调试构建也可能改变排队、cache 与执行计划。不同采集运行的时间不能直接拼成一个无扰动的生产样本。

把新增主机工作量粗略写成 `Hobs=H0+na ha+nk hk+nshape hshape+nstack hstack`，各项单位为 CPU 时间；trace 字节记为 `Qtrace`，保存通路速率为 `βstore`。`Qtrace/βstore` 是给定通路的搬运时间尺度。它与设备工作能否重叠、是否发生背压，以及引用延长引起的额外分配，共同决定端到端增量，不能把所有项直接相加作精确延迟预测。

| 成本 | 条件与影响 |
|---|---|
| 计算 | 事件处理、调用栈展开和图管理增加主机工作；小 kernel 密集或 launch 受限时占比更高 |
| 访存 | 记录缓冲和元数据访问增加流量；延长引用可能阻止复用或改变峰值 |
| 通信 | 本地记录不必产生网络通信；远端收集、跨进程传递或导出另按实际字节与频率计费 |
| 准备 | 采集初始化、调试构建、编译映射和产物加载，按实际复用次数摊销 |
| 同步 | 刷新、捕获和计数器采集可能增加等待；已包含在关键路径中的等待不能重复加算 |
| 驻留 | trace 缓冲、编译映射、被保留张量及在途对象共同占容量；保存后何时可释放另有边界 |

分析本身也有成本。N 个区间的排序并集为 `O(N log N)` 时间；完整键连接在哈希表假设下为 `O(|A|+|K|)` 期望时间，另计输出关系大小；内存事件扫描需要对生存期端点排序。若输入已经按时间排序可以流式推进，但需要保留尚未结束的区间或 storage 状态，不能假定驻留恒定。

采集策略随条件调整：主机供给不足时减少不必要的 stack/shape 活动并缩短窗口；需要定位布局或生命周期时，再对相关范围启用它们。融合和图执行使算子级事件变粗时，保留业务范围与 executable 身份，补编译映射。若采集持续改变目标现象，应放弃用该配置直接估计服务分布，改用普通运行测量目标、局部采集解释机制。

## 内存口径与 storage 生命周期

逻辑 tensor 字节与物理 storage 容量不同。多个视图可以覆盖同一 storage，逻辑元素数之和会重复计账。定义 `Astorage(t)` 为本模型中仍受对象或在途读者保护的不同 storage 容量之和；每个 storage 按身份和代次计一次。若只统计视图覆盖的有效元素字节，则是另一种量，不能据此直接推断分配容量。

把每个对象引用或异步读者的保护期表示为一条 lease：`(storage身份及代次, 容量, 开始, 结束)`。同一 storage 的多个 lease 可以重叠。保护期结束不代表分配器已把缓存归还驱动，因此该模型计算活跃存储，不计算全部 reserved。

```pseudocode
输入：保护期集合；窗口W=[T0,T1)
输出：活跃storage容量曲线及峰值
初始化：容量表为空；端点变化表为空；各storage保护计数为0
对每条保护期：
    检查容量非负、开始不晚于结束
    同一storage身份及代次必须具有一致容量
    将保护期与W求交；空交集不产生事件
    在交集开始处为该storage加入+1，在结束处加入−1
按时间排序所有端点：
    在时刻t先汇总每个storage的全部变化
    对每个发生变化的storage：
        old←保护计数；new←old+汇总变化；检查new非负
        若old=0且new>0：活跃容量增加该storage容量
        若old>0且new=0：活跃容量减少该storage容量
        更新保护计数
    所有storage更新完成后，记录[t,下一端点)的容量并更新峰值
结束时检查裁剪后的保护计数全部归零
空窗口或没有保护期时，峰值为0
```

窗口开始前已经存活的对象通过裁剪进入初始端点，不能只读取窗口内的申请事件。同一时刻释放和建立保护期要整体处理，再评估容量；否则可能制造不存在的瞬时峰值。真实记录中若缺失窗口前的存活快照或释放事件，应输出不完整状态，不能假定账本已闭合。

| 口径 | 描述什么 | 不能替代什么 |
|---|---|---|
| 活跃逻辑 tensor 字节 | 逻辑对象及有效元素规模 | 去重后的物理 storage 容量 |
| 分配器管理的活跃 storage | 尚受保护的存储及生存期 | 缓存、碎片、外部分配和设备总占用 |
| reserved | 分配器保留的容量 | 全部可回收容量 |
| 设备整体占用 | 对应设备或进程范围的整体使用 | 框架可以释放的字节 |
| 主机 RSS | 主机代码、栈和缓冲等驻留 | 设备驻留 |
| 累计分配字节 | 分配 churn | 同时存活峰值 |

只有在作用域、采样边界和覆盖对象兼容时，才可能使用 `Astorage≤R≤D`：Astorage 必须属于该分配器，R 必须包含在 D 的定义中。框架外分配、不同采样时刻或不同设备会破坏这种直接比较的前提。

生命周期需要区分申请、写入就绪、读者消费、最后读者完成、逻辑引用释放、分配器可复用和驱动归还。释放一个视图句柄不代表 storage 已无其他读者；主机释放引用也不代表异步访问已经结束。设 storage 的复用时刻为 `treuse`，相关消费者完成时刻为 `ci`，必要条件为 `treuse≥maxi ci`，且仍需满足对应平台的可见性与完成契约。

设同一完成边界下 Astorage 为10 GiB、R为14 GiB、D为16 GiB。4 GiB可能包含缓存、碎片和分配粒度，另2 GiB可能在框架观测范围之外。差额是待核查分类，不能凭减法证明全部可回收或已经泄漏。降低同时存活对象后A下降而R不变，支持保留或碎片解释；若D与R仍有差额，应继续调查外部分配及统计范围。

全窗口峰值相同不能证明整条容量曲线正确。别名重复计账可能只抬高一个较低阶段，被稍后更高的真实峰值遮蔽。验证去重机制时，应比较别名同时存活时的容量，或选取覆盖该阶段的局部窗口；同时保留完整窗口，确认局部修正没有改变其他阶段。

## 五类平台的观测落点

| 平台 | 系统或框架尺度 | 设备尺度 | 合法连接与限制 |
|---|---|---|---|
| CUDA | Nsight Systems的API、stream、copy和主机范围 | Nsight Compute的kernel计数器 | 沿明确范围和correlation关联具体实例；系统时间线与计数器采集分别解释 |
| ROCm | rocprofv3的HIP/HSA、dispatch、复制、分配与迁移等记录 | 设备计数、dispatch计数和其他受支持能力 | 保留进程、agent、queue与dispatch身份；能力与指标组合须核实目标设备 |
| Metal/MLX | 求值边界、对象标签与capture窗口 | 固定版本支持的GPU capture及Xcode操作依赖 | 捕获实际求值产生的工作；该来源没有证明完整Instruments或所有计数器覆盖 |
| Trainium | Neuron Explorer中的runtime、框架函数和HBM分配 | NeuronCore指令起止、DMA与计算引擎 | NTFF事件与对应编译NEFF后处理关联，系统长调用不能直接证明片上瓶颈 |
| CPU | 框架范围与进程、线程、CPU集合或cgroup | perf可用的cycles、instructions、cache等事件 | 保留计数对象、事件组、运行范围和聚合方式；不能把CPU信号解释成GPU stall |

ROCprofiler固定README区分API trace与设备、dispatch计数等能力；gfx11/gfx12的counter collection有稳定电源状态条件。列出能力不表示当前设备、权限与指标组合已经满足；多次采集时每次身份、条件和额外成本分别保留。

MLX固定Metal文档说明调试选项可以记录Metal编译源码并标记对象，capture需要允许捕获的环境，可在Xcode打开和重放trace、查看依赖。构图发生在窗口内但实际求值发生在窗口外时，不能以capture缺失推断无设备工作。

Neuron Explorer系统视图显示runtime和框架函数，并可连接硬件事件与HBM分配；设备trace用起止事件和编译NEFF形成详细报告。NKI架构资料进一步区分HBM、SBUF、PSUM、DMA和计算引擎。因此，解释片上数据供给应落到对应搬运和计算依赖，不能由主机runtime时长直接推断Tensor Engine饱和。

CPU的 `IPC=instructions/cycles` 需要分子分母的计数范围可比。perf固定手册说明，事件是否共同调度、multiplexing和聚合方式影响指标解释；低IPC仍允许访存、依赖、分支或调度等竞争解释。跨厂商同名utilization可能使用不同分母，不应直接比较百分比。

## 一条请求、执行与内存的组合轨迹

以下是符号模型，时间单位为τ，容量为GiB，不是设备实测。窗口为 `[0,40)`，假定主机与设备时间已经在同一可比较坐标上，设备只展示一个顺序队列。

| 层 | 事件与身份 |
|---|---|
| host | normalize `[0,2)`；linear入队 `[2,3)`；attention入队 `[3,4)`；标量读取 `[4,24)`；采样/序列化 `[24,28)` |
| 提交关系 | linear提交关联K1；attention提交关联K2；入队返回不代表完成 |
| device | K1为linear融合kernel `[6,14)`，共同实现gemm与bias；K2为attention `[14,22)` |
| counter | 若只覆盖整个执行范围，则保留聚合身份，不拆成两个kernel的贡献 |
| storage | weights 6 `[0,40)`；compile workspace 3 `[0,5)`；temp 2 `[6,14)`；KV 4 `[14,40)` |

kernel并集为 `[6,22)`，长度16τ，区间和也为16τ。host范围并集为28τ，包含标量读取等待；主机与设备观测区间的联合并集仍为28τ。把28与16相加会得到44τ，重复计算了重叠时间。`[22,24)` 是模型中读取尚未返回的尾部，但没有额外事件时，不能仅凭这2τ断言发生了某个具体CPU操作；`[28,40)` 同样保留未解释状态。

K1时长8τ，可以声明gemm和bias各分4τ，K2分给attention 8τ，总计16τ。若把K1分别完整计给gemm与bias，再加K2，就得到24τ。若另一个队列在 `[10,18)` 执行K3，则kernel区间和变成24τ，并集仍为16τ；合法分摊应守恒到24τ，而不是强行压成16τ。

storage活跃容量依次为 `[0,5)` 的9、`[5,6)` 的6、`[6,14)` 的8和 `[14,40)` 的10，峰值10 GiB。temp另有一个 `[8,14)` 的视图时，物理容量不增加。在8τ，正确容量为weights 6加temp 2，共8 GiB；按句柄重复计temp会得到10 GiB。错误曲线的全窗口峰值仍是10 GiB，恰好与正确峰值相同，因此只比较全窗口峰值会漏掉错误。改查 `[8,14)`，正确峰值8与错误峰值10便能区分；逐时容量参考也能发现该差异。

若诊断性引用保留让temp的保护期持续到18，便与KV重叠，峰值升至12。该变化描述诊断条件下的生命周期，不证明普通运行的峰值也是12。在14τ释放temp并建立KV，半开区间不会制造两者同时存活；但真实设备复用仍要确认最后消费者完成。若temp的最后消费者完成于14，而存储在13就交给下一次写入，即使容量曲线看似更低，也已违反复用条件。

这条轨迹同时连接请求消费、提交、融合、设备执行和驻留。改变求值频率可能减少固定主机成本，却延长temp保护时间；改变融合边界可能减少中间写读，却改变临时状态和归属粒度。选择需要在同一候选、同一负载与完成边界下重新列账。

## 竞争解释、区分实验与选择修正

| 观测 | 竞争解释 | 区分实验与预测 | 反证后的修正 |
|---|---|---|---|
| 每token出现增长的concatenate | 复制历史、惰性构图、元数据路径、融合或采集缺失 | 固定输出语义，记录shape和实际复制；预分配后若历史复制成立，相应字节增长应减少 | 无对应执行或字节证据时，降低历史复制解释的置信度 |
| 首次每种shape有长段 | 编译、guard变体、加载、首次分配或autotune | 同签名重复，再分别改变guard相关条件，观察新产物与首次成本 | 同签名仍持续长时，编译不能解释全部 |
| scalar extraction后出现空洞 | 设备完成等待、锁、Python处理或采集扰动 | 移动读取边界，比较设备工作量、等待位置和最终完成 | 只移动等待而输出不提前，不能称为计算加速 |
| 算子时间和大于墙钟 | 跨队列重叠、祖先inclusive范围、融合重复归属或时钟错误 | 分别恢复实例，算区间和与并集，核查祖先和shared关系 | 无重叠时转查重复归属与时钟，而非继续声称并发 |
| active下降而reserved不降 | 缓存保留、碎片、在途读者或外部分配 | 在相同完成边界减少同时存活对象，并对齐A、R、D口径 | 差额未分类前保留未知，不能直接宣称泄漏 |
| 两种内存统计的全窗口峰值相同 | 曲线确实相同，或局部错误被另一阶段峰值遮蔽 | 在别名重叠阶段比较曲线，独立按storage去重；保持其他阶段不变 | 局部容量不同即推翻统计等价，不能以全局峰值相同关闭问题 |
| capture缺少预期工作 | 未求值、窗口错误、产物不匹配或工具覆盖不足 | 覆盖明确求值和消费边界，确认执行身份 | 缺失事件不等于零工作；必要时降低结论精度 |
| Trainium runtime区域很长 | 主机等待、加载、数据供给或设备指令受限 | 用匹配NEFF的设备trace区分DMA、计算和依赖 | 系统调用没有对应片上证据时保留运行时解释 |
| CPU低IPC | 工作集、依赖、分支、调度或计数范围混杂 | 固定任务，分别改变工作集与线程预算，并检查事件共同运行范围 | 单个比值不能确定缓存层或GPU原因 |

例如，最初认为concatenate每步复制完整历史，但随后只发现host图构造增长，没有相应复制或shape证据。此时应把原解释降级。再固定每个外层迭代的求值边界：若设备工作直到求值才出现，支持定义与执行边界解释；若真实历史读取字节仍随长度增长，复制解释才重新获得支持。预分配若改善端到端时间，却没有出现预测的流量下降，应保留候选收益并修正原因。

工具选择允许反转：稳定形状、频繁小提交时，减少提交的预测更值得验证；设备已持续繁忙时，同样的主机优化可能只有很小收益。并发增加后，原本有效的融合或延后求值可能因驻留和排队退化，应调整边界；目标设备缺少所需计数器时，放弃具体stall归因，保留可测的路径级结论。

## 最小观测、独立检查与未测边界

分层测量先保留无profiler的请求完成、失败、输入输出规模与负载条件，再用代表窗口建立框架/系统关联，最后针对少量实例取得细粒度计数。普通运行验证目标，诊断运行解释机制；不同配置的数据各自保留身份。

工具不可用时，仍可使用客户端完成时间、主机经过时间、独立正确性参考及明确完成边界的结果。若某接口确实至少要搬运 `Bmin` 字节，完整路径时间为T，则实际平均接口流量至少为 `Bmin/T`；超过可信上界时，应核查字节模型、时间边界和漏计异步工作。逻辑tensor字节不能未经证明就当作必须穿过DRAM或网络接口的字节，因为缓存、复用和布局会改变实际交通。

容量下界只能排除明显不可能：必须同时存活的非别名storage超过容量时，方案不合法；没有超过则不证明峰值满足，因为workspace、外部分配和粒度可能尚未计入。

配套检查验证以下软件模型关系：区间并集与独立整数时间格参考一致；完整作用域连接与逐对关系参考一致；已匹配和未决dispatch形成完整分区；共享分摊守恒到kernel区间和；storage扫描曲线和峰值与逐时去重参考一致；复用不早于读者完成；记录事件只覆盖所选RECORD区间。

负对照包括漏掉K7、只用correlation连接、重复计视图、过早复用和把窗口外尾部纳入记录。视图负对照明确展示全窗口峰值的遮蔽，再在8τ及 `[8,14)` 触发差异；不能只检查一个错误实现恰好算对的聚合量。独立参考以实际存活storage身份去重，不调用事件扫描算法。

这些检查不能证明真实设备的时钟校准、事件完整性、内存可见性、counter可用性、电源状态或profiler扰动，也不证明Agent构建效果。整数时间格参考只验证离散模型；真实连续时间戳与校准误差需要设备证据。Python脚本是否成功执行，应由真实执行记录单独确认，不能用静态审阅、其他语言的复核或另一语言模型的通过代替。
