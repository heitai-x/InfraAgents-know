# K-FW-003：Stream 与分配器：依赖顺序和对象生存期

stream 解决设备操作何时可以开始，分配器和所有权协议解决地址何时可以交给下一使用者。正确的异步程序既要保证生产先于消费，也要保证最后一次访问先于覆盖或释放。host 已经取得 tensor、复制句柄或取消确认，都不能单独证明这两种关系成立。

## 从地址与操作构造依赖图

本章考虑单进程、单设备上由主机提交的普通 kernel、复制和分配操作；设备执行可以并发，主机账务由一个状态拥有者串行更新。跨设备、IPC、外部 DMA 和特殊的程序化依赖启动需要各自的访问与同步契约，不能直接套用这里的全部 API 映射。

把设备执行表示为有向无环图 G=(V,E)。每个操作 u 有开始 s(u) 和结束 e(u)，边表示前项完成后后项才能开始。记 u≺v 表示图中可达，而不是主机先调用了 u。普通 stream 内的顺序、正确记录和等待的 event，以及相应的图依赖，都可以提供这样的边。不同 stream 允许并发，也允许串行；程序正确性不能依靠它们恰好同时运行。

一个存储对象记为 X=(device,address,bytes,epoch)。bytes 以字节计，epoch 每次把同一物理槽交给新对象时递增。tensor 视图和切片可能共享同一个 X；指针相同、Python 对象不同或者输出 tensor 不同，都不足以证明访问独立。本章保守地以整个底层存储为冲突单位，不推测库内部访问的细分范围。

对 X 定义：

- A_X：分配在设备顺序中生效的完成点；它不保证内容已经初始化。
- U_X：本代所有已经接受的设备访问，每项有 READ、OVERWRITE 或 UPDATE 模式及最后访问完成点。OVERWRITE 完整定义本对象内容而不读旧内容；UPDATE 同时读写旧内容。
- F_X：本代释放操作的开始点。对于应用自己的 arena，F_X 对应槽重新分配的边界；对于原始 CUDA 分配，才对应相应释放操作。
- O_X：仍可授权新访问的逻辑拥有者，包括必要的图、迁移或输出拥有者。已提交操作的在途责任另行保留。

合法性至少要求：对每个 u∈U_X，A_X≺s(u)，且 e(u)≺F_X；读取依赖的最后生产写入必须先于读取；同一范围内至少一方写入的访问必须有明确次序，或采用本章范围之外、经证明的并发协议。只读访问之间不必增加互相等待。

这些条件分别防止未生效分配被访问、读取旧或部分内容、读写竞争以及释放后访问。即便新操作只写而不读，它也不能覆盖尚被旧操作访问的同一地址。PyTorch 固定文档特别指出，缓存分配器重用的地址可能仍有旧操作在途，因此没有读依赖也可能需要跨 stream 同步。

对象输出不只是一个地址，而应包含存储句柄、该代内容身份、生产完成证据和回收责任。内容版本可以在提交时登记为“将由某操作生成”，不能把这个登记解释成设备已经完成。

## 生产、等待与分配器记录各保护什么

对生产 stream P 和消费 stream C，一条普通的生产消费链是：P 写入 X，在最后一次相关写入后记录 ready；C 在消费操作前等待 ready，再提交读取。等待通常约束 C 后续的设备执行，不要求 host 立刻阻塞。event 若记录在生产写入之前，只证明更早的前缀完成。

事件还必须覆盖真正执行访问的队列。某个库调用在内部 stream 上继续访问 workspace，而调用者只在外部 stream 上记录事件时，除非库明确把内部访问汇合回来，该事件不能作为最后使用证据。调用返回与最后设备读取不是同一个边界。

PyTorch 的两个职责需要分别处理：

| 操作或策略 | 提供的关系 | 仍需处理的关系 |
|---|---|---|
| 消费 stream 等待生产 event 或生产 stream 的相应前缀 | 生产完成先于消费 | 消费结束前的存储保护 |
| 对 tensor 记录实际消费 stream 的使用 | 让框架 allocator 获知跨 stream 生存期 | 生产消费顺序、原地覆盖和未来使用 |
| 显式持有 tensor，完成跨 stream 汇合后再释放 | 由应用承担最后引用与完成关系 | 持有期间仍不能无序原地改写 |
| 设备级同步后再推进 | 覆盖此前更大范围的完成 | 定位具体缺边，并重新评估丢失的并行性 |

`record_stream` 不是等待生产者，也不是读写锁。它保护分配器不要过早重用已记录的存储，不能阻止另一个仍持有别名的调用者直接修改内容。仅保留 Python 引用同样不能阻止这种原地写入。

手工管理生存期时，一种文档支持的办法是在分配所在 stream 上汇合实际消费 stream 的最后使用，再让对象的最后引用释放。等待应放在真正需要回收的位置；在发出消费者后立即等待，会使后续独立工作失去原本可能的重叠。这里的最后使用必须覆盖全部消费者，而非只覆盖最晚发起的那个调用。

默认 stream 不能作为通用的隐含依赖证明。CUDA 固定指南区分 legacy NULL stream 和 per-thread default stream，非阻塞 stream 又影响 NULL stream 的隐式同步。框架、扩展和库的配置可能不同；可移植的对象协议应显式说明依赖来自哪里。

## 用读写前沿推导事件，而不是逐处补同步

下面给出一种可重建的保守算法。它管理完整存储对象，所有提交和关闭由单一主机状态拥有者串行处理。若多个主机线程提交，则要把“检查、提交、登记”置于同一协调协议中；不能先把裸指针交给另一线程，再假定关闭方已经知道未来访问。

每个 X 保存以下状态：

| 字段 | 含义 |
|---|---|
| phase | OPEN、CLOSING、FREE_QUEUED、RETIRED 或 QUARANTINED |
| owners | 带 epoch 的逻辑拥有者集合，重复释放同一拥有者不重复扣账 |
| A | 分配生效票据 |
| W | 最近一次已提交写入的完成票据；未写入时取 A |
| R[stream] | 自 W 之后，各 stream 最新的读取完成票据 |
| initialized、version | 是否已有完整内容定义，以及已安排的内容版本 |
| free_done | 释放及本应用所需回收边界的完成票据 |

票据包括对象 epoch、事件身份和记录位置。本章不在相关等待和查询尚未结清时重新录制同一个物理 event，以免把旧票据与新记录混淆。这是简化实现的选择；其他事件复用方案需要自行证明对应关系。

```pseudocode
算法：初始化、提交访问、关闭和回收
输入：存储申请；操作及其全部读写存储；带代次的拥有者释放通知
输出：已提交操作及完成票据；或等待、拒绝、隔离结果

创建 X：
    若本次逻辑工作不访问任何字节，返回显式空结果，不制造假完成事件
    取得容量；在分配 stream 上提交分配，并在其后记录 A
    初始化 phase=OPEN，owners={申请者}，W=A，R=空
    initialized=false，version=未定义；不向读者发布未初始化内容
    分配失败则不发布 X；已提交但完成范围未知的工作进入隔离处理

提交操作 U：
    解析全部输入、输出、workspace、计划和别名，合并同一存储的访问模式
    对每个 X 检查 epoch、OPEN、调用方拥有访问授权及范围合法
    READ 或 UPDATE 要求已有完整内容定义
    为每个 X 收集先决票据：
        READ：{W}
        OVERWRITE 或 UPDATE：{W} ∪ R 的全部值
    将所有对象的先决票据去重；它们必须来自已经提交的过去操作
    在 U 的实际执行 stream 上先等待这些票据，再提交 U
    在 U 对相关对象的最后访问之后记录完成票据 E
    对每个只读 X：R[执行 stream]=E
    对每个写入 X：W=E，R=空，更新已安排的 version
        完整 OVERWRITE 使 initialized=true；UPDATE 保留完整性契约
    完成账务登记后才返回可供后续操作使用的描述符

释放拥有者 (X,epoch,owner)：
    旧 epoch 或重复释放不改变本代账务
    删除匹配 owner；仍有其他拥有者则保持可用
    owners 为空时进入 CLOSING，禁止接受任何新访问
    所有已经接受的访问必须已有有效完成票据
    在回收 stream F 上等待 A、W 和 R 的全部值
    原始 CUDA 分配：提交相容的异步 free，再记录 free_done
    应用 arena 槽：记录覆盖上述汇合的 free_done，不释放整个 arena
    phase=FREE_QUEUED

推进回收：
    free_done 查询未完成：继续保护存储
    成功完成：phase=RETIRED，允许应用把槽交给下一 epoch
    完成状态失败或无法证明访问已结束：phase=QUARANTINED
    隔离对象不进入可用集合，交由具体错误恢复协议结算
```

多对象操作应先收集所有旧前沿，再提交并统一更新。例如 U 读取 X 并写入 Y，不能先发布 Y 的新前沿，再把它错误地作为 U 自己的先决条件。同一存储既作输入又作输出时，应合并为 UPDATE，而非误判为两个独立对象。这里提交只等待过去票据，因此不会因等待尚未生成的未来事件构造环。

正确性不变量是：W 覆盖最近写入；R 覆盖 W 之后所有尚未被后继写入汇合的读取。同 stream 的后一次读取结束已覆盖前一次读取，因此每个 stream 只保留最新读取票据足够。新写入等待 W 和全部 R，故覆盖之前的所有冲突；新读取等待 W，故看到它应消费的版本。关闭再汇合最后前沿，便覆盖所有已接受访问。

这不是最细粒度的依赖图。两个不重叠切片也会被本算法按整个存储串行化；只有证明真实访问区间不相交，并包含库内部辅助访问后，才适合拆分前沿。反过来，给每个 tensor 对象分别建账可能漏掉底层别名。

部分提交失败必须保留已发生的责任。例如 kernel 已成功入队、随后事件记录失败，不能删除该访问并立即回收。若可通过明确的 stream 完成关系补齐证据，可据此收敛；无法确认时保留隔离。错误返回或超时不自动等于设备已经停止访问。

## Stream-ordered allocator 的释放边界

CUDA 12.8 所供 §11.3 摘录明确区分了同步取得指针值与分配在 stream 顺序中生效。`cudaMallocAsync` 返回的地址可以用于构造未来工作；在其他 stream 上使用时，访问仍须排在分配之后。释放必须排在分配及全部使用之后，释放操作开始后的访问属于未定义行为。

因此，生产消费顺序正确仍可能释放错误。设 A 分配并写入，B 等待 A 后读取，回收 stream F 却只等待 A：B 的读取与 F 的释放之间仍没有所需关系。修复是让 F 等待 B 的最后使用；存在 B、C 两个读者时，两条路径都要汇合。不能按事件的主机发起时间选择“最后一个”。

本章在关闭时禁止提交未来访问，比尝试在 free 开始前临时追加工作更容易证明。没有消费者时仍需保证 free 排在分配之后；分配后取消且内容未初始化，可以沿这个路径释放，不必伪造一次生产。

混用接口也不能依赖名称猜测。固定摘录允许用异步 free 释放普通分配，但要求应用保证访问结束；对异步分配调用普通 `cudaFree` 时，驱动假定相关访问已完成，并不补做所需同步。该规则不能推广为任意 free 都会排空设备。框架管理的 tensor 也不能绕过其 allocator 随意调用原始 CUDA free。

内存池复用是合法性之后的策略。所供 §11.9 摘录分别描述了沿 event 依赖复用，以及在 free 已满足执行顺序后进行机会式复用。是否实际复用同一物理块取决于池策略、驱动和容量条件，不是应用可以要求的地址身份保证。本轮摘录在内部依赖策略处截断，本章不据此断言其完整触发规则。

应用槽池在查询 free_done 成功后才把槽交给下一 epoch，是本章选择的保守主机协议。CUDA allocator 可以利用已证明的设备顺序更早安排未来复用；“已安排复用”和“新使用者此刻可无序访问”仍是不同命题。

## 共享 workspace、图与未来访问权

两个算子的输入输出独立，但内部共用 workspace 时，仍可能在该 workspace 上发生写写或读写冲突。计划对象、分区归约中间值、通信暂存和库 handle 绑定的工作区，都应进入操作的访问集合。只记录显式输入输出不能覆盖这些访问。

可比较三种组织：一个 workspace 用事件串行化；每个在途执行独立 workspace；或者在库明确支持的条件下按不重叠范围分区。第一种省容量但增加依赖，第二种增加并发候选与容量，第三种增加布局、边界和内部访问范围的证明责任。独立工作区只消除这一处冲突，不保证设备具有同时执行两个 kernel 的资源。

图重放还包含未来访问权。若捕获节点直接保存 X 的指针，即使上一次 replay 已完成，只要未来仍允许 replay，就不能释放其地址。图或长期绑定应作为 owners 中的拥有者；停止未来 replay、结清在途执行、解除绑定后才能撤销它。稳定 arena 内按页号间接访问时，arena 的地址生命期与其中各页内容的复用生命期又要分开管理。

固定 PyTorch 文档说明，图私有池随图及捕获期间创建的相关 tensor 保活。多个图按捕获顺序且不并发重放，是一种安全共享情形；文档还允许互不依赖对方输出的独立图在不并发时共享池。共享池可能覆盖另一图的输出，需要的输出应先复制到独立受保护的存储，且复制读取源结束后才允许覆盖源。host 发出复制不等于源已可重用。

图的固定地址、捕获限制与逐槽绑定见[CUDA Graph](cuda-graph-buffers.md)。这里的核心边界是：上一次执行完成解决在途访问，图仍可重放则保留未来访问资格，两者不能合成一个“完成”标志。

## 两个消费者、迁移与取消的一条完整轨迹

考虑临时设备存储 X，大小 64 MiB，内容不承担系统最后一份恢复副本的责任。P 生成 X；B 是计算消费者，使用独立的 16 MiB workspace W；C 把 X 复制到 64 MiB pinned 主机缓冲 H，交给独立快照任务。快照任务与计算请求有不同拥有者。下表时间均为设定的 ms，不是设备测量。

| 时刻或区间 | 发生的操作 | 仍然有效的责任 |
|---|---|---|
| 0–2 | P 分配并完整写入 X，末尾记录 ready | X 的生产者；计算与快照拥有者 |
| 2–5 | B 等待 ready 后读取 X，并读写 W | X 的 B 读取票据；W 的最后访问票据 |
| 2–6 | C 等待 ready 后执行 D2H，读取 X、写入 H | X 的 C 读取票据；H 的传输写入责任 |
| 3 | 计算请求取消，撤销后续业务提交并释放自己的拥有者 | 已入队的 B 仍访问 X；独立快照任务继续 |
| 5 | B 的最后使用完成 | W 可供下一次执行使用；X 仍受 C 和快照拥有者保护 |
| 6 | D2H 完成，快照任务解除对 X 的源端拥有权 | X 可在汇合后回收；H 的内容现在才能交给 CPU 消费 |
| 6–10 | 独立快照任务读取 H 并写入存储 | H 不能在 CPU/I/O 最后读取前被下一次 D2H 覆盖 |
| 10 | H 的最后使用结束 | H 可回到主机槽池 |

这条轨迹包含三个不同回收点：W 为 5，X 不早于 6，H 不早于 10。取消的逻辑响应在 3 已经完成，却不能使其中任意一次旧访问消失。若快照任务也取消，可以停止尚未开始的后续 I/O，但已提交 D2H 仍需结算；此时 H 的生存期会按真实最后使用缩短，而不是统一保留到 10。

若 X 是迁移前最后一份必须保留的有效 KV，源端逻辑拥有者还可能必须等目的验证和接管确认，不能在 D2H 完成时直接删除。传输源最后读取与恢复责任移交是两个边界，相关协议见[KV 卸载与预取](../algorithms/kv-offload-prefetch.md)。

复用 X 的地址后，迟到的 B 完成通知仍带旧 epoch，只能结算旧责任，不能减少新对象的读者集合。重复一个读者的完成也不能抵消另一个读者。代次检查保护账务与结果归属；真正等待旧访问结束才保护物理内容。只递增 epoch、立即让旧 DMA 与新对象共用地址，仍然会发生覆盖。

## 条件化成本与容量账

事件和生存期管理通常不减少模型 FLOPs；它们改变等待、提交和可复用容量。列账应覆盖同一工作量和相同的完成边界：

| 成本 | 本章机制带来的项目 | 估计与观测边界 |
|---|---|---|
| 计算 | 业务计算通常不变；取消后已提交工作可能成为无效计算 | 分开统计执行量与有效业务产出 |
| 访存 | 独立副本、workspace 初始化、计划更新及可能的额外转换 | 事件不等于搬运整个对象；实际设备事务另测 |
| 通信 | H2D、D2H、设备间复制或外部传输的实际字节 | 同步 event 不传输 tensor 内容；跨设备可访问性需另核对 |
| 准备 | 存储别名解析、拥有者登记、票据创建、记录与查询 | 小操作可能由这些固定开销主导 |
| 同步 | 合法依赖造成的等待，以及过粗前沿增加的串行化 | 按关键路径分析，不能累加所有并发等待区间 |
| 驻留 | 所有在途对象、独立 workspace、图保活、pinned 缓冲和池空闲保留 | 按同一时刻物理存储的并集计量 |

对 N 次访问、S 个实际使用 stream，本算法每个对象最多保存一个写票据及 S 个读前沿，元数据为 O(S)。读取只需依赖 W；写入和回收可能需要检查 O(S) 个读票据。事件记录数量随访问次数增长；相同 stream 上已由顺序保证的等待可以省略。减少事件前应证明传递关系仍覆盖全部访问。

设任务 u 的完成时间为 t(u)，持续时间为 d(u)。忽略额外资源冲突时，可用 t(u)=d(u)+max_{v∈pred(u)}t(v) 估计依赖下界。增加一条不必要的 workspace 边可能直接延长最长路径；取消这条边也不保证两项工作能同时占用相同 SM、内存控制器或复制引擎。

容量以实际占用区间计算。若槽从取得到最后使用结束固定占用 L ms，每隔 P ms 启动一批，边界结束后可立即复用，则所需槽数至少为 ceil(L/P)。随机长尾或主机迟迟未处理完成通知时，平均 L 不能保证足够槽；复用仍以完成证据为准。

对上节轨迹，假设每 4 ms 启动一批、阶段持续时间保持不变、没有其他资源瓶颈：X 占用区间为 [0,6)，W 为 [2,5)，H 为 [2,10)，各需 2、1、2 个槽。对应设备缓冲为 2×64+16=144 MiB，pinned 主机缓冲为 2×64=128 MiB。这里不包括模型、KV、其他库工作区或池空闲保留。64 MiB 在 4 ms 内搬运意味着约 15.625 GiB/s 的有效传输需求，是这一设定的资源前提，不是实测带宽。

如果该并发条件下 D2H 实际需要 6 ms，单一串行传输资源的持续服务周期就不能保持 4 ms。增槽只能延迟背压，不能消除每批的字节需求。共享资源 r 每批承担 Q_r 字节、可持续带宽 B_r 时，还要求 P≥Q_r/B_r；不要把同一内存控制器的全部带宽分别许给每条 stream。

独立 workspace 的容量交换也可单独计算：两项各需 16 MiB、耗时各 6 ms 的操作，共用一个 workspace 会形成至少 12 ms 的执行链；两个 workspace 多用 16 MiB，在资源充足时才可能接近 6 ms。若两项操作已各自占满设备资源，额外 workspace 可能只增加驻留。

缓存池中的已用存储是池保留量的一部分，不能把 reserved 与其中的 used 直接相加。张量已释放而驱动报告占用未降，可能是合法缓存保留，也可能是在途回收或其他库工作区；需要对象和池口径，不能仅凭一个总显存数判断泄漏。

## 条件变化后如何保留、调整或放弃

| 条件变化 | 必须保留的关系 | 可调整的方案及反转信号 |
|---|---|---|
| 只有一个普通执行 stream | 分配、内容定义、最后使用和释放仍须有序 | 可以利用同 stream 顺序减少 event；引入库内部 stream 后重新核对 |
| 读者增加或结束时间长尾明显 | 全部最后使用者都必须受保护 | 按 stream 压缩票据或拆分不同生存期对象；只看最后提交者会失效 |
| 容量紧张 | 不因 OOM 压力提前覆盖在途对象 | 降低在途深度、共享 workspace 并串行、等待或分块；额外缓冲挤出 KV 时可能反转收益 |
| 对象很小且提交频繁 | 顺序与生存期不能省略 | 合并提交和完成记录；若固定管理开销主导，可退回较简单执行路径 |
| 图长期保留固定地址 | 在途完成之外还要保留未来 replay 的地址资格 | 减少不再需要的绑定与图；不能用上次 replay 完成代替图生命期结束 |
| 切片和别名增多 | 冲突按真实底层存储判断 | 保守全存储前沿，或在可证明范围后细分；只按 tensor 身份建账应放弃 |
| 更换 allocator 后端 | 使用必须位于合法分配生命期内 | 重核对回收接口、统计口径与池策略；不能沿用仅对 native 有意义的配置或统计 |
| 改为统一内存或外部传输 | 生产可见性与最后使用仍存在 | 按平台重建可见性、迁移和外部完成关系；不能把 CUDA event 当作任意外部设备的完成证明 |

## 竞争解释、区分实验与反证修正

先固定输入、存储别名、事件记录点和结果参考，再比较时序与性能。全设备同步使错误消失，只能说明时序相关，不能定位生产边、回收边还是 workspace 冲突。

| 观察与竞争解释 | 区分干预 | 预测与反证后的修正 |
|---|---|---|
| 消费读到旧值：生产等待缺失，或等待事件记录过早 | 保持对象长期存活，延迟最后生产写入；把记录点移到全部写入之后 | 若单纯保活无效而正确记录点消错，支持生产边解释；仍错则检查别名及实际执行 stream |
| 仅压力下错误：跨 stream 生存期遗漏，或显式原地覆盖 | 分别延长对象保活、记录实际消费 stream、禁止所有别名写入 | allocator 保护消错支持回收问题；只有禁止原地写入才消错时，应修改写入协议 |
| 两个消费者时错误：只等待最近提交者 | 分别拉长 B、C，交换提交与结束顺序 | 安全回收应由真正最后使用者决定；只随提交顺序变化说明汇合不完整 |
| 输入输出独立却并发出错：共享 workspace，或其他数值/布局问题 | 对照独立 workspace 与事件串行化，保持计算输入一致 | 两种隔离均消错支持共享区竞争；仍错则继续检查计划状态、地址绑定和数值参考 |
| 显存不下降：合法池保留、在途回收、图保活或泄漏 | 停止新工作，确认最后使用，分别记录对象、池 reserved/used 和图/库持有者 | used 回基线而 reserved 稳定支持缓存保留；排空后仍持续增加需查未结责任，不能统称泄漏 |
| 取消很快但资源迟迟不归还：正常排空或完成通知处理阻塞 | 独立延迟设备消费与主机通知处理，记录逻辑取消、设备结束和槽归还 | 设备结束随负载变化支持排空；设备早已结束而归还晚，应查主机控制路径 |
| 多 stream 没有变快：依赖串行、资源饱和或管理开销 | 查看实际等待边；对照独立 workspace，扫描工作量与并发 | 去掉错误依赖仍无收益时，不能继续归因同步；需重算资源与固定开销 |

正确性实验应让不同代使用可区分内容，覆盖无消费者、仅写不读、两个读者反序结束、读后写、部分提交失败、取消、重复完成与旧 epoch。错误对照要实际删除一条保护或错误合并一个责任，确认独立参考确实能发现它。

目标 GPU 验证还需核对事件是否覆盖真正的最后访问、外部库的 stream 契约、编译后访问范围、复制与计算的物理重叠，以及同步与 profiler 的扰动。主机函数调用时长不是设备工作完成时间；多个 stream 的累计 kernel 时长也不是墙钟关键路径，相关口径见[主机与设备时间](../system-semantics/host-device-timing.md)。
