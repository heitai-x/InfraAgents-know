# K-SYS-015：服务主机运行时：执行域、队列与缓冲所有权

推理服务的 CPU 工作包括接收与解析、tokenization、调度、张量准备、提交、结果处理和响应编码。它们有不同的阻塞方式、并行度和生命期，必须与模型算子共享同一份主机资源预算。

## 执行域与有界通信

事件循环适合协调大量等待中的连接和完成通知；一个长时间占用该执行域的解析或分词任务会延迟其他连接处理。线程池可以隔离阻塞工作，但是否获得 CPU 并行还取决于运行时和所调用的原生库。进程池增加隔离和独立执行能力，同时引入 IPC、序列化、地址空间和模型副本问题。线程数或进程数本身不是吞吐量。

一个可分析的划分是：网络接入域产生规范化请求；输入处理域产生带身份的 token/模态张量；调度域拥有请求状态和可执行批次；模型域拥有执行资源；响应域按提交顺序发送结果。跨域传递明确的请求身份、版本、完成事件和缓冲所有权，而不是让所有线程直接修改同一份批次数组。

队列必须有界，界限可以是项数、字节、token 或工作量。仅限制请求数会把 100 个短提示与 100 个长视频当作相同负载。若上游生产速率持续高于下游消费速率，无界队列只把过载变成增长的内存和尾延迟；容量满时需要等待、拒绝或明确降载策略，并让 deadline 与取消能够穿过等待队列。

## 统一计算 CPU 与内存预算

设阶段 j 每请求平均消耗 cⱼ 个 CPU 秒，分配 pⱼ 个有效核，单看该阶段的稳定性必要条件为 λcⱼ<pⱼ。它忽略了方差和排队，因此不足以保证尾延迟。多个阶段共用 CPU 时还要满足总预算，另计模型内部线程、垃圾回收、通信和操作系统工作。

设定 tokenization 每请求占用 8 ms CPU，输入域有两个有效核，其理想上限为 250 请求/秒；事件循环还有每请求 1 ms 的不可重叠 CPU 工作，理想上限为 1000 请求/秒。假设模型可以处理 500 请求/秒，当前输入域已经限制整体。把模型线程翻倍不会消除这个瓶颈；若大量长提示使分词成本翻倍，输入容量还会下降。

主机内存要计入连接缓冲、未分词输入、token 数组、共享 IPC 段、pinned staging 和待发送输出。共享内存省去一次复制，但生产者不能在消费者结束前重用它；进程异常退出后，也需要由明确的资源拥有者回收。复制路径虽然多搬字节，却可能简化生命期并改善隔离，应比较数据大小、频率与错误处理成本。

## 从取消到可回收

| 请求位置 | 取消后的动作 | 仍需保护的对象 |
|---|---|---|
| 尚在输入队列 | 移除或跳过该代请求 | 仍被其他阶段读取的输入缓冲 |
| 正在分词或预处理 | 标记结果不再提交，必要时协作停止 | 原生调用在用的输入与输出 |
| 已提交模型执行 | 禁止后续调度与客户端提交 | 在途 DMA、kernel、通信和 KV |
| 输出等待发送 | 终止发送，释放已无读者的结果 | 网络层尚未完成的缓冲访问 |

取消标志不能倒转已发起的 DMA，也不能保证一个阻塞调用立即返回。迟到结果携带原请求及代次，不能写进已复用的槽位；最终清理要汇合各执行域的完成事件。对断开连接的响应行为以 [本地 ASGI 规范](../sources/S-ASGI.md) 的相应版本为准，不能把发送函数返回等同于客户端已经消费数据。

## 背压如何连接到模型调度

慢客户端会让输出积累。若每个请求的输出缓冲有上限，服务可以暂停该请求后续生成或按协议终止；暂停又会延长 KV 占用时间。因此网络背压也参与容量准入。批量刷出多个 token 降低封包开销，但增加可见延迟，并改变 ITL 事件位置；不能在没有说明口径时与逐 token 刷出比较。

主机轮询减少唤醒延迟，却占用核和功耗；阻塞等待节省空闲资源，却引入唤醒与调度延迟。完成通知的批处理也存在同样取舍。对延迟敏感的小请求，调度和序列化可能占主导；对大张量，复制与内存带宽可能占主导。两类负载应通过测量决定执行域和缓冲设计。

## 观测与反例

沿同一请求记录各阶段入队、开始、结束、提交和取消事件，区分排队时间与 CPU 服务时间。检查 CPU 实际可用额度、进程/线程数、上下文切换、主存流量和分配次数，避免用“CPU 总利用率不高”排除单一执行域饱和。

验证应包括长输入阻塞短输入、慢客户端、突发到达、队列饱和、分词失败、worker 退出和各阶段取消。比较纯复制与共享缓冲、单域与分域、请求并行与算子并行时固定任务语义和资源总预算。改善单阶段吞吐而使模型饥饿、内存峰值或请求尾延迟恶化，说明资源划分仍需调整。
