# K-SYS-007：输入输出语义：Tokenizer、Chat Template 与流式文本

模型消费的是确定的 token/特征序列，而用户提交和接收的是消息、文本与媒体。模板、规范化、分词、位置、输出转换和停止协议共同连接这两种表示；其中任一步改变，都可能改变模型函数或用户收到的结果。优化这条链路首先要保存语义，再比较准备、搬运和流式提交成本。

## 输入表示与状态边界

设消息序列为 M，固定制品档案为 A，模板选项为 f，截断策略为 τ。纯文本输入可以表示为：

x = Trunc_τ(Encode_A(Render_A(M,f)))。

Render 决定角色、内容和回合标记如何序列化；Encode 包含制品规定的 normalization、预分词、词表与特殊 token 策略；τ 明确截断单位、方向和允许删除的语义单元。最终输入还包含可见性 mask 和模型位置坐标 φ。多模态路径另外产生特征 z、模态对应关系及位置元数据，不能只保存文本 placeholder。

输入档案至少绑定模板、tokenizer/processor、普通与特殊 token 分类、词表映射以及兼容的模型版本。ID 落在 embedding 行范围内只是形状合法：两套同大小词表可能把同一个整数解释成不同内容。输出 decoder 同样必须绑定这个档案。

运行时需要区分以下量：

| 状态 | 含义 | 不能由它推断 |
|---|---|---|
| logical_len | 已知有效 token 序列的长度 | 每个 token 的模型状态都已计算 |
| consumed_len | 已消费并成功提交必要模型状态的有效位置数 | 已具备下一次采样所需的末行 logits |
| physical_width | 执行张量的物理宽度 | 有效输入长度或模型位置 |
| sampled_count | 已正式选出的生成 token 数 | 已交付字符数或已计算 KV 数 |
| decoded_bytes | decoder 已确认的文本字节数 | 这些字节均可绕过 stop 检查发送 |
| submitted_bytes | 按服务协议提交的内容字节数 | 远端客户端已经消费 |

consumed_len 是计算进度，不是 KV 存储张量的长度；滑动窗口或静态缓存尤其不能通过张量宽度反推它。即使全部输入 KV 命中，缺少末行 logits 时仍需合法重算或恢复分布，见[前缀缓存](../algorithms/prefix-cache-identity.md)。

## 消息、特殊 token 与截断的合法性

[S-CHAT](../sources/S-CHAT.md) 说明，chat model 仍然延续 token 序列，模板把角色和回合边界写进这条序列。来自同一底座的模型也可以使用不同控制标记。因此模板不是可随意调整的展示格式。

`add_generation_prompt` 表示开始新的 assistant 消息；具体模板可能不需要额外标记，此时该选项可以没有效果。`continue_final_message` 表示继续末条预填消息，移除阻止继续生成的结尾标记。固定文档规定二者不能同时启用。工具调用身份、参数序列化和工具结果顺序也参与输入构造；业务上等价的 JSON 对象可能因键顺序、转义或空白产生不同 token。

模板通常已经包含所需特殊 token。先以 `tokenize=False` 渲染，再单独 tokenize 的路径应禁用自动特殊 token，避免重复 BOS/EOS；直接由模板接口产生 token 的路径由该接口统一处理。合法性应核对控制标记的语义位置，而不是要求所有特殊 token 在整段中只出现一次：多轮消息本来就可能具有多个结束标记。

用户内容中出现控制 token 的可显示拼写时，究竟被识别为特殊 ID 还是普通文本，由选定 tokenizer 和入口合同决定。服务必须固定并测试这种解释；简单字符串插值不能证明角色边界得到隔离。即使序列化边界正确，也不构成对自然语言指令注入的完整防护。

截断需要同时满足资源限制与消息结构。按 token 预算直接删除序列前部，可能切掉系统指令或留下半个角色结构；按字符删除还可能改变边界分词。可选择拒绝、按消息/内容单元删除后重新渲染，或采用制品允许的 token 截断，但必须记录所选路径、删除范围和重建后的实际长度。预算不足以容纳必需包络时应失败。原始内容到规范化字节、再到 token 的 offset 可能是多对多关系，不能总用简单字符区间表示。

模型上下文上限、请求输出预算和服务容量上限分别核对。字节、Unicode 码点、token、视觉 patch 与音频样本不能互相代替计数。多模态 placeholder 展开后的实际位置数才参与相应模型预算。

```pseudocode
算法 构造纯文本模型输入
输入：消息 M、固定档案 A、模板选项 f、预算 b、截断合同 τ
输出：有效 token x、mask、positions、输入身份与删除记录，或失败
1. 核对角色顺序、内容类型、工具调用与结果对应关系，以及 A 的制品兼容性。
2. 若两个模板选项冲突，失败；若输入为空，按合同插入合法起始输入或拒绝。
3. 用 A 的模板渲染 M；选择直接产出 token，或渲染后关闭自动特殊 token 再分词。
4. 核对 ID 范围、控制标记位置，以及需要保存的内容/模态对齐关系。
5. 若超出 b：
       若禁止截断，失败。
       否则依 τ 删除允许的单元并记录来源范围；需要时重新渲染、分词。
       每次重建都重新计算实际长度；不可删除内容仍超预算则失败。
6. n ← 有效 token 数；按模型合同生成模型位置 positions。
7. 按执行布局建立物理张量与 mask，同时保存有效位置到物理行的映射。
8. 新请求令 consumed_len ← 0；恢复请求只接受身份相容且已就绪的状态证明。
9. 返回输入与记录；尚未完成的前处理和模型计算不推进 consumed_len。
```

## 一条可重建的分词路径与增量边界

tokenizer 家族各异。下面定义一个确定性的 byte-BPE 教学模型，用来展开合并和边界问题；它不是对任意真实 tokenizer 的替代实现，也不是来源文档提供的上游算法。

固定 normalization N、预分词边界、256 个初始字节符号、普通词表，以及相邻符号对到新符号和优先级 rank 的映射。特殊控制片段由模板合同先识别，不参与普通文本合并。对普通文本先执行 N，再按预分词规则切段，各段转成 UTF-8 初始字节符号。一个合并符号的字节展开等于两个子符号展开的串接。

```pseudocode
算法 确定性 byte-BPE 段编码
输入：一段规范化字节 w、字节初始符号表、合并表 R
输出：普通 token ID 序列
1. symbols ← w 的逐字节符号序列；空段返回空序列。
2. 重复：
       从所有相邻符号对中找出 R 允许的候选。
       若没有候选，结束。
       按最小 rank、再按最左位置选择一对。
       用对应新符号替换这两个相邻符号；序列长度减少一。
3. 将剩余符号映射为 ID；任一符号缺少映射则失败。
4. 按原段顺序串接各段结果；不得跨声明的预分词边界合并。
```

每次合并减少一个符号，因此有限输入必然结束。符号字节展开串接始终等于该段规范化字节，这是独立于合并顺序的守恒关系。若使用未知词符号、非字节初始单位、随机合并或其他后处理，需要另行定义合同。一般只能期待解码恢复规范化后的表示，不能要求 `decode(encode(s))` 总是恢复原始 s。

最小边界反例是：合并表含 `(a,b)→ab`。分别编码片段 `a`、`b` 得到两个 token，完整编码 `ab` 得到一个 token。normalization 也可能改变旧后缀：NFC 下，`e` 后追加组合重音，可能形成预组合字符。因而“只对新增片段分词并追加”通常没有等价性保证。

增量输入只能提交已经证明稳定的 token 前缀。可保存原始输入，从制品证明的稳定边界重新规范化与分词，并比较旧 token 前缀；没有有限重算窗口保证时，应重算更大范围或等待完整输入。若重算改变了已经消费的 token，就必须从最后相容的模型状态重建，不能保留旧 KV 再覆盖 token 数组。重新渲染历史回合还可能改变末尾标记，因此稳定性必须在完整模板路径上判断。

## Padding、位置与末行选择

设请求 i 的有效长度为 nᵢ，物理宽度为 L。零基普通文本的一个合法布局是：右 padding 将有效 token j 放在物理行 j；左 padding 放在 L−nᵢ+j。模型位置可以仍为 j，但是否如此必须按制品核对；物理行号不是位置编码的通用定义。

对长度 1、3 的两条输入，右 padding 到 3 后，最后有效行分别为 0、2；左 padding 后均为 2。需要最后输入位置的 logits 时，应通过有效行映射取得对应行。固定读取最后一列只在所选布局保证它有效时成立。模型使用特殊 pooling 或任务头时，输出行选择还必须遵循该任务的合同。

attention 只能读取模型允许的有效位置；新增多行的可见集合同时包含合法历史与块内因果前缀。[S-HF-CACHE](../sources/S-HF-CACHE.md) 支持历史与新增 K/V 合并及增量 mask 覆盖两者的要求，但没有定义所有实现的 position 字段。

padding 不推进有效 consumed_len，也不能成为后续可见历史。密集实现可能物理计算或存储 padding 行，静态缓存也可能预留这些槽位；这与“padding 没有有效语义”并不矛盾。只有显式跳过无效行的实现，才能声称避免了相应计算或写入。对全空 mask，末行选择必须失败或进入声明的空输入路径，不能默认返回最后一行。

## 输出转换与停止规则

输出链至少分为特殊 token 分派、decoder 稳定文本、stop 检查、协议提交四步。EOS 是特殊终止事件；其可显示名称不等于普通文本中的同名字符串。其他控制 token、padding 或非文本产物也按合同单独处理。

普通 token 若有固定字节展开 σ(v)，可以先串接字节再增量解释 UTF-8。字符“你”的字节 E4 BD A0 可以跨三个 token；逐 token 用忽略错误或替换字符的方式 decode 会破坏内容。严格增量 decoder 应保留最多三个未完成 UTF-8 字节，在后续字节到达后再产出完整码点。非法字节与终止时未完成字符应按明确合同报错；本章检查采用严格报错。

并非所有 decoder 都等于 σ 的简单串接。空白清理、片段规则或特殊 token 处理可能修订旧后缀。此时必须由有状态转换器给出稳定输出边界，只把不会被未来扩展改写的字符交给 stop 层。没有稳定性保证时，可选择整段解码；不能先提交不稳定文本再默默撤回。

### 明确选择首次完成语义

多 stop 模式存在真正的选择问题。本章选定以下流式合同：按稳定 Unicode 码点顺序扫描，在第一个使任一完整模式结束的位置立即停止；同一结束位置选择最长模式，相同模式按配置顺序去重。这对应先比较结束位置，再比较开始位置。模式非空，默认排除停止串；是否包含停止串必须在流开始前固定。

例如模式 `ab`、`abc` 遇到 `abc`，在读到 b 时就命中 `ab`，不会等待 c。模式 `abcd`、`bc` 遇到 `abcd`，在 c 处先完成 `bc`，排除模式时输出 a。若一次处理整个 chunk 后才寻找“开始位置最早的完整命中”，会选 `abcd`，结果随 chunk 切分变化。

另一种合法合同可以等待更早开始的候选决议，或采用最长匹配，但必须增加相应待决状态与终止处理。本章算法及检查只证明已声明的首次完成语义，不将它归为所有服务的默认行为。

### 有界未提交后缀算法

设模式集合为 P，W 为最长模式的码点数，P 为空时 W=0。状态包含严格增量 UTF-8 decoder、尚未提交的字符缓冲 pending、运行阶段和终止原因。每确认一个码点，都先检查完整模式，再只保留可能成为模式真前缀的最长后缀。

```pseudocode
算法 稳定文本的流式提交
初始化：pending ← 空；阶段 ← RUNNING；严格 UTF-8 decoder 状态为空。
验证所有 stop 都是非空有效 Unicode 字符串；固定包含/排除策略。

输入字节片段 piece：
    若已停止或取消，忽略片段；失败状态按失败合同处理。
    按字节顺序推进 decoder；非法序列则标记 FAILED 并报错。
    每产生一个完整稳定码点 c：
        pending ← pending ∥ c。
        hits ← 所有为 pending 后缀的完整 stop。
        若 hits 非空：
            p ← hits 中最长模式，相同者按配置顺序。
            提交 pending 去掉末尾 p 后的前缀；包含策略再提交 p。
            清空 pending；阶段 ← STOPPED；原因 ← stop；保存 p。
            忽略本片段及以后片段的剩余字节，返回。
        k ← pending 后缀中，同时为某一 stop 真前缀的最大长度；无则为零。
        提交 pending 的前 |pending|−k 个码点，仅保留末尾 k 个。

正常结束事件 reason，reason 为 eos 或 length：
    若已终止，不重复提交。
    完成 decoder 的严格 flush；未完成字符则 FAILED。
    将 flush 产生的稳定字符按上述规则扫描。
    若尚未命中 stop，提交 pending 并清空，保存给定 reason，进入终态。

取消事件：
    撤销未来提交资格，丢弃 pending 和 decoder 残留，进入 CANCELLED。
    已经提交的内容仍属于输出记录；设备排空与缓冲回收另行完成。
```

未命中时，任何未来跨边界 stop 的已知部分必定是当前文本的后缀和某模式的真前缀，因此只保留最长这样的后缀就覆盖所有较短候选。被提交的部分不再可能属于未来首次完成的 stop。命中时，模式开始处之前的内容才可提交；已提交前缀始终是最终协议内容的前缀。

正常 EOS 或长度终止说明不会再有文本，因此未完成的 stop 前缀成为普通文本，可以 flush。取消采用丢弃待决后缀的合同，不能伪装成正常 EOS。若长度上限到达的最后一个普通 token 内同时命中 stop，本章先处理该 token 的文本，再以 stop 为终止原因；usage 仍按协议记录已正式采样的 token。计数规则和事件优先级必须一起固定。

停止窗口限制的是待决内容量，不保证墙钟等待上限：模型暂停或客户端背压可以让一个模式前缀等待很久。若输出转换器还有自己的不稳定后缀，它的驻留和延迟另计。

## 一次组合轨迹：采样、字节、KV 与交付

取纯文本 prompt 已消费两个有效 token，初始 logical_len=consumed_len=2，并已有末行 logits。假设三个普通输出 token 的原始字节展开依次为 `41 E4`、`BD A0`、`21`，即共同组成文本 `A你!`；stop 为 `你!`，采用排除策略。这个词表切分是设定，不代表某个真实 tokenizer。

| 事件 | logical_len / consumed_len | decoder 与 stop 层 | 已提交内容 |
|---|---|---|---|
| 采样 y₁ | 3 / 2 | A 已完整且安全；E4 留在 UTF-8 状态 | A |
| 消费 y₁，再采样 y₂ | 4 / 3 | BD A0 完成“你”；它是 stop 真前缀，进入 pending | A |
| 消费 y₂，再采样 y₃ | 5 / 4 | ! 完成 stop，丢弃“你!”并终止 | A |

此时正式采样了三个 token，稳定文本共五个 UTF-8 字节，提交内容只有一个字节，模型状态只覆盖 prompt、y₁、y₂。y₃ 已知但不必为了终止再做前向。把 sampled_count 写成 consumed_len 会凭空制造 y₃ 的 KV；把 decoded_bytes 写成 submitted_bytes 会泄漏 stop。

若在 y₂ 后以 length 正常结束，则应提交待决的“你”，最终为 `A你`；若此时取消，则按本章取消合同保留 A 并丢弃待决字符。这些分支使用相同 token 前缀，却有不同终止语义。协议提交进入服务器发送缓冲也不等于客户端已收到；[S-ASGI](../sources/S-ASGI.md) 的发送与断开边界要求继续区分这两个事件。

## 成本、关键路径与选择反转

输入准备成本可写成 C_render(M)+C_norm(B)+C_tokenize(U)+O(n)，其中 B 是渲染字节数，U 是规范化后的初始符号数，n 是有效 token 数。上述朴素 BPE 每次扫描相邻对，最坏比较工作为 O(Σⱼuⱼ²)，uⱼ 是各预分词段的初始长度；不是所有 tokenizer 都具有这个复杂度。带相邻关系、候选堆和失效候选检查的实现，在常数时间 pair 查找等假设下可将该模型的候选维护降到约 O(U log U)，但增加元数据、分配和局部性成本。

访存与驻留至少覆盖原始内容、渲染/规范化副本、符号工作区、ID、可选 offsets 和模态张量。只有确实共享同一存储的表示才可去重计容量；保留调试快照会产生额外副本。进程池分词还要计 IPC 序列化、复制和队列驻留。批处理有机会摊销调用成本，但等待聚批和 padding 可能增加时延与工作量。

设一批有 R 个请求、物理宽度 L，ID 每元素 s_id 字节，则密集 ID 主体传输为 RLs_id；ragged 主体为 s_idΣᵢnᵢ，另有边界元数据。mask、d 轴位置坐标和模态特征另列。主机到设备准备完成、DMA 完成和消费者可读之间需要依赖；不能为减少等待就提前复用输入缓冲。

输出若在设备完成采样，回传的是 token ID 与必要事件；若把整行 logits 回传主机再采样，每步还要传词表宽度乘 logits 元素字节数。二者的通信量与同步点不同。逐 token 等待设备结果还可能支付 G 次通知/同步成本；批量回传能摊销开销，却增加可见内容等待。没有设备时间线时，不能把这些逻辑字节直接称为 PCIe 实际事务或 GPU 实测时延。

对 stop 算法，设输出有 C 个稳定码点，模式总长度为 H。直接枚举各模式的所有真前缀，并逐个比较后缀，朴素最坏为 O(CΣₚ|p|²)，还要计缓冲搬移；不能将整段反复搜索写成线性算法。多模式自动机可以预先建立转移、失败边和匹配输出，在线逐字符推进，并按相同首次完成规则选择命中。其状态构建/存储取决于稀疏或稠密转移表示；使用常数摊销转移时，扫描可达 O(C+匹配处理量)。这项准备只有在模式规模和复用次数足够时才容易摊销。

运行中的 pending 最多 W−1 个码点；与严格 UTF-8 decoder 合计，文本待决字节上界为 4·max(W−1,0)+3。生产实现可只保留这个窗口，提交后丢弃旧前缀。保存全部 candidate 再反复搜索会额外驻留 O(C) 内容，不能沿用有界窗口的容量结论。测试为核对历史而保存完整输出，是独立审计记录。

网络账按实际编码后的内容 D_enc、事件数 N_evt 和每事件封装开销 h 估计为 D_enc+N_evt·h；JSON 转义、压缩和代理缓冲会改变实际大小与时序。待发送队列容量 Q 与 stop 窗口分别计账。慢消费暂停生成后，KV 可能继续驻留，因此降低发送频率并不必然降低总内存。

主机阶段若每请求消耗 c CPU 秒，到达率为 λ、有效核预算为 p，则 λc<p 是稳定性的必要条件，不能保证尾延迟。设定 c=2 ms、λ=1000 请求/s，仅该阶段已需 2 CPU 秒/s，未计网络、调度和其他线程。更换分词实现后应分别测服务时间和排队时间，避免将设备等待归为 CPU 分词开销。

首内容时间取准备、传输、prefill、采样、解码、stop 确认和发送依赖图的关键路径。仅串行依赖项可相加；并行准备可能受共享主存带宽或执行域限制。模型计算支配且主机充足时，复杂输入缓存可能只增加驻留与失效逻辑；主机饱和时，有界工作池、原生实现或减少副本才可能改变整体容量。

模板或 tokenizer 变化后，应重验实际 ID 和 decoder 身份；是否使某个已有缓存失效，取决于其真实依赖。最终 token、位置和前向条件完全相同的 KV 不必仅因模板文件名变化而判错；只按旧字符串猜测相同则没有证明。输入增量缺乏稳定边界时应放弃直接追加；停止模式很少且输出短时可保留易审计的朴素实现；模式多、长或高复用时再比较自动机准备与在线总成本。

多模态改变 processor、采样率、resize/crop、patch 网格或媒体内容后，要重建受影响特征与位置。相同 URL 或 placeholder 不能证明输入身份。输出音频需要样本偏移、编码格式和播放/提交边界，不能沿用文本 UTF-8 窗口。

## 竞争解释、区分实验与反证

| 观察 | 竞争解释 | 可区分的干预与判断 |
|---|---|---|
| 显示相同的输入产生不同结果 | 模板、normalization、特殊 token、截断或采样不同 | 固定模型和采样，逐层比较渲染字节、规范化表示、ID、位置及删除记录；从第一个不同的表示修正归因 |
| 增量输入复用后结果变化 | 跨边界合并、规范化改写、模板末尾变化、旧 KV 被保留 | 完整重建作参考，分别只改变文本切分和回合边界；若 ID 已不同，先撤回 KV 复用合法性的判断 |
| 输出乱码或少字 | 逐 token 错误处理、decoder 制品不匹配、过早提交清理后缀 | 固定完整有效字节串，枚举 UTF-8 字节切分，与严格整段解码比较；故意逐片段忽略错误必须被拒绝 |
| 最终文本正确但流中泄漏 stop | 中间内容先发后截、未保留真前缀 | 每次提交后检查累计内容是否仍是独立参考最终内容的前缀；只比最终字符串不能通过此检查 |
| stop 身份或内容随 chunk 改变 | 整块搜索的顺序与流式合同冲突 | 用 `ab/abc` 和 `abcd/bc` 枚举所有切分；首次完成参考应分别选 ab、bc |
| 批处理后输出错误 | 末行选择、mask、位置或请求映射错误 | 同一输入分别独立、左/右 padding、批次置换执行；先检查有效行，再比较位置和模型输出 |
| usage 与文本长度不一致 | 合法多字节/多字符 token、被排除的 stop、EOS 或计数边界错误 | 记录正式采样、已消费、已解码、已提交四条边界，按组合轨迹复算；不能要求它们数值相等 |
| 分词优化后端到端不变 | 原先不在关键路径、节省被复制/排队抵消 | 固定实际输入与输出工作量，分开测 CPU 服务、队列、搬运和首内容；服务时间下降而总时延不变时撤回关键路径假设 |

随章检查采用独立整段参考：先严格解码完整有效字节串，再枚举模式出现位置，按最小结束位置、最小开始位置和配置顺序选取终止；它不调用被测后缀保留逻辑。检查对同一字节串枚举 chunk 切分，比较最终内容、原因、模式身份以及每一步提交前缀，并覆盖空模式集合、空输入、重叠模式、包含停止串、长度 flush、取消与非法 UTF-8。

负对照分别破坏整块匹配顺序、UTF-8 跨片段恢复和中间提交边界，必须由同一比较规则检出。padding 的独立有效索引集合还应拒绝固定取末列的错误实现。这些是小规模 CPU 逻辑模型；真实 tokenizer 合同、模型前向、GPU 同步、网络交付、吞吐和 Agent 使用效果均需独立验证。
