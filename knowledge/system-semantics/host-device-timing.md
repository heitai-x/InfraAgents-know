# K-SYS-001：主机与设备时间：偏序、区间并集和关键路径

服务延迟来自生产、提交、执行与消费之间的依赖路径。主机 API、设备执行、完成通知和业务消费可以重叠；把所有记录按时间排序，不会自动得到因果链，把各段持续时间相加，也不会自动得到墙钟时间。

## 事件、身份与时间域

一次观测至少需要事件语义、时间戳、单位、时间域、进程/线程/设备/队列作用域，以及请求、对象范围、执行尝试和对象代次。地址、队列序号或 correlation ID 都不能独立承担这些身份。重试沿用请求 ID、物理槽重新分配、多个请求共享一次计算时，必须另有映射，否则可能把旧发送与新确认配成一次传输，或把一次物理工作重复计数。

host 调用开始、命令被接受、kernel 开始、host API 返回、kernel 完成和 CPU 消费结果，是不同事件。设定 API 区间为 [0,5)，设备工作为 [3,8)，则设备开始减 API 结束为 −2。这与异步执行相容，因为 API 返回并不是 kernel 开始的必需前驱。只有已经证明 u 完成先于 v 开始，且两钟可比较时，负的对应等待才构成矛盾。

区间统一采用半开形式 I=[s,e)，时长 d=e−s，要求 s≤e。零长区间可以保留为事件点，但不贡献忙碌时间；e<s 必须拒绝。两个区间的重叠长度为：

\[
o(I,J)=\max(0,\min(e_I,e_J)-\max(s_I,s_J)).
\]

观测还应区分发生时刻与发现时刻。设备完成后，主机可能很晚才查询、收到通知或处理回调。若只记录回调处理时刻，它度量的是完成加上通知及调度延迟，不能直接充当设备完成时刻。记录中应说明时间戳来自执行活动、完成事件，还是主机观察。

同一进程内应使用适合测量经过时间的时钟。跨 CPU/GPU 时间域需要可靠映射；跨机器还需要处理偏移与漂移。设同一物理时刻的读数满足 t_B=t_A+δ，在当前窗口内 δ∈[δ_lo,δ_hi]。A 发送读数为 a，B 接收读数为 b，则传输经过时间属于：

\[
T\in[b-a-\delta_{hi},\ b-a-\delta_{lo}]\cap[0,\infty).
\]

非负约束来自发送先于接收。若交集为空，关联身份、校准界限或事件语义至少有一项不相容，不能把负上界静默改成零。若 a=10 ms、b=15 ms、δ∈[−2,4] ms，则 T∈[1,7] ms；图上的 5 ms 不能支持相差 1 ms 的方案判断。δ∈[4,8] ms 时则只能得到 [0,1] ms。这个模型假定窗口内的偏移已被同一界限覆盖；校准后经过 h 时间、相对漂移率有界为 ρ 时，可把偏移界限向两侧各放宽 ρh，再计入时间戳误差。没有漂移或映射误差界限，就不应沿用旧校准给出精确单向时间。

往返经过时间还包含回程和对端处理。设去程 2、处理 1、回程 5 个时间单位，往返为 8，除二得到 4，并不是去程 2。上下文传播连接跨服务操作，但不提供链路对称性或时钟校准。

## 比较成立的条件与观测方案

把时间差解释为延迟，至少要检查以下关系：

- 两端事件有明确语义和正确身份，单位相同，且处于同一时间域或可靠映射范围内。
- 声称的因果边有证据。普通 stream 顺序、覆盖最后写入的 event 等待、数据依赖和资源移交可以提供边；时间戳较早本身不提供边。
- 采集覆盖所讨论的进程、设备、事件类型与窗口。缺表、空表、过滤后为空、窗口外和无法关联必须分别保留，不能都写成零成本。
- 聚合对象一致。单 engine 覆盖、单设备活动覆盖、SM 资源使用、请求延迟和整机墙钟回答不同问题。
- 正常路径与采集条件有记录。额外同步、缓冲刷新、采样和详细回溯可能改变队列与重叠。
- 失败、部分完成、取消和零工作有明确状态。逻辑取消不证明设备已停止访问；提交成功不证明工作成功完成。

选择范围标注、原始事件、聚合表或短窗口，是观测方案选择。它们改变成本和可回答的问题，不改变异步执行的合法性。若只需要找累计热点，聚合表可能足够；若要判断重叠、空洞、单请求路径或尾部，必须保留相应事件及身份。父子 span 的包含关系也不等于父 span 完成先于子 span 开始，不能直接转成完成依赖。

## 区间并集与最大并发

对已限定资源作用域、转换到同一时间域的区间，定义累计时长 S 与覆盖时间 U：

\[
S=\sum_i(e_i-s_i),\qquad U=\left|\bigcup_i[s_i,e_i)\right|.
\]

只有采集确实覆盖指定资源，才可以把 U 解释为该资源被所选活动占用的时间。即便如此，一个 memcpy 覆盖某段时间也不证明 SM 忙碌，更不证明整机达到容量上限。

```pseudocode
算法 IntervalStatistics(intervals, window)
输入：已按身份去除重复导出记录、限定作用域并统一时钟和单位的有限区间；window=[W0,W1)
输出：规范合并区间 merged、累计 S、并集 U、最大并发 K、窗口未覆盖时间 idle

检查 W0、W1 和所有端点有限，W0<=W1；不满足则拒绝
work=空
for 每条原始区间 [s,e):
    若 e<s，拒绝；必须先检查，再做窗口裁剪
    a=max(s,W0)，b=min(e,W1)
    若 a<b，把 [a,b) 加入 work；否则不贡献覆盖
S=work 中各区间长度之和
按 (开始,结束) 排序 work；merged=空
for [a,b) in work:
    若 merged 非空且 a<=最后一段的结束：
        最后一段的结束=max(原结束,b)
    否则追加 [a,b)
为每个 work 区间建立 (a,+1)、(b,-1)
按 (时间,增量) 排序；同一时刻先结束、后开始
active=0；K=0
for (时间,增量) in events:
    active=active+增量
    检查 active>=0；K=max(K,active)
检查最终 active==0
U=merged 中各段长度之和
idle=(W1-W0)-U
返回 merged,S,U,K,idle；空输入自然返回空区间和零覆盖
```

扫描不变量是：merged 的全部区间表示已处理输入的并集，区间互不重叠且不相邻，最后一段保存当前连续覆盖的最大右端。开始已排序后，新区间只能延长最后一段或开新段。相邻半开区间不同时活动，但可以合并成连续覆盖；[0,10) 与 [10,20) 的并集为 [0,20)，最大并发为 1。把它们保留为两个相邻段也能表示相同集合；这只是表示差异，不能把它作为覆盖算法错误的负对照。

重复记录与不同操作具有相同区间必须区分。前者按稳定事件身份去重；后者是两项真实工作，累计与并发都应计两次。嵌套、完全落在窗口外、跨越窗口、零长窗口和零长事件都由上述裁剪和分支覆盖。逆向区间即使落在窗口外也不能借裁剪掩盖。

令 C(t) 为活动区间数，则：

\[
S=\int C(t)\,dt,\qquad U=\int\mathbf{1}[C(t)>0]\,dt,\qquad U\le S\le KU.
\]

[0,10)、[5,15) 给出 S=20、U=15、K=2。窗口为 [0,20) 时未覆盖时间为 5。该恒等式说明累计量为什么可以超过墙钟；它不把点并发数 K 变成 GPU occupancy。Nsight Systems 所供统计说明也区分了累计时间百分比与应用墙钟，并明确时间利用率不等于资源利用率。

通用实现排序和扫描需要 O(n log n) 时间、O(n) 空间。仅求并集时，输入若已按开始排序，可以 O(n) 扫描；最大并发还需要按时间排序的端点，不能因为开始有序就省略结束次序。在线处理开始事件时，可用结束时间结构维护在途活动，其成本应另计。

## 关键路径的递推、证据与边界

建立有限有向图 G=(V,E)。节点 v 是一段不可再分的工作或事件，持续时间下界 d_v≥0；r_v≥0 是相对共同起点的释放时间下界。边 u→v 表示 u 完成后至少经过 l_uv≥0，v 才能开始。时间单位统一；共同起点应选在全部释放之前。若关系连接开始点或部分范围完成点，先拆成事件节点，不能强行把整个 API 或 kernel 当成一个完成边。

每个节点都受自己的释放约束，包括已有前驱的节点：

\[
ES_v=\max\left(r_v,\max_{u\to v}(EF_u+l_{uv})\right),\qquad EF_v=ES_v+d_v.
\]

空前驱集合只留下 r_v。漏掉 r_v 会低估等待外部输入、容量或准入的节点。例如 d=(2,3)、r=(0,10)、边 0→1 的等待为 4，节点 0 在 2 完成，边约束只要求节点 1 在 6 开始，但其释放时间是 10，因此最终完成下界为 13，而不是 9。

```pseudocode
算法 EarliestCompletion(V,d,r,E,target)
输入：有限节点；非负有限 d、r；边 (u,v,l)；可选目标 target
输出：ES、EF、完成下界和一条达到该下界的约束路径；或拒绝原因

检查端点、数值和目标身份
同一有序节点对的重复边须先明确合并语义，本算法直接拒绝重复
建立 pred、succ 和入度；将所有零入度节点放入队列
order=空
while 队列非空:
    取出 u，加入 order
    for v in succ[u]:
        入度[v]减一；变成零时入队
若 order 未包含全部节点，返回 Cycle
若图为空：无目标时返回完成下界 0 和空路径；指定目标则拒绝
for v in order:
    ES[v]=r[v]；parent[v]=空
    for 每条 (u,v,l) in pred[v]:
        若 EF[u]+l>ES[v]:
            ES[v]=EF[u]+l；parent[v]=u
    EF[v]=ES[v]+d[v]
若指定 target，end=target；否则 end=使 EF 最大的节点
从 end 沿 parent 回溯，到 parent 为空处停止，再反转路径
路径分数=r[路径首节点]+路径节点 d 之和+路径边 l 之和
检查路径分数==EF[end]，返回结果
```

释放约束可以主导内部节点，所以回溯路径不必始于原图的根。等价地，增加一个时间为零的虚拟起点，并用长度 r_v 的边连接每个节点，就把所有释放约束纳入最长路径。独立检查因此必须枚举从每个节点开始的路径，仅枚举原图根到汇点会漏掉释放主导的情况。

拓扑归纳保证 ES 同时满足本节点释放与全部前驱约束，并在这些约束下最早。若 d、r、l 是可靠下界，EF 是完成下界；若它们是精确值且没有遗漏资源和依赖，最早日程可达到该值。普通依赖图不求解多资源调度：没有边的工作允许并发，却可能因共享 SM、复制 engine、CPU、链路或缓冲容量而排队。表达某次真实日程时可以加入有证据的资源等待关系；预测另一方案时，这些顺序和持续时间可能改变，不能照搬。

计算目标请求时仍须保留它的全部前驱。只保留“从请求到达可达”的节点，可能删掉一个提前启动、但目标必须等待的加载分支。最直接的做法是计算完整图，再读取目标 EF；需要缩图时，只能在保留目标全部祖先及其释放约束后计算。与目标无连接的慢工作不会改变它的 EF，但可能通过尚未建模的资源竞争间接影响目标。

主机等待 API 的区间可能包含等待先前设备工作的时间；kernel 从开始到结束的区间可能包含 stall 和尾部执行，但不包含启动前的队列等待。应分别记录提交、就绪、获得资源、执行和完成，避免把排队误写成纯计算，或把包含同一次等待的节点重复串联。

建图和拓扑递推为 O(|V|+|E|) 时间、O(|V|+|E|) 空间；回溯一条目标路径为 O(|V|)。配套检查为了核对每个节点会生成多条路径，不能把检查的额外开销当成正文算法的复杂度。

## 把完成事件接到数据与资源状态

加载路径至少区分预留缓冲、文件读取提交、块层派发、所需范围完成、用户可读、转换完成、H2D 完成、GPU 消费结束和资源归还。Linux blk-mq 文档明确不保证完成顺序，因此不能按提交先后匹配结果。iomap 的排队返回、部分字节返回和写回语义也不允许把文件调用返回统一解释为完整数据已交付或已持久。

对对象 X=(身份,代次,范围)，可以用下面的逻辑推进建立时间图：

```pseudocode
算法 AssembleObjectPath(X,events)
输入：带完整身份的提交、完成、发布、消费与归还证据
输出：本代已知状态、带依据的依赖边、尚未闭合的观测缺口

预留成功：登记本代范围和容量；状态 RESERVED
提交被接受：登记实际提交范围；状态 IN_FLIGHT，保留在途责任
收到完成：先匹配对象、范围、尝试和代次，再检查状态及成功字节
    旧代或重复证据不推进本代；部分完成只更新对应范围
    错误或未知完成不发布完整内容，保留尚未结束的责任
全部必需范围完成且相应平台可见性成立：状态 READY
消费者取得本代读取权：连接 READY 到实际消费开始，登记使用责任
消费者最后访问完成：只撤销该消费者自己的责任
关闭未来授权且全部实际使用结束：允许归还，状态 RETIRED
任一事件缺失：保留 UNKNOWN，不以提交顺序或通知时刻填造完成
```

这是重建观测关系的抽象规则，不是已经选择某个 CUDA、文件或 RDMA API 的实现。CUDA event 必须覆盖实际最后写入；库内部 stream 若未汇合到记录点，外部 event 不能替它证明完成。RDMA 的提交、CQE、通道通知和应用消费也分开：通知可能在 CQ 已被 poll 后才处理；本地完成不证明远端应用已消费。外部设备写 GPU 内存的可见性需要对应平台契约，本章不以普通主机时间戳证明它。

逻辑取消禁止后继业务推进，但不会自动结束已提交读取、DMA 或 kernel。取消响应、最后物理访问和实际归还应分别计时。若设备早已结束而归还很晚，应调查完成通知和控制线程；不能继续把全部滞后归因于设备执行。

## 条件化成本与完整组合轨迹

同一候选要在同一工作量和时间边界内列账：

| 成本 | 应计算的对象与条件 |
|---|---|
| 计算 | 被观测工作本身的计算量与服务需求；分析端另计区间排序、关联和建图 |
| 访存 | 实际读取、转换读写和 DMA 字节；trace 记录、索引与导出也产生内存流量 |
| 通信 | payload、重试与上下文传播，以及 trace 跨节点汇聚；ID 字节不等于网络延迟 |
| 准备 | 初始化、校准、注册/锁页、描述符、请求到 batch/API/kernel 的映射与标注 |
| 同步 | 合法依赖等待、结果交付与排空；采集刷新等额外同步单独说明 |
| 驻留 | 在途对象和保护缓冲、采集缓冲、索引与文件；聚合省空间但丢失实例关系 |

这些成本不是六个可直接相加的阶段时间。对固定日程，端到端由依赖和资源约束共同决定；某阶段的计算与访存可能已经包含在同一持续时间里，不能再重复加上字节除带宽。

设一个请求在 0 到达，读取、转换、H2D、GPU 消费依次执行；另有完全独立且不争用这些资源的工作。以下均为设定的 ms：

| 阶段 | 区间 | 必需前驱与资源 |
|---|---|---|
| 读取 | [0,40) | 已取得主机缓冲；I/O 路径 |
| 转换 | [40,48) | 所需读取范围完成；CPU 与主存 |
| H2D | [48,60) | 转换完成；传输路径 |
| GPU 消费 | [60,75) | 复制完成且可见；GPU |
| 独立工作 | [0,35) | 无数据边且假定无资源冲突 |

累计为 40+8+12+15+35=110。全部所列活动的时间覆盖为 [0,75)，长度为 75；这是跨资源活动覆盖，不是 GPU 忙碌时间。目标请求完成下界为 75。仅看该请求的 GPU 消费覆盖是 15；若 H2D 也属于所选设备活动口径，则该口径覆盖 [48,75)，长度为 27。独立工作的设备归属未指定，不能凭其名称加到 GPU 统计中。

把独立工作缩到 15，只把累计降为 90，目标仍在 75 完成。把读取从 40 缩到 20，其他持续时间和边不变时，请求路径变成 [0,20)、[20,28)、[28,40)、[40,55)，预测完成变成 55。这是条件化反事实；若改变读取方式也增加转换、注册或共享链路压力，必须重新计算。

资源和驻留可沿同一轨迹核对。设主机读取与转换原地使用一块 64 MiB 缓冲，H2D 结束后不再读取它；它至少受保护到 60。设备输入也是 64 MiB，从 48 开始持有，到 GPU 最后读取 75 才可归还。忽略其他对象和管理开销，48–60 期间两块物理内存同时存活，共 128 MiB；H2D 返回得早不能缩短这段保护。若转换另需输出副本，就应加入该副本的独立区间，不能仍沿用 128 MiB。

对去重后的物理对象集合 X，容量轨迹是：

\[
M(t)=\sum_{x\in X}b_x\mathbf{1}[a_x\le t<f_x],\qquad M_{peak}=\max_t M(t).
\]

其中 b_x 是字节数，a_x 是取得容量时刻，f_x 是满足全部最后使用条件后的归还时刻。这是带权生存期扫描，与执行忙碌并集不同。池 reserved 已包含其中 used 时，两者不能再次相加；共享对象也只计一份物理容量。

如果多个请求共享一次物理加载，它在资源并集与字节账上只出现一次，但每个等待它的请求都可以在关键路径解释中引用该阶段。把这些逻辑等待再次相加成总线物理时间会改变统计对象。

稳态还受共享资源需求限制。资源 r 每个有效工作单位承受 Q_r 字节、在同一并发条件下可持续带宽为 B_r 时，启动周期至少为 Q_r/B_r；CPU 转换和 DMA 共用主存时必须合计流量。更多缓冲可以减少容量等待，却不能消除每单位资源需求。有限窗口的 U/T 只是所选活动的时间覆盖比例，吞吐仍需有效完成量与明确窗口；到达但未完成、失败和取消不能从账中消失。

## 条件改变后保留什么

| 条件变化 | 保留、调整与放弃的依据 |
|---|---|
| 单 stream 变成多 stream | 保留真实生产、消费和最后使用关系；增加跨 stream 边，重新核对内部队列；不能再依靠一个全序 |
| 单设备变成多设备或多 engine | 各作用域分别求并集，再沿请求依赖连接；放弃把跨设备累计当墙钟或把设备覆盖当 SM 利用率 |
| 跨节点或校准老化 | 保留因果关系与本地经过时间；扩大误差界限；界限宽于决策差异时放弃精确单向归因 |
| 完成长尾、取消或重试增加 | 保留尝试和代次、全部物理责任；记录排空与归还；不能用平均阶段时间保证安全复用 |
| 负载接近饱和 | 增加队列、有效完成量和共享资源证据；非关键工作缩短可能改善容量，却未必缩短当前请求 |
| 采集缺失或扰动增大 | 保留未知和正常运行测量；补针对性信号或缩短采集；只在 profiler 下出现的收益不外推 |

多条等长关键路径也会限制优化收益：只缩短其中一条，另一条仍决定完成。每次改变持续时间、释放时间或边后，都应重新求最大约束路径，而不是永久给某节点贴上关键标签。

## 用区分实验修正解释

先固定请求身份、输入、有效工作量与输出完成边界，再选择能使竞争解释给出不同预测的干预。

| 观察与竞争解释 | 区分实验 | 预测及反证后的修正 |
|---|---|---|
| 设备空洞：主机准备不足、线程阻塞或采集缺口 | 补线程运行/阻塞与输入就绪事件；保持工作量增加合法预取 | 等待和完成均提前支持供给解释；补表才填满图而本地完成不变，支持观测缺口 |
| API 很长：提交开销或内部同步 | 分记 API、此前设备完成和请求输出；对照等待位置 | 仅 API 缩短、输出不变支持等待转移；不能据此声称服务加速 |
| 多 stream 不快：错误依赖或共享资源饱和 | 核对事件记录点，比较合法去边与独立 workspace | 去边改变空洞支持依赖解释；并发只增加排队则重查资源需求 |
| 累计 kernel 很大但目标不慢：重叠或共享工作重复归因 | 按物理身份去重，分作用域求并集，再求目标路径 | 非关键工作缩短而目标不变，反驳它直接决定该请求延迟 |
| 跨节点差值变化：真实链路变化或时钟变化 | 保留校准界限，同时观察客户端本地完成与往返 | 仅显示对齐变化支持时钟解释；界限仍宽则结论是未区分 |
| 取消很快而槽归还晚：物理排空或通知处理滞后 | 分别延迟设备消费和主机通知处理，记录三种边界 | 最后设备访问已结束但归还仍晚，转查控制路径 |

负对照应触发实质错误。[0,10)、[5,15) 可以检出累计冒充并集；相邻区间可以检出同刻先开始导致的假并发；有内部释放时间的 DAG 可以检出漏掉 r_v；两前驱汇合可以检出只等最早完成者；删掉读取到转换的边，会错误地预测后续可提前开始。不能仅凭全设备同步使异常消失就定位缺的是哪条边，因为同步同时改变了多个候选关系。

若观察反驳预测，应修改机制解释，即使候选总体仍然有益。平均阶段时间之和也不能解释请求 p99：队列形成、跨请求干扰、不同完成边界和窗口未完成项需要原始轨迹。最终性能在正常运行条件下重复评价，相关实验口径见[性能实验](../tools/statistical-experiments.md)。

## 配套检查与证据范围

配套文件为 `tools/check_k_sys_001_full.py`。它使用 Python 标准库，以独立整数单元覆盖参考核对并集、累计、最大并发与窗口守恒；以从每个节点出发的全部路径枚举核对带释放时间和边等待的 DAG；以可行偏移枚举核对因果时间界限。覆盖空输入、零长、裁剪、重复与嵌套、乱序节点标签、多前驱、内部释放、零持续时间和非法输入，并实际构造会被检出的错误对照。检查使用显式失败判断，避免解释器关闭普通 assert 后静默跳过验证。

检查脚本、输入绑定与实际执行结果见[检查记录](../../docs/evidence/knowledge-workflow-20261028-batch8/K-SYS-001/round-2/check-0.json)。

这些检查不执行 CUDA、DMA、文件 I/O、RDMA、profiler 或真实服务，不证明设备可见性、事件覆盖、真实重叠、目标机性能或 Agent 使用效果。一般实数端点、时间戳精度、漂移、采集丢失和实际资源调度仍有各自的验证边界。
