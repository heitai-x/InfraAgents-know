# K-FW-013：张量执行接口：布局、别名与后端分派

一个数学算子成为可执行部件，需要生产者和消费者对同一段数据作出相同解释。本文将这种边界称为张量执行接口：它包括逻辑轴、物理地址、数值过程、状态副作用和完成关系；文件名中的 ABI 指这个执行边界，不承诺某个库的 C++ 二进制兼容性。从零构建引擎时，可以复用成熟算子，但必须自行建立这些部件之间的契约，才能把局部实现组合成正确且高效的执行路径。

## 从数学函数到可消费的张量

以 Y=XW 为例，X 为 M×K、W 为 K×N，只确定了实数域的函数和轴关系。一次实际调用还需要说明输入和输出的存储类型、乘法与累加精度、布局、设备、哪些地址允许重叠，以及返回时设备工作是否已完成。一个适配器若只检查 shape，仍可能把数学上正确的组件接成错误系统。

可以把某个张量的描述分成三层。语义层说明各轴代表 token、head、channel 还是物理页；表示层说明 shape、stride、基址、偏移、对齐和量化 scale；执行层说明可写区域、所有权、使用它的设备与 stream，以及最后一次使用的完成事件。三层共同决定合法消费范围。页表或 ragged indptr 是另一份带单位和生命周期的输入，不是可以由连续张量 shape 自动恢复的信息。

算子边界还要说明空域。M=0 是没有待算 token，K=0 是空归约，某一 attention 行没有可见 key 则涉及归一化函数是否有定义；三者不能共用“返回零即可”的默认解释。库接口若不覆盖任务允许的域，引擎需要建立合法替代路径或在进入该接口之前组织工作，而不能把不支持的输入当作已实现能力。

## stride 是地址关系，不是轴标签

对元素大小为 b 字节的普通 strided 张量，设存储基址为 A、以元素计的存储偏移为 o，各维 stride 为 sᵢ，则逻辑下标 i 的地址为

\[
\operatorname{addr}(i)=A+b\left(o+\sum_j i_j s_j\right).
\]

这里的 stride 单位是元素；以字节为单位的外部接口必须相应换算。公式只描述给定表示，不能据此推断某个库接受任意负 stride、重叠 view 或未对齐地址。合法性还由具体函数的可接受域决定。

设一个 B×L×H×D 的连续张量大小为 2×3×2×4，其 stride 为 (24,8,4,1)。把轴解释为 B×H×L×D 后，正确的转置视图 stride 为 (24,4,8,1)，没有搬运数据。相同 shape 的连续新缓冲则为 (24,12,4,1)。逻辑位置 (0,1,0,0) 在两者中分别指向原存储偏移 4 与 12；只改 shape 或在消费者中硬写连续偏移，会把不同 token/head 的数据混在一起。这个算例是地址公式的推导，不是某个框架的运行结果。

维度大小相同也不能消除区别。特别是把 QKV 合并投影的输出切成三个 view 后，每个 view 的 token stride 可能仍是完整投影宽度。末维 stride 为 1 并不意味着整个张量连续；某个 backend 只要求末维连续，另一个可能要求完整紧密布局。适配器应遵循实际要求，避免为“看起来更规整”而复制整个历史缓存。

广播 view 的某个 stride 可以为零：多个逻辑元素读同一地址是有意的共享，但把它作为独立输出位置并行写入，会产生重叠写。量化布局则可能连一个逻辑元素对应一个存储元素的假设都不成立。两个 4-bit 值打包进一个字节时，还需要 nibble 次序、分组轴、scale 布局和解码规则；把容器 dtype 改成另一种类型不能完成数值转换。[FlashInfer 固定接口](../sources/S-FI.md)对 NVFP4 KV 数据与 block scale 分别规定布局，正说明这些信息必须一起传递。

## dtype 必须展开为一条数值路径

输入 FP16、累加 FP32、输出 FP16，与输入输出相同但中间允许低精度截断的计算，并非同一条舍入路径。FP32 存储也不保证矩阵乘法使用完整 FP32 尾数：固定 PyTorch 数值资料明确区分 TF32 乘法、FP16/BF16 的 reduced-precision reduction，以及 SDPA math backend 对低精度输入的中间提升。[数值原文](../../references/S-TORCH-NUMERIC/reader.html)给出这些边界；具体默认值随版本变化，工程比较应固定实际策略。

因此，算子的数值描述应覆盖输入转换、乘法格式、累加和归约、非线性近似、输出舍入，以及 NaN/Inf 等特殊值的处理域。融合可能删除参考路径中的中间舍入，分区归约可能改变加法次序，fallback 也可能从融合低精度路径转到具有 FP32 中间量的路径。它们可以保持实数数学函数，却不保证逐位相同。

当任务规定容差时，误差判断应按输出尺度和后续用途建立；当任务规定确定 token 或严格数值行为时，不能以“数学等价”直接放行。例如，若某一步 logits 的逐元素绝对误差均不超过 δ，参考 top-1 与次大值的间隔大于 2δ，就足以保持该步的唯一 argmax。这只是单步充分条件：后续状态、采样随机数和近似策略仍须单独满足任务要求，不能把它扩大为整段生成保证。若任务没有授权近似，不能靠更宽容差或删去小概率项来制造加速。

## 别名与状态副作用决定哪些融合合法

把算子写成 y=F(x) 容易隐藏缓存更新。更完整的表示是 (y,c′)=F(x,c)，其中 c 是调用前持久状态，c′ 是调用后的状态。接口需要说明 c 的哪些区域可变，旧 x/c 是否仍被其他消费者使用，以及 y 是否占用已有存储。

允许传入输出缓冲不等于允许它与输入任意重叠。一个 GEMM 的输出 tile 写回时，其他 block 可能仍在读取同一输入；一个归约也可能在统计量尚未形成前覆盖未读元素。原地版本必须有独立的依赖论证或明确的库保证。对仅逐元素且每个输出只读自己对应输入的函数，某种一一对应的别名可能合法；把这个结论转移到带广播、gather、归约或跨行消费的算子就不成立。

[FlashAttention 的 KV-cache 接口](../sources/S-FA-IMPL.md)给出具体的状态例子：提供新增 K/V 时会原地更新缓存；若 cache_batch_idx 存在重复且同时写入，文档不保证哪一个重复输入最终写入该位置。共享只读 prefix 与两个请求写入同一尾槽，具有不同的合法性。引擎必须把逻辑请求身份、物理槽和更新范围保持一致，不能让一个快速接口替自己决定所有权。

## workspace、stream 与完成边界

workspace 是参与执行的活跃存储。若两个调用会同时写同一区域，即使其输入输出互不重叠，也不能直接共享该区域。能否复用取决于实际读写区域和完成顺序；一个 wrapper 对象可以重用，并不说明同一对象及其可变计划可被并发调用。

容量设计应计入权重、持久状态、活跃输入输出、临时工作区和图捕获保留空间。假设两个互不依赖、并发执行的调用各需要 64 MiB 可写 scratch，则在没有区域分割或明确串行化时需要 128 MiB。若按依赖顺序执行且前者已完成，可复用同一 64 MiB；这个节省伴随并行机会变化。不能只把最大单次 workspace 加入容量账，也不能把所有串行阶段的 workspace 无条件相加。

GPU 函数返回通常只说明工作已排入队列。[PyTorch CUDA stream 原文](../../references/S-TORCH-CUDA/reader.html)明确区分同一 stream 的顺序与不同 stream 间的显式等待，还区分等待数据生产完成和防止 allocator 过早复用存储。消费者等待生产者，解决的是数据可读；保留存储到最后使用完成，解决的是地址仍属于这份数据。两种责任缺一不可。

设备也属于接口。CPU 指针、另一块 GPU 的张量、当前设备上的 workspace，不能因为 shape/dtype 一致就视为可直接组合。需要传输的路径还包含复制、目的端依赖和原缓冲存活期。把每个调用都强制全设备同步可能暂时掩盖生命周期错误，却改变了正常路径的并行成本。

图捕获进一步固定了指针和执行结构。固定 PyTorch CUDA Graph 文档要求重放使用相同虚拟地址；适配器中的临时复制、重新分配或 CPU 侧数据依赖不能假定在重放时继续发生。需要把允许变化的内容写入已约定的稳定缓冲，并使这些写入先于相应设备读取完成。完整图规则见 [CUDA Graph](cuda-graph-buffers.md)。

## 后端分派应先确定可行域，再比较完整成本

一次分派可以理解为从候选实现集合中先筛出满足当前调用契约的集合，再从其中选择合适的执行路径。前一层关注数学语义、表示、数值策略、平台和资源合法性；后一层关注当前形状、负载和生命周期下的成本。省去前一层会把“不支持”误当成“较慢”，省去后一层则容易选中需要昂贵适配的快内核。

库的总览、配置中的 backend 名称、实际执行的实现是三种不同信息。固定 SDPA 文档说明 fused backend 有输入限制，并提供限定实现的控制入口；固定 FlashInfer wrapper 在 plan 中根据条件解析 auto，随后保存选定 backend 和计划状态。因此，调查一次性能变化时，应把具体函数、版本、分派结果与实际设备工作对应起来，不能仅凭配置字符串推断路径。

fallback 的职责是覆盖允许的输入域，并保持用户要求的数学和状态语义。它可以是接受更一般 stride 的内核，也可以是显式转换后调用另一实现。若候选不支持窗口可见性，直接改成全 attention 会改变函数；若 FP16 路径失败后改用 FP32 中间结果，需说明数值与容量变化。某个库也可能选择报错而不自动回退，工程不能假设所有不支持组合都有备用实现。

这些分派条件宜沿真正会改变路径的维度描述：Q/KV 的几何、head 分组、stride 与对齐、mask/位置模式、存储和累加类型、设备能力、可用 workspace 与捕获模式。请求 ID 通常不影响内核合法性，但请求所引用的缓存布局和当前长度会影响。把这些条件与一次调用的实际值关联，才能判断缓存的分派决定是否仍适用。

## 预打包与转换的收益必须按复用次数计算

设通用路径每次成本为 T₀，专用内核每次成本为 T₁，专用表示的一次准备成本为 C。只有这份表示在 N 次调用中保持有效、且没有额外容量或同步代价时，总收益条件才是

\[
N(T_0-T_1)>C.
\]

假设 T₀=20 μs、T₁=12 μs、权重预打包 C=240 μs，则需要 N>30 才抵消准备成本。数值是设定算例，不是库性能。若 240 μs 是每次变化激活的转换成本，就没有这项跨调用摊销，每次专用路径变为 252 μs。权重更新、量化 scale 改变或布局消费规则变化，也会使原来的预打包表示失效。

真实调用还可能包含 metadata 准备、mask 打包、plan、传输、kernel、合并和输出路由。串行片段可以相加，重叠部分需要按依赖关键路径计算；共享带宽或资源争用又可能改变各片段时长。设备内核更快，并不自动降低从输入可用到输出可消费的完整时间。

## 用区分实验定位接口成本

可以先固定同一逻辑输入，分别观察三种路径：直接消费原布局的基线、预先准备好目标布局后的候选、包含真实转换与元数据更新的完整候选。第二种测候选内核的机会，第三种测引擎实际获得的收益。若只有第二种更快，瓶颈在适配边界；若第二种也慢，才继续调查内核资源与分派选择。

正确性输入应主动穿过接口边界：相同逻辑值的连续与合法非连续表示、只改变存储偏移的对齐变体、非整除尾维、不同合法归约长度、读共享与写独占的缓存、不同完成顺序。对不在支持域内的输入检查明确拒绝或合法 fallback，不能把崩溃、静默更换语义或偶然正确当作覆盖。

之后在完整模型层和真实请求路径中检查首次分歧、内存驻留、冷启动与稳态时间、输出完成和资源复用。固定源码中的断言和文档提供需要验证的边界；它们不代替目标设备上的结果。本文所有成本与数值示例均为解析推导，未进行 GPU 实测。
