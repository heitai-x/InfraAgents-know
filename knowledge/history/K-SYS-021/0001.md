# K-SYS-021：推理接口契约：外部服务、引擎推进与完成语义

推理 API 是组件之间对输入解释、状态变化、返回结果和责任边界的约定。字段或函数签名只描述可传递的形式；可替换的实现还必须在正确的时间产生相同含义的结果。本章围绕从零构建引擎时需要主动决定的契约，不规定一种通用接口名称，也不把任何具体引擎的内部 API 当作跨版本标准。

## 使用场景与先决信息

当外部接口已经能接收请求但内部执行尚未明确、调度器和模型执行器由不同工作项实现、同步引擎准备改为异步或多进程、执行后端替换，或者取消和流式返回出现歧义时，应先核对本章。输入包括目标协议的明确版本及支持子集、模型与前处理身份、请求状态模型、执行平台的完成与内存规则，以及允许的并发、错误和重试行为。

预期产物是一份能够指导实现和验收的边界说明：谁拥有哪份状态，调用何时被接受，哪些对象可以改变，返回是否表示完成，失败之后谁仍有责任，结果怎样归属原请求。它可以映射为工程中的具体类型与方法，但知识正文只保留语义与决策依据。

## 将三种接口分开解释

| 边界 | 输入的语义单位 | 输出或通知 | 不能暗中承担的额外含义 |
|---|---|---|---|
| 外部服务接口 | 一次用户请求、会话回合或媒体块 | 受协议约束的内容、状态和终止事件 | HTTP 响应开始不证明模型执行成功或客户端消费完成 |
| 请求引擎接口 | 已规范化且具有身份的任务，连同准入与取消意图 | 接收/拒绝、推进结果、请求终态和可查询状态 | 接收请求不等于已分配全部未来 KV，也不等于立刻开始计算 |
| 一次执行接口 | 一个固定批次视图、输入位置、状态句柄与执行条件 | 与该次视图对应的模型结果、状态进度及完成信息 | 提交返回不等于设备操作已完成，更不等于缓冲可回收 |

模型算子接口处于一次执行内部，还需要定义形状、布局、数值类型（dtype）、设备、可见性与误差。外部服务层不必理解每个物理页号，模型算子也不应自行猜测 HTTP 连接是否仍有效。需要跨层传播的是明确的身份、版本、取消与完成关系。[Orca](../sources/S-ORCA.md) 展示按迭代组织调度与执行的实例；这种职责关系并不要求所有系统采用相同进程布局。

## 在逐步推进和后台执行之间选择

一种候选是由请求引擎显式选择一次执行，等待或观察其结果，再决定下一轮；其状态更新点容易解释，适合作为受限初版或需要严格控制执行顺序的场景。代价是主机准备、设备执行与结果处理可能串行。另一种候选是请求进入后台执行域，由它持续调度并输出完成通知；这种方式可以重叠阶段，但需要有界入队、在途批次身份、关闭与排空契约。

两者都可以支持批处理。逐步推进接口并不意味着只能处理一个请求，后台接口也不自动提供连续批或更高吞吐。选择取决于实际主机间隙、可重叠的依赖、缓冲容量和错误处理成本。把同步函数改成返回一个等待对象，只改变调用形式；若所有工作仍串行且新增等待开销，性能不会自然改善。

对一次执行，至少确定输入视图在提交后是否不可变、输入是否被复制或借用、状态更新何时提交、结果存储位于哪个设备、消费者何时可读，以及最后一个使用者如何报告完成。PyTorch 固定 CUDA 文档明确区分操作入队和实际执行；不同执行流（stream）之间的依赖与缓冲生命周期也需要明确处理。因此接口可以在设备完成前返回，但必须使调用方知道仍有哪些对象不能复用。

## 身份、位置和版本共同决定结果归属

一次结果应能关联到稳定请求身份、请求内分支、逻辑输出位置、模型版本，以及产生它的执行尝试或批次。物理 slot 和 batch 行会重排，不适合作为长期身份。客户端可以提供业务 ID，但服务仍需明确其作用域、冲突行为和内部唯一身份；一个字符串相同，不足以证明两次调用应去重或共享状态。

输入长度、已计算长度、已采样长度与已提交长度分别描述不同进度。例如 prefill 覆盖位置 0 至 127 后采样得到一个新 token，此时输出序列可能已含 129 个 token，而该新 token 的 KV 尚待下一次计算。接口若只保留一个模糊的 length，调度、位置编码、缓存复用与统计可能各取不同含义。投机候选还需要区分暂定位置与已确认位置，详情见 [分支生成](../algorithms/branch-generation.md)。

| 版本对象 | 何时需要固定 | 改变之后首先检查什么 |
|---|---|---|
| 外部协议及支持子集 | 输入解析和响应解释时 | 默认参数、错误格式、流式事件和兼容性 |
| 模型函数制品 | 请求准入或明确的会话版本绑定时 | 权重、配置、processor、adapter、量化与输出质量 |
| 内部消息及状态表示 | 组件交接和在途执行创建时 | 字段含义、页表/布局、设备位置和读写所有权 |
| worker 或执行尝试代次 | 启动、重建或迁移时 | 迟到消息是否仍有提交权，旧缓冲是否确已结束使用 |

模型版本没有改变，不代表内部布局一定相容；外部字段没有改变，也不代表默认采样或错误行为没有改变。组件升级时至少需要一个明确兼容的组合。如果不支持混合版本运行，应在准入或部署时拒绝混合，而不是依赖未定义的字段解释继续执行。

## 将接收、完成、提交和释放分别表达

请求接收表示责任已经转移给引擎，或表示进入了一个已声明的有界等待域。一次执行完成表示相关计算达到某个可观察完成点。结果提交表示该结果被正式纳入请求输出；发送到协议服务器表示传输路径接管了一份输出。资源释放则要求该对象的全部有关使用者结束。这些事件可能相邻，也可能相隔很久。

一个设定的竞争轨迹可以说明差别：执行尝试 7 在 2 ms 提交，5 ms 收到取消，9 ms 设备工作完成。若取消契约只承诺撤销后续调度，5 ms 的取消确认不能宣布 2–9 ms 的在途访问已经停止。该次业务结果可以在完成后丢弃，相关内存仍应等待真实最后使用者。给 slot 增加代次能防止旧结果提交给新请求，却不能防止旧的直接内存搬运（DMA）写入一个过早复用的物理地址。

同样，5 ms 之前已经交给传输层的内容可能在取消后才被客户端看到。接口必须说明取消约束的提交边界；不能承诺撤回已经发送的字节。需要“停止意图已登记”和“所有相关资源已排空”两种完成含义时，应分别提供可观察状态。按所引用的 ASGI 规范，成功处理 http.response.body 的 send 返回时，本次 body 已交给服务器发送缓冲，但不提供远端应用已经消费的确认。http.response.start 没有同样的即时 flush 要求，服务器可以等到第一次 Response Body 再发送响应头。

## 错误要携带失败阶段和剩余责任

| 失败位置 | 可形成的契约结果 | 后续需要确定的责任 |
|---|---|---|
| 参数或版本验证失败，尚未接收 | 拒绝及明确原因 | 不产生执行任务；已接收的传输输入缓冲正常结束 |
| 准入不足或模型尚未就绪 | 拒绝，或进入有期限的等待域 | 是否可重试、是否保留身份与排队资源 |
| 已接收但未产生外部内容 | 请求失败或按约定内部重试 | 原执行是否仍在途，新尝试是否取得唯一提交权 |
| 已发送部分内容后失败 | 明确的流内错误/异常终止，或无法投递时记录断开 | 已交付内容不能撤销；客户端恢复能力取决于已承诺协议 |
| 一个执行批或 worker 出错 | 受影响范围内的结果失效或失败 | 哪些请求可独立恢复，哪些共享状态已不可信，执行域何时可复用 |

异常类型本身不证明重试安全。对于已产生外部内容的请求，简单重跑可能重复输出；对于随机采样、分支状态或多模态上下文，仅保存输入文本未必足以继续同一轨迹。若没有完整恢复契约，可以明确采用失败后重新发起新请求的语义，不能将它标成透明恢复。

内部错误也要保留根因和范围。把所有异常转换成空输出，会使客户端把失败当成合法短回答；把一个请求错误升级成无条件终止全部请求，又可能破坏隔离。应先判断故障是否污染共享状态，再依据已定义的请求、批次、worker 或执行组边界处理。[服务恢复](serving-recovery.md)进一步展开这种选择。

## 背压是接口的正常状态

入队接口需要说明容量使用什么单位，以及满载时是等待、拒绝还是形成可取消的未来接收。输出接口需要说明消费者可滞后多少、是否允许合并事件、哪个对象持有结果字节。暂停读取消息不等于底层模型已经暂停；暂停模型也不意味着 KV 能立即归还。

若采用输出额度，额度归还点必须对应一种明确资源：从引擎输出队列取走，可能足以归还引擎的队列槽，但未必释放协议服务器持有的另一份字节，更不表示客户端消费。各层可以拥有各自预算，并在上游准入或调度处汇合。只有这样，局部队列有界才有机会形成全路径有界。

取消、故障与完成通知还需有可达路径。如果它们与大量数据共用一个已满队列，生产者等待队列空位、消费者等待取消完成，可能形成互相等待。可选择独立控制容量、保留通知额度或不依赖数据队列的状态观察；具体机制由运行时决定，但必须用饱和情况下的轨迹验证，而不是只检查正常吞吐。

## 契约验证的三个层次

局部接口验证使用最小输入、边界输入和非法输入，检查默认值、身份、长度单位、返回含义与错误分类。为执行边界构造可控的延迟完成与重复通知，证明提交返回、结果可读和资源可重用没有被混为一谈。模拟完成仅验证消息与状态逻辑，真实设备的内存可见性仍需真实路径检查。

集成验证把外部适配、请求引擎和一次执行连接起来。对同一模型输入比较直达内部引擎与经外部接口的规范化结果；对重排、迟到、取消、队列饱和、请求 ID 冲突、版本切换与部分流错误检查逐实例归属。两条路径共用错误的前处理时可能一起通过，因此模型质量比较需要独立参考，不能只检查适配器与自身一致。

系统验证使用声明的真实到达、输入、消费速度和生命周期。分别记录进入服务、获得接收、开始计算、产生有效结果、外部提交、终止和清理。固定 GenAI-Perf 的指标表将 TTFT 描述为请求发出至首个 response；若当前任务要求“首个有效内容”，必须明确哪些事件计入，并核对实际解析与统计路径，不能仅凭字段名假设已经排除了空事件。

一个合格的接口交付应同时说明已实现的行为、明确拒绝的能力、超出范围的未知，以及能够复查的验证证据。schema 校验、通信连通和数值正确各自有用，但没有任何一个可以单独代替其他层次。
