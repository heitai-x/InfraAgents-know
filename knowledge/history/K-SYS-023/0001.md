# K-SYS-023：从知识到设计决定：场景、条件、产物与区分实验

知识在完整引擎构建中的作用，是帮助设计者从当前条件推出可实现的选择，并知道需要哪些观察才能保留或推翻这个选择。同一机制可以支持架构形成、组件实现、组合优化和失败诊断；使用场景由当前要作出的决定定义，不能仅用模型名或技术名替代。

## 两个正交的使用坐标

第一个坐标是工程问题：空工程需要形成什么架构，组件接口怎样实现，哪个瓶颈值得优化，现有失败由什么关系破坏引起。第二个坐标是部署条件：模型函数与状态、硬件和执行库版本、负载与服务目标。前者决定需要什么形式的解释，后者决定解释是否适用。

例如“多卡 MoE”是部署条件；“决定一次专家分派的参与 rank 与完成点”是工程问题。相同的 MoE 任务在模型接入、布局选择和通信诊断阶段需要读取不同部分；相同的完成点问题又可以出现在 KV 搬运、CPU–GPU 拷贝和网络响应中。按这两个坐标连接正文，能复用共同机制而不把不同接口的具体保证混为一谈。

## 先明确当前决定所依赖的输入

一个可推进的设计问题至少需要任务函数与不可改变的质量约束、真实硬件/库版本、负载条件、已有能力、当前观察和待解释的不确定性。条件尚未获得时，应保留未知及其影响，不以章节中的设定数字填补实际环境。

“降低延迟”缺少观察边界；“开放到达下首有效内容的尾延迟增加，模型执行时间近似不变，入口等待尚未记录”已经指明需要补充排队观察。此时读取调度、主机执行与指标事件的关系，能够形成区分实验。仅用“CUDA 优化”检索不能代替这个问题定义。

任务约束、推导前提和设计选择分开保存。最大执行批大小属于用户约束时必须遵守；连续批、分页和图重放通常是可选机制。已有 [迭代调度](../algorithms/iteration-batching.md) 与 [系统组合](design-synthesis.md) 说明这些选择如何改变工作组织，但不能把它们自动添加为每个新任务的功能要求。

## 七类决策时刻与对应产物

| 决策时刻 | 要建立的关系 | 知识使用后应形成的产物 | 下一层证据 |
|---|---|---|---|
| 空工程启动 | 任务函数、持久状态、资源与对外服务之间的连接 | 必要能力、组件责任、接口与可交付阶段；未定问题另列 | 固定输入的真实执行与完整请求路径 |
| 组件实现 | 数学对象如何映射到 shape、布局、dtype、状态和执行 API | 可实现的组件契约、允许变化和参考关系 | 局部数值/状态检查与真实相邻组件集成 |
| 在线服务形成 | 到达、请求身份、状态驻留、推进与终止的关系 | 调度与准入选择、状态所有权、取消和回收约定 | 请求重叠、长短混合、多轮、背压和取消场景 |
| 性能方向选择 | 资源成本、关键路径和端到端目标之间的联系 | 竞争解释、候选改动、预期信号与最低区分实验 | 合格候选在相同负载下的系统测量 |
| 跨组件组合 | 共享对象上的前提是否仍同时成立 | 受影响接口、共同不变量、实施依赖和回归边界 | 专门触发交互的状态轨迹与完整系统检查 |
| 故障诊断 | 最早偏离来自函数、实现、环境还是测量 | 可复现反例、候选原因、最小修复与回归范围 | 原反例及受影响真实路径重新执行 |
| 新条件迁移 | 原结论的哪些前提随模型、硬件或负载改变 | 可继承关系、待重测成本与需要重新选择的部分 | 新条件中的独立参考、资源观察和保留验证 |

这是一组问题入口，不是强制角色每轮依次执行的固定流程。任务已经具有合格实现时可以直接研究瓶颈；缺少函数或状态语义时，先做性能实验通常无法解释结果。新增或修订知识的条件见 [认识与独立检查](evidence-and-independent-checks.md)。

## 把阅读转化为一项可检查的设计决定

阅读一个相关章节后，设计者需要说明当前对象与章节对象怎样对应、哪些前提已有证据、哪些仍未知，并给出选择造成的具体改变。例如“采用前缀复用”需要明确共享身份、可恢复位置、私有尾部与回收条件；它还应预测省掉哪些 prefill，而不是承诺全部 attention 流量同比下降。

对有实际分支的决定，保留一个满足约束的替代方案，并写出使选择反转的条件。无替代方案的数学必需关系不强行凑两个候选。选择来自事实约束、推导和待检验假设的组合，三者各自可追溯；源论文中的成功实例只能帮助提出候选。

工程产物保存在当前工程：组件边界、接口责任、设计变更和实验方案。知识正文解释这些产物应该满足什么关系，不嵌入可以直接套用的完整引擎骨架。源码位置和当前已实现状态属于项目事实；章节中的机制不能替代对实际实现的检查。

## 组合成本的算例：便宜的 kernel 为什么可能使服务变慢

以下是设定数字的代数推导，不是硬件实测。假设一个关键路径段中，原 kernel 用时 1.0 ms，输入已经满足其布局；新 kernel 的计算用时为 0.6 ms，但每次需要 0.5 ms 的布局转换。若转换与计算有依赖且不能被其他独立工作隐藏，新路径至少为 1.1 ms，计算部分加速不支持该段变快。

若布局转换后的同一份不可变数据可以合法复用 R 次，旧路径成本为 R×1.0 ms，新路径为 0.5+R×0.6 ms。新路径更优要求 R>1.25；整数次数至少为 2。这个条件只涉及所列成本。复用需要数据版本和消费者解释不变；持久副本增加的容量、缓存失效、并发争用和额外同步还要进入系统预算。

该决定需要两个不同实验：固定合法输入检验新旧结果在任务质量规则下的关系；记录真实转换次数、kernel 路径和关键路径，检验 R 是否真的大于 1。若只测已转换输入的微基准，就没有检验实际调用链。更完整的接口与隐式转换分析见 [张量接口与 dispatch](../frameworks/tensor-abi-dispatch.md)。

## 用能区分解释的实验推进下一步

假设前缀复用后首内容变快，至少有三种解释：少算了历史输入、队列条件不同、比较时预热状态不同。固定到达轨迹和缓存初态，比较有效 prefill token、实际执行区间、排队时间与端到端事件，能够分别检查这些解释。缓存命中率自身既不证明少算，也不证明用户延迟改善。

一个实验要写清观察对象、干预、保持相同的条件、预期变化和反例。能够否定候选的结果应在运行前说明，例如转换次数没有减少、隐藏传输的计算窗口不足、服务尾延迟越界。结果仍不足区分时，应记录未决，而非把没有失败当作支持。

从空工程推进时，早期实验可以证明必要能力已经形成；只有完整任务的质量、服务与资源要求全部满足，才支持交付。某个局部阶段达到相对自有基线的改善，不会使未覆盖的任务要求自动完成。[引擎构建](engine-construction.md) 进一步展开能力依赖与阶段交接。

## 四层验证回答四种不同问题

| 层次 | 验证对象 | 能支持的结论 | 仍不能推出 |
|---|---|---|---|
| 局部语义 | 数值函数、索引、布局、状态转换 | 已检查的输入、性质及证据范围内满足组件契约 | 调度、异步或服务组合正确 |
| 集成交互 | 真实相邻组件与共同状态 | 指定交互路径及不变量成立 | 所有负载和失败时序都覆盖 |
| 完整系统 | 正常执行路径、真实负载、质量/协议/资源 | 目标运行点下任务要求得到检验 | 新硬件或新负载自动继承性能 |
| 知识迁移 | 不同任务中同一机制版本的使用 | 条件范围内具有复用支持 | 被读取的所有知识都造成收益 |

各层使用独立程度适当的参考，并将数值、模型质量和协议语义分别处理。PyTorch 固定数值文档说明改变批量组织或归约路径可能改变舍入结果；因此变形测试应遵循任务原定的数值/输出标准，不能看到差异后临时放宽标准。若任务明确要求精确 greedy 输出，就须继续证明该要求，不能以一般浮点误差解释替代验收。

## 条件变化后怎样复用这次决定

把结论写成“在这些前提和观测下选择此方案”，并保留反转条件。更换 API 或后端版本后，先核对输入输出、默认数值策略、工作区、异步完成与 fallback 语义；更换硬件后，容量关系可以重算，但有效带宽与重叠比例必须重新观察；改变负载后，需要重建复用距离、batch 与排队条件。

本章提出的是知识应用与设计验证的方法，不声称现有 Agent 已自动完成这些工作。检索到、读过、声明采用与产生作用分别记录。验证知识的作用需要固定任务、模型和预算，比较不同知识条件的完整交付结果及成本；统计边界见 [性能实验](../tools/statistical-experiments.md)。
