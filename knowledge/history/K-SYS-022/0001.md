# K-SYS-022：分布式执行契约：张量解释、通信提交与共同完成

从单设备引擎扩展到张量并行、流水并行或专家并行时，数学分解必须落实为各参与者都能执行的边界。多卡均有进程、通信 API 返回成功，尚不能说明各 rank 计算的是同一批请求、交换的是同一个张量，或得到了可共同提交的结果。本章将这些设计判断连接到可检查的张量、状态与完成关系。

## 什么时候需要这份契约

适用于引入新的并行轴、替换 collective、融合通信与计算、接入新的传输后端，以及动态 batch、取消或 MoE 路由改变通信形状的阶段。输入需要明确：模型函数和数值要求，rank 到设备及拓扑的映射，逐 rank 权重/激活/状态布局，当前请求顺序，固定库版本，以及可用设备与缓冲预算。

在实现前，规划应给出每个通信边界的数学作用与两个以上适用候选。例如，输入轴分片的线性层需要合并部分和；可以使结果复制在所有 rank，也可以保留分片供下一层使用。选择依赖下一消费者要求及容量，不应先固定一种 collective，再让模型布局迁就错误的结果解释。

可交付产物是一张随源码与实验版本绑定的边界表：谁提供哪些元素、接收后由谁解释哪些元素、操作属于哪次逻辑推进、哪些完成事件允许下一步执行，以及失败时哪些结果不得提交。

## 一个张量边界同时约定值、布局和身份

| 边界要素 | 必须明确的内容 | 漏掉后可能出现的问题 |
|---|---|---|
| 数学对象 | 张量轴的含义、局部与全局形状、分片轴、有效元素与 padding | count 相同但把不同通道或 token 相加 |
| 物理表示 | dtype、元素字节、连续性或打包方式、偏移、对齐、允许的别名和 workspace | 字节够大但数据解释错误；转换抵消收益 |
| 参与者 | communicator 身份、rank 顺序、rank 到设备/分片的映射、root 或 peer | root 被误当设备号；gather 后顺序错误 |
| 逻辑身份 | 请求/微批顺序、模型版本、层、迭代、通信阶段、执行代次 | 不同请求或不同层的合法形状被错误匹配 |
| 生命周期 | 生产完成、通信可提交、通信完成、消费者完成、槽位回收 | 跨 stream 提前读；取消后覆盖仍在传输的缓冲 |
| 失败含义 | 未提交、部分提交、异步失败、共同终止及恢复点 | 幸存 rank 将局部成功误认为全组成功 |

NCCL collective 按固定接口解释数量与 dtype，不负责为应用推断张量轴、请求身份或 stride。若上游是非连续视图，应明确后端是否直接支持，还是先打包成满足契约的表示；打包与解包的成本和缓存生存期都属于候选。别名与原位使用也需要具体 API 的固定版本依据，不能由“发送接收地址相同”自行推断合法。

## 从 collective 语义推导每个 rank 的容量

固定 NCCL 2.25.1 的 Collective Operations 要求各 rank 形成匹配操作，数量与 dtype 一致；不匹配可能挂起、崩溃或破坏数据。下表以参与者数 \(p\)、每个元素 \(b\) 字节、语义中的块长 \(N\) 为符号，列出分离输入/输出时的主缓冲需求，不把库内部暂存包括在内。

| 操作 | 每 rank 输入/输出的语义 | 容量与布局含义 |
|---|---|---|
| AllReduce | 每 rank 输入 \(N\) 个值，每 rank 得到同一归约结果 \(N\) 个值 | 输入与输出各 \(Nb\) 字节；同一位置必须具有相同全局含义 |
| AllGather | 每 rank 提供 \(N\) 个值，每 rank 接收 \(pN\) 个值 | 输出 \(pNb\) 字节，块按 communicator rank 顺序排列 |
| ReduceScatter | 每 rank 提供可划成 \(p\) 个等长块的 \(pN\) 个值，归约后各 rank 获得一个 \(N\) 元素块 | 输入 \(pNb\)、输出 \(Nb\) 字节；rank 决定取得哪一块 |
| Reduce | 各 rank 提供同一逻辑位置的值，仅 root 获得归约输出 | root 是 communicator 中的 rank，不能直接用设备编号替代 |
| Broadcast | root 的 \(N\) 元素内容分发给参与者 | 要同时约定 root、内容版本与接收后的解释 |

这里的 \(N\) 定义是解释操作的数学记法，实际 API 中 count 或 sendcount/recvcount 的选择仍需按目标函数合同核对。尤其不能把 AllGather 的总接收元素数传成每 rank 提供的数量，或在 ReduceScatter 中按总输入长度给每 rank 分配输出。字节数由元素数量乘 dtype 大小得到，字节和元素不能混用。

设四个 rank 各提供 8 个整数，rank \(r\) 的第 \(i\) 项为 \(100r+i\)，其中 \(r=0,1,2,3\)，\(i=0,\ldots,7\)。AllReduce 求和后每个 rank 应得到第 \(i\) 项 \(600+4i\)；AllGather 应按 rank 顺序保存四个完整块。若检查 ReduceScatter，可令各 rank 输入 32 项并采用同一生成关系，归约后 rank \(r\) 应得到索引 \(8r\) 到 \(8r+7\) 对应的八项。这是精确小整数的验证构造，不是随机浮点误差的替代，也不是模型质量评测。

全一输入会掩盖 rank 重排和部分重复，因此单次全一归约通过不足以确认布局。换一个合法的 rank 到设备映射后，数学对象可以不变，但 AllGather/ReduceScatter 的 rank 顺序仍要由解释层正确还原。

## TP、PP 与 EP 需要不同的应用层对象

TP 是张量并行。输入轴分片产生的部分和只有在 token、输出通道、层和执行代次一致时才能相加。若从 AllReduce 改为 ReduceScatter，下一消费者也必须接受相应分片；随后无条件 AllGather 回来可能抵消原本收益。归约次序变化还要遵守任务数值要求，不能把实数等式直接当作逐位一致的浮点承诺。

PP 是流水并行。阶段间传输的是指定微批的激活及解释它所需的长度、位置、请求映射等信息。发送方需要保留源，接收方需要预留目的；微批取消不能让接收方把迟到数据接给下一个同形状微批。阶段划分必须保留完整模型依赖，自回归下一 token 仍可能等待上一 token 完整经过所有阶段。

EP 是专家并行。需要建立从原 token 到专家分派项，再回到原 token 的逆映射。对每对源与目的，以 \(n_{ab}\) 表示从 rank \(a\) 发给 rank \(b\) 的有效分派项数量；数据形状与双方认可的计数相符，零项与不均匀项也有明确处理。一个 token 的多个专家结果按模型的 gating 规则合并，通信层不能自行丢弃慢专家或重复合并。

这里给出的是应用协议要求，并未声称已有集合操作自动提供可变长 all-to-all，或所有后端的点对点函数采用同一参数约定。采用按 peer 分组、填充到统一容量或其他交换方案时，应分别说明 metadata、padding、真实有效项与所选 API 的匹配关系。

## 提交、设备完成与应用提交是三道边界

NCCL Group Calls 区分组内调用返回与组结束。组内单个通信调用返回时，操作可能尚未排入 stream；相关 CUDA 完成检查必须位于合法的组提交边界之后。更具体地，对 nonblocking communicator，`ncclGroupEnd` 返回 `ncclInProgress` 表示 kernel 仍可能在后台提交。应按固定接口确认相关 communicator 的状态进入成功，再使用依赖这些提交的 CUDA 操作；成功提交仍不表示通信设备工作已经结束。

通信设备完成之后，后续计算还需位于正确的消费依赖中。同一 stream 的顺序可以提供一种安排，独立计算 stream 则需要相应等待。结果经过模型语义与当前请求代次的解释后，才能成为应用可提交的输出或 KV 状态。一个 rank 观察到自身 stream 完成，不自动证明其他 rank 的状态均可共同恢复。

若绕过 NCCL 使用 verbs 或自定义 GPUDirect RDMA 路径，应单独证明内存注册、工作请求、完成记录与 GPU 可见性。固定 rdma-core v54.0 对一般发送缓冲要求工作完成后再复用，inline 发送有特定例外；CUDA 12.8 GPUDirect §2.7 则说明第三方 DMA 完成不能直接替代依赖 GPU 工作所需的排序。两者属于不同边界，不能用一个主机“发送成功”标志概括。此处不将该固定路径的保证扩张到所有设备和未来版本。

## 成本模型要从实际不能隐藏的路径计算

对一个明确选择的理想 ring AllReduce，令每 rank 输入大小为 \(A\) 字节、参与者为 \(p\)、每轮启动成本为 \(\alpha\)、单向有效链路带宽为 \(B\)。假设链路支持全双工，发送与接收可以并发，且 \(B\) 是其中单向的有效带宽。在均匀分块、稳定带宽、无额外争用的简化模型下，reduce-scatter 与 all-gather 共 \(2(p-1)\) 轮，每 rank 的发送流量为 \(2(p-1)A/p\)，因此

\[
T_{\mathrm{ring}}\approx 2(p-1)\alpha+\frac{2(p-1)A}{pB}.
\]

这是应用可用于比较的算法推导，不声明 NCCL 一定选用 ring，也不是任何设备的实测公式。接收流量是另一计量边界，不能把它再乘进已经按链路传输定义的时间项。树形、分层、不同协议与拥塞需要另外的模型或测量。

设 \(p=4\)、\(\alpha=5\) 微秒、\(B=40\) GiB/s。\(A=16\) MiB 时，上式约为 0.61594 ms；\(A=8\) KiB 时约为 30.286 微秒，主要是设定的启动项。以上全是设定算例。它解释为何小 batch decode 即使通信字节少，也需要研究调用次数与依赖长度；也解释为何大 prefill 需要检查实际流量与带宽。

聚合多个通信可减少某些启动成本，但只有不违反计算依赖、且等待聚合不显著延迟关键消费者时才可能获益。通信与计算在时间线上重叠也可能争用 HBM、SM 或同一链路。应比较完整层或完整推进的完成时间，并把 packing、workspace、慢 rank 和下一消费者等待计入，而不是从孤立通信时间中扣掉任意计算时间。

## 从小对象检查到完整引擎验收

局部检查先用独立数学关系核对分片、打包、rank 次序和 collective 的值，涵盖非整除维度、padding、空分派、热点路由及重复地址的新代次。静态边界检查应在提交前拒绝不匹配的形状或操作计划；实际故障注入应在有界的隔离执行组中进行，避免把未完成的通信误记为通过。

集成检查覆盖一层或一个阶段的真实生产—通信—消费路径，包括输入准备延迟、不同 stream、group/nonblocking 提交、某 rank 取消或退出。记录各 rank 的逻辑操作序号、最早错误与最后共同提交点，检查所有参与者最终进入一致的失败或完成状态。对不确定的部分结果，应禁止发布并重建执行组；超时只是一种观测，不是顺序错误、网络慢或对端失败的共同根因标签。

系统检查使用相同模型、输入轨迹、质量要求和资源预算，比较并行布局及通信候选的合格吞吐、TTFT、ITL、尾延迟和各 rank 的资源峰值。报告哪些算子变化引起数值差异，哪些成本来自启动、数据流量、packing 或慢端；单独的通信 microbenchmark 只能支持它所测的消息大小与拓扑。

只有在模型输出、请求身份、共同提交和资源回收都保持成立时，端到端收益才支持该并行设计。一次任务可以沉淀适用范围与反例，但不能据此得出“更多并行度总是更快”或“某个 collective 对所有模型最优”的结论。
