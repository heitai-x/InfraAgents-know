# K-HW-015：CPU–GPU 重叠执行：完成依赖、缓冲预算与关键路径

当完整引擎已经能正确执行，但设备之间的等待占据明显时间，或者准备引入输入预取、CPU 计算、KV 搬运与 GPU 计算重叠时，需要先构造执行依赖与资源模型。异步提交提供了安排工作的机会；是否有可重叠的独立工作、是否有足够缓冲、是否争用同一带宽，决定这个机会能否转化为服务收益。

## 使用前先还原一份工作经过哪些对象

输入应包含当前请求或微批的真实形状与字节、模型语义、主机准备步骤、主机与设备的物理驻留、允许复用的后端，以及观测到的提交、完成和用户交付时间。模型、权重、tokenizer、processor 与缓存配置的版本应固定；不同输入处理不能因传输更快而被当作相同任务。

将一次推进拆成有明确输出的对象关系：CPU 准备输入，主机输入成为传输源，设备输入被模型消费，设备输出成为传输源，CPU 输出才被解析或发给客户端。若 CPU 还计算某层的分片，必须再连接输入到达、CPU 分片、GPU 分片与结果合并。两条分支只有在模型函数上独立时才可并发，后一层依赖当前层输出时不能越过合并点。

这一阅读场景的工程产物是一份执行关系说明：每个对象的大小与所有者、生产者与最后消费者、可开始事件、允许复用事件、候选并发安排，以及需要测量的未知量。它应足以让实现者安排队列与缓冲，并让实验者判断某段空洞是数据未就绪、资源未可用，还是提交不及时。

## 同一条数据至少有四种不同的完成含义

| 边界 | 已经成立的事实 | 尚不能推出的事实 |
|---|---|---|
| 主机 API 返回 | 主机已经完成该 API 在此版本、参数和内存类型下承诺的动作 | 异步设备工作已结束；另一 stream 已可消费 |
| 设备生产完成 | 生产者在其执行依赖中完成写入 | 无依赖的消费者已经等待；所有后续读者已结束 |
| 消费者获得可用数据 | 数据生产与该消费者之间存在足够的顺序和可见性保证 | 输入缓冲可以覆盖；其他消费者也已结束 |
| 最后使用完成 | 该代次的所有已登记访问结束 | 同地址属于新对象后，旧完成记录还能用于新对象 |

CUDA 12.8 的同一 stream 按提交顺序执行，跨 stream 可以交错，是否真正并发并无保证。`cudaStreamWaitEvent` 建立设备侧的等待关系；`cudaStreamSynchronize` 等待一个 stream 的先前工作；`cudaDeviceSynchronize` 的等待范围更大。这些选择改变等待边界和性能，不能为了让错误消失而把全局同步永久加到每次 token 推进中，再仍宣称实现了重叠。

在固定 PyTorch CUDA 来源中，`wait_stream` 处理生产与消费的顺序，`record_stream` 向缓存分配器说明张量仍在另一个 stream 使用。后者解决存活期，并不独自使数据生产完成；前者也不自动登记全部未来消费者。引擎必须同时证明数据何时可用与内存何时可回收。CUDA stream-ordered allocator 同样要求跨 stream 使用发生在分配之后、释放之前，返回了指针不等于任意 stream 可以立即访问。

## 可重叠的条件需要按实际平台核对

H2D 表示主机到设备，D2H 表示设备到主机。对本章采用的 CUDA 12.8 路径，主机锁页内存、设备复制引擎能力、独立 stream 和依赖关系共同影响复制与 kernel 的重叠。`asyncEngineCount` 提供设备能力信息；仅存在这一能力并不保证当前工作负载实现了相应带宽或并发度。pageable 内存可能引入 staging 或同步，临时锁页也有成本，不能只在函数名中出现 Async 就按理想异步路径建模。

默认 stream 还需分清 legacy NULL stream 与每线程默认 stream。前者与相关 blocking stream 可能引入隐式同步；每线程默认 stream 是普通 stream，非阻塞 stream 也有自己的条件。固定 Best Practices 文档中的简化默认流说明，应结合同版本 Programming Guide §3.2.8.5.2–5.4 阅读，不能扩张成“任何默认流都会同步全设备”。

如果模型使用统一内存或映射主机内存，应重新描述实际驻留与访问路径。省去显式复制可能转化为 GPU 远端读取或缺页迁移；数据共享仍需正确的完成与可见性关系。CPU 分片与 H2D 又可能竞争同一 DRAM 通道，两个 stream 或线程不代表两份独立带宽。

## 从理想流水周期推导缓冲数量

设固定形状的一批输入顺序经过准备、H2D、GPU 计算与 D2H，阶段时间分别为 \(t_p,t_h,t_g,t_d\)，单位一致。若四阶段使用独立资源、不同批可并发、具有足够缓冲，且不存在跨批额外依赖，那么理想稳态周期为

\[
P_0=\max(t_p,t_h,t_g,t_d).
\]

在这些确定性假设下，完成 \(N\) 批的流水时间为

\[
T_N=t_p+t_h+t_g+t_d+(N-1)P_0.
\]

第一批延迟仍包含四阶段之和。有限请求、逐 token 反馈、不同长度、排队和共享资源都会改变这个模型，因此它是设计下界与可区分预测，不是可直接承诺的服务延迟。

对缓冲池 \(j\)，设一个槽从被占用到最后消费者完成的固定时间为 \(L_j\)，每隔 \(P\) 启动一批，且槽位可在完成边界立即复用。至少需要

\[
n_j\geq\left\lceil L_j/P\right\rceil.
\]

这条关系解释双缓冲何时足够，也解释为什么三段流水不必机械配置三个完全相同的缓冲。主机输入、设备输入与设备输出有不同生存期，应分别估计。若长度或完成时间变化，应按真实完成门限制复用；用平均 \(L_j\) 估算容量不能保证长尾情况下安全。

进一步设资源 \(r\) 每批承担 \(Q_r\) 字节，当前并发条件下可持续带宽为 \(B_r\)，则周期还满足 \(P\geq Q_r/B_r\)。多个传输共用一个链路或 DRAM 时，应先合计该资源承担的流量；这些下界与阶段、槽位约束一起考虑，不能把各自孤立测得的峰值同时分配给所有阶段。

## 设定算例：增加槽位何时有效

设准备为 3 ms、H2D 为 2 ms、GPU 计算为 8 ms、D2H 为 1 ms；这些是解释公式的设定值，不是硬件实测。八批串行为 112 ms，理想流水为 \(14+7\times8=70\) ms，第一批仍为 14 ms。

设备输入从 H2D 开始到 GPU 读完至少占用 10 ms，按 8 ms 周期需两个槽；若设备输出从 kernel 开始就保留，直到 D2H 完成占用 9 ms，也需两个槽。设每批设备输入 16 MiB、输出 1 MiB，则这两个池共需 \(2\times16+2\times1=34\) MiB，另计模型状态、workspace、主机池和其他并发工作。多配到八个槽不会把 8 ms 的计算阶段缩短。

现在假设 CPU 分片和 DMA 在同一 DRAM 资源上每批累计搬运 128 MiB，而此并发条件下可持续带宽只有 8 GiB/s，则该资源给出的周期下界为 15.625 ms，已超过 8 ms。此时继续增加槽位更可能增加驻留与等待，应比较减少数据流量、改变计算放置或改善亲和性的方案。具体流量和带宽必须在目标环境测量，不能把此设定反写成平台规格。

NUMA 是非均匀内存访问结构，CPU 访问不同内存节点具有不同路径和竞争关系。需要同时记录工作线程、主机页、GPU 及 NIC 的拓扑位置；固定 Linux v6.12 的 `cpuset.cpus.effective` 和 `cpuset.mems.effective` 表示实际获准资源，可能不同于请求配置。仅绑定 CPU 线程不能证明已分配页面位于目标节点；更改内存节点策略也可能触发有成本且不完整的迁移。

## 用可区分实验选择同步、重叠或减少搬运

保留一个相同模型函数与负载下的串行参考，再比较有界槽位的重叠候选，以及减少搬运的候选。减少搬运可能来自持久设备状态、合并 metadata 或改变 CPU/GPU 计算放置，具体适用性由该任务的语义决定。三者可以有不同资源峰值，应共同报告。

局部检查在每个对象的生产与消费边界对照数据、形状与版本，覆盖尾批、不同大小、重复槽位、乱序完成和取消。可用不同请求和代次的可辨识内容构造反例，不能让所有批输入相同而掩盖过早覆盖。

集成检查连接真实准备、复制、kernel 与结果消费，确认既没有在生产前读取，也没有在最后消费者之前复用。分别延迟 CPU 准备、H2D 或 GPU 消费，检查有界队列和背压传播；减少为单槽位应表现为等待增加，仍须保持正确。取消只终止业务需求，不意味着已经提交的设备访问已完成。

系统检查使用完整目标负载，报告完成吞吐、首个结果和尾延迟、CPU 利用与资源限制、主机/锁页/设备峰值、实际传输字节，以及各阶段就绪到开始的等待。有限任务集的完成时间须包含管线排空，不能以主机提交结束为完成。稳态吞吐可以另设明确的稳态窗口，但需记录窗口两端的在途工作、完成计数口径及窗口后仍未结束任务的结果，不能借窗口截断隐藏积压或失败。诊断时的同步和 profiler 扰动应与正常 benchmark 区分。

若时间线显示复制与计算重叠，但端到端延迟或合格吞吐未改善，应检查它是否增加了共享带宽竞争、排队、取消尾部或状态容量压力。支持“重叠确实缩短关键路径”的证据，需要同时保留完成关系、资源账与用户指标，而不是只展示重叠的彩色区间。
