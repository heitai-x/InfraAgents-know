# K-HW-003：主机准备、DMA 与流水缓冲

输入流水的吞吐取决于准备、传输和计算阶段的平衡；数据可见性和缓冲所有权决定能否正确重叠。异步接口主要改变提交与完成的关系，并不自动减少字节、建立跨 stream 依赖或增加复制引擎。设计输入路径时，需要同时回答：传什么内容、驻留在哪里、谁仍在访问，以及哪个完成事件允许下一次读写。

本章输入是一组有限或受准入限制的载荷，每项携带请求身份、内容版本、有效范围、shape、布局和 dtype；输出是相应计算结果、明确失败或取消状态，以及可核对的资源归还记录。处理器配置也是内容身份的一部分：同一图片采用不同 resize、归一化或抽帧配置，即使最终形状相同，也不是可随意互换的输入。路径选择要解释哪些对象保持驻留、哪些经过 staging、何时可消费与复用；未知时间和带宽可以先作为设定量，再用目标环境观察修正。

## 准备不是一次复制

文本服务包含解析和 tokenization，多模态还包含媒体解码、采样、resize 和特征整理。原始载荷 A 经 CPU 准备成为连续主机输入 H；pageable 输出若要转入显式 pinned staging S，还多一次主机复制。随后 H 或 S 经 H2D 到设备输入 D，kernel 读取 D、写设备输出 O，D2H 再将 O 写入主机结果 R。CPU 消费 R 也有独立的结束时刻。

这里 DMA 指由相应传输硬件执行内存搬运；CPU 仍需准备地址、字节范围、依赖与提交描述。主机调用返回说明提交路径取得进展，不能单独证明源已读完、目的已写全或消费者已经结束。所有范围采用半开字节区间 [a,a+b)，b 为有效字节数；容量、实际搬运量和逻辑载荷大小分别记账。

| 对象 | 典型状态路径 | 最早允许覆盖的证据 |
|---|---|---|
| H 或 S | FREE → PREPARING → READY → H2D_SOURCE → FREE | 主机准备已结束，且全部 DMA 源读取结束 |
| D | FREE → H2D_TARGET → READY → KERNEL_INPUT → FREE | H2D 写入及全部 kernel 读取结束 |
| O | FREE → KERNEL_OUTPUT → READY → D2H_SOURCE → FREE | kernel 写入及全部 D2H/其他读取结束 |
| R | FREE → D2H_TARGET → READY → CPU_INPUT → FREE | D2H 写入及全部 CPU/发送消费者结束 |

一个对象还需要区别“生产完成，等待下游取得读取权”和“已经没有人使用”。READY 对象即使暂时没有在途读者，也不能立即回收，否则消费者还未启动，内容已被覆盖。后文用 hold 表达这项待消费保留，用 writer 和具名 readers 表达已经启动的物理访问。

pageable 主存路径可能经过额外 staging 或主机等待，具体行为随 API、方向和运行时路径而变。固定 CUDA 最佳实践文档的异步重叠方案使用 pinned 主存；本章的显式异步算法也采用可复用的 pinned 传输池，不依赖未确认的 pageable 行为。pinned memory 使页面在相关生命周期内保持锁定，但不意味着整个虚拟区间物理连续，也不免除范围与平台条件检查。

已有范围可通过注册建立锁页条件，或直接分配 pinned 缓冲。注册避免另分配再复制，却有建立、页面处理和撤销成本。PyTorch 固定文档中的 pin_memory 返回锁页副本，不能把它当成原地址零成本改变属性。若原始 A、准备后的 pageable H 和 pinned S 同时存活，三者都进入主存峰值；锁页不能无限使用，其压力还会影响其他系统工作。

## 依赖、stream 与硬件能力

合法性先于性能选择。目的范围必须足以容纳所需表示，源与目的的地址类别和复制方向应合法；非连续对象必须按消费者布局显式 packing 或采用被接口支持的分段路径。只写完部分范围，不能把未写区域中的旧字节发布为新 tensor。别名范围若发生读写或写写冲突，也要统一保护，不能因为对象名称不同就视为独立。

一批内部必须保持 H/S 写完 → H2D 写完 D → kernel 写完 O → D2H 写完 R → CPU 消费的依赖。复制与 kernel 在同一 stream 时，队列顺序可以提供相应设备依赖；位于不同 stream 时，应在最后生产写入之后记录事件，让消费 stream 等待。主机读取 R 还需取得对应完成证据。事件位置错误，例如记录在最后一个分段复制之前，会留下未覆盖范围。

能够重叠的是不同批或不同独立块的工作。同一批的 H2D 尚未完成时，其 kernel 不能为了重叠提前读取所需区域。跨 stream 建立正确依赖，也不保证硬件一定并发执行。

固定 CUDA 最佳实践文档描述了 legacy 默认 stream 的串行化行为和不同非默认 stream 的重叠方案。不能将该行为无条件推广为所有默认 stream 模式；per-thread default stream、非阻塞 stream 及框架内部 stream 应按实际执行契约核对。即使没有跨 stream 的隐式串行化，同一个 stream 内仍按其队列顺序执行。

还要区分软件队列与硬件资源。固定文档以 asyncEngineCount 等属性说明复制与计算能力：单复制引擎模型一次服务一个复制方向，但可能与 kernel 并行；双复制引擎模型可允许一个 H2D、一个 D2H 与 kernel 同时运行。创建更多 stream 不会增加复制引擎。实际设备不能仅凭属性数值就保证达到孤立复制带宽，还需核对方向、拓扑、内存竞争和实际时间线。

执行顺序与地址生存期是两条约束。跨 stream 等待生产完成后，还需防止 allocator 在最后消费者结束前回收地址。stream-ordered allocator 将分配、使用和释放置于相容的执行顺序；释放请求返回不是任意 stream 可立即重用地址的证据。CUDA Graph 重放固定地址也不固定其中的内容：下一批填充、并发重放与输出保存仍需要对象级保护。

## 流水周期与有限批完成

设固定形状的一批依次经过准备、H2D、GPU 计算和 D2H，服务时间为 t_p、t_h、t_g、t_d，单位均为时间/批。假定每阶段有自己的串行服务资源，各批独立、缓冲充足、没有反馈或额外同步，理想稳态周期为

P₀ = max(t_p,t_h,t_g,t_d)。

不返回主机时可以令 t_d=0。在上述确定性条件下，N≥1 批的理想完成时间为

T_N = t_p+t_h+t_g+t_d+(N−1)P₀；T_0=0。

可用逐阶段递推验证：第 i 批在阶段 s 的开始，取该批上一阶段完成与上一批本阶段完成的较晚者，再加本阶段服务时间。固定等长阶段的递推给出首批依赖链之和，以及后续每批一个最慢阶段周期。该式包含填充与排空；“全部复制已提交”不能作为结束条件。所有阶段时间均为零时只是抽象模型退化，不能据此宣称无限硬件吞吐。

若 H2D、D2H 共用一个复制引擎，每批对它的服务需求为 t_h+t_d，因此周期至少满足

P ≥ max(t_p,t_g,t_h+t_d)。

这是资源下界，未证明某种有限缓冲与命令排序能达到它。对 N≥1，若首个复制不早于首批准备结束，该复制引擎的总工作还给出 T_N ≥ t_p+N(t_h+t_d)。精确完成时间要把两种复制放在同一个资源日历上，并保留 H2D → kernel → D2H 的依赖；不能分别计算两个日历后直接合并。

逐 token 反馈又不同。若下一输入依赖刚生成的 token，必要的结果交付、CPU 处理与再次提交仍处于同一请求的依赖链，多个独立请求的聚合流水周期不能直接充当单请求 ITL。CPU 结果处理若占用与准备相同的线程，也应合并该线程每批的服务需求，或显式说明独立执行资源。

## 缓冲池的槽位与代次

每个物理槽记录 pool、slot、gen、owner、容量、有效范围、phase、hold、writer 和 readers。owner 是请求身份，gen 在重新取得槽时增加；每次操作另有不复用的 uid。writer 至多一个，readers 是具名责任集合，而非只计总数。完成记录包含 uid、请求、各端点代次、实际完成范围、状态和访问是否确实结束的证据。

回收条件是 hold=false、writer 为空且 readers 为空。READY 的 hold 防止“尚无在途读者”被误解为“可回收”。提交时，应先原子登记源读责任和目的写责任，再将源从 READY 移到 IN_USE、撤销源的待消费 hold，最后入队；这样同一 READY 源不能被推进循环重复提交。目的在写入成功前也不进入 READY。

下面给出一种保守而完整的路径：CPU 直接准备到最终 pinned H，四池分别管理 H、D、O、R，每个对象只有一个下游阶段；CPU 将 R 复制/编码到独立响应对象后结束。需要显式 pageable → pinned staging 时，应在同一协议中再加入一个主机复制阶段，而不是把额外副本藏入 H2D。原始载荷、注册映射和 workspace 若被操作借用，也属于该操作的端点或具名责任。

请求的业务终态与物理排空分别记录。live 表示仍允许执行，terminal 保存一次性的 SUCCESS、FAILED 或 CANCELED。隔离集合 Q 保存带请求、uid 和具体原因的责任；quarantined 由该请求是否仍有 Q 项计算，不能由一次完成直接置为 false。只有 live、无 terminal 且无隔离原因的请求有执行资格。输入游标 next 指向第一个尚未由 prepare 接受或明确终结的输入；WAIT_CAPACITY 不等于已经接纳。

隔离原因至少区分 ACCEPTANCE_UNKNOWN（整个操作是否接受尚未澄清）、END_UNCONFIRMED（全部相关访问的最后结束尚未确认）和身份核验原因。它们不是同一个布尔量：明确 ACCEPTED 的操作也可能缺少最后结束证据；最后访问已结束也不自动证明整个抽象操作曾被接受或内容身份正确。Q 独立于 pending 保存，即使访问责任已结算，未获证据的其他原因也不能随着 pending 删除而消失。物理访问结束而接受分类仍未决时，另在待澄清表 E 保存不可变的请求、uid、操作类型、原端点代次/范围和结束证明；E 不保存可变槽对象或待发布载荷，也不重新占用已经证明结束的物理访问责任。每项原因只保护其对应的身份或范围；身份破坏涉及的范围在核清前不得复用，不能仅凭一份结束通知认定地址安全。

入队适配层必须区分三种结果：ACCEPTED 表示接受了整个抽象操作；NOT_ACCEPTED 表示有证据证明整个操作未被接受；UNKNOWN 包括部分接受或无法确定是否接受。错误码本身不能替代这种分类。先登记再入队，使可能提前到达的完成也能匹配；串行状态拥有者在当前提交处理结束后再处理外部通知。确定未接受可以本地结算，不会收到一个可等待的真实完成；未知接受必须保留保护，不能复制为第二次尝试。

```pseudocode
  定时重试只在无通知接口且策略允许时使用；不得在同一推进中无限重试

    否则不改变任何当前对象；重复物理完成幂等忽略

    禁止发布或复用，结束证明不能代替身份核验

      仅解除 (request,uid,ACCEPTANCE_UNKNOWN)
    其他原因只由其各自充分证据解除，不能因 success 或 ended 自动清空

      将其不可变身份、范围及充分结束证明保存到 E，再删除 pending
    仅删除这个 uid 的源读责任、目的写责任及外部借用，结算 pending[uid]
    若剩余隔离使请求不能发布这份已完成结果：
      本参考策略终止请求为 FAILED；已有 FAILED/CANCELED 终态保持
      丢弃未发布载荷，保留 Q、E 及仍欠其他证明的范围保护
    success = 状态成功且 covered 覆盖全部所需写范围
    若失败或范围不完整：调用终止(request,FAILED)，不发布部分内容
    若有目的且 success 且请求仍有执行资格：
      设置同代有效范围、布局和内容身份；phase=READY；hold=true
    否则有目的时：hold=false，内容无效；仍受其他隔离保护的范围不得复用
    若 kind=CPU 且 success 且有执行资格且 committed=false：
      确认 result 是独立响应，不再借用 R
      一次性提交响应；committed=true；terminal=SUCCESS；live=false
    对涉及对象按回收条件及剩余隔离范围归还；容量归还唤醒推进
    剩余 Q 独立保留并报告所欠证据；pending 清空不等于隔离已经解除

处理 接受分类证据(uid,已接受或从未接受,原操作身份及范围)：
  在 pending 或 E 中查找该 uid；二者都无记录时作为旧/未知证明忽略
  按记录核对请求、操作类型、原端点代次及全部范围；不匹配则不结算
  不重新读取当前槽对象作为旧操作的身份依据
  若记录在 E（物理访问已结算）：
    按分类证明仅解除本 uid 的 ACCEPTANCE_UNKNOWN，删除 E 中该记录
    保存终结身份用于去重；不再次回滚、释放、发布或提交该操作
    请求已有失败或取消终态保持；后到确认接受也不复活请求
  否则若证明确认整个操作被接受：
    解除本 uid 的 ACCEPTANCE_UNKNOWN，标记为 ACCEPTED
    保留 pending 及真实访问责任，仍等待充分结束证明后才能消费结果
  否则证明确认整个操作从未接受：
    仅解除本 uid 的 ACCEPTANCE_UNKNOWN 和 END_UNCONFIRMED
    按未接受回滚结算该 uid 的访问责任；本方案终止请求为 FAILED
    不在已经前移的输入游标后隐式重试，也不等待不存在的完成
  不解除身份核验等其他原因；按剩余原因重算隔离并唤醒可推进工作

终止(request,CANCELED或FAILED)：
  已有终态不改写；否则保存一次终态；设置 live=false
  禁止新阶段与未来响应提交；删除该请求的 blocked 和未开始的重试入口
  撤销该请求所有尚待消费的 hold，但不撤销已启动的读写责任
  已在途准备、复制、kernel 和 CPU 消费仍按真实完成结算
  无在途责任且无相关隔离保护的对象立即回收；未知访问状态继续隔离
  未准入输入留给游标按终态跳过；不得重新建立 WAIT_INPUT
  唤醒推进，让其他请求使用已经归还的容量

结束：
  所有请求已成功、失败或取消，且 pending、blocked、Q、E 均清空、
  各池无未归还对象才称排空；next 尚指向终态输入时先本地跳过
  若访问结束或其他必要证明仍未确认，报告 uid、原因、范围、代次和最后使用者
  不宣称排空
```

这里选择 FIFO 输入游标：某输入等待 prepare 容量时，后续尚未准入输入也等待，已经准入的其他请求仍可向下游推进。这种队首等待是明确的调度选择；需要绕过时可改成显式待办队列，但必须保证每项输入始终属于“未尝试、等待重试、已接受/隔离或终态”之一，不能只增加游标而丢失待办。容量永久不恢复时没有成功进度保证，策略应选择有依据的失败或继续报告等待。

以 N=1、首次 prepare 确定被拒绝为例：先预留 H 并登记 uid₁；拒绝后删除 pending[uid₁]，撤销其写者和外部借用，归还 H，next 仍为 0，保存 WAIT_CAPACITY。此时没有 READY H，也没有预期完成，等待入口是容量通知。资源 epoch 改变后清除等待，重新取得 H 的新代次，生成 uid₂；真正接受后 next 才变成 1，随后依次完成 H2D、kernel、D2H 和 CPU 消费。若拒绝策略选择失败，同一处理内进入 FAILED，清除等待并归还预留，next 跳过终态后即可排空，不接收一个永远不会出现的 uid₁ 完成。

另一条 N=1 轨迹从正常 ACCEPTED 开始。prepare 被接受后 next=1，H 的 writer 和原始载荷借用均归该 uid；第一次通知 ended 不充分，只加入 END_UNCONFIRMED，pending、writer、借用及预留保持，H 不发布。随后同 uid 的通知证明成功、完整写入及所有访问结束，必定解除它的 END_UNCONFIRMED，即使接受状态从未是 UNKNOWN；再结算该 uid 的访问责任。没有其他隔离原因且未取消/失败时，H 成为 READY，容量唤醒使 H2D → kernel → D2H → CPU 自动继续，响应只提交一次，最终各池和全部责任排空。若遗漏这次解除，H 会因请求仍无资格而失去正确后继。即使按本章保守策略进入失败，也不能满足这条本应成功的轨迹；若既丢弃结果又不终止，则形成“next=1、无 pending、无输出、无终态”的停滞。两者都不能解释为硬件尚慢或尚未验证。

若同 uid 另有身份核验原因，充分结束证据只解除 END_UNCONFIRMED，不能解除身份核验或其他 uid 的隔离。该请求仍不允许发布和新提交，涉及的隔离范围仍受保护，并明确报告剩余证明责任。本参考选择在物理结束后因剩余隔离无法交付时进入 FAILED，以免丢弃唯一后继后仍留下活请求；不能通过删除 pending 或清除最后原因隐式恢复资格。取消或失败若先被处理，即使所有隔离后来解除，也不改变其终态或恢复发布资格。已结算 uid 的重复物理完成不能再次提交响应；携带新的充分分类证据时，只允许经 E 的专用入口结算尚欠的分类原因。

物理结束与接受分类分开到达时，选择策略也必须闭合。设 prepare 返回 UNKNOWN，next 已为 1；随后通知证明全部访问结束但还不能证明整个抽象操作被接受。该通知结算物理责任，将分类责任转到 E，并按本章保守策略将请求置为 FAILED；未发布 H 可在无其他保护时归还，接受未决本身不虚构仍在途访问。后到的“整个操作已接受”或“整个操作从未接受”证明都由原 uid、请求和不可变范围定位 E，清除相应分类原因并结清 E；两条路径均保持 FAILED、无响应提交且可以完整排空，不依赖已经删除的 pending，也不触碰可能已复用的新代槽。重复证明幂等忽略，错配范围不能清账。若还有身份核验等原因，仍报告这些原因，不能把分类结算当作全面解除隔离。

这里的失败选择使协议简单且保守，并不规定所有系统必须放弃结果。另一合法方案可以保留私有结果和阶段续执行记录，在接受证据充分后继续；它必须为保留的数据、后继和取消责任另给完整协议，不能只删除 Q 后留下无结果、无终态、无待办的请求。

取消先于首次 H 预留时，输入保持 CANCELED；游标无论是否遇到空池，都先跳过该输入。设 A 已占 H，B 尚未准入就取消，C 等待：A 的完成会唤醒推进，B 只使 next 前移，不能建立新的槽或 uid，C 则可以继续取得容量。启动前的资格复查同时保护另一个入口：调用者已经取得但尚未访问的目的预留，在取消后交给启动时必须归还，不得登记新责任。单一状态拥有者使取消与实际提交有明确先后；提交先被接受时，之后的取消仍需保护已有访问。

零字节载荷可以省去实际 DMA，但仍需沿依赖发布明确的空范围完成；它不意味着后续计算、元数据或结果也为空。准备失败不能进入 H2D，目的空间不足不能截断后继续按完整对象发布。长度变化时先检查容量，再提交；不在 DMA 进行中改变描述符。

多消费者扩展需要在启动任何消费者前登记所有独立 uid，再撤销待消费 hold。copy 完成两次不能抵消 archive 的责任。若发送继续借用 R 而没有复制到独立响应，发送也必须成为 R 的读者。增加消费者后，回收仍等待整个集合为空。

代次检查保护账务身份，不能挽救已经发生的物理覆盖。真正仍在途的旧 DMA 不应遇到已复用的新代槽；若发生，说明更早的回收规则已被破坏，忽略旧事件无法恢复新内容。正常的“迟到旧完成”主要是重复或延迟送达的通知：其对应访问已经结算，新的 uid 和 gen 使它不能再次删除新代责任。uid 不复用；终态记录可在安全条件下清理，未知 uid 仍不得被解释成当前操作。

该推进的资源依赖是 H → D → O → R → CPU，且不在等待时占有反向所需资源；每池有合适槽、调度公平、外部操作最终完成、可重试资源最终通知以及 CPU 消费不无限背压时可以继续推进。未知设备状态、永不结束的消费者或额外循环 workspace 依赖不满足此进度前提，应报告阻塞原因。

## 槽位下界与一条完整映射轨迹

对池 j，若每隔 P>0 启动一批，槽从取得到最后消费者结束的固定占用时间为 L_j，则半开占用区间为 [a_i,a_i+L_j)。稳定周期下至少需要

n_j ≥ ceil(L_j/P)。

当 L_j=0 时模型占用为零；当 L_j 恰好为 P 的整数倍时，先处理边界完成再重新取得，恰好 L_j/P 个槽可能足够。有限 N 批的实际同时存活数最多为 N，精确最小值应从这些区间的最大重叠计算。变长、排队和尾部延迟会改变 L_j，平均生存期不能保证安全；真实复用永远由完成责任决定。

设 t_p=3 ms、t_h=2 ms、t_g=8 ms、t_d=1 ms，均为设定值。为得到周期 8 ms 的一条可重建轨迹，按每 8 ms 启动准备，而不是让 CPU 无限制提前准备。各阶段资源独立且槽位充足时：

| 批 | CPU 准备 | H2D | kernel | D2H |
|---|---|---|---|---|
| A | [0,3) | [3,5) | [5,13) | [13,14) |
| B | [8,11) | [11,13) | [13,21) | [21,22) |
| C | [16,19) | [19,21) | [21,29) | [29,30) |

H 使用 pinned 主机槽，D/O 使用相互隔离的设备地址范围，R 使用主机目的槽。A 的 H2D 命令进入复制 stream，其结束位置记录 h_A；计算 stream 等待 h_A 后读取 D_A。kernel 后记录 g_A；返回 stream 等待 g_A，才允许复制引擎读取 O_A、写 R_A。主机确认 d_A 完成后再读取 R_A。事件覆盖整个有效范围，且对象引用保护持续到最后访问。

在 [11,13) 内，复制引擎将 B 的 pinned 字节写入 D_B，GPU 同时读取 D_A；它们使用不同设备输入槽。13 ms 后 A 的输入槽可以回收，但 O_A 仍被 D2H 读取，B 的 kernel 必须使用另一个输出槽。A 的 R 即使在 14 ms 已写完，也要等 CPU 消费结束才归还。若 CPU 消费被延迟，其占用时间和返回池需求都要增加。

设备输入的固定占用是 [3,13)，L_D=10 ms；设备输出为 [5,14)，L_O=9 ms，因此各需要两个槽。每个输入 16 MiB、输出 1 MiB，这两个预留池合计 2×16+2×1=34 MiB。池内活对象已经包含在预留容量中，不再重复加一遍；另计模型、KV、workspace、主机池和 allocator 额外保留区。

这条具体轨迹没有让 H2D 与 D2H 同时工作，因此单复制引擎也未必排除它；双引擎是一般独立方向模型的能力前提之一，不能反过来声称本例必须有两个引擎。八批在上述理想条件下为 14+7×8=70 ms，串行为 8×14=112 ms，首批仍需 14 ms。若 CPU 提前堆积多批，输入槽会经历更长等待，不能继续把占用时间固定为 10 ms。

再构造复制引擎主导的反例：t_p=1、t_h=8、t_g=2、t_d=4 ms，N=5。错误套用独立方向公式得到 15+4×8=47 ms；单复制引擎光是复制工作就需要 5×12=60 ms，且首个复制不早于 1 ms，因此 T_5≥61 ms，直接排除 47 ms。61 ms 仍只是下界，不是已经构造出的最优调度。

## 减少次数、分块与共享带宽

小而频繁的 token IDs、lengths 和 sampling metadata 容易受提交与同步成本主导。设 B 字节分成 m 次提交，每次固定成本 c_s，有效路径带宽 B_eff；合并后增加 packing/unpacking 成本 c_pack，其他条件不变，则

T_sep ≈ m c_s+B/B_eff，T_merge ≈ c_s+B/B_eff+c_pack。

只有 (m−1)c_s>c_pack 时，合并才有该简化模型下的收益。若合并增加 padding、需要等待慢请求或改变原来的重叠，必须分别加入额外字节和等待；吞吐改善不保证单请求尾延迟改善。

对 D 字节对象分成 q=ceil(D/b) 块，第 k 块有效范围为 [kb,min((k+1)b,D))。末块按实际长度处理，不能默认整除。若块之间没有计算依赖，可以对每块应用同样的准备、复制、消费与回收协议；若消费者必须取得完整对象，则先等待所有必要块的完整范围，再发布整体对象。任何一块失败都不能将混合旧字节的整体标为成功。

设每次传输固定开销 α，分块会增加 qα 的提交/服务需求；小块可能较早启动计算，却增加事件、索引和尾块处理，大块减少次数却推迟首块可用并增加驻留。真实时间仍要用块依赖和共享资源日历求得，不能无条件把单对象时间除以 q。

输入还可能先从 SSD 或远端存储到主存，再解码、转换和 H2D。存储部分完成、应用范围完整、布局转换完成和设备可读是不同边界。Linux 固定文档说明块请求可以乱序完成，iomap 还区分异步排队、传输字节数和部分完成；上游成功通知必须转换成当前对象的完整范围证明。

对共享资源 r，每批实际承担 Q_r 字节，在同一并发条件下可持续带宽为 B_r，则 P≥Q_r/B_r。主机准备读取、转换写入、staging 读写及 DMA 读写若共享 DRAM，流量应合计。上游链路若按双向共享容量建模，也应合并相应方向；若硬件有独立方向容量，则分别列约束，不能一律把 H2D+D2H 除以单向带宽。

在相应假设下，周期需要同时满足阶段、引擎及共享资源下界，但这些约束通常取最大值，不能把已经包含在阶段时间内的访存耗时再次相加。设共享 DRAM 每批累计搬运 128 MiB、并发可持续带宽为 8 GiB/s，资源下界为 15.625 ms，便排除了先前 8 ms 周期的可达性。增槽不能减少这项字节需求。

## 同一候选的完整成本账

| 成本 | 应记内容 | 能否因异步直接消失 |
|---|---|---|
| 计算 | 原有 kernel 工作、CPU 解码/转换、额外 packing 或校验 | 异步本身不减少模型 FLOPs |
| 访存 | 主机转换读写、staging 额外副本、kernel 设备访存 | 布局、融合与复用可以改变实际流量 |
| 通信 | H2D/D2H 有效字节、padding、重复传输及路径放大 | 重叠只改变关键路径，不消除传输 |
| 准备 | 分配/注册、页处理、描述符、索引和内容身份检查 | 池化与复用可摊薄，不能记为零 |
| 同步 | 事件记录/查询、队列等待、CPU 唤醒、跨 stream 依赖 | 对象级依赖可减少全局等待，必要边仍保留 |
| 驻留 | A/H/S/D/O/R、workspace、未排空旧代和池预留 | 深流水通常增加同时存活容量 |

若同一锁页范围复用 r 次，建立成本 C_pin 的每次分摊约为 C_pin/r，另有复制、注册缓存维护和最终撤销成本。复用范围并不意味着复用旧内容；每次仍要满足身份与最后读取关系。一次性小对象可能被锁页成本主导，重复的大对象才更容易摊薄。

固定容量池的显式预留为各池容量之和；存在别名或共享存储时按物理并集计算。只统计活对象的曲线与统计整个预留池是两种口径，不能相加。取消也会形成驻留：逻辑上不再输出的请求，仍可能占有正在被复制引擎或 kernel 使用的对象。

固定阶段数且无重试时，每批建立常数个事件和责任，控制工作为 O(1)；N 批另有 A 次拒绝/重试尝试时，事件与账本更新为 O(N+A)。若分成 q 块，则正常描述符、事件及账本工作为每批 O(q)，重试另外计数。在途 ledger 空间随实际在途操作数增长，blocked 随尚待重试的阶段数增长。确定未接受的目的预留立即归还，但 READY 源与等待时间仍占资源；未知接受继续计入隔离驻留。隔离表还随尚未结清的“uid、原因”项增长；待澄清表 E 随物理已结束但分类未决的操作数增长，仅保存固定大小的身份、范围和证据元数据，不保存结果缓冲。访问结算不能提前抹去这些项；迟到证据去重记录按接口允许的安全期限回收。具名 readers 可以避免重复通知抵消其他责任；高效查询、资源等待表与池空闲表避免每次完成扫描全部历史请求。这里的复杂度不包括解码、布局转换和设备计算本身，也不把示意扫描循环当成高效实现已经完成。

## 共享路径与选择反转

物理统一内存、映射主机页和可迁移统一内存有不同的物理位置、访问与可见性关系，见[共享内存路径](shared-memory-paths.md)。省掉显式复制不意味着省掉实际交通：GPU 可能通过链路远端读取，或因页迁移、缺页与 CPU/GPU 交替访问付出成本。

固定 CUDA 最佳实践文档在独立 GPU 的 mapped pinned memory 模型中建议一次性、合并的访问，并提醒重复访问会产生重复 CPU–GPU 传输，可另建设备副本缓存。其缓存描述受固定平台与文档模型限定，不能作为所有 CPU–GPU 互连的统一结论。

设 GPU 完整读取 D 字节 R 次，链路带宽 B_l、设备本地带宽 B_d，忽略 cache、排队与重叠，显式复制后读取约为 D/B_l+RD/B_d，直接远端读取约为 RD/B_l。重用增加通常有利于设备副本；若实际只读很小部分，应换成实际访问量与事务放大重新比较。write-combining 主机内存还会改变 CPU 读成本，不能只用 H2D 带宽决定分配方式。

| 条件变化 | 保留的正确性关系 | 调整或放弃的选择 |
|---|---|---|
| 双方向独立变成单复制引擎 | 同批生产消费依赖、最后访问保护 | 合并方向服务日历；放弃被复制总工作排除的周期预测 |
| 锁页预算缩小或注册昂贵 | DMA 源在最后读取前稳定 | 缩小并复用 pinned 池；一次性小对象比较含 staging 的路径 |
| GPU 已持续饱和 | 完成与结果归属 | 增槽只增加队列/驻留时，降低在途预算 |
| CPU 准备成为关键路径 | 发布前写全范围 | 调整准备并行、处理缓存或计算放置；复制槽不能替代 CPU 能力 |
| 输入长度或消费者时间出现长尾 | 按真实事件回收 | 放弃用平均 L/P 保证容量；按大小分池、限制字节准入 |
| 设备副本重复使用增加 | 内容版本与缓存失效 | 比较保留 D 与反复远端读取，重算驻留机会成本 |
| 图重放固定地址 | 输入生产、图读取、输出最后消费 | 分槽或串行保护；放弃并发覆盖同一静态输入/输出 |
| 高取消率或逐 token 反馈 | 取消不撤销已有访问 | 缩短队列，分别评估逻辑取消与物理排空，不沿用独立批吞吐作为 ITL |
| 执行器暂时拒绝提交 | 未接受操作没有可等待的完成；输入身份不丢失 | 归还目的、保存重试并由容量通知唤醒；永久不可用时明确失败 |

## 用反例与区分实验修正解释

先固定逻辑输入、输出契约、到达轨迹、计时边界和实际资源环境，再分别改变一个可控条件。主机 API 区间、设备事件区间与端到端完成时间属于不同统计口径；未同步的主机提交计时不能代表 DMA 或 kernel 完成。诊断时全局同步与 profiler 的扰动也应单列。

| 竞争解释 | 区分实验与预测 | 出现反证后怎样修正 |
|---|---|---|
| CPU 准备不足，而非设备计算慢 | 增加独立准备机会；若设备空洞减少而 kernel 服务时间不变，支持准备限制 | 设备已满、仅排队增长时，转查设备服务需求或准入 |
| 槽位不足，而非带宽饱和 | 固定输入与字节扫描池深度；容量不足时生产者停顿减少，服务区间近似不变 | 增槽不减空洞却增加峰值时，不能继续归因槽位 |
| 固定提交成本，而非大字节搬运 | 固定总字节改变提交次数，再固定次数改变字节 | 只有字节变化有效时，修正为带宽/实际路径解释 |
| 单引擎或隐式串行化，而非计算不足 | 记录两方向复制及 kernel 区间，核对 stream 模式与设备能力 | 依赖允许但未重叠时，继续检查共享链路、DRAM 和命令排序 |
| pageable staging 或锁页准备主导 | 分开记录分配、注册、主机复制与设备复制；比较一次性和复用路径 | pinned 路径仍慢时，不能只用隐式 staging 解释 |
| 共享带宽，而非单阶段孤立速度 | 固定字节增加并发 CPU 内存工作，观察有效带宽和关键路径是否同时改变 | 字节需求不变、仅调池深度即改善时，容量/调度更可疑 |
| H2D 源或目的过早复用 | 延迟复制，让相邻代内容完全不同，核对实际消费字节 | 全同步使错误消失只提供线索，仍需定位源保护或目的依赖的缺边 |
| 重复完成或代次混淆 | 两消费者乱序结束，重复第一个通知；复用后再投递旧 uid | 身份安全但内容仍变时，检查真实在途访问，代次不能修复物理覆盖 |
| D2H 完成前读取或结果回收过早 | 分别延迟 D2H 和 CPU 消费，核对旧值、部分值及 R 的最后读者 | 仅延迟 CPU 才出错时，应查结果生存期而非 H2D |
| 部分范围被当成完整结果 | 注入短读、尾块失败和入队状态不明；检查是否仍发布整体 | 不发布但泄漏时，继续核对错误是否证明访问结束及清理责任 |
| prepare 被拒绝后的协议停滞，而非准备缓慢 | N=1，首次明确拒绝且不生成完成；恢复容量后检查相同输入是否重试并排空；另测立即失败 | 无实际访问却仍有 pending，或 next 已越过唯一输入时，修回滚与待办归属，不能靠增加槽掩盖 |
| 取消后重新准入，而非正常排空 | 首次 H 预留前取消，再让其他请求完成和容量恢复；观察取消请求的新增 reserve/intent | 新责任出现在取消处理之后时修准入和启动资格；已有责任仅结束则属于正常排空 |
| 物理结束后分类证据迟到，或结算记录被删除 | UNKNOWN 后先给充分 ended、不给接受证明，再分别补给接受和从未接受证明；观察 E、终态、归还和重复通知 | 本参考两条路径都保持失败并结清 E/Q；证据已充分仍有无后继活请求或依赖已删 pending 时，修记录与解析入口 |
| 结束证据不足，或充分证据后的隔离结算遗漏 | 未取消的 ACCEPTED prepare 先收 ended=false，再收同 uid 成功、完整且充分 ended；前者保留保护，后者应恢复完整输出并排空 | 全部访问已结算但只剩该 uid 的 END_UNCONFIRMED 时修原因解除；仍有独立原因时继续隔离并指出所欠证据 |

明确反例包括：L>P 却用单槽提前覆盖；把 API 返回当成 DMA 源读取结束；只记录最后一个消费者；取消时直接清空 readers；一个复制引擎却预测前述 47 ms；READY 无读者就回收；以旧 gen 检查代替在途保护；prepare 确定未接受却既前移 next 又等待完成；取消输入在其他请求完成后重新取得 H；ACCEPTED 的最后访问已获充分结束证明，却因只对 UNKNOWN 解除隔离而丢失唯一后继。这些错误可能提高表面提交速度，却破坏内容、低估完成时间或使请求无法结束。

配套检查用逐阶段资源日历独立核对流水闭式，用占用区间逐点计数核对槽位公式；缓冲模型检查完整发布、待消费 hold、具名多读者、取消后的在途保护及复用后的重复完成，并把一条准备→H2D→计算→D2H→CPU 路径的结果与直接函数参考比较。事件推进模型另外执行四池准入、pending 登记、拒绝回滚、游标保留、容量唤醒、终态跳过及启动资格复查；独立观察器从 reserve、intent、submission、settle、free、terminal、commit 的事件顺序重建责任，不以生产者的空闲标志证明释放安全。

隔离恢复检查采用同一推进模型：N=1 的非空载荷先正常 ACCEPTED，ended=false 时核对 pending、目的 writer、外部借用及隔离保留且无发布；随后充分完成后自动推进全部后继，以独立 raw→响应参考、唯一提交、终态和全池排空核对恢复。另保留同 uid 的独立身份核验原因，确认只解除结束未确认不会恢复请求或复用其隔离范围；两请求的不同 uid 对照确认完成一个不会解除另一个。取消/失败后的同样结束证据不能重新发布。原因事件的观察重放核对解除类型、请求和 uid，并检查原因表没有随 pending 删除而丢失。

故意错误的对照覆盖忽略共享复制引擎、槽数向下取整、DMA 源覆盖、重复通知误删其他责任、拒绝后无条件前移游标、撤销访问却遗留 pending、取消后新准入，以及只遗漏 ACCEPTED 操作的 END_UNCONFIRMED 解除。最后一种故障实际执行相同恢复轨迹，让推进自然无后继，再由独立输出参考、终态和排空要求检出；检查不替故障模型补清原因。后到分类回归继续 UNKNOWN 的物理已结束轨迹，分别投递接受和从未接受证明，核对失败终态不复活、E/Q 完整结清、物理责任只结算一次及槽复用后旧证据不改新代。历史事件观察器从原 intent、充分结束、待澄清登记和后到证明独立重建 E；丢失 E 的故障仍实际接收两类后到证明，再由相同排空与账务判据检出。

这些是确定性的 CPU 算术与协议模型，不证明真实 CUDA API 的错误恢复、事件作用域、编译后访存、DMA 可见性、物理重叠或服务性能。模型把执行器容量通知、全部访问结束和整个操作接受证明作为显式输入事件，不验证真实适配层能否产生这些证明，也不验证并发注册等待与 epoch 检查的实现。身份核验控制只模拟一项尚未澄清的原因与范围保护，不证明真实身份破坏后的修复算法。目标环境仍需记录实际版本、设备、stream 模式、内存路径、有效资源配额，以及分阶段与端到端测量；局部检查通过不能声称改善了 Agent 构建能力或完整引擎收益。
