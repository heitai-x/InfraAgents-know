{"chapter": "# K-SYS-001：主机与设备时间：偏序、区间并集和关键路径\n\n服务延迟来自生产、提交、执行与消费之间的依赖路径；主机 API 区间、设备执行区间和观测区间可以重叠。把时间戳排序得到的线不是因果链，把各段时长相加也不自动得到墙钟时间。\n\n## 事件、区间与时间域\n\n一次时间观测至少记录：事件类型、时间戳、时间域、进程/线程/设备/stream 或队列作用域、对象与范围、请求和尝试身份。只保留一个时间戳而丢掉这些身份，后续无法区分同一地址上的旧传输与新传输，也无法把一次完成的持续时间归给正确请求。\n\n区间采用半开形式 \\(I=[s,e)\\)，其中 \\(s\\) 表示开始生效，\\(e\\) 表示释放；时长为 \\(d=e-s\\)，要求 \\(s\\le e\\)。零长区间可以作为事件点保留，但不构成忙碌时间；\\(e<s\\) 是非法区间。若改用闭区间或采样点的口径，边界判断随之改变，不能在一张统计表中混用。\n\n同一时间域内的两个区间可以定义重叠长度：\n\n\\[\no(I,J)=\\max(0,\\min(e_I,e_J)-\\max(s_I,s_J)).\n\\]\n\n累计时长是 \\(S=\\sum_i(e_i-s_i)\\)，区间并集是 \\(U=\\left|\\bigcup_i I_i\\right|\\)。若只讨论一个设备、一个资源或一个指定作用域，才可以把该作用域的并集称为它的忙碌时间；若不先限定作用域，并集只是被选记录覆盖的时间，不是设备能力、SM 占用率或服务吞吐。\n\n主机 API 调用开始、命令进入设备队列、kernel 开始、host API 返回、kernel 完成、CPU 消费结果，是不同事件。异步 launch 可以在 API 返回前就开始设备工作，也可以返回很久后才执行。于是设备开始减 API 结束为负值并不自动表示时钟错误；它可能只是说明两个事件属于不同偏序位置，或设备工作已经开始而主机调用尚未返回。\n\n跨时间域比较还要引入偏移。设同一物理时刻在 A、B 两钟上的读数满足 \\(t_B=t_A+\\delta\\)，且只知道 \\(\\delta\\in[\\delta_{lo},\\delta_{hi}]\\)。B 收到 A 所发消息的传输时间 \\(T\\) 满足：\n\n\\[\nT=(t_B-\\delta)-t_A=t_B-t_A-\\delta,\n\\]\n\n因此只能给出\n\n\\[\nt_B-t_A-\\delta_{hi}\\le T\\le t_B-t_A-\\delta_{lo}.\n\\]\n\n例如 A 发送读数 10、B 接收读数 15、偏移只知道位于 \\([-2,4]\\)，则 \\(T\\in[1,7]\\)。若偏移界限不能确定，只能保留发送先于接收的因果顺序，不能把图上 5 个单位当作精确单向延迟，更不能用它区分相差 1 个单位的实现。\n\ncorrelation ID 表达因果或采集关联，不能单独提供持续时间。固定来源说明指出，关联标识并不保证在所有进程、设备或重试之间唯一；正文因此额外要求请求、对象、执行尝试和代次身份。相同 correlation ID 对应两次重试时，不能把前一次发送与后一次确认配成一次传输。\n\n## 合法性：哪些量可以比较\n\n合法性不是由字段名决定，而由事件语义、时间域和依赖证据共同决定。以下条件至少同时成立，才可以把一个时间差解释为某段延迟。\n\n- L1 同一时间域，或存在可复核的校准与偏移界限。同一进程的单调经过时间可以使用适合测量持续时间的时钟；不同机器的时间戳相减还必须处理偏移与漂移。\n- L2 两端事件语义一致。API 调用区间量的是主机调用跨度，kernel 区间量的是设备执行跨度；两者都叫 duration，也不能在没有连接时比较谁更快。\n- L3 因果边显式存在。stream 内顺序、正确记录的 event 等待、数据依赖、资源释放和提交协议都能提供边；仅仅时间戳更早只能提供候选顺序。\n- L4 采集范围完整。表未启用、窗口外、过滤后为空、无法关联和确实没有事件是不同状态。缺表只能说明该观测未覆盖，不能把缺失阶段当成零成本。\n- L5 聚合作用域一致。单设备并集、单 engine 并集、SM 占用、请求关键路径和整机墙钟是不同对象；跨设备累计时间不能直接当作墙钟。\n- L6 跨节点先判断可比较。偏移区间过宽时，只能报告偏序或本地持续时间，不能报告虚假的毫秒级单向延迟。\n- L7 采样和仪表化条件匹配。高开销采集、短窗口、缓冲溢出或额外同步可以改变队列和重叠；机制解释与最终性能应分别取证。\n- L8 零工作、取消和失败有明确表示。没有 payload 的阶段可以产生显式空结果；逻辑取消不等于设备已停止访问，更不等于资源已归还。\n\n哪些事件被采集、是否使用范围标注、是否按 kernel 汇总、是否采用区间并集，属于观测方案选择，不是异步执行本身的合法性条件。方案选择可以改变精度和扰动，却不能改变事件定义。\n\n## 区间并集：从事件到忙碌时间\n\n下面的算法面向有限、已按同一时间域转换并限定作用域的区间。半开区间在端点 \\(e=s\\) 处不重叠；相邻但可合并为连续覆盖时，合并后的并集长度不变。\n\n```pseudocode\n算法 IntervalUnion(records, domain, resource, window)\n输入：有限记录 records；每条含 clock_domain、device、resource、[s,e)、单位；目标 domain/resource；window=[W0,W1)，W0<=W1\n输出：merged 区间、sum_len、union_len、max_concurrency、idle_in_window；或拒绝比较的原因\n\n1. 若记录的单位不同或时钟域未经映射，返回 Incomparable，不把数字混合相加\n2. 对每条记录：\n     若不匹配 domain 或 resource，跳过并计入 filtered\n     若 e<s，返回 InvalidInterval\n     若 s==e，作为瞬时事件保留，但不进入忙碌区间\n     s1=max(s,W0); e1=min(e,W1)\n     若 s1<e1，把 [s1,e1) 加入 work\n3. sum_len = 所有 work 区间的时长之和\n4. 按 (s,e,稳定身份) 对 work 排序\n5. merged=空\n   for [s,e) in work:\n     若 merged 为空：加入 [s,e)\n     否则令 cur 为 merged 的最后一段：\n        若 s<=cur.e：cur.e=max(cur.e,e)\n        否则：加入 [s,e)\n6. 构造事件 (s,+1) 与 (e,-1)\n   按 (time, delta) 排序，同一时刻 delta=-1 的事件先于 +1\n   active=0; max_concurrency=0\n   for (time,delta) in events:\n     若 delta==-1：active=active-1\n     否则：active=active+1; max_concurrency=max(max_concurrency,active)\n7. union_len = merged 中所有区间时长之和\n8. idle_in_window = (W1-W0)-union_len，仅在有限窗口且所有记录已裁剪时报告\n9. 若 work 为空：返回 [],0,0,0,W1-W0\n10. 返回 merged,sum_len,union_len,max_concurrency,idle_in_window\n```\n\n正确性不变量可以这样陈述：按开始时间扫描后，merged 的最后一段始终覆盖已处理区间的并集，并保持其右端最大；当新区间与当前段相交或相邻时，要么延长当前段，要么开新段。半开区间中，结束事件先于同一时刻的开始事件处理，因此 [0,10) 与 [10,20) 的最大并发数为 1，而不是 2。\n\n边界要单独检查：空输入返回零并集；窗口完全落在区间外返回空；重复区间增加累计时长但不增加并集；嵌套区间只保留外层覆盖；大量零长事件不制造忙碌时间；单位混用要拒绝而不是静默换算。对于已按时间排序的流式事件，若只需要 active 和并集长度，可以在线推进；若要输出合并后的区间清单，仍需保留当前段和必要的快照。\n\n成本上，通用实现要对 \\(n\\) 个区间排序，时间 \\(O(n\\log n)\\)、空间 \\(O(n)\\)；事件扫描也是 \\(O(n\\log n)\\)，若输入已排序则可降为 \\(O(n)\\)。采集和保存记录的准备成本、驻留成本与分析成本要分开：分析一个已导出的短窗口，不包含采集期间的仪表化和缓冲开销。\n\n由累计量还可以得到一个有用恒等式。令 \\(C(t)\\) 为时刻 \\(t\\) 同时活动的区间数，则\n\n\\[\nS=\\int C(t)\\,dt,\\qquad U=\\int \\mathbf{1}[C(t)>0]\\,dt.\n\\]\n\n若在窗口内 \\(C(t)\\le K\\)，则 \\(U\\le S\\le K U\\)。这解释了为什么重叠越多，累计时长越容易超过墙钟；但 \\(K\\) 只是点并发数，不是 SM 利用率，也不是每个 engine 的资源占用。一个正在运行的 memcpy 与一个占满 SM 的 kernel，在时间并集上都可以只贡献一个覆盖段；Nsight Systems 文档也明确其时间利用率不等于资源利用率，并发操作在局部窗口还可能被叠加显示。\n\n## 关键路径：从偏序到完成下界\n\n把请求相关的工作建成有向图 \\(G=(V,E)\\)。节点 \\(v\\) 至少有持续时间下界 \\(d_v\\ge0\\)，边 \\(u\\to v\\) 表示 \\(u\\) 的完成必须先于 \\(v\\) 的开始，或存在最小等待 \\(l_{uv}\\ge0\\)。发布事件 \\(r_v\\) 表示节点最早可被释放。没有边的两个节点可以并发，但也可以因共享资源而排队；后者需要额外的容量或资源边，不能仅凭时间重叠推断。\n\n算法先用拓扑序计算最早开始与最早完成：\n\n```pseudocode\n算法 EarliestCompletion(V,E,r,d,l,source,target)\n输入：有限节点 V；边 E；每个节点的持续时间下界 d[v]>=0；释放时间 r[v]；边等待 l[u,v]>=0；可选 source/target\n输出：最早完成下界、关键路径节点序列、各节点 ES/EF；或 Cycle/Unreachable\n\n1. 建 pred、succ，检查边的端点和非负持续时间\n2. 用 Kahn 拓扑排序；若处理节点数小于 |V|，返回 Cycle，不把环强行压平成最长路径\n3. 若给定 source/target：\n     只保留 source 可达且可到达 target 的节点与边\n     若 target 不在保留图中，返回 Unreachable\n4. for v in 拓扑序：\n     若 v 没有前驱：ES[v]=r[v]\n     否则：ES[v]=max 对所有 u->v 的 (EF[u]+l[u,v])\n     EF[v]=ES[v]+d[v]\n5. 若给定 target：完成下界=EF[target]，从 target 回溯使上述 max 成立的前驱\n   否则：完成下界=max 所有汇点的 EF[v]，从取得最大值的汇点回溯\n6. 校验回溯路径上的每条边存在，返回长度、路径、ES/EF\n```\n\n在边和持续时间都完整的有限 DAG 中，拓扑归纳给出的是满足所有前驱的最早开始，因此 target 的 EF 是完成时间的下界。若实际设备区间更长，可能是真实服务时间更大、队列等待未被建模、资源共享未被边表示，或采集范围不完整；这些都应继续调查，而不是直接把关键路径调大。若实际完成早于按完整边和可靠时间戳算出的 EF，则至少要怀疑边、持续时间、时间域或身份关联有误。\n\n实际 trace 中的区间长度通常包含等待。要区分服务与排队，应把节点拆成进入队列、获得资源、执行和完成；只把一个长 kernel 区间当作纯计算，会把其内部 stall、尾部 block 和资源竞争混入关键路径。多条 stream 并发也不能靠累计 kernel 时长估计请求完成；请求路径还可能经过复制、通信、CPU 转换与输出交付。\n\n## 成本：计算、访存、同步与驻留\n\n区间并集的计算成本是排序与扫描；关键路径的计算成本是建图和拓扑排序，通常为 \\(O(|V|+|E|)\\)，回溯与保存路径为 \\(O(|V|)\\)。这些是分析算法的成本，不是被观测系统的时间。\n\n访存成本来自记录数量、字段宽度、索引和导出格式。每个区间至少需要开始、结束、作用域和身份；跨进程、跨设备还要保留上下文。采集窗口越长、对象越多，驻留缓冲和导出文件越大。用聚合表代替原始事件可以降低存储，但会失去重叠、尾部和单请求关键路径能力。\n\n通信成本包括跨节点 trace 导出、上下文传播和聚合查询。传播 trace ID 或 span ID 只建立关联，不给时钟校准；上下文头大小也不是单向网络延迟。跨节点保存本地持续时间、发送/接收区间和偏移界限，通常比只保存一个全局时间点更能经受校准误差。\n\n准备成本包括启用采集、建立时间域映射、构造请求到 batch 到 API/kernel 的关联，以及必要时的手工范围标注。同步成本包括停止采集、刷新缓冲、等待设备结束和保证数据完整。固定文档说明，某些采集选项会增加应用开销，缓冲刷新甚至可能插入同步；因此 profiler 下的完整时间和正常运行时间必须分开报告。\n\n驻留成本与分析范围要一起说明。有限窗口内的设备忙碌并集不包含窗口外工作；窗口内到达但未完成的请求不能从分母消失。用 \\(T\\) 表示测量窗口，则时间忙碌比例为 \\(U/T\\)，有效吞吐仍是完成的业务单位除以窗口或完成时间，不能把 \\(U\\) 当成吞吐。若 \\(N\\) 个请求共享一次物理阶段，该阶段在资源并集中只占一次，但在每个请求的依赖路径上都可能贡献等待；两种账不能相加成一个更大的物理总线时间。\n\n## 组合轨迹：加载、复制、消费\n\n设一个请求的路径为：读取 [0,40)，转换为 [40,48)，主机到设备复制为 [48,60)，GPU 消费为 [60,75)，单位是假设的时间单位。另有一条独立工作 [0,35)，它不向该请求提供输入，也不与这些阶段争用同一资源。\n\n| 对象 | 区间或依赖 |\n|---|---|\n| 读取 | [0,40) |\n| 转换 | [40,48)，读取完成是前置 |\n| 复制 | [48,60)，转换完成是前置 |\n| 消费 | [60,75)，复制完成是前置 |\n| 独立工作 | [0,35)，无数据边 |\n\n所有阶段时长相加为 \\(40+8+12+15+35=110\\)。若只看这段路径与独立工作的设备覆盖，并集是 [0,75)，长度为 75；请求的关键路径也是 75。这里的 110 不是设备忙碌时间，也不是请求完成时间。\n\n把独立工作从 35 缩短到 15，累计时长降为 90，设备覆盖仍为 75，请求关键路径仍为 75。把读取从 40 缩短到 20，在其他资源和依赖均不变化时，路径变为 [0,20)、[20,28)、[28,40)、[40,55)，预测完成时间降到 55。这不是硬件实测，只是对给定边和持续时间的条件化推演。\n\n资源条件会反转结论。若独立工作与转换争用同一 CPU、与复制争用同一内存控制器或同一复制 engine，原本没有数据边的两条路径会通过排队产生新的等待边；此时缩短独立工作可能缩短读、转换或复制的实际区间，也可能只是减少其他请求的排队。反过来，减少一条依赖边或空出一个 buffer，也可能因资源已饱和而没有端到端收益。\n\n## 条件变化后的保留、调整与放弃\n\n| 条件变化 | 必须保留的关系 | 可调整方案 | 反转或放弃信号 |\n|---|---|---|---|\n| 单设备、单 stream | 区间语义、同时间域和半开边界 | 可用 stream 顺序减少显式边；保留原始事件便于复核 | 引入库内部 stream 后仍沿用一个顺序假设 |\n| 多设备或多 engine | 每设备/每 engine 的覆盖和资源语义 | 分别计算并集，再沿请求依赖连接；不要把跨设备并集当墙钟 | 请求实际只等一个设备，却被汇总成全局空闲 |\n| 多 stream 并发 | 所有数据、事件和资源边仍成立 | 增加显式 event/依赖边，保留非关键路径工作 | 去掉一条边后完成时间不变，说明原边可能不关键或图不完整 |\n| 跨节点时间戳 | 因果偏序与偏移界限 | 用本地持续时间、往返区间或校准补充单向延迟 | 偏移区间宽于决策差异，仍报告精确等待 |\n| 采集事件缺失 | 缺失不等于零工作量 | 补充采集范围或改用独立业务测量；保留缺口标记 | 表补齐后空洞消失而服务不变，支持观测缺口解释 |\n| 采集扰动明显 | 正常运行点仍是性能依据 | 用短窗口定位机制，用无 profiler 重复测量评价性能 | 只在该 profiler 配置下出现收益，不能外推 |\n| 队列接近饱和 | 完成量、排队和有效输出仍要计入 | 缩短非关键工作可提高容量，但未必降低当前请求延迟 | 并集长时间接近窗口而尾延迟继续增长，应查排队而非只查空洞 |\n| 取消或抢占 | 逻辑取消与物理排空分离 | 分别记录逻辑响应、最后设备访问和槽归还 | 设备早已结束而资源晚归还，应查控制路径而非设备执行 |\n\n方案选择应随条件更新：多设备时，单设备并集仍成立，但不能替代请求路径；偏移无法校准时，本地持续时间仍可保留，但跨节点精确延迟应放弃；资源计数无法按 engine 分开时，时间并集仍可说明总覆盖，却不能证明 SM 或复制 engine 饱和。\n\n## 诊断：竞争解释与区分实验\n\n时间线诊断要先固定请求、输入、工作量和计时边界，再比较候选解释。全设备同步使异常消失，只能说明存在时序相关，不能定位是主机生产、设备依赖、存储完成还是采集缺口。\n\n| 观察 | 竞争解释 | 区分干预 | 预测与反证后的修正 |\n|---|---|---|---|\n| 设备前有长空洞，CPU 看似空闲 |
