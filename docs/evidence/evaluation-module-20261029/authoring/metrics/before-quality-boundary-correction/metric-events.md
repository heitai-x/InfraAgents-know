# K-WORK-001：服务指标：事件边界、Token 间隔与用户时间

一个延迟指标是两个有明确身份的事件之间的时间差。指标名字相同，而事件边界、时钟、输出计数或聚合总体不同，仍可能得到不可比较的结果。服务指标需要连接模型计算、协议交付与客户端消费，并保留拒绝、失败和未完成工作，才能解释优化究竟改善了哪条路径。

## 事件对象、输入与状态

生成服务依次经历请求发出、接收、准入、执行、产生内容、交付内容和终止，但这些责任可以异步推进。模型产生 token、服务器接受发送数据和客户端显示字符是不同事件。

一次事件至少记录为 `e=(r,g,id,seq,k,t,d,s,p)`：`r` 是逻辑请求，`g` 是尝试或输出代次，`id` 是稳定事件身份，`seq` 是该观察者的顺序，`k` 是事件类型，`t` 是时间戳，`d` 是时间域，`s` 是连接、请求、执行队列等作用域，`p` 是内容范围或元数据。时间戳可以使用任意原点；要求有限、单位一致，并满足已经证明的顺序关系，不要求绝对读数为正。

请求记录保存发出事件、准入决定及其时间、内容范围、终态及其时间、质量与 SLO 判定。客户端消费、模型执行和资源排空可以另有记录，通过请求与尝试身份关联，不能强行装进一条可直接相减的时间轴。

核心不变量如下。

- 同一逻辑请求的重试拥有不同尝试身份；旧尝试内容不能修改新尝试的 TTFT。
- 同一事件的完全相同重复导出可以去重；相同身份但负载不同必须报冲突。内容相同而事件身份不同，不足以证明可以去重。
- 内容范围必须连续、不重叠、不遗漏。响应头、空角色、心跳、usage 和结束标记不自动构成首个有效内容。
- 时间域、观察边界和计数单位必须随数值保存。模型时间不能填入客户端内容时间字段。
- 终止需要显式事件。最后内容不是默认的协议结束；取消、超时和错误不是正常完成，也不证明设备已经排空。
- 未定义值携带原因和覆盖率。缺失间隔不是零间隔；没有观测到完成也不是零延迟。

输入不必包含所有内部阶段。只测客户端 TTFT 时，可以仅保留发出、内容和终止事件；没有采集准入或执行事件，不能据此补出排队时间为零。完整 offered 账务则需要关联准入记录，明确区分尚未决定、已拒绝、准入前终止和准入后推进。

## 时间轴、数学定义与可观测性

记客户端发出为 `t_0`，客户端第 `i` 个有效内容 token 的可见时间为 `u_i`，`i=1..N`，协议正常结束为 `t_F`，客户端完成解析或提交为 `t_C`。它们必须来自同一个客户端持续时间时钟，或经过有误差界限的映射。

客户端首内容延迟为 `TTFT_client=u_1-t_0`，仅在 `N>0` 时定义。协议正常完成延迟为 `L_protocol=t_F-t_0`，客户端消费完成延迟为 `L_user=t_C-t_0`。服务端从接收到首个模型 token、从开始执行到首个内容发送，可以分别定义内部指标，但其终点和时间域要单独命名，不能将客户端 `u_1` 直接减服务端接收读数。

若同一边界的逐 token 时间确实可用，则

`ITL_i=u_i-u_(i-1)`，`i=2..N`；

`TPOT=(u_N-u_1)/(N-1)=Σ ITL_i/(N-1)`，仅当 `N>1`。

相邻时间相等是合法的同时可见事件，因此精确观测到的零间隔可以保留；错误在于没有逐 token 观测却声称得到了这种精确结果。`N=1` 没有 token 间隔，TPOT 未定义；`N=0` 连 TTFT 也未定义，但仍可以有空结果、拒绝、失败或协议完成状态。空结果是否满足任务，由任务质量契约决定。

若生成阶段持续时间为正，同一组间隔上的速率为 `(N-1)/(u_N-u_1)`。分子是 token，分母是时间；时间为零时不能报告有限速率。它也不是包含首次等待的整请求输出速率，更不是多请求服务吞吐。

TPOT 只约束间隔总和。例如 11 个 token 的 10 个间隔全部为 10 ms，与 9 个零间隔加一个 100 ms 间隔，TPOT 都是 10 ms；后一条轨迹存在明显停顿。尾部 ITL 需要原始间隔或能够重建其分布的记录，不能由平均 TPOT 恢复。

## 常用指标如何对应同一条时间线

指标的完整身份是“起点、终点、观察边界、人口、计数单位、聚合与窗口”，名称只是简写。将一次尝试的外部计划记为 p、依赖与时间都就绪记为 r、实际发送记为 s；本章原来的 t₀=s。准入发生在另一个阶段，记为 a；客户端内容仍记为 u₁…u_N，协议结束为 t_F。这些符号分别映射到[到达过程](arrival-and-concurrency.md)的 pᵢ、rᵢ、sᵢ、aᵢ，不能把相邻章节中同名的 a 自动当成同一事件。只有完成时钟映射后，才可作跨观察端差值。

| 指标或目标 | 明确的样本量或公式 | 人口、边界与常见误读 |
|---|---|---|
| 客户端 TTFT | u₁−s | 发出到首个有效内容；不是纯 prefill、排队或模型首 token 时间 |
| 相对计划的首内容等待 | u₁−p=(r−p)+(s−r)+(u₁−s) | 包含依赖与迟发；独立开放计划常有 r=p。将其与客户端 TTFT 同名汇总会掩盖发生在哪里的改善 |
| 相对就绪的首内容等待 | u₁−r | 去掉尚不能发送的依赖时间，保留生成器与服务路径；不能把依赖等待归咎于生成器 CPU |
| 最后内容延迟 | u_N−s | 最后一个有效内容可见；不自动包含协议尾部和应用提交 |
| 协议/应用 E2E | t_F−s / t_C−s | 必须注明选哪一个终点；最后内容、FINAL、最终解析或用户提交可以分离 |
| ITL、TPOT | uᵢ−uᵢ₋₁；(u_N−u₁)/(N−1) | 仅对声明边界下的实际逐 token 观测成立；N=1 无间隔，chunk-only 不补造 token 时间 |
| 每请求生成速率 | (N−1)/(u_N−u₁) | 只在 N>1 且分母为正时定义。它是同请求 TPOT 的倒数，不是多请求吞吐；先平均速率和先平均 TPOT 再取倒数也不同 |
| 请求完成吞吐 | 所选窗口/人口中正常 FINAL 数 ÷ 声明历时 | offered、实际发送、准入、全部终止和成功完成是不同计数；错误或拒绝响应很快，不代表成功服务吞吐提高 |
| 输出 token 吞吐 | 所选人口的输出 token 数 ÷ 声明历时 | 先声明按内容发生窗口、完成窗口还是到达 cohort 计数。前者可以包含失败前已交付内容；后两者可以把整条输出归入完成或到达人口 |
| 输入 token 供给率 | 所选 offered 请求的完整规范 prompt token 数 ÷ 到达窗长度 | 包括命中缓存和随后被拒绝的输入，是工作负载描述；不能冒充设备实际执行的 prefill 位置率 |
| 实际工作率 | 对指定资源实际执行的位置、候选或操作数 ÷ 相同资源计时 | 计算量口径；明确是否含重放、投机拒绝项、padding、转换与失败工作。位置数仍不等于 FLOPs |
| 合格完成率 goodput | 同一请求成功、输出、质量与联合时延条件的交集数 ÷ 声明历时 | 需要完整 offered 账和资格覆盖，不能只筛快请求；每 GPU 归一化还须固定 GPU 数、资源份额与任务形态 |
| SLI 与 SLO | SLI 是所选指标/资格比例；SLO 为其阈值和要求覆盖的人口 | “TTFT≤阈值”和“至少ρ的 offered 请求同时合格”是两层条件。SLO 本身不是另一个有统一公式的延迟数 |

当 N>1 且逐 token 端点可用时，严格有

`u_N−s = TTFT_client+(N−1)TPOT`；

`L_protocol = TTFT_client+(N−1)TPOT+(t_F−u_N)`。

因此将“E2E−TTFT”除以 N−1，只有 E2E 终点确为最后内容，或协议尾部差值为零时，才恢复本章 TPOT。现有轨迹的 token 时间为 10、20、30 ms、FINAL 为 45 ms、发送为 0：TPOT=10 ms，而协议 E2E 代入得到 (45−10)/2=17.5 ms。多出的 7.5 ms 来自把 15 ms 协议尾部平均进两个间隔。改变尾部 flush 或日志结束方式会改变后者，即使生成节奏完全未变。

窗口吞吐也须保留三个不同分子。对内容发生窗 W=[w₀,w₁)，令 M_emit 为窗内实际交付的有效内容 token 数；对完成窗，令 F_W 为 FINAL 落窗的请求集合，M_final=Σ_{i∈F_W}Nᵢ；对到达 cohort C，令 F_{C,H} 为 C 中服务截止 H 前完成者，M_cohort=Σ_{i∈F_{C,H}}Nᵢ。三者分别除以自己声明的窗口或历时；输出跨窗口、失败或未完成时通常不同。按最终文本重新分词不能自动产生窗内 token 时间，只有 chunk 粒度时也只能把整块内容计入相应 chunk 的观察时刻。

对缓存与投机至少并列三本计数账：业务输入/输出、模型逻辑推进、资源实际工作。完整 prompt 为 P、命中缓存为 C，不代表本次实际工作总是 P−C：末行输出缺失、抢占重放、不同层恢复和失败都可能增加计算。投机的 draft 候选、target 验证位置和最终对外内容分别计数，不能把被拒绝候选算成用户输出。比较不同形状时还须按实际矩阵几何、可见 key 和 dtype 重算 FLOPs、字节与资源，而不是只换一个 token/s 分母。

准入也有两个合法人口。`actual_service_admission_decisions` 数服务器确实作出的接受决定；它服务于尝试流量与物理工作审计。[到达过程](arrival-and-concurrency.md)中的决定账会保留取消之后才发生的接受。`effective_business_admitted` 则数业务仍有效时取得的合法接受；本章 CohortReport 和[Goodput](slo-goodput.md)采用这一本账。请求先取消、后被远端接受时，前者可以加一，后者保持零，并保留清理责任。两者不能共享一个无说明的 admitted 字段。原 CohortReport 按实际发送 t₀纳入人口；采用计划 p 的开放负载 cohort 时须明确换纳入键，不能直接复制其 offered 数。

## Token、传输 chunk 与日志分组

需要区分三种对象。

| 对象 | 时间含义 | 可以恢复的指标 |
|---|---|---|
| 逐 token 内容事件 | 同一观察边界下每个 token 的实际时间 | TTFT、精确观测 ITL、TPOT |
| 传输 chunk 事件 | 这一整块在所选边界被接收或解析的时间 | 首内容 chunk、chunk 间隔、输出量；多 token 块不能恢复其内部生成节奏 |
| token 轨迹的日志分组 | 多条已有独立时间戳的 token 事件被一起存储 | 原有 token 时间；日志分组不应改变指标 |

设内容 chunk `k` 的时间为 `τ_k`，包含 `m_k` 个规范输出 token。对相邻内容 chunk，可以定义响应级估计 `h_k=(τ_k-τ_(k-1))/m_k`，`k≥2`。它给每个后续响应一个数；直接对这些数平均，与按 `m_k` 加权平均又是不同总体。它不是把一个真实大间隔拆成已经观测到的多个小间隔。

当所有 token 在同一个 chunk 到达时，首末 chunk 端点相减为零。这可以描述该 chunk 的可见突发，但不能证明模型生成间隔或独立逐 token 交付间隔为零。可以另报明确命名的 chunk 投影统计；本章算法对只有多 token chunk 的记录不输出精确 TPOT。若每个内容 chunk 恰好一个 token，其时间可以作为该客户端边界的 token 观测时间。

日志分组具有另一种契约。例如 `{t=20, token_times=[10,20]}` 可以表示两条客户端 token 事件被合并导出，`t` 表示分组结束，必须等于最后一条 token 时间。它不能同时声称“这是在 20 一次性到达的网络块，而其中一个 token 已在 10 被客户端收到”。两种记录需要不同类型，不能靠字段名字猜测。

若分组标成 `t=10`，却携带 `[10,20]`，其结束字段与内容矛盾；若又把缺失的协议结束默认为 10，还会产生早于最后内容的假终态。合法记录应保存分组结束 20 和独立的协议终态。不能删除结束顺序校验，也不能用取最大值来伪造完成事件。

计数还需要稳定的 tokenizer、模板、特殊 token、停止与过滤规则。分别对每段字符串重新分词，其 token 数之和不一定等于最终字符串的 token 数，因为分词可能跨段合并。优先保留正式提交的 token 身份与范围；若只能事后对最终文本计数，就要说明它怎样映射回内容事件，无法稳定映射时不声称精确 token 时间。模型生成量、usage 计数与用户可见内容量可以并列，不能静默互换。

## 协议边界与合法状态推进

固定 ASGI 规范允许服务器等到第一次 Response Body 才将 Response Start 数据刷新到发送缓冲。Response Body 的成功 send 返回要求本次数据已进入服务器发送缓冲，并不确认远端应用已经消费。发送失败还可能早于应用收到断开通知。

因此至少分开记录准备发送、发送缓冲接受、客户端收到并解析。ASGI 的响应体结束还受 `more_body` 和是否等待 trailers 影响；应用的业务结束、HTTP 响应结束与设备最后访问不是同一个事件。

下面的算法处理已经选定观察边界的一次请求。输入顺序来自该观察者的稳定序号，不能先按时间排序，把一条本来发生在终态后的内容偷偷移到终态前。跨观察者事件先保留为偏序诊断，不能混入此串行归约。

```pseudocode
算法 BuildRequestMetrics(raw_events, request, attempt, boundary, mode)
输入：有限事件流；mode 为 TOKEN 或 CHUNK
输出：请求指标、终态、部分观测及诊断；或明确拒绝原因

初始化 seen=空映射，expected_seq=0，state=UNSENT
初始化 send=空，end=空，cursor=0，content_times=空，content_sizes=空
foreign_attempt_events=空

for 原始事件 e，保持观察者顺序：
    检查请求身份
    若 e.attempt 不等于所选 attempt：保留到诊断集合；continue
    若 e.id 已存在：
        若完整事件与已有事件相同：continue
        否则拒绝身份冲突
    登记 e.id
    检查时间有限、单位和时间域匹配 boundary
    要求 e.seq==expected_seq；expected_seq 加一
    要求时间相对前一条已接受事件非递减

    若 state==UNSENT：
        要求 e 为 SEND；记录 send；state=OPEN；continue
    要求 state==OPEN，否则拒绝所选内容流中的终态后事件

    若 e 为已声明的非内容元数据：continue
    若 e 为 CONTENT：
        要求整数范围 [start,stop)，start==cursor，stop>start
        若 mode==TOKEN：要求 stop-start==1
        记录 e.time 和 stop-start；cursor=stop
    否则若 e 为 FINAL、CANCEL、TIMEOUT 或 ERROR：
        end=e.time；state=e.type
    否则拒绝未知事件类型

要求存在 SEND
N=cursor
TTFT=首个内容时间-send，若 N==0 则未定义
协议完成延迟=end-send，仅当 state==FINAL
终止观察时间=end-send，仅当存在终态，并同时保留终止原因
若 state==OPEN：保持未完成，不从最后内容推断 end

exact_available=(mode==TOKEN 或每个内容范围都只有一个 token)
若 N>1 且 exact_available：
    ITL=相邻内容时间差
    TPOT=(最后内容时间-首个内容时间)/(N-1)
否则：
    ITL、TPOT 未定义，保留 no_content、no_interval 或 chunk_only 原因

对非 FINAL 的内容记录，明确标为部分观测
返回全部状态、覆盖信息和指标
```

正常内容流结束后的设备完成、清理、日志上报或迟到网络通知仍可发生，应进入相应诊断流。上述拒绝针对“它们被错误归为同一内容流中的新内容或第二个终态”，并不是要求真实系统在取消后不再产生任何内部事件。

这个归约器只判断客户端内容流：没有准入埋点也可以记录取消、超时或协议 FINAL。把协议 FINAL 进一步计为完整服务账中的正常完成，需要关联合法准入；客户端单独收到结束标记不证明这个前提已经核验。计算队列等待还需要同一服务端时间域的准入、就绪和执行边界。

## 从缓冲到取消与重试的一条轨迹

以下全部时间为设定的毫秒，不是服务实测。模型在 5、15、25 产生三个 token，内容适配层合并后在 26 交给发送缓冲，客户端在 30 收到一个三 token chunk，在 45 收到协议结束，在 50 完成应用提交。另在 2 收到的空角色事件不算内容。

客户端 TTFT 为 30 ms，协议延迟为 45 ms，应用总时间为 50 ms；模型侧平均间隔为 10 ms。客户端只有一条多 token chunk，不能用其零端点差声称精确 TPOT 为零。模型时间也不能填入客户端逐 token 字段。

若另一候选逐个交付，并实际观察到客户端内容时间为 10、20、30，TTFT 降到 10 ms，客户端 TPOT 为 10 ms；若协议仍在 45 结束，则协议完成延迟不变。这说明首内容改善与完成改善可以分离。改变刷新策略后需要重新核对实际到达时间，不能从模型生成时间直接推算网络收益。

再考虑客户端在 35 取消旧尝试，36 发出新尝试，新尝试在 41 收到首内容、46 正常结束。旧尝试在 40 出现的迟到回调携带旧代次，只进入旧尝试诊断；新尝试 TTFT 为 5 ms，而不是误用旧回调得到的 4 ms。若从最初逻辑请求发出计时，重试总时间还要包含先前等待和取消；必须单独命名，不能拿每尝试 TTFT 替代。

取消前已经交付的内容是历史事实，可以保留部分 TTFT 和间隔。它不使旧尝试成为正常完成，也不允许从客户端取消时间推断设备资源已经可复用。

## 聚合、分位数与窗口账务

对请求 `r`，令 `n_r=N_r-1` 是有定义的精确间隔数，`m_r` 是其 TPOT。每请求宏平均为 `M_macro=Σm_r/R'`；合并间隔平均为 `M_pooled=Σn_r m_r/Σn_r`。`R'` 是纳入该总体的请求数。两者分别给请求和间隔等权。

设三条完整 token 轨迹为 `[10,20]`、`[10,20,...,110]`、`[10,40]`。每请求 TPOT 是 10、10、30 ms，宏平均为 `50/3` ms；共有 12 个间隔，总间隔时间 140 ms，合并平均为 `35/3` ms。互换这两个数会改变问题，而不是修复测量噪声。

nearest-rank 分位数对 `m>0` 个值排序，取第 `ceil(pm)` 个，`0<p≤1`。独立核对可以使用经验分布条件：结果 `q` 必须是观测值，且 `count(x<q)/m < p ≤ count(x≤q)/m`。插值分位数是另一合法定义，需要单独声明。每请求 TPOT 的 p99、全局 ITL 的 p99 和每请求 p99 再平均不能替代。空分位数总体返回未定义；少量请求或相关 token 不足以支持很精确的总体尾部结论。

聚合首先声明纳入哪些状态。本章的完整请求延迟与 TPOT 总体使用正常完成的所选请求；取消、失败和开放请求的部分内容另报，并保留完整 offered 账。只报告完整请求延迟会有完成选择效应，不能将它解释为全部 offered 请求的延迟分布。

到达队列采用 `[W0,W1)`，排空观察截止为 `D≥W1`。发出时间落在到达窗内的请求组成 cohort，所有状态按截止 `D` 观察，等于 `D` 的事件计入。以下账务假设已关联同一请求及尝试的完整准入与终止记录，并已把时间转换到可比较的边界。没有采集准入事件与确实尚无准入决定是不同情况；若日志覆盖不足，先报告覆盖未知，不能凭字段缺失把实际已准入请求认定为准入前终止。

请求记录中的 `decision=(a,accepted)` 表示决定发生的时间和结果，`terminal=(z,reason)` 表示所选业务边界上的显式终止。两者都不能早于发出。正常完成 `FINAL` 必须具有 `accepted=true` 且 `a≤z` 的决定。取消、超时和错误则可以发生在准入前，无需为了记账伪造一个拒绝决定。

在尚未决定时，取消、超时或错误会使请求进入吸收态 `pre_cancel`、`pre_timeout` 或 `pre_error`。此后才作出的接受或拒绝决定保留为 `late_decision` 诊断，不复活请求，也不把它改记为 admitted、rejected 或 pending。这里的“迟到”指决定发生在终止之后；若只是日志晚到、但可靠发生时间早于终止，应补齐证据后产生带身份的新报表修订，不能静默改写已经发布的截止账。

同一记录若决定与终止时间相等，本章按“决定先、终止后”解释：接受后取消计为准入后取消；拒绝后收到取消通知仍计 rejected。若真实系统需要相反顺序，应记录额外顺序或线性化证据并调整规则；时间戳相等本身不能证明哪一个先发生。拒绝之后的非正常终止通知可作为诊断保留，不形成第二个 offered 请求或第二次关账。

```pseudocode
算法 CohortReport(records, W0, W1, D)
输入：身份已去重、覆盖完整的请求账；W0<W1，D>=W1
输出：截止状态计数、联合合格数、迟到决定诊断和明确分母的率

初始化所有计数为零；seen_request_ids=空
for 每个请求 r：
    拒绝重复请求身份
    读取发出时间 o、可选决定 (a,accepted)、可选终止 (z,reason)
    检查数值、决定结果和终止原因；要求存在的 a、z 均不早于 o
    若 reason==FINAL：要求存在 accepted=true 且 a<=z 的决定
    若 o 不在 [W0,W1)：continue
    offered 加一

    若存在非 FINAL 终止，z<=D，且无决定或 z<a：
        preterminated 加一；pre_reason 加一
        若存在决定且 a<=D：late_decision 加一
        continue

    若无决定，或 a>D：pending 加一；continue
    若 accepted=false：rejected 加一；continue
    admitted 加一
    若无终止，或 z>D：incomplete 加一；continue
    finished 加一；按 final、cancel、timeout、error 分别计数
    仅当 FINAL 且 success、quality、joint_SLO 全部为真：good 加一

检查 offered==pending+rejected+preterminated+admitted
检查 preterminated==pre_cancel+pre_timeout+pre_error
检查 admitted==finished+incomplete
检查 finished==final+cancel+timeout+error
检查 late_decision<=preterminated

goodput_cohort_elapsed=good/(D-W0)
offered_rate=offered/(W1-W0)
qualified_fraction=good/offered，offered==0 时未定义
返回计数与覆盖；late_decision 是诊断子计数，不再加入 offered 分区
```

例如请求 `x` 在 0 发出，没有准入决定，在 2 取消；到达窗 `[0,10)`、截止 10 时，独立期望账为 `offered=1, preterminated=1, pre_cancel=1`，其余状态计数均为零。它已经终止，不能计 pending。把取消换成超时，同理进入 `pre_timeout`。若它在 5 才得到接受决定，截止 4 时仍是 `pre_cancel` 且 `late_decision=0`，截止 10 时为 `pre_cancel` 且 `late_decision=1`；两个截止都不能把它变成一次获接收但未完成的请求。

相反，没有合法准入却声称在 2 正常完成，或准入发生在正常完成之后，都应拒绝进入这份完整业务账。客户端事件归约仍可保留原始协议结束用于调查，但不能据此生成合格完成。这个区别使请求观测和业务资格可以衔接，而不混淆各自需要的证据。

正常完成也不等于质量或 SLO 合格。单 token 请求是否豁免 ITL 条件、空输出是否允许、质量尚未评定如何处理，都必须由评测策略事先定义；缺少判定不能默认为合格。

设定 10 s 到达窗内发出 100 个请求，拒绝 10，准入 90，截止 10 s 正常完成 80，另有 10 未完成；其中 72 同时满足成功、质量和全部时延条件。此时合格完成率为 7.2 请求/s，合格比例为 offered 的 72%、admitted 的 80%。`72/80=90%` 是完成者中的合格比例，不是 goodput。若继续排空到 12 s 并得到 81 个合格结果，本章历时口径为 `81/12=6.75` 请求/s；除以原到达窗得到的 8.1 是另一种 cohort 归一化量，不能沿用同一标签。若发生准入前终止，还需在 offered 分区中单列，不能继续套用只有拒绝和准入的二分账。

固定完成窗口则允许早先到达、当前完成的请求进入计数，回答的是另一问题。GenAI-Perf 固定文档描述的窗口完成统计，不能被自动当成这里的到达 cohort 口径。

联合 SLO 必须统计同一请求的条件交集。TTFT 与 ITL 各有 95% 合格，交集在最坏情况下可以只有 90%。超时、拒绝和残留请求不能通过只保留快请求来消失。空 cohort 的计数率可以合法为零；没有样本的均值、分位数和比例则未定义。

## 一份事件表怎样同时产生延迟、吞吐与覆盖

下面全部为合成毫秒，共用一个说明性时钟，不是设备或服务实测。评测人口为 p∈[0,100) 的八个独立计划，服务观察截止 H=160；本例实际发送也都在到达窗内，所以计划 cohort 与发送 cohort 恰好同集。若迟发越过 100，两者就不再相同。r=p，token 数使用固定规范身份；表中“块3”只给三个 token 的一次 chunk 观察，没有逐 token 时间。

| 请求 | p / s | 准入决定 | 客户端有效内容时刻 | 业务终止 | 最终输出质量证据 |
|---|---|---|---|---|---|
| A | 0 / 0 | 1 接受 | 10、20、30 | 45 FINAL | 180 得到通过标签 |
| B | 10 / 30 | 31 接受 | 40、50、60 | 65 FINAL | 75 通过 |
| C | 20 / 20 | 21 接受 | 50：块3 | 55 FINAL | 70 通过 |
| D | 30 / 30 | 35 拒绝 | 无 | 拒绝已关业务账 | 不适用 |
| E | 40 / 40 | 41 接受 | 60 | 100 TIMEOUT | 不适用 |
| F | 50 / 50 | 51 接受 | 70、80、90 | 到 H 未完成；之后170才FINAL | 到证据截止仍待判 |
| G | 60 / 60 | 90 才接受 | 无 | 80 CANCEL | 不适用 |
| H | 70 / 70 | 71 接受 | 100 | 110 FINAL | 120 通过 |

A 的 TTFT 为 10、TPOT 为 10、最后内容延迟为 30、协议延迟为 45。B 的客户端 TTFT 同为 10，相对计划首内容等待却为 30，其中生成器迟发为 20；把首内容时刻减计划当作同名客户端 TTFT，会改变这个比较。H 的 TTFT 为 30，没有后续间隔。C 的 TTFT 为 30，精确 TPOT 未定义；它不能按单个 chunk 的零端点差报告 TPOT=0。

H=160 时，八个计划分成拒绝 D、准入前终止 G、有效准入 A/B/C/E/F/H。六个有效准入中正常完成四个、超时一个、未完成一个。服务器实际接受决定为七次，因为 G 的接受确实发生过；它不能使 G 回到有效业务人口。F 在 170 的未来 FINAL 不属于这个固定服务截止，不能因为后来取得日志就静默加进旧报表。

三个输出吞吐口径分别为：

- [0,100) 内内容发生数为 13：A/B/C 各3，E为1，F为3；H在100的一个token不在半开窗口。内容发生吞吐为 130 token/s，包含后来超时和未完成请求已经交付的内容。
- [0,100) 内正常完成 A/B/C，共3请求、9输出token，完成窗请求吞吐为30请求/s，完成输出吞吐为90 token/s。
- 八个计划中到 H 完成 A/B/C/H，共4请求、10输出token；cohort历时口径分别为4/0.160=25请求/s、10/0.160=62.5 token/s。

三个值的差异不表示某个归约器算错。它们回答不同人口与时间范围的问题，报告必须并列名称和原始计数。A/B 的完整精确 TPOT 均为10；C缺逐token证据，H单token豁免间隔。因此正常完成者有4个，适合定义TPOT的多token完成者有3个，其中精确可观测2个；覆盖应报2/3，同时保留单token数量，不能只输出一个无覆盖信息的“平均TPOT=10”。

若 A…H 的规范输入长度依次为100、200、300、400、500、600、700、800，则 offered 输入量3600，计划输入供给率为36000 token/s。本例另有独立资源记录：A复用80位置、C复用200位置；实际prefill工作位置分别为20、200、100、0、500、600、0、800，总计2220。D拒绝、G终止后虽有迟到接受却未执行，E/F执行过的工作也不能从资源账删去。若资源观察范围为[0,160]，对应位置率为2220/0.160=13875位置/s；这仍不是FLOP/s，也不表示每个位置代价相同。

再独立记录24个draft候选、30个target验证位置和到H实际交付的14个内容token，三者都可能为真。将候选数加入13个窗内用户输出，或把3600个offered输入充当2220个真实prefill工作，都会人为提高“有效吞吐”。只取得客户端事件时，本来就没有足够证据恢复这些资源计数。

这份表可以成为实际实验的事前观测合同：先冻结人口、长度/停止、窗口、质量与SLO，再采集相应事件。在低负载区分模型计算与发送/flush，在开放负载扫描时同时检查p/r/s和积压；故意降低生成器配额时，若只有s−r变大而发送后路径未变，应先归因于供给不足。固定内容只改变协议尾部时，TPOT应保持、协议E2E可以变化。改变缓存或投机时，业务量保持可比而资源工作变化，才有机会区分“省计算”与“改变了计数”。这些干预需要真实目标实验，合成表只检验观测和归约逻辑。

## 服务截止与事后质量证据怎样分别结算

服务事件时间和评价器知道结果的时间有不同责任。设 H 固定服务窗口或排空观察截止，J≥H 为本次报告允许使用的证据截止。离线质量评价返回一个绑定请求、最终输出版本和评价规则的标签；标签在J之前可用，不代表其产生时刻是客户端完成时刻。对已在H前完成的输出，事后标签可以在新报表修订中更新资格证据，不能把H改为J、把质量评定耗时加入原服务E2E，或改写原有服务事件。

若产品本身要求在线质量审核后才交付，审核就是服务依赖，必须把对应最终交付事件作为完成边界，并计入其计算、排队、通信与驻留。两种设计都合法；需要解释在线/离线评价在用户路径中的位置，不能为获得有利数字临时切换。

对固定cohort与H，先保留正常完成且输出与时延仍可能合格的对象。已知合格数记g，仍可合格但缺质量标签或缺必要时延观测者记u，确定不合格者记b。未在H前正常完成的对象对这个固定“截止完成”指标不进入u；较晚完成可以进入另一个显式延长H的报表。于是这一批有限对象的最终合格数满足[g,g+u]，合格完成率在[g/(H−W₀),(g+u)/(H−W₀)]，qualified fraction在[g/O,(g+u)/O]。这是缺证据造成的确定性范围，不是总体概率的置信区间，不能靠bootstrap替代。已有一项确定失败时，即使另项未知，也不能把该请求再列作潜在合格。

给上表预先选定一个合同：客户端TTFT≤35 ms、精确TPOT≤15 ms，单token豁免后续间隔，非空输出且质量通过。J=160时，B/H已证合格，A等待质量，C缺精确TPOT；g=2、u=2，所以goodput证据范围为[12.5,25]请求/s。J=200时A的质量标签到达，g=3、u=1，范围收窄为[18.75,25]请求/s；其中已证合格输出为A/B/H的7个token，token goodput下界为43.75 token/s。H始终是160，F在170完成也不会追加入这个服务截止。

J变大并没有证明服务变快，它只改善了证据覆盖。C的区间仍无法从块3恢复；需要明确另一种chunk SLO，或在新的可比试验中取得更细的真实事件，不能将缺失TPOT补成零。延迟“已知合格”低于目标时，先区分真实失败与证据不足；若下界已超过目标可支持本批条件判定，若上界仍低于目标则本批不满足，跨越目标则继续补证或报告未区分。总体SLO概率和迁移到新负载的结论，还需要独立重复与统计不确定性，不能由这八条轨迹推出。

```pseudocode
算法 SettlePerformanceEvidence(service_snapshot, H, certificates_asof_J, policy)
固定service_snapshot的人口、截止H、计时边界和内容事实，不以J重算服务历时
逐个对象核对证书的请求、输出版本、评价规则及证据发生时间
仅对H前已正常完成者计算输出与时延条件
任何已知条件失败：记确定不合格
全部条件均已知通过：记已证合格，累计其输出量
没有确定失败但仍缺必要证据：记潜在合格，并列出缺失原因
发布g、u、b、g至g+u的范围、metric覆盖、H与J及证据身份
J推进后另存新修订；原服务快照与旧证据截止报表保持可复核
```

证据归约可以重用原事件账，不需要为每个指标额外同步GPU。已排序E条内容事件与R条请求记录可作O(E+R)扫描，质量证书按身份关联；持有原始事件和未决对象延长日志、索引与证据存储，离线评价另有CPU/GPU与费用。只有真正进入服务依赖的评价才改变服务关键路径；观测器或评价器的成本须按选定实验范围另列，不能既把它们移出分子，又声称整条交付代价已经覆盖。

## 时钟区间如何限制解释

同一客户端的发出与接收差值不需要服务器时钟同步；拆解跨机单向阶段则需要偏移界限。设同一物理时刻满足 `t_B=t_A+δ`，且 `δ∈[δ_lo,δ_hi]`。A 发出读数为 `a`，B 接收读数为 `b`，则

`T∈[b-a-δ_hi, b-a-δ_lo]∩[0,+∞)`。

非负约束来自已经确认的发送先于接收。若交集为空，身份关联、边界或校准至少有一项不相容，不能把负上界改成零。

例如 `a=10`、`b=15` ms，偏移在 `[-2,4]` ms，只能得到 `[1,7]` ms；偏移在 `[4,8]` ms，则得到 `[0,1]` ms。图上的 5 ms 点差不能支持相差 1 ms 的单向优化结论。校准后漂移和采样误差需要继续扩大界限；trace ID 只关联操作，不提供时钟校准。

## 条件化成本与采集粒度

事件采集与指标计算也会改变被观察系统。成本需要对同一候选、同一负载和同一观察边界列账。

| 成本 | 可推导的量及条件 |
|---|---|
| 计算 | 已有序的事件校验和状态推进为 `O(E)`；无序离线归并一般需要 `O(E log E)`。TPOT 的端点与计数可以流式维护，额外状态为常数；保留全部 ITL 才需要随输出增长。精确排序分位数为 `O(M log M)`，其中 `M` 是声明的统计总体大小 |
| 访存 | 逐 token 记录读写 `O(N)` 个时间与身份字段；chunk 记录为 `O(C)`。字符串保存、重分词、哈希、索引和导出副本另计，逻辑时间戳字节不等于实际对象或缓存事务 |
| 通信 | 上报原始事件的字节约为事件数乘记录大小，另有批头、协议和压缩成本。批量上报降低调用次数，但延迟发现；上报时间不能冒充事件发生时间 |
| 准备 | 固定 tokenizer、模板、内容过滤、事件 schema、代次映射、时钟校准和聚合定义。版本变化可能改变内容范围，准备不能从冷启动比较中静默删去 |
| 同步 | 在内容 flush、设备等待或窗口关闭处新增同步，可能打断重叠或改变队列。诊断采集条件与正常路径性能分别报告 |
| 驻留 | 原始 trace、去重集合、活跃请求账和未完成内容占用容量。在线去重需要明确保留期限；提前忘记身份可能把迟到重复再次计入 |

设定 10,000 请求、每个 100 token，仅用 8 字节整数保存 token 时间，原始时间字段为 8,000,000 B，约 7.63 MiB；每请求 20 个 chunk 时对应 1,600,000 B。身份、对象头、内容和索引不包含在这些数中。

窗口账在已关联的 `R` 个请求上为 `O(R)` 扫描，计数状态为常数；身份去重集合为 `O(R)`。等待补齐准入记录、保留准入前终止及其迟到决定，会延长账本驻留。若提前删除终止记录，就可能把迟到接受误认为新准入。业务终止记录的保留与设备物理资源的排空是两种责任，不能用同一个计数替代。

chunk 大小还形成直接可算的取舍。设每请求输出 `N` 个 token，固定生成间隔 `Δ`，每块合并 `k` 个 token，单次封包和事件处理消耗 `c` 个 CPU 时间单位，则调用成本约为 `c·ceil(N/k)`；忽略其他等待时，首块相对逐 token 交付多等待 `(min(k,N)-1)Δ`。

例如 `N=100`、`Δ=10 ms`、`c=0.05 ms CPU`，`k=1` 需要 100 次调用、5 ms CPU；`k=5` 需要 20 次、1 ms CPU，但首次交付增加 40 ms 收集等待。这是设定模型，不意味着所有 CPU 时间都会串入该请求延迟。按请求率 `λ`、有效核数 `p`，仅这一工作项就有必要条件 `λc·ceil(N/k)<p`，单位须统一为 CPU 秒；它不足以保证尾部 SLO。

若首内容只剩 20 ms 可用等待预算，在该固定间隔模型中，`k=5` 不满足目标；更大的块虽然省调用，却不再是可行候选。若网络或主机已饱和，较小块引起额外排队，收益又可能反转，需要实际事件与资源证据。

## 成本与能量使用同一有效输出分母

单位有效输出成本为所选资源边界内总成本除以合格输出数，单位能量同理。分子包含这段范围内的失败、重算、预热、排空和空闲保留；分母为零时单位指标未定义。

整机、设备和主机计量域分别报告，不能将有包含关系的能量域简单相加。扣除空闲基线得到的是增量能量，不能替代总能量。并发请求间的分摊是归因规则，不自动成为逐请求物理测量。

例如同一窗口内 A 用 1000 J 完成 100 个合格任务，为 10 J/任务；B 用 800 J 完成 50 个，为 16 J/任务。总能量下降而有效单位能量上升。若 B 还缩短输出、降低图像分辨率或裁掉音频，其任务身份也改变了，不能仅凭 tokens/s 或平均功率认定改善。完整讨论见[服务成本与能耗](cost-and-energy.md)。

## 非文本任务的完成与连续供给

| 任务 | 可交付事件 | 必须一起保存的任务条件 |
|---|---|---|
| 会话与工具流程 | 必要依赖完成且最终回答可用 | 中间失败、重试、会话质量与总时间；多个请求完成不能替代会话成功 |
| Embedding | 规定的全部向量可消费 | 输入条数、维度、归一化、数值及检索质量 |
| 检索与 reranking | 规定候选和过滤下的排序结果可用 | top-k、索引与候选版本、召回或排序质量 |
| 图像 | 完整图像或明确标识的预览可用 | 分辨率、生成步数、内容与质量 |
| 语音识别 | 首个稳定文本与最终转录分别可用 | 修订规则、音频窗口和错误率 |
| 语音与视频生成 | 首个可播放包、连续供给及完整输出 | sample offset 或帧顺序、实际时长、间隙、质量和打断行为 |

对音频，codec token 数不能直接充当播放时长。设 `B` 为尚未播放的音频秒数，固定播放速率为每秒消耗一秒音频；包 `j` 在 `a_j` 到达，新增不重叠、可播放的时长为 `d_j`。从上一事件 `t` 推进到 `a_j` 时：

`underrun += max(0, a_j-t-B)`；

`B = max(0, B-(a_j-t)) + d_j`。

播放开始前到达的包先累入缓冲；播放后按上式推进，最后还要推进到明确观察终点 `H`。不定义终点就无法判断最后一包之后的断供。此模型假设欠载期间播放暂停，无丢弃和时间伸缩；真实客户端若补静音或追赶播放，需要换成相应状态方程。

例如播放从 0 开始，0 到达 0.2 s 音频，0.3 s 再到达 0.2 s，观察到 0.5 s，则欠载为 0.1 s。若首包改成 0.4 s，其他条件相同，则无欠载，但更大的首包是否需要更长生成等待仍要另计。重复 sample 范围或 overlap 不能再次计入新增 `d_j`。

对未压缩 PCM，播放时长 `d` 秒、采样率 `f` 样本/秒、声道数 `c`、每声道每样本 `b` 字节时，要求 `df` 为整数，原始负载为 `dfcb` 字节，容器头与传输封装另计。24 kHz、单声道、16-bit PCM 的 200 ms 有 4800 个样本、9600 B，400 ms 缓冲为 19200 B。codec token 数依赖编码规则，不能替代此式中的字节；压缩改变传输负载，不消除数据代表的播放时间。视频同样需要可解码帧、顺序与播放时间，而不只是服务器帧完成数。

## 条件变化与区分实验

| 当前观察与竞争解释 | 应保留或调整的内容 | 区分实验与反证后的修正 |
|---|---|---|
| 模型首 token 提前，客户端 TTFT 不变：执行改善、过滤、缓冲或网络等待 | 保留模型、发送缓冲和客户端三类边界 | 固定内容与到达负载，逐层记录；只有模型事件提前时，继续定位内容与传输等待，不能直接声称用户路径改善 |
| 平均 TPOT 不变而停顿增加：突发交付、尾部执行或聚合变化 | 保留原始间隔和统计总体 | 固定长度，对比逐 token 与 chunk 记录；精确间隔不变而响应级估计变化，先修正观测口径；精确间隔也变化再查执行和资源竞争 |
| 输出长度分布改变：长输出权重或真实变慢 | 保留宏平均、合并平均和各自覆盖 | 对同一批间隔重算，再按长度分层；权重解释足够时，不归因为系统抖动 |
| 吞吐上升而 goodput 下降：拒绝、任务缩短或联合条件退化 | 保留 offered、全部状态、质量与联合 SLO | 固定任务和窗口逐请求核对；合格数仍下降时放弃以吞吐提升代表目标改善 |
| 无准入决定却出现取消：真正准入前终止、准入日志缺失或关联错误 | 保留原始终止、准入覆盖和两种事件时间 | 在完整合成账中先取消后接受，检查状态不复活；生产中补查请求代次与准入覆盖，证据不足时报告未知而非确定的准入前状态 |
| 截止推进后 admitted 增加：正常准入或终止后的迟到决定被误用 | 保留多个截止的状态快照和吸收态 | 固定终止时间，只移动决定到终止前、同刻、之后；只有终止前或约定的同刻接受可计入 admitted，终止后的接受只能增加诊断子计数 |
| 单 token 或单 chunk 多 token 报零 TPOT：无间隔、观测不足或真实同时事件 | 保留粒度和未定义原因 | 分别注入单 token、只有 chunk 的多 token、真实同刻逐 token；前两类不输出精确 TPOT，最后一类允许零间隔 |
| 跨机差值变化落在校准范围内：链路变化或时钟变化 | 保留偏移、漂移和客户端本地时间 | 对所有可行偏移求区间；区间无法区分时报告未区分，不能挑选有利点估计 |
| 重试后 TTFT 变好：恢复更快或旧代次污染 | 保留逻辑请求与每尝试两层身份 | 注入旧内容和冲突重复；过滤后恢复说明身份关联问题；逻辑请求总时间仍需包含先前尝试 |
| 首音很早但播放卡顿：首包改善或后续断供 | 改用可播放时间、连续 sample offset 和缓冲轨迹 | 固定最终音频与质量，改变包间隙和初始缓冲；平均速率充足仍欠载时，放弃仅用平均实时率解释体验 |
| 详细 trace 下尾延迟恶化：服务本身变慢或采集扰动 | 保留正常路径与采集条件 | 固定负载扫描采集粒度；只有详细采集恶化时，调整记录与上报方式，再在正常条件验证 |

负对照必须实际进入相应判据。PCM 检查让正确换算与“直接返回输入中的 codec token 数作为字节数”的故障变体消费相同输入，再把实际输出交给同一个独立字节参考。改变采样率、声道和样本表示时，正确 PCM 字节随这些条件变化；codec 数冒充字节的变体不具备此关系。仅比较两个预先写好的不同常数，不能证明已经检测了这个换算错误。

输出字段篡改也能检查参考判据是否敏感，例如均值冒充 p99、开放请求伪造完成或宏平均与合并平均互换；这种证据应称为判据敏感性，不能声称执行了对应故障算法。实验反驳预测后，先修改解释和模型适用范围，再决定继续优化哪一阶段。

## 检查与证据范围

配套文件为 `tools/check_k_work_001_full.py`，只用 Python 标准库，确定性、离线、只读。它以端点算法对照相邻差分求和，以经验分布条件核对分位数，以手工窗口账和独立事件回放核对截止状态，以可行偏移枚举核对时钟区间，以离散播放步骤核对音频递推。

窗口检查保留明确的准入前取消期望账，覆盖准入前超时与错误、终止之后的接受和拒绝、截止前后变化及同刻事件规则；同时拒绝无合法准入的正常完成。独立回放从 pending 出发，按决定和终止事件逐步推进，与正文按时间条件分类的实现形成不同计算路径。删除准入前终止的故障输入变换会产生错误 pending，接受迟到决定的故障变换会产生错误 admitted，均交给原期望账检出。

PCM 参考按固定样本格式打包静音帧，并使用独立给定、与时长及采样率核对过的帧数构造原始字节串，取其长度。正确换算与 codec 数冒充字节的变体使用同一组时长、采样率、声道、样本表示和 codec 计数输入。检查同时打印两种输出和参考字节，不把常数不等计作换算故障。

其他检查覆盖空输出、单 token、同刻 token、chunk 粒度、日志分组不变性、重复身份、旧尝试、终态缺失及非法顺序。分组 `t=10` 却包含 token 时间 `[10,20]` 仍是应拒绝输入；合法回归将分组结束设为 20，并显式给出 FINAL 20，保留结束不早于最后内容的校验。

执行记录必须绑定实际脚本与正文；历史脚本通过、对应语言模型通过和本轮 Python 文件通过是三种不同证据。本轮作者执行范围与待执行入口在交付说明中分别记录，不以未执行的 Python 结果宣称完成检查。

新增 `tools/check_evaluation_metrics.py` 将八请求表与逐请求端点、有理数手算账、资源侧位置身份枚举及未决资格的有限赋值枚举核对。它覆盖实际发送/计划起点、协议尾部与TPOT、三种吞吐人口、半开内容窗口、迟到接受的两本账、质量证据截止、空与单token及chunk-only的未定义值，并让错误算法分支消费同一输入。例如协议终点代替内容终点、发出起点改成计划、chunk补造token时间、未知资格算通过或失败、把offered输入当真实工作和将draft候选并入输出，都交给相同参考判据。这些是有限合成检查的覆盖定义，实际是否通过由绑定脚本和输入的执行记录承担；不执行真实tokenizer、服务、网络、负载生成器、GPU或质量评价器，也不证明总体SLO概率。

这些检查不测 GPU、真实服务、网络、时钟校准、音频设备、采集覆盖或 Agent 使用效果。真实 tokenizer 的增量映射、丢失事件、多观察者合并、时钟漂移、生产尾延迟和硬件资源状态仍需各自的实现与实验验证。
