## 常用指标如何对应同一条时间线

指标的完整身份是“起点、终点、观察边界、人口、计数单位、聚合与窗口”，名称只是简写。将一次尝试的外部计划记为 p、依赖与时间都就绪记为 r、实际发送记为 s；本章原来的 t₀=s。准入发生在另一个阶段，记为 a；客户端内容仍记为 u₁…u_N，协议结束为 t_F。这些符号分别映射到[到达过程](arrival-and-concurrency.md)的 pᵢ、rᵢ、sᵢ、aᵢ，不能把相邻章节中同名的 a 自动当成同一事件。只有完成时钟映射后，才可作跨观察端差值。

| 指标或目标 | 明确的样本量或公式 | 人口、边界与常见误读 |
|---|---|---|
| 客户端 TTFT | u₁−s | 发出到首个有效内容；不是纯 prefill、排队或模型首 token 时间 |
| 相对计划的首内容等待 | u₁−p=(r−p)+(s−r)+(u₁−s) | 包含依赖与迟发；独立开放计划常有 r=p。将其与客户端 TTFT 同名汇总会掩盖发生在哪里的改善 |
| 相对就绪的首内容等待 | u₁−r | 去掉尚不能发送的依赖时间，保留生成器与服务路径；不能把依赖等待归咎于生成器 CPU |
| 最后内容延迟 | u_N−s | 最后一个有效内容可见；不自动包含协议尾部和应用提交 |
| 协议/应用 E2E | t_F−s / t_C−s | 必须注明选哪一个终点；最后内容、FINAL、最终解析或用户提交可以分离 |
| ITL、TPOT | uᵢ−uᵢ₋₁；(u_N−u₁)/(N−1) | 仅对声明边界下的实际逐 token 观测成立；N=1 无间隔，chunk-only 不补造 token 时间 |
| 每请求生成速率 | (N−1)/(u_N−u₁) | 只在 N>1 且分母为正时定义。它是同请求 TPOT 的倒数，不是多请求吞吐；先平均速率和先平均 TPOT 再取倒数也不同 |
| 请求完成吞吐 | 所选窗口/人口中正常 FINAL 数 ÷ 声明历时 | offered、实际发送、准入、全部终止和成功完成是不同计数；错误或拒绝响应很快，不代表成功服务吞吐提高 |
| 输出 token 吞吐 | 所选人口的输出 token 数 ÷ 声明历时 | 先声明按内容发生窗口、完成窗口还是到达 cohort 计数。前者可以包含失败前已交付内容；后两者可以把整条输出归入完成或到达人口 |
| 输入 token 供给率 | 所选 offered 请求的完整规范 prompt token 数 ÷ 到达窗长度 | 包括命中缓存和随后被拒绝的输入，是工作负载描述；不能冒充设备实际执行的 prefill 位置率 |
| 实际工作率 | 对指定资源实际执行的位置、候选或操作数 ÷ 相同资源计时 | 计算量口径；明确是否含重放、投机拒绝项、padding、转换与失败工作。位置数仍不等于 FLOPs |
| 合格完成率 goodput | 同一请求成功、输出、质量与联合时延条件的交集数 ÷ 声明历时 | 需要完整 offered 账和资格覆盖，不能只筛快请求；每 GPU 归一化还须固定 GPU 数、资源份额与任务形态 |
| SLI 与 SLO | SLI 是所选指标/资格比例；SLO 为其阈值和要求覆盖的人口 | “TTFT≤阈值”和“至少ρ的 offered 请求同时合格”是两层条件。SLO 本身不是另一个有统一公式的延迟数 |

当 N>1 且逐 token 端点可用时，严格有

`u_N−s = TTFT_client+(N−1)TPOT`；

`L_protocol = TTFT_client+(N−1)TPOT+(t_F−u_N)`。

因此将“E2E−TTFT”除以 N−1，只有 E2E 终点确为最后内容，或协议尾部差值为零时，才恢复本章 TPOT。现有轨迹的 token 时间为 10、20、30 ms、FINAL 为 45 ms、发送为 0：TPOT=10 ms，而协议 E2E 代入得到 (45−10)/2=17.5 ms。多出的 7.5 ms 来自把 15 ms 协议尾部平均进两个间隔。改变尾部 flush 或日志结束方式会改变后者，即使生成节奏完全未变。

窗口吞吐也须保留三个不同分子。对内容发生窗 W=[w₀,w₁)，令 M_emit 为窗内实际交付的有效内容 token 数；对完成窗，令 F_W 为 FINAL 落窗的请求集合，M_final=Σ_{i∈F_W}Nᵢ；对到达 cohort C，令 F_{C,H} 为 C 中服务截止 H 前完成者，M_cohort=Σ_{i∈F_{C,H}}Nᵢ。三者分别除以自己声明的窗口或历时；输出跨窗口、失败或未完成时通常不同。按最终文本重新分词不能自动产生窗内 token 时间，只有 chunk 粒度时也只能把整块内容计入相应 chunk 的观察时刻。

对缓存与投机至少并列三本计数账：业务输入/输出、模型逻辑推进、资源实际工作。完整 prompt 为 P、命中缓存为 C，不代表本次实际工作总是 P−C：末行输出缺失、抢占重放、不同层恢复和失败都可能增加计算。投机的 draft 候选、target 验证位置和最终对外内容分别计数，不能把被拒绝候选算成用户输出。比较不同形状时还须按实际矩阵几何、可见 key 和 dtype 重算 FLOPs、字节与资源，而不是只换一个 token/s 分母。

准入也有两个合法人口。`actual_service_admission_decisions` 数服务器确实作出的接受决定；它服务于尝试流量与物理工作审计。[到达过程](arrival-and-concurrency.md)中的决定账会保留取消之后才发生的接受。`effective_business_admitted` 则数业务仍有效时取得的合法接受；本章 CohortReport 和[Goodput](slo-goodput.md)采用这一本账。请求先取消、后被远端接受时，前者可以加一，后者保持零，并保留清理责任。两者不能共享一个无说明的 admitted 字段。原 CohortReport 按实际发送 t₀纳入人口；采用计划 p 的开放负载 cohort 时须明确换纳入键，不能直接复制其 offered 数。

## 一份事件表怎样同时产生延迟、吞吐与覆盖

下面全部为合成毫秒，共用一个说明性时钟，不是设备或服务实测。评测人口为 p∈[0,100) 的八个独立计划，服务观察截止 H=160；本例实际发送也都在到达窗内，所以计划 cohort 与发送 cohort 恰好同集。若迟发越过 100，两者就不再相同。r=p，token 数使用固定规范身份；表中“块3”只给三个 token 的一次 chunk 观察，没有逐 token 时间。

| 请求 | p / s | 准入决定 | 客户端有效内容时刻 | 业务终止 | 最终输出质量证据 |
|---|---|---|---|---|---|
| A | 0 / 0 | 1 接受 | 10、20、30 | 45 FINAL | 180 得到通过标签 |
| B | 10 / 30 | 31 接受 | 40、50、60 | 65 FINAL | 75 通过 |
| C | 20 / 20 | 21 接受 | 50：块3 | 55 FINAL | 70 通过 |
| D | 30 / 30 | 35 拒绝 | 无 | 拒绝已关业务账 | 不适用 |
| E | 40 / 40 | 41 接受 | 60 | 100 TIMEOUT | 不适用 |
| F | 50 / 50 | 51 接受 | 70、80、90 | 到 H 未完成；之后170才FINAL | 到证据截止仍待判 |
| G | 60 / 60 | 90 才接受 | 无 | 80 CANCEL | 不适用 |
| H | 70 / 70 | 71 接受 | 100 | 110 FINAL | 120 通过 |

A 的 TTFT 为 10、TPOT 为 10、最后内容延迟为 30、协议延迟为 45。B 的客户端 TTFT 同为 10，相对计划首内容等待却为 30，其中生成器迟发为 20；把首内容时刻减计划当作同名客户端 TTFT，会改变这个比较。H 的 TTFT 为 30，没有后续间隔。C 的 TTFT 为 30，精确 TPOT 未定义；它不能按单个 chunk 的零端点差报告 TPOT=0。

H=160 时，八个计划分成拒绝 D、准入前终止 G、有效准入 A/B/C/E/F/H。六个有效准入中正常完成四个、超时一个、未完成一个。服务器实际接受决定为七次，因为 G 的接受确实发生过；它不能使 G 回到有效业务人口。F 在 170 的未来 FINAL 不属于这个固定服务截止，不能因为后来取得日志就静默加进旧报表。

三个输出吞吐口径分别为：

- [0,100) 内内容发生数为 13：A/B/C 各3，E为1，F为3；H在100的一个token不在半开窗口。内容发生吞吐为 130 token/s，包含后来超时和未完成请求已经交付的内容。
- [0,100) 内正常完成 A/B/C，共3请求、9输出token，完成窗请求吞吐为30请求/s，完成输出吞吐为90 token/s。
- 八个计划中到 H 完成 A/B/C/H，共4请求、10输出token；cohort历时口径分别为4/0.160=25请求/s、10/0.160=62.5 token/s。

三个值的差异不表示某个归约器算错。它们回答不同人口与时间范围的问题，报告必须并列名称和原始计数。A/B 的完整精确 TPOT 均为10；C缺逐token证据，H单token豁免间隔。因此正常完成者有4个，适合定义TPOT的多token完成者有3个，其中精确可观测2个；覆盖应报2/3，同时保留单token数量，不能只输出一个无覆盖信息的“平均TPOT=10”。

若 A…H 的规范输入长度依次为100、200、300、400、500、600、700、800，则 offered 输入量3600，计划输入供给率为36000 token/s。本例另有独立资源记录：A复用80位置、C复用200位置；实际prefill工作位置分别为20、200、100、0、500、600、0、800，总计2220。D拒绝、G终止后虽有迟到接受却未执行，E/F执行过的工作也不能从资源账删去。若资源观察范围为[0,160]，对应位置率为2220/0.160=13875位置/s；这仍不是FLOP/s，也不表示每个位置代价相同。

再独立记录24个draft候选、30个target验证位置和到H实际交付的14个内容token，三者都可能为真。将候选数加入13个窗内用户输出，或把3600个offered输入充当2220个真实prefill工作，都会人为提高“有效吞吐”。只取得客户端事件时，本来就没有足够证据恢复这些资源计数。

这份表可以成为实际实验的事前观测合同：先冻结人口、长度/停止、窗口、质量与SLO，再采集相应事件。在低负载区分模型计算与发送/flush，在开放负载扫描时同时检查p/r/s和积压；故意降低生成器配额时，若只有s−r变大而发送后路径未变，应先归因于供给不足。固定内容只改变协议尾部时，TPOT应保持、协议E2E可以变化。改变缓存或投机时，业务量保持可比而资源工作变化，才有机会区分“省计算”与“改变了计数”。这些干预需要真实目标实验，合成表只检验观测和归约逻辑。

## 服务截止与事后质量证据怎样分别结算

服务事件时间和评价器知道结果的时间有不同责任。设 H 固定服务窗口或排空观察截止，J≥H 为本次报告允许使用的证据截止。离线质量评价返回一个绑定请求、最终输出版本和评价规则的标签；标签在J之前可用，不代表其产生时刻是客户端完成时刻。对已在H前完成的输出，事后标签可以在新报表修订中更新资格证据，不能把H改为J、把质量评定耗时加入原服务E2E，或改写原有服务事件。

若产品本身要求在线质量审核后才交付，审核就是服务依赖，必须把对应最终交付事件作为完成边界，并计入其计算、排队、通信与驻留。两种设计都合法；需要解释在线/离线评价在用户路径中的位置，不能为获得有利数字临时切换。

对固定cohort与H，先保留正常完成且输出与时延仍可能合格的对象。已知合格数记g，仍可合格但缺质量标签或缺必要时延观测者记u，确定不合格者记b。未在H前正常完成的对象对这个固定“截止完成”指标不进入u；较晚完成可以进入另一个显式延长H的报表。于是这一批有限对象的最终合格数满足[g,g+u]，合格完成率在[g/(H−W₀),(g+u)/(H−W₀)]，qualified fraction在[g/O,(g+u)/O]。这是缺证据造成的确定性范围，不是总体概率的置信区间，不能靠bootstrap替代。已有一项确定失败时，即使另项未知，也不能把该请求再列作潜在合格。

给上表预先选定一个合同：客户端TTFT≤35 ms、精确TPOT≤15 ms，单token豁免后续间隔，非空输出且质量通过。J=160时，B/H已证合格，A等待质量，C缺精确TPOT；g=2、u=2，所以goodput证据范围为[12.5,25]请求/s。J=200时A的质量标签到达，g=3、u=1，范围收窄为[18.75,25]请求/s；其中已证合格输出为A/B/H的7个token，token goodput下界为43.75 token/s。H始终是160，F在170完成也不会追加入这个服务截止。

J变大并没有证明服务变快，它只改善了证据覆盖。C的区间仍无法从块3恢复；需要明确另一种chunk SLO，或在新的可比试验中取得更细的真实事件，不能将缺失TPOT补成零。延迟“已知合格”低于目标时，先区分真实失败与证据不足；若下界已超过目标可支持本批条件判定，若上界仍低于目标则本批不满足，跨越目标则继续补证或报告未区分。总体SLO概率和迁移到新负载的结论，还需要独立重复与统计不确定性，不能由这八条轨迹推出。

```pseudocode
算法 SettlePerformanceEvidence(service_snapshot, H, certificates_asof_J, policy)
固定service_snapshot的人口、截止H、计时边界和内容事实，不以J重算服务历时
逐个对象核对证书的请求、输出版本、评价规则及证据发生时间
仅对H前已正常完成者计算输出与时延条件
任何已知条件失败：记确定不合格
全部条件均已知通过：记已证合格，累计其输出量
没有确定失败但仍缺必要证据：记潜在合格，并列出缺失原因
发布g、u、b、g至g+u的范围、metric覆盖、H与J及证据身份
J推进后另存新修订；原服务快照与旧证据截止报表保持可复核
```

证据归约可以重用原事件账，不需要为每个指标额外同步GPU。已排序E条内容事件与R条请求记录可作O(E+R)扫描，质量证书按身份关联；持有原始事件和未决对象延长日志、索引与证据存储，离线评价另有CPU/GPU与费用。只有真正进入服务依赖的评价才改变服务关键路径；观测器或评价器的成本须按选定实验范围另列，不能既把它们移出分子，又声称整条交付代价已经覆盖。
