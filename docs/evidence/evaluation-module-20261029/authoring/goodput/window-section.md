## 窗口账与可复算的资格归约

本章选用到达 cohort：外部到达 aᵢ∈[0,T) 的请求进入分母，服务事件观察截止 H≥T，截止时刻发生的服务事件计入。质量证据另按可用截止 J≥H 选择，H与J分别冻结。它们须在可比较的报告时间域中表达；质量机的原始时钟不能直接拿来与客户端时延相减。令 O、A、N、V 分别为 offered、有效业务 admitted、H前正常完成和已证合格完成数。在资格证据完整且无冲突时，

G＝V/H，单位为请求/s；token goodput＝Σᵢ nᵢ1(Cᵢ)/H。

若仍有潜在合格但缺必要证据的u个请求，V/H只作已证下界，上界为(V+u)/H；尚未在H前正常完成的请求对这个固定“截止完成”问题不能因为J较晚就进入u。存在输出/证书身份冲突或同一固定规则的矛盾证书时，保留业务计数和冲突，但本轮资格归约为UNRESOLVED，不发布一个伪装完整的goodput或资格区间。有限对象的缺证据范围不是总体SLO概率置信区间。

token goodput偏重长输出，是另一个目标。V/O为offered合格比例，V/A为有效准入合格比例，V/N只是正常完成者中的合格比例。分母为零时比例未定义；空cohort的计数率仍可为零。固定完成窗口允许以前到达、当前完成的请求进入，是另一种人口；不能与这里的cohort数字混用。服务器取消后实际作出的接受决定属于物理责任账，不增加这里的有效A。

有限窗口中恒有G＝(O/T)(V/O)(T/H)，前提是O>0且V所需资格已结算；采用已证下界时也只能将右侧解释为同一下界。只有H=T，或长期稳定且首尾影响可忽略时，才能直接用offered到达率乘offered合格比例解释G。设10 s到达窗有100个请求，服务截止10 s得到72个合格结果，G为7.2请求/s；若明确延长服务观察到12 s得到81个合格结果，历时口径为6.75请求/s。81/10＝8.1是按原到达窗归一化的cohort产出，必须另标名称。仅把质量证据截止J从10改成12而不延长H，不能采用这个新分母，也不能加入10后才完成的请求。

账本不能只有accepted/completed两列。准入决定尚未到达时可能发生取消、超时或输入失败；准入之后也可能正常完成、失败、取消或超时。截止H的守恒分区为：

O＝准入待决＋拒绝＋准入前终止＋A；

A＝业务进行中＋N＋准入后失败/取消/超时；

N＝质量通过＋质量失败＋质量待判＋质量冲突。

最后一式在固定输出与评价规则、证据截止J下核算，前两式只由H服务快照决定。质量通过者仍须与Lᵢ、Uᵢ求交才能进入V。准入前已终止，之后才收到接受决定的请求，保留迟到决定计数和清理责任，不能追溯改成有效准入。业务进行中、质量待判和质量冲突不能静默丢弃；“截至H未正常完成”与“已完成但尚缺证据”不同。

对一个输出定义完整不可变描述Oᵢ：请求/尝试身份、输出版本、完整内容身份、有效范围或token数、停止规则及生产侧完整就绪事实。下文以SEAL表示这个事实成立，不要求系统实现一个同名API。SEAL不能由“这是日志里最后一条内容”或shape相同推出来。生产侧可以先完整就绪并评质，客户端仍在缓冲；例如SEAL25、质量证据28、客户端最后内容30、协议FINAL45并不矛盾。指标仍使用客户端内容时刻，质量绑定该生产侧完整Oᵢ。完整描述的证据若晚到，可以在J视图补证已经属于H前结果的身份；它的可用时间与所证明的生产就绪事实分别保留，不能用J中新产生的另一个输出替换H快照。

证书c包含请求/尝试、Oᵢ、评价规则及其版本、证据身份、判定与证据可用时刻。选择固定规则后，重复的同身份同载荷证书幂等；身份载荷不同，或同一输出与固定规则出现FAIL和PASS，进入CONFLICT而非最后写者获胜。不同规则的结论保留为不同视图，不能覆盖本合同。若评价器产生随机原始评分，先由明确的采样/聚合规则形成证书；原始评分不同不自动构成确定证书逻辑冲突，后来一个PASS也不自动修订既有FAIL。

```pseudocode
算法 CohortGoodput(service_events, quality_evidence, T, H, J, policy)
输入：完整到达身份、服务事件、完整输出描述、质量证据及固定资格合同
输出：H业务快照、J证据状态、已证/潜在资格或UNRESOLVED、计数与历时

要求T>0、H>=T、J>=H；固定cohort键与TTFT起点，它们不必相同
对每个a属于[0,T)的唯一请求/尝试：
    state←准入待决；content←空；output_descriptor←未知
    仅取发生时间<=H的服务事件，核对身份与字段并按稳定因果顺序推进
    同刻服务事件采用：准入决定、整数位置序的内容、SEAL、业务终止
    相同事件身份同载荷幂等；冲突身份或不可能转移使业务快照不可审计
    准入决定：
        不相同的重复决定报冲突
        若已准入前终止：只增加真实决定/迟到决定账与清理责任，不复活业务
        否则从待决转入拒绝或业务进行中
    内容：要求业务仍进行中，所选观察边界、位置与请求身份正确
    SEAL：核对并保存完整不可变输出描述；不将生产就绪当客户端已经看见
        不能改写同一输出版本的内容身份；有矛盾描述则报冲突
    业务终止：
        待决只允许准入前取消、超时或失败
        进行中转为正常完成或准入后失败/取消/超时；已有终态不被后续证据覆盖
    冻结state、内容事实、输出合同、TTFT/TPOT可观测性与业务完成时刻

另按证据可用时刻<=J收集证书；早期到达的证书不要求当时已经FINAL
按请求/尝试、完整输出、固定规则与证据身份归一：
    相同身份同载荷去重；身份载荷或固定规则判定冲突记CONFLICT
    尚无完整输出绑定事实：保留待绑定证据，质量为UNKNOWN，不能直接置PASS
    绑定有效且规则相符：保存PASS或FAIL；其他规则保持独立视图
    不把证据时刻改写成服务完成、内容可见或资源排空时刻

对H快照的每个请求：
    若没有H前正常完成：保持原业务分区；证书只留作诊断，不增加正常完成或资格
    若已正常完成：在J视图中计入PASS/FAIL/UNKNOWN/CONFLICT之一
    Q、L、U有一项确定FAIL：不合格；没有确定失败但缺必要证据：潜在合格
    全部已证PASS且正常完成：V加一，累计其合法输出数
    资格相关证据冲突：整份资格结算标记UNRESOLVED，保留原始业务计数与冲突
核对三条守恒式；无冲突时给V/H及潜在资格范围，完整时给确定合格率
J推进时另存新报表修订，复用同一个H快照；H改变则另立服务观察版本
```

此算法把服务状态推进和证据归一分成两个责任域，因此质量早到、晚到都不会改变业务终态。在线取J=H是一个明确的特殊观察契约：截至H没得到证书就保持待判，不表示该输出质量失败。离线评价常用J>H；它可以补齐H前完整结果的标签，不能把J内发生的未来FINAL算到H里。若用户交付本身等待审核，应另选审核后交付事件作为业务完成边界并计其真实成本。

与[服务指标](metric-events.md)的可执行衔接是：请求事件归约提供内容与终态事实，CohortGoodput的第一阶段提供不可变H业务快照；按Oᵢ/规则归一的证书视图进入SettlePerformanceEvidence，返回PASS、FAIL、UNKNOWN或CONFLICT及原因，再由这里的最后阶段计数。旧CohortReport中的good仅接受显式已证真资格；未知仍在待决清单和上界中，冲突阻止确定结算，不能把UNKNOWN强转成False后称最终失败，也不能重复运行一遍“最后标签覆盖”的质量分支。

例如SEAL30、证书35、FINAL45、H=60、J=60：证书在35时可以挂起，45后完成资格，G=1/(60 ms)=50/3请求/s，不必伪造一个45后的证书时刻。SEAL25、证书28、客户端末内容30同样合法。相同输出/规则先FAIL35、后PASS40时，即使FINAL45正常，也保持证据冲突；不能得到一个合格完成。若证书改在80到达，H=60、J=100可以补齐同一H前输出的标签，G分母仍是60；若FINAL改为70，H=60、J=100仍是未完成，证书不能使它进入V。

同刻排序在时间相同且类型相同后才比较该类型的载荷，因此没有混合类型之间的隐式比较。参考检查将决定和证书判定限定为布尔值，位置限定为非负整数，终态限定为normal、cancel、timeout、failed；先验证，再形成全为整数的排序键。证书按自己的证据域归一，不靠与FINAL的同刻类型优先级建立资格。枚举序只使冲突处理确定，不能让冲突事件变成合法事件。

例如一个请求在0获准，位置0…10的11个内容事件都记为1，完整描述在1可得，随后在2正常结束、3质量通过。数值位置序为0、1、2…10，合同下得到1个合格请求、11个合格token。字符串序为0、1、10、2…9，会在期待位置2时读到位置10，错误报告非法内容。检查必须让这条合法轨迹与不排序事件的端点参考一致，并让字符串排序负对照被检出。

这里的同刻服务类型顺序是一种明确合同：同刻接受再取消属于准入后取消；真正较早发生的取消属于准入前取消。实际协议若提供更细因果序号，应使用它，不能靠日志行顺序猜测。冲突、缺失必要字段或不可能转移使本次统计不可审计，不能通过删除该请求改善结果。设备晚完成与网络清理另记，不能再次触发业务成功。相关事件边界见[服务指标](metric-events.md)。

逻辑任务重试还需保留task_id与attempt_id。资源需求按所有尝试累计；业务任务goodput只在规定提交点成功一次。将失败尝试删去，或将两个成功重试都计成两个有效任务，都会改变定义。若offered单位选为尝试，应在整个账本和比例中保持该单位，另报逻辑任务结果。
