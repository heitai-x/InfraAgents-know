## 来源支持的机制与定义

CUDA stream 表达设备工作的顺序，event 可以在不同执行队列间建立完成依赖。host 调用返回、设备工作开始和设备完成属于不同事件。

固定归档是完整编程指南，本来源说明的异步主题包括§2.5的异步操作模型、§7.26的barrier、§7.27的异步复制和§7.28的多级pipeline。这里“异步”描述发出线程与执行完成的关系，不保证另一项计算一定在同时进行。

§7.26.1–7.26.4区分CTA同步与拆开的arrive/wait：参与者在arrive之前的写入，经对应阶段的wait完成后对约定作用域的参与者可见；arrive本身不会等待其他线程。barrier初始化必须先于参与，每阶段的预期到达次数、实际参与者和阶段票据须一致。一个warp完成不自动等于整个CTA都不再访问某缓冲。

§7.27.4说明复制完成之前，修改其全局源或读写共享目标会造成竞态；等候必须覆盖复制操作。§7.27.6.1说明CC 8.0所述硬件复制指令支持4/8/16字节粒度及相应对齐，错误的显式对齐证明会导致未定义行为。128字节对齐是该API的性能建议，不能把它混同于所有4字节复制的合法性条件。

§7.27.6.3–7.27.6.6还区分warp实际批次序列与线程感知序列。分歧commit可能使一次线程等待覆盖比预想更多的批次；commit与arrive-on应按文档要求的参与/收敛关系组织。只数源程序中的“第几次wait”不能证明其覆盖的真实批次正确。

§7.28.1–7.28.2用单级与多级pipeline区分“避免寄存器中转”与“隐藏复制延迟”：发出复制后立即等待可以得到正确结果，却没有由此形成计算与复制的重叠。多级组织还需启动预取、稳态消费与最后一批排空，并在消费者释放阶段后才允许生产者复用；零批次应直接处理，没有可等待的最后票据。

## InfraAgents 如何据此推导

本库据此解释负的“设备开始减 API 结束”、双缓冲时序、传输源的生命周期以及可真正隐藏的 host 工作。

[GPU流水章节](../hardware/gpu-kernel-pipelines.md)据此独立构造一个双warp的SIMT GEMM与带代次输入槽。逻辑协议把复制完成、CTA可见性和两个warp最后读取分开；实际实现可以用不同同步对象承担这些依赖，但应逐项证明覆盖，不能把伪代码中的抽象票据当成已经选择正确CUDA API。

该章节的L/I/C递推和6KiB容量案例是本库2026-10-27的假设算例，不是指南报告的某设备时间或容量。指南的架构规格由独立的[能力来源说明](S-CUDA-CAPABILITY.md)承担；不同CC的线程、共享存储与矩阵指令支持不应用一个8.x标签概括。

## 适用边界

机制与接口说明；不构成当前目标的性能或可达性证明。 原始版本、日期依据与归档范围见本地 provenance.json；版本日期不证明模型训练实际包含该资料。

有限事件模型可以发现遗漏等候、提前复用或代次混淆，不能证明编译后指令、真实GPU的内存作用域、物理重叠或性能。跨CTA、跨stream、host/device之间使用相同概念时，同步对象和作用域必须分别核实。
