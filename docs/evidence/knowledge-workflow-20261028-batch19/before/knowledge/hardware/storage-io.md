# K-HW-012：存储 I/O：请求粒度、队列和加载流水

SSD 带宽是某种访问模式下的能力，推理实际获得的是经过文件布局、页缓存、块层排队、主存缓冲、布局转换和设备传输后的供给速度。存储设计既要回答每段搬运多少字节，也要回答哪些范围已经完整、哪个消费者可以读取，以及哪个完成事件允许复用缓冲。加载速度改善只有发生在实际关键路径上，才会转化为启动或在线推理收益。

## 文件范围、张量布局与完成对象

把一次加载对象记为 O=(a,t,g)，其中 a 是固定制品版本，t 是逻辑张量及其表示合同，g 是本次加载尝试。源段必须携带文件内容身份 f、文件偏移 o、长度 l 和所覆盖的逻辑范围；目的缓冲携带物理槽及其 lease 代次 z。相同路径不证明文件内容相同，相同地址也不证明仍是同一次分配。

一次读取可记为 X=(a,t,f,g,z,o,l,dest,request_id)。其中 [o,o+l) 是半开字节区间，dest 是该范围对应的目的位置。接收完成时先匹配身份，再解释成功字节和错误状态；不能先去掉文件或代次，再把所有偏移合成一个区间。

合法性包括：范围属于固定制品和文件内容版本；偏移、长度、目标容量及大小运算合法；对齐与所用 I/O 路径相容；源表示能够转换成消费者要求的表示；目的槽没有仍在访问它的旧操作；发布前全部必需范围完整且可见。空载荷只使字节覆盖条件立即成立，不会自动补齐缺失的张量描述、版本或目标视图。

| 状态或事件 | 已经成立 | 尚不能推断 |
|---|---|---|
| RESERVED | 本代容量和槽已取得 | 源字节已到达 |
| SUBMITTED | 操作已被接受，存在实际在途责任 | 请求已完整完成 |
| PARTIAL | 部分必需字节已有成功完成证据 | 整个对象可发布 |
| HOST_READY | 主机必需源范围齐备，相关写者结束，错误已处理 | 转换、H2D 或消费已结束 |
| CONVERTED | 目标表示已经形成 | 设备消费者已经可读 |
| DEVICE_READY | 必需设备写入结束且消费依赖成立 | 最后消费者已经读完 |
| CONSUMED | 已授权消费者的最后访问结束 | 写出数据已经持久化 |
| FAILED / CANCELLED | 本代未来业务授权已关闭 | 已接受的 I/O、DMA 或 kernel 已结束 |
| RETIRED | 未来授权已关闭，全部实际访问责任结束，槽已归还 | 其他对象也已完成 |
| ISOLATED | 无法取得足够完成证据，保护责任已移交明确拥有者 | 可以复用或销毁受保护存储 |

文件范围不是张量布局。权重可能按 shard、tensor 或目标设备保存，执行器却按层、专家或 tile 消费。连续读取可以减少提交次数，但文件中的连续字节未必就是目标内核需要的排列。

对于未打包的行主序张量，设源 shape 为 s，目标轴排列 p 是一个置换，目标 shape 为 u_k=s_(p_k)。目标坐标 q 对应源坐标 c，关系为 c_(p_k)=q_k。定义 L_s(c)=Σ_i c_i∏_(j>i)s_j，目标同理为 L_u(q)。源逻辑字节位置为 e_s L_s(c)，目标地址为 base+e_d L_u(q)，e_s、e_d 分别为源和目标元素字节数。若张量跨文件保存，还要按源逻辑位置查找所属段，再加该段文件内偏移，不能把逻辑线性位置直接当成任意 shard 的文件偏移。

例如，源为 2×3 的 int32 张量，两行分别为 [0,1,2] 和 [3,4,5]，两行各存于一个文件的 offset=0。转置后的 3×2 行主序结果应为 [0,3,1,4,2,5]。目标 q=(1,0) 读取第一文件 offset=4，q=(1,1) 读取第二文件 offset=4；这两个相同偏移属于不同文件，不能互相补齐。该例只说明轴排列，不涵盖量化组、scale、字节序或 QKV 分段。

[ServerlessLLM](../sources/S-SERVERLESSLLM.md) §4.1 给出一种预先整理布局的方案：每个 GPU 的参数二进制数据分组到独立文件，索引记录 tensor.name、GPU id、offset 和 size，运行时以 base+offset 恢复视图，并通过初始化同步再交付模型。它减少运行时逐张量反序列化，但离线转换、额外制品、布局失效和分发仍有成本；目标并行计划或执行表示改变后，必须重新检查这些产物。

## 页缓存、mmap 与直接 I/O

缓冲读取利用页缓存。热缓存可能减少实际存储事务，读取到应用缓冲、校验和转换仍有成本。mmap 建立文件范围的虚拟映射，映射成功不代表页已驻留，也不代表首次访问不会缺页等待。多个进程可以共享只读文件页，转换后的私有目标却可能各持一份副本。

直接 I/O 绕过页缓存，便于应用管理块池与并发，但仍受文件系统、对齐和具体路径约束。[Linux 6.12 iomap 文档](../sources/S-LINUX-IO.md)说明：直接读前会刷新相关脏页缓存；直接写前刷新，写前后进行相应页缓存失效。排队返回、已经传输的部分字节、失败和回退到缓冲路径具有不同含义。直接 I/O 不自动等于异步，也不自动等于 SSD 向 GPU 直接 DMA。

这些语义属于所归档的 iomap 接口，不能把内核内部返回值原样当作任意用户态读取 API 的合同。应用适配层应把实际接口结果规范化到每个操作：明确未接受、接受后仍在途、已经同步终结，或接受情况未知。同步终结还应包含成功范围与错误；明确未接受则不会另有该操作的完成。批量提交可以同时包含这些结果，整个调用的一个失败码不足以撤销全部责任。

频繁复用且缓存容量足够时，缓存路径可能更便宜；单遍大制品、缓存污染严重或需要精确控制驻留时，可以比较直接 I/O 和有界块池。比较必须固定对象与有效字节，分别观察冷缓存、热缓存、实际存储字节、CPU 时间和主存峰值。热 mmap 的访问速度不能记成 SSD 带宽；直接 I/O 的时间也不能只按设备传输估算。

## 请求粒度、在途数与排队

设请求有效载荷为 b 字节，完成率为 I 次/s，有效数据率为 Ib。实际读取 b_read 可能大于 b，例如合并相邻范围时读取了中间空隙，或为了对齐扩大了范围。还应分别记录块层物理事务字节、主存复制字节和 H2D 字节，不能把它们全部称为模型大小。

小请求可能先达到 IOPS、CPU 提交或元数据处理上限；大请求可摊薄固定成本，却增加首块等待、过读、尾块浪费和驻留。一个条件化的服务模型是 S(b_read)=S0+b_read/B_eff，其中 S0 是所声明服务边界内的固定开销，B_eff 是相同访问与并发条件下的有效速率。另记排队 W，提交到完成的驻留时间为 R=W+S。三者必须使用相同请求人群和边界。

对目标有效数据率 X、每请求有效字节 b，请求率为 λ=X/b。Little 关系给出平均在途数 E[N]=λE[R]。如果系统仅允许 n 个在途请求，而同一条件下的平均驻留时间为 R，则 X≤nb/R；反推所需整数槽数时向上取整。它是均值容量关系，不是尾延迟或不丢请求的保证；增加深度也会改变 R，不能把一个深度下的时间无限外推。

设定 X=4 GiB/s、R=1 ms、b=1 MiB，则 λ=4096 次/s，平均在途数为 4.096，至少考虑 5 个槽。4 槽的均值供给上限为 3.90625 GiB/s。这里的 1 ms 是设定的提交到完成时间，不是 SSD 实测服务时间。

队列稳定性需要另用不含排队的服务需求。对单服务者，ρ=λE[S]<1 是常用稳定条件；不能把已经含 W 的 R 再代入该利用率。对于泊松到达、独立同分布服务、单服务者 FIFO 且二阶矩有限的 M/G/1 模型，W_q=λE[S²]/(2(1−ρ))。它解释为何相同服务均值、不同方差会产生不同等待；现代 SSD 的多通道、批处理及相关请求不必符合这个模型，不能直接据此承诺 p99。

预算应同时限制请求数和在途字节。远期权重预取、临近消费的 KV、媒体读取和多个模型冷启动可能争用同一 SSD、DRAM 或 PCIe 上游。deadline、预期重用收益与公平性可以参与选序，但它们是方案选择；增加读取线程或队列深度不产生额外物理带宽。

## 乱序、短读与范围拼接

应用所需的是各身份域内的覆盖，不是完成通知的数量。对固定键 K=(a,t,f,g,z)，设必需范围集合为 R_K，已成功交付到正确目标位置的范围集合为 D_K，则字节覆盖条件为 ∪R_K⊆∪D_K。它还需与错误处理、所有相关写者结束及可见性条件共同成立，才能推进消费者。重复完成不增加覆盖，也不能重复减少责任计数。

范围合并只接受二元区间 (start,end)。带身份的完成记录必须先按 K 筛选，再投影为二元区间。把 (generation,start,end) 三元记录直接传给二元区间合并器属于输入形状错误，不能靠默默丢弃身份字段让它通过。

```pseudocode
算法 Covers(required, completed)
输入：同一身份域内的二元半开区间列表，端点为合法非负字节位置
输出：是否覆盖全部必需字节；非法区间则拒绝

分别检查两列表的每项恰有两个端点，且 start<=end
分别按 start、end 排序，丢弃零长区间
扫描合并相交或端点相接的区间，得到 R 和 D
j=0
for R 中每个 [a,b)：
    while j<长度(D) 且 D[j].end<=a：j 增一
    若 j 越界，或 D[j].start>a，或 D[j].end<b：返回 false
    保留 j，供下一个必需区间继续使用
返回 true
```

保留 j 很关键：必需范围 [0,2) 与 [4,6) 可以由一个完成范围 [0,6) 同时覆盖。处理完第一个需求就无条件消耗整个完成区间，会错误拒绝第二个需求。合并后，一个连续必需区间必须被某个合并完成区间包含，因此不需要逐字节扫描。排序与扫描成本为 O((r+d)log(r+d))，存储为 O(r+d)；检查器的逐字节集合参考只用于小整数范围。

短读需要区分操作终结和对象终结。若一次请求 [o,o+l) 终结并成功返回 n 字节，0<n<l，则只增加 [o,o+n) 的覆盖；剩余后缀没有因为该请求结束而自动继续在途。若仍需要它，应以新 request_id 重提后缀。n=0 且仍缺必需字节时，应按接口合同处理 EOF 或失败，避免无进展重试。接口若报告整个操作尚在途，则保留其责任，等待真正终结。

错误对象可以保留已成功范围用于有条件重试，但失败或取消后不得继续发布。重试若覆盖同一目的范围，必须先结束旧写者，或使用隔离槽；否则按代次忽略旧通知也阻止不了旧 DMA 实际覆盖新内容。

## 有限缓冲下的加载推进算法

以 CPU 转换路径为例，四阶段为 read→convert→H2D→consume。read 产生源字节，convert 产生目标表示，H2D 写入设备输入，consume 汇合所有已声明消费者的实际最后读取。GPU 转换路径应改成 read→H2D→device-convert→consume，并保护设备源到转换最后读取、目标到消费最后读取，不能套用 CPU 转换的顺序。

下面选择保守容量方案：每次接纳一个块，原子取得一组主机读槽、转换输出槽和设备槽，全部保留到该块终结并排空。它可能增加驻留，却避免不同池逐项占有造成循环等待。进一步缩短各池生存期是合法优化，但必须分别证明最后使用条件，不能混用这套保守方案的容量与另一套方案的时间。

算法还选择本次 plan 内首次不可恢复错误后停止后续业务提交，排空已经接受的操作，再返回失败。这是本次计划的失败策略，不代表其他加载计划或已经有效的独立对象也必须失败。取消和失败都关闭未来接纳、短读重提、阶段提交及新消费者授权；已经授权的消费者仍有实际访问责任。

每个准备提交的操作先登记 INTENT。适配层返回后，必须立即把它变为以下结果之一，不能把“调用返回失败”留作没有后继的 RESERVED 块：

| 同步返回的规范化结果 | 责任与块状态变化 | 能否等待该操作的未来完成 |
|---|---|---|
| 明确未接受 | 撤回该 INTENT；记录未提交范围；不可恢复错误关闭未来授权 | 不能；没有该操作的完成 |
| 接受且仍在途 | INTENT 转为实际访问责任；登记可获取终结证据的通道 | 可以，但不能由此提前释放槽 |
| 已同步终结 | 立即执行与异步终结相同的幂等处理，记录字节与错误，关闭本操作责任 | 不再等待第二次终结 |
| 接受情况未知 | 保留可能访问责任并隔离；不能按未接受撤回 | 只按实际恢复合同处理，不能虚构完成 |

批量提交必须逐操作解释。只接受一部分再失败时，未接受部分撤回，已接受部分继续排空；全部明确未接受且失败时，责任立即归零，关闭未来授权后即可归还槽。

```pseudocode
算法 LoadBlocks(plan, capacities, channels)
输入：固定版本与范围计划；阶段和消费者合同；有界槽组；完成及控制通道
输出：逐块结果、已发布内容、缺失范围、从未接受的范围、隔离责任

校验描述、依赖和单块容量；不可容纳的单块直接报告不可行
初始化 waiting、active、空闲槽、操作表、已终结操作集合
初始化 stop_reason=空、cancelled=false；全部阶段尚未提交

过程 Stop(reason)：
    记录原因；取消时另置 cancelled=true
    关闭本计划未来接纳和全部 active 块的未来业务授权
    撤销尚未发出的阶段与后缀待办，不撤销实际访问责任

过程 Terminal(op, result)：
    按完整身份、request_id、lease 匹配；未知身份记录诊断，不猜测释放
    若 op 已终结：按一致性合同幂等忽略，不再次减责任
    若属于旧代：只处理旧责任，不修改新 lease
    验证结果属于该请求范围且符合实际接口合同
    关闭 op 自己的责任，加入已终结集合
    读取终结：记录成功范围和错误
        有不可恢复错误：Stop(失败)
        正常短读且仍需后缀：
            n=0：Stop(无进展或 EOF)
            n>0 且未来授权未关闭：登记新 request_id 的后缀待办
            已停止：只报告缺失后缀，不重提
    其他阶段终结：
        失败则 Stop(失败)
        成功则更新该阶段完成状态；不在回调中绕过控制检查提交后继

过程 Submit(stage_batch)：
    先登记全部 INTENT、身份、lease 和可能访问范围
    调用非阻塞提交适配层，取得逐操作规范化结果
    明确未接受：撤回对应 INTENT，记录未提交范围和错误
    接受在途：转为实际责任，登记终结证据路径
    同步终结：立即调用 Terminal，不等待额外完成
    未知：保留可能责任，Stop(提交状态未知)，移入隔离集合
    若本批存在不可恢复拒绝：Stop(失败)
    立即重新检查无责任且授权关闭的块，不把清理推迟到下一完成之后

循环：
    非阻塞取得当前已经到达的控制和完成事件
    同刻取消先处理，再处理完成；两者都先于新接纳和新提交
    取消事件调用 Stop(取消)；终结事件调用 Terminal

    对授权已关闭且全部实际/可能访问责任为零的块：
        归还槽组，记录 RETIRED，并从 active 移除

    若 cancelled 且 active 为空：
        直接返回取消、缺失范围及从未接受范围
    若已失败且 active 为空：直接返回失败和相应范围
    若 waiting 与 active 都为空：返回成功
    若剩余责任只能交由隔离恢复且没有本循环可取得的终结路径：
        移交保护责任，返回 ISOLATED；不归还其槽

    若有本地可执行工作：每次选择一项推进，再回到循环首部
        已接纳块的必需源范围齐备、相关写者结束且无错误：
            至多提交一次转换，或本地完成零载荷阶段
        转换完成：至多提交一次 H2D
        H2D 完成且消费依赖成立：
            先登记消费者责任，再发布 DEVICE_READY 并授权消费
        所有消费者最后访问结束：记录 CONSUMED，关闭未来授权
        正常短读后缀待办：Submit(该后缀)
        尚未停止且依赖、容量满足的 waiting 块：
            原子取得槽组和新 lease，移入 active，登记 RESERVED
            将读取列为本地可执行工作
        每项新提交之前重新检查已到达控制，不在一个长接纳循环中跳过取消
        继续循环，不进入阻塞接收

    此处已没有本地可执行工作，先检查实际责任，再决定等待：
        若没有实际或可能访问责任：
            waiting 或 active 尚非空说明容量/依赖/阶段状态无后继
            Stop(停滞)，回收无责任槽，返回停滞及未完成范围
        若存在责任但终结通道已失效或接受状态不可判定：
            保留隔离与拥有者，返回 ISOLATED
        否则：
            挂接能唤醒本循环的完成及控制等待
            再次非阻塞检查控制、完成、本地工作和终态，避免检查与睡眠间丢失唤醒
            若有进展条件则继续循环
            仅在真实在途责任及其终结路径仍存在时阻塞接收，醒来回循环首部
```

等待判定覆盖 waiting 为空但 active 卡住的情况。一个 active 块若既无在途访问，也无可执行后继，又没有关闭授权，就属于状态或依赖停滞，不能因为 waiting 为空而忽略。反过来，已停止且全部 active 排空时必须立即返回；未来可能到达的取消、定时器或无关通知不能成为继续等待的理由。

同刻顺序指已经到达推进拥有者的控制与提交之间的线性化关系。若取消在一次不可分提交已经接受后才到达，已接受工作照常排空；不能追溯当成从未接受。真实系统若有多个提交线程，必须用相应协调关系实现这个授权边界，仅给事件堆设置 priority=0 不足以阻止堆外先行接纳。

责任登记必须先于可能立即完成的提交。快速回调先到时，应由同一状态拥有者按 request_id 幂等合并回调和返回结果，不能在处理返回时重新建立已经终结的责任。未知完成不释放当前槽，重复终结只关闭一次责任。代次检查防止通知混淆，物理访问排空防止真实覆盖，两者都需要。

算法的有限返回依赖真实接口最终提供终结证据，或提供明确的隔离移交路径。超时本身不会结束 DMA；设备失联而责任未知时，不能把槽标成空闲。这里修复的是没有任何操作被接受却等待其完成的算法错误，不以 CPU 事件模型保证设备永不失联。

## 从文件读取到设备消费的硬件路径

第一步，清单与索引把逻辑对象映射到固定文件及范围；布局不相容时生成转换计划。第二步，缓冲路径可能从页缓存满足读取，mmap 可能因缺页进入存储路径，直接 I/O 则按具体合同读取用户缓冲。一个逻辑范围可以拆成多个物理请求，多次相邻逻辑读取也可能合并。

第三步，[Linux blk-mq 文档](../sources/S-LINUX-IO.md)区分软件暂存队列与硬件派发队列。能够走最短路径的请求可以直接送往硬件；需要合并或 I/O scheduler 处理时进入软件队列。相邻 sector 可在适用队列内合并，scheduler 可以重排以改善公平或性能；不能假定任意不同软件队列都能合并。硬件无法接受时，请求保留在待派发列表。块层用 tag 匹配驱动完成，块层和设备协议均不保证提交顺序就是完成顺序。

第四步，应用按文件、范围、尝试和 lease 重建完成集合。块层 tag 不是永久对象身份，不能把它跨复用周期直接当作模型版本。必需源范围齐备、相关写者终结且错误已处理后，CPU 转换读取源、写入目标表示；随后 H2D DMA 读取主机目标并写入设备输入。主机源必须保护到 DMA 实际读完，设备输入保护到 kernel 最后读取。

第五步，复制完成和消费者执行通过实际覆盖这些操作的 stream/event 或其他平台关系连接。某个 host API 返回、某个外层 event 被记录，不能独自证明库内部所有 stream 已完成。硬件能并发不等于该负载一定重叠，合法依赖也不等于共享资源足够。

[ServerlessLLM](../sources/S-SERVERLESSLLM.md) §4.2 将固定大小块池、直接文件访问、锁页内存、层内并行读取与层间任务队列组合起来；线程把已读块的 offset/size 交给下一层。论文报告的是该系统的数据路径与测试床，不证明所有 mmap、直接 I/O、锁页或线程组织都具有相同表现。

## 外部 DMA 直达 GPU 的边界

绕过主机 staging 是另一条设计轴。[GPUDirect RDMA 固定文档](../sources/S-GPUDIRECT.md)把存储适配器列为第三方设备示例，但这不等于普通文件读取自动支持设备内存。所述路径需要第三方驱动、GPU 分配类型、注册与 BAR 映射相容，并满足 PCIe 拓扑和平台条件。固定文档要求共享上游 PCIe root complex，IOMMU 不执行非 1:1 地址翻译；即使拓扑满足，具体平台仍可能受芯片组或驱动限制。

pin 与注册可能达到毫秒级，因此可通过 lazy unpinning 或 registration cache 摊销。缓存必须检测分配撤销和地址复用，不能只按虚拟地址命中。固定文档还要求相应 CUDA 内存操作一致性注册，例如按其合同设置整分配的 SYNC_MEMOPS；这会限制某些优化，也有成本。映射撤销回调需要清除引用并等待外部 DMA，不能在持锁回调中等待 GPU 做其他工作而形成死锁。

内存顺序是独立条件。§2.7 说明：GPU 对 GPUDirect 操作的观察顺序由 CPU 发起的 CUDA 同步或工作提交 API 建立。所需 DMA 写必须先相对于将提交依赖工作的 CPU 线程完成，再由该线程发起依赖 CUDA 工作。仅有设备发出事务、稍后的主机读回，或一组看起来递增的时间戳，都不能补上这条因果边。

一条合法的抽象路径是：分配与映射有效→外部 DMA 写→提交线程取得完成保证→后续 CUDA 提交→依赖 kernel。若 kernel 已经与该 DMA 写并发读取同一范围，固定文档允许它读到旧值、部分值或乱序值；稍后读回新值不能追溯修复这个读取。unpin 还必须晚于相关外部 DMA 完成；释放 GPU 分配则另需等待所有 GPU 使用者，两个释放条件不能混同。

直通可以省去该路径原有的主机 staging 及其流量，但不会消除存储 IOPS、排队、校验和表示转换。若转换仍是主项，或准备成本无法摊销，端到端时间未必降低。本章没有存储直通、GPUDirect Storage 或 GPUDirect RDMA 的目标机实测，不能从映射和顺序合同推导吞吐提升。

## 有限流水、容量与组合轨迹

在各阶段独立、各阶段单服务者按块顺序处理、缓冲足够且无其他跨块依赖时，第 i 块第 k 阶段完成时间为 F[i,k]=max(F[i−1,k],F[i,k−1])+t[i,k]，不存在的前驱取零。对各块阶段时间相同的 N 块，T_0=0，N≥1 时 T_N=Σ_k t_k+(N−1)max_k t_k。第一块仍支付依赖阶段之和，最后一块仍要排空。

该递推不包含有限槽等待。采用整组保留到最后消费的 S 个槽组，按块顺序接纳、各阶段 FIFO 时，第零阶段还要等待 F[i−S,last]，因此把它加入 max 的前驱即可得到这个特定方案的有限容量参考。若各池分别释放，则应按各池最后使用者建立不同边，不能沿用整组方案的释放关系。

固定周期 P、固定生存期 L_j、同刻结束后可以立即复用时，池 j 至少需要 ceil(L_j/P) 个槽。L=9 ms、P=4 ms 时需要 3 槽；只有 2 槽会让在 8 ms 启动的块覆盖到 9 ms 才结束的块。相邻 [0,4)、[4,8) 可以复用一个槽。长度可变、乱序、预留早于实际开始或取消排空时，不能用平均 L 保证安全；实际回收仍由最后访问控制。

设定四阶段分别耗 8、3、2、5 ms。四块在独立资源、充足缓冲下于 42 ms 完成，完全串行为 72 ms。对七块，理想流水为 66 ms。采用前述保守槽组，每组同时预留主机源、转换输出和设备输入，有限事件模型与增加容量边的参考递推得到：

| 槽组数 | 七块完成时间 | 三种等大缓冲的显式容量 |
|---|---|---|
| 1 | 126 ms | 3b |
| 2 | 72 ms | 6b |
| 3 | 66 ms | 9b |

这是规定资源和释放方案下的模型结果，不是硬件测量。更多槽在此条件下可以解除等待，达到慢阶段限制后则不能继续缩短周期。若缩短某池的持有时间，容量和时序都要按新方案重算。

取消沿同一轨迹检查。设两槽组、五个待加载块，0 ms 时接纳块 0、1；单读取资源使 read0 在 [0,8)，read1 已被接受但安排在 [8,16)。8 ms 时 read0 完成并提交 convert0，在 [8,11) 执行。9 ms 收到取消：停止新接纳及后继业务阶段，convert0 到 11 ms 才结束，read1 到 16 ms 才结束。

| 时刻 | 输入事件与状态变化 | 仍需保护的资源 |
|---|---|---|
| 0 ms | 两块取得不同 lease，读取被接受 | 两个槽组 |
| 8 ms | 块 0 源齐备，转换被接受 | 块 0 转换访问；块 1 读取访问 |
| 9 ms | 取消关闭未来接纳、H2D 和消费授权 | 两个已接受阶段仍存活 |
| 11 ms | convert0 终结，块 0 可回收 | 块 1 的槽组 |
| 16 ms | read1 终结，块 1 可回收，直接返回取消 | 无在途访问；另三块未提交 |

此方案没有发布任何设备就绪块。取消响应是 9 ms，物理排空是 16 ms；9 ms 就归还全部槽会违反实际访问责任。若取消在 0 ms 已经到达，第一轮先处理取消，接纳数与新提交数都为零，0 ms 直接返回全部五块从未提交。若取消恰在 8 ms 到达，它先于 read0 完成后的转换提交，因此 convert0 不会被授权；已接受的 read1 仍排空到 16 ms。

同步拒绝需要另一条没有外部完成的有限轨迹。设两个待加载块、一个空闲槽组，首块读取批次全部被明确同步拒绝，采用本计划首次错误后停止的策略：

| 同一推进时刻内的步骤 | 状态与责任 | 容量账 |
|---|---|---|
| 处理当前控制 | 没有取消，允许接纳 | free=1，active=0 |
| 接纳块 0 | RESERVED；登记读取 INTENT | free=0，active=1 |
| 提交返回全部未接受及错误 | 撤回全部 INTENT；实际在途数为 0；关闭未来授权 | free=0，active=1 |
| 执行本地清理 | 块 0 失败并 RETIRED | free=1，active=0 |
| 阻塞接收前检查终态 | 直接返回失败；块 0 范围未接受，块 1 尚未接纳 | free=1，active=0 |

全程无需任何完成事件，模型时间仍为 0，free+active 始终为 1。只保留单块时，waiting 已经为空，仍按同样路径回收并返回。若误把接收放在清理和终态检查前，两个输入都会等待不存在的完成；把 waiting 非空作为唯一停滞条件也会漏掉单块情形。

部分接受则不同：首块读取的一部分被接受、另一部分明确拒绝时，立即停止后续业务，但已接受部分仍持有槽。设其终结在 8 ms，则 0–8 ms 为 free=0、active=1，8 ms 才变成 free=1、active=0 并返回失败。全部未接受与部分接受不能共用“立即归还全部预留”的错误处理。

## 条件化成本与方案反转

| 成本 | 同一候选内应计算的对象 | 影响选择的条件 |
|---|---|---|
| 计算 | 索引、排序、范围合并、校验、解包、转置与设备转换 | 小请求时固定处理主导；源存储变快后转换可能成为瓶颈 |
| 访存 | 页缓存复制、主机源和转换目标读写、DMA、设备转换读写 | 转换另需副本或低位展开时，逻辑权重字节不足以表示流量 |
| 通信 | 存储、网络、PCIe 与共享上游的实际事务 | 多模型和多 rank 不能同时各取一份独占带宽 |
| 准备 | 打开文件、索引解析、离线格式整理、池分配、锁页与注册 | 一次冷启动难以摊销；频繁切换或复用时可能有利 |
| 同步 | 排队、依赖等待、完成处理、取消排空与持久化 | 只缩短提交调用而未缩短消费者等待，不能算加载完成收益 |
| 驻留 | 各池、转换工作区、页缓存、旧版本与在途对象 | 过深预取会挤出可常驻 KV，并增加失败后的排空成本 |

容量按唯一物理 backing 及同时存活区间统计。同一 backing 的多个视图只计一次，确实复制的两份分别计；池 reserved 已包含 active 槽时不能再次相加。各项各自峰值之和通常只是上界，应计算同一时刻的总和再取峰值。同步拒绝只撤销没有实际访问的预留，部分接受、取消和未知状态则延长真实驻留。

责任表按 request_id 索引时，单次匹配可采用预期 O(1) 的散列表操作；总状态至少随当前在途操作、范围覆盖和待办增长。重复通知判定还需保留足够的终结身份，不能在可能收到旧通知时无条件复用 request_id。检查脚本使用事件堆模拟完成，O(log E) 的堆开销属于检查实现，不是全部真实 I/O 路径的统一开销。

设定 16 MiB 块，SSD 顺序读为 4 GiB/s、H2D 为 16 GiB/s，纯传输项分别为 3.90625 ms 和 0.9765625 ms。这里没有包含提交、转换和排队，也没有证明两段能同时取得各自速率。资源 r 每块累计 Q_r 字节，在该并发下可持续带宽为 B_r，则周期须满足 P≥Q_r/B_r；CPU 转换和 DMA 共用 DRAM 时，需要把实际读写流量合计。使用实测有效速率所得是条件化估计，不是硬件能力上界给出的严格下界。

多 rank 资源独立、各自排队 q_r 位于本地流水 L_r 之前、共同屏障位于其后时，T_ready=max_r(q_r+L_r)+T_barrier。共享 SSD、网络或 CPU 时，应建立共同资源图；不能让每个 rank 同时领取独占带宽，也不能把已经进入依赖图的屏障再加一次。

模型常驻时，SSD 优化主要影响启动；活跃 KV 每步往返 SSD 时，容量可行仍可能无法满足 ITL。数据频繁复用且页缓存充足时保留缓存路径；单遍大流量与应用驻留控制可能使直接 I/O 更合适。随机专家路由改变预取命中和实际范围，错误预取消耗容量与带宽，不能靠跳过实际必需数据维持原函数。

写出需要区分应用缓冲可复用、存储栈完成和所需持久性。缓冲写返回可能只是进入页缓存，固定 iomap 文档还说明写回错误可留待同步接口取得。可重建 KV 与不可丢制品或提交记录有不同合同；更快写入不能代替发布和恢复条件。对可重建缓存，丢失后的重算仍会争用 CPU/GPU。

## 竞争解释与区分实验

先固定版本、有效字节、缓存状态、并发和完成边界，再选择让竞争解释产生不同预测的干预。

| 观察 | 竞争解释 | 区分实验与反证后的修正 |
|---|---|---|
| 吞吐低 | IOPS、存储带宽、提交 CPU、转换或共享链路 | 固定有效字节扫描请求大小，分别记录实际存储字节和各阶段完成；热读快而冷读慢支持缓存解释，CPU 转换仍主导则撤回纯存储解释 |
| 增加深度没有收益 | 资源饱和、有限槽等待或后续阶段受限 | 固定块大小、缓存和工作量，改变在途预算；完成率不升而等待上升时减少排队，继续定位共享资源 |
| 大块反而慢 | 过读、尾块、首块等待或消费者粒度不匹配 | 分记有效字节、实际字节、首块与排空；过读增长时调整合并范围，不能只按标称带宽选择块大小 |
| 数据混杂或范围不齐 | 错误文件、旧尝试、旧 lease、短读或提交顺序匹配 | 两文件同偏移放不同内容，打乱完成并注入旧代、重复和缺失后缀；只有本代本文件覆盖可推进，旧物理写未排空则改用隔离槽 |
| 池满后不再推进 | 真正容量不足、全提交后才处理完成、同步拒绝后仍等待或控制通道被阻塞 | 用 N 大于槽数的有限任务；再令首块同步拒绝且不生成完成，分别测试单块和两块；无实际在途却阻塞时修状态推进和等待位置，不能归因于 SSD 慢 |
| 取消后仍出现新工作 | 取消迟到、同刻处理顺序错误或其他提交线程绕过授权 | 固定取消到达点为 0、读取完成同刻和转换完成同刻；独立观察器以输入到达时间检查接纳与提交，不只检查 cancel 记录之后的事件 |
| 取消已响应但槽仍占用 | 物理排空或通知处理滞后 | 分别延迟操作完成和完成处理；实际访问已结束却迟迟不回收时转查控制路径，在途访问仍存在时继续保护 |
| 直通没有收益或读旧值 | 注册成本、存储/转换瓶颈、映射或消费顺序错误 | 分开检查映射资格、主存流量、准备和 DMA→提交线程→CUDA 依赖；主机读回正确不能排除并发 kernel 竞态 |
| 写入返回但恢复缺失 | 页缓存、设备缓存、发布过早或旧版本提前清理 | 明确故障点并核对同步、清单发布和旧读者；只有满足所需持久性才报告可恢复 |

全设备同步使错误消失，只能说明某些执行关系被改变，不能唯一定位缺失哪条依赖边。性能对照应回到正常运行条件；阶段均值之和不能代替服务尾延迟证据。

## 检查与证据范围

配套 `tools/check_k_hw_012_full.py` 是确定性、只读、离线的 Python 标准库 CPU 模型。范围算法与逐字节集合参考比较，覆盖 12,321 组小整数区间；未经投影的三元记录必须拒绝，按完整身份筛选投影后的重复完成必须通过。布局检查用目标反查与独立源坐标散射比较。

有限槽事件推进与增加容量边的阶段递推比较，覆盖空输入、N 大于槽数、零持续时间及分数时间。观察器从申请、INTENT、接受、拒绝、终结、关闭授权和归还记录重建责任，每一步检查 free+live=capacity，归还时检查没有未终结访问。它不读取生产者的 active 或 free 标志来判定最后访问安全。

同步拒绝检查同时覆盖单块与两块、一个槽组、没有任何外部完成事件；要求 0 ms 返回失败、容量全部归还、没有进入等待，并保留所有从未接受范围。部分接受再失败要求先排空已接受部分。另构造 waiting 为空、active 无责任且无后继的停滞，要求报告并回收；未来取消不能拖延一个已经失败并排空的计划。

取消检查覆盖 0、8、9、11、18 ms 和正常完成之后才预定到达的取消。0 ms 取消必须零接纳、零提交、零在途；同刻取消先于新阶段提交。独立观察器直接使用输入 cancel_at 检查新工作时间，避免仅从错误排序的 cancel 记录重建同一个错误。故意延后处理起始取消、在同步拒绝后先等待、以及带在途责任提前归还的负对照都必须被检出。GPUDirect 顺序检查仍以图可达性和全部合法事件排列比较，检测遗漏 DMA 到后续 CUDA 提交及提前 unpin 的依赖。

检查脚本、输入绑定与实际执行结果见[检查记录](../../docs/evidence/knowledge-workflow-20261028-batch11/K-HW-012/round-3/check-0.json)。

这些检查不执行真实文件读取、块设备、O_DIRECT、页缓存、锁页、CUDA、PCIe 或 GPUDirect，不证明设备可见性、编译后同步、实际重叠、吞吐、尾延迟或 Agent 使用效果。事件模型假定被接受操作能按输入合同提供终结；未实现真实接口适配、接受未知后的驱动恢复、通用短读重提调度、任意张量格式或完整文件系统恢复。范围穷举限小整数端点，布局检查限未打包的 2×3 转置。
