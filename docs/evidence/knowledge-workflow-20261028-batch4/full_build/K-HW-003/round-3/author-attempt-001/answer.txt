  "chapter": "# K-HW-003：主机准备、DMA 与流水缓冲\n\n输入流水的吞吐取决于准备、传输和计算阶段的平衡；数据可见性和缓冲所有权决定能否正确重叠。异步接口主要改变提交与完成的关系，并不自动减少字节、建立跨 stream 依赖或增加复制引擎。设计输入路径时，需要同时回答：传什么内容、驻留在哪里、谁仍在访问，以及哪个完成事件允许下一次读写。\n\n本章输入是一组有限或受准入限制的载荷，每项携带请求身份、内容版本、有效范围、shape、布局和 dtype；输出是相应计算结果、明确失败或取消状态，以及可核对的资源归还记录。处理器配置也是内容身份的一部分：同一图片采用不同 resize、归一化或抽帧配置，即使最终形状相同，也不是可随意互换的输入。路径选择要解释哪些对象保持驻留、哪些经过 staging、何时可消费与复用；未知时间和带宽可以先作为设定量，再用目标环境观察修正。\n\n## 准备不是一次复制\n\n文本服务包含解析和 tokenization，多模态还包含媒体解码、采样、resize 和特征整理。原始载荷 A 经 CPU 准备成为连续主机输入 H；pageable 输出若要转入显式 pinned staging S，还多一次主机复制。随后 H 或 S 经 H2D 到设备输入 D，kernel 读取 D、写设备输出 O，D2H 再将 O 写入主机结果 R。CPU 消费 R 也有独立的结束时刻。\n\n这里 DMA 指由相应传输硬件执行内存搬运；CPU 仍需准备地址、字节范围、依赖与提交描述。主机调用返回说明提交路径取得进展，不能单独证明源已读完、目的已写全或消费者已经结束。所有范围采用半开字节区间 [a,a+b)，b 为有效字节数；容量、实际搬运量和逻辑载荷大小分别记账。\n\n| 对象 | 典型状态路径 | 最早允许覆盖的证据 |\n|---|---|---|\n| H 或 S | FREE → PREPARING → READY → H2D_SOURCE → FREE | 主机准备已结束，且全部 DMA 源读取结束 |\n| D | FREE → H2D_TARGET → READY → KERNEL_INPUT → FREE | H2D 写入及全部 kernel 读取结束 |\n| O | FREE → KERNEL_OUTPUT → READY → D2H_SOURCE → FREE | kernel 写入及全部 D2H/其他读取结束 |\n| R | FREE → D2H_TARGET → READY → CPU_INPUT → FREE | D2H 写入及全部 CPU/发送消费者结束 |\n\n一个对象还需要区别“生产完成，等待下游取得读取权”和“已经没有人使用”。READY 对象即使暂时没有在途读者，也不能立即回收，否则消费者还未启动，内容已被覆盖。后文用 hold 表达这项待消费保留，用 writer 和具名 readers 表达已经启动的物理访问。\n\npageable 主存路径可能经过额外 staging 或主机等待，具体行为随 API、方向和运行时路径而变。固定 CUDA 最佳实践文档的异步重叠方案使用 pinned 主存；本章的显式异步算法也采用可复用的 pinned 传输池，不依赖未确认的 pageable 行为。pinned memory 使页面在相关生命周期内保持锁定，但不意味着整个虚拟区间物理连续，也不免除范围与平台条件检查。\n\n已有范围可通过注册建立锁页条件，或直接分配 pinned 缓冲。注册避免另分配再复制，却有建立、页面处理和撤销成本。PyTorch 固定文档中的 pin_memory 返回锁页副本，不能把它当成原地址零成本改变属性。若原始 A、准备后的 pageable H 和 pinned S 同时存活，三者都进入主存峰值；锁页不能无限使用，其压力还会影响其他系统工作。\n\n## 依赖、stream 与硬件能力\n\n合法性先于性能选择。目的范围必须足以容纳所需表示，源与目的的地址类别和复制方向应合法；非连续对象必须按消费者布局显式 packing 或采用被接口支持的分段路径。只写完部分范围，不能把未写区域中的旧字节发布为新 tensor。别名范围若发生读写或写写冲突，也要统一保护，不能因为对象名称不同就视为独立。\n\n一批内部必须保持 H/S 写完 → H2D 写完 D → kernel 写完 O → D2H 写完 R → CPU 消费的依赖。复制与 kernel 在同一 stream 时，队列顺序可以提供相应设备依赖；位于不同 stream 时，应在最后生产写入之后记录事件，让消费 stream 等待。主机读取 R 还需取得对应完成证据。事件位置错误，例如记录在最后一个分段复制之前，会留下未覆盖范围。\n\n能够重叠的是不同批或不同独立块的工作。同一批的 H2D 尚未完成时，其 kernel 不能为了重叠提前读取所需区域。跨 stream 建立正确依赖，也不保证硬件一定并发执行。\n\n固定 CUDA 最佳实践文档描述了 legacy 默认 stream 的串行化行为和不同非默认 stream 的重叠方案。不能将该行为无条件推广为所有默认 stream 模式；per-thread default stream、非阻塞 stream 及框架内部 stream 应按实际执行契约核对。即使没有跨 stream 的隐式串行化，同一个 stream 内仍按其队列顺序执行。\n\n还要区分软件队列与硬件资源。固定文档以 asyncEngineCount 等属性说明复制与计算能力：单复制引擎模型一次服务一个复制方向，但可能与 kernel 并行；双复制引擎模型可允许一个 H2D、一个 D2H 与 kernel 同时运行。创建更多 stream 不会增加复制引擎。实际设备不能仅凭属性数值就保证达到孤立复制带宽，还需核对方向、拓扑、内存竞争和实际时间线。\n\n执行顺序与地址生存期是两条约束。跨 stream 等待生产完成后，还需防止 allocator 在最后消费者结束前回收地址。stream-ordered allocator 将分配、使用和释放置于相容的执行顺序；释放请求返回不是任意 stream 可立即重用地址的证据。CUDA Graph 重放固定地址也不固定其中的内容：下一批填充、并发重放与输出保存仍需要对象级保护。\n\n## 流水周期与有限批完成\n\n设固定形状的一批依次经过准备、H2D、GPU 计算和 D2H，服务时间为 t_p、t_h、t_g、t_d，单位均为时间/批。假定每阶段有自己的串行服务资源，各批独立、缓冲充足、没有反馈或额外同步，理想稳态周期为\n\nP₀ = max(t_p,t_h,t_g,t_d)。\n\n不返回主机时可以令 t_d=0。在上述确定性条件下，N≥1 批的理想完成时间为\n\nT_N = t_p+t_h+t_g+t_d+(N−1)P₀；T_0=0。\n\n可用逐阶段递推验证：第 i 批在阶段 s 的开始，取该批上一阶段完成与上一批本阶段完成的较晚者，再加本阶段服务时间。固定等长阶段的递推给出首批依赖链之和，以及后续每批一个最慢阶段周期。该式包含填充与排空；“全部复制已提交”不能作为结束条件。所有阶段时间均为零时只是抽象模型退化，不能据此宣称无限硬件吞吐。\n\n若 H2D、D2H 共用一个复制引擎，每批对它的服务需求为 t_h+t_d，因此周期至少满足\n\nP ≥ max(t_p,t_g,t_h+t_d)。\n\n这是资源下界，未证明某种有限缓冲与命令排序能达到它。对 N≥1，若首个复制不早于首批准备结束，该复制引擎的总工作还给出 T_N ≥ t_p+N(t_h+t_d)。精确完成时间要把两种复制放在同一个资源日历上，并保留 H2D → kernel → D2H 的依赖；不能分别计算两个日历后直接合并。\n\n逐 token 反馈又不同。若下一输入依赖刚生成的 token，必要的结果交付、CPU 处理与再次提交仍处于同一请求的依赖链，多个独立请求的聚合流水周期不能直接充当单请求 ITL。CPU 结果处理若占用与准备相同的线程，也应合并该线程每批的服务需求，或显式说明独立执行资源。\n\n## 缓冲池的槽位与代次\n\n每个物理槽记录 pool、slot、gen、owner、容量、有效范围、phase、hold、writer 和 readers。owner 是请求身份，gen 在重新取得槽时增加；每次操作另有不复用的 uid。writer 至多一个，readers 是具名责任集合，而非只计总数。完成记录包含 uid、请求、各端点代次、实际完成范围、状态和访问是否确实结束的证据。\n\n回收条件是 hold=false、writer 为空且 readers 为空。READY 的 hold 防止“尚无在途读者”被误解为“可回收”。提交时，应先原子登记源读责任和目的写责任，再将源从 READY 移到 IN_USE、撤销源的待消费 hold，最后入队；这样同一 READY 源不能被推进循环重复提交。目的在写入成功前也不进入 READY。\n\n下面给出一种保守而完整的路径：CPU 直接准备到最终 pinned H，四池分别管理 H、D、O、R，每个对象只有一个下游阶段；CPU 将 R 复制/编码到独立响应对象后结束。需要显式 pageable → pinned staging 时，应在同一协议中再加入一个主机复制阶段，而不是把额外副本藏入 H2D。原始载荷、注册映射和 workspace 若被操作借用，也属于该操作的端点或具名责任。\n\n```pseudocode\n算法 有界四池输入流水\n输入：N 个不可变载荷描述；准备变换与设备计算契约；四池容量与字节预算\n输出：每个请求的独立响应、失败或取消；排空或隔离责任记录\n初始化：\n  N=0 时直接返回空结果，不等待任何“最后事件”\n  校验非空路径的每个池至少有一个可容纳对象的槽，否则报告配置不可行\n  所有槽 FREE，gen=0，owner=空，hold=false，writer=空，readers=空\n  每请求 live=true，committed=false；next=0；pending=空；uid 单调增加\n  所有状态转换由一个状态拥有者串行处理；外部只投递带身份的事件\n\n取得(pool, request)：\n  要求 FREE 且容量/总字节预算足够\n  gen 加一；设置 owner、有效范围为空、hold=true、phase=RESERVED\n  返回带 pool、slot、gen、request 的端点引用\n\n启动(kind, source, destination)：\n  source 存在时要求身份匹配、READY、hold=true、没有 writer\n  destination 存在时要求已取得、没有 writer 或 readers\n  生成新 uid；pending[uid] 保存 kind、所有端点身份、所需范围\n  先把 uid 加入 source.readers，再设 source.hold=false、phase=IN_USE\n  设置 destination.writer=uid、phase=WRITING，禁止发布\n  将对应工作入队；准备工作逐段执行描述中的读取、变换与写入\n  若确定没有入队：\n    撤销这个 uid 的读写责任与目的预留\n    若请求仍 live，则恢复源 READY 和 hold；否则允许其回收\n    按错误策略标记失败或等待容量，不伪造一次成功完成\n  若已经入队或入队状态不明：\n    保留责任；不明时停止该请求推进，隔离相关范围，等待排空证据\n\n推进：\n  从下游向上游扫描，每个动作只消费一次 READY 状态\n  对 live 的 READY R：启动 CPU 消费，无目的池槽\n  对 live 的 READY O 且 R 有槽：取得 R；启动 D2H(O,R)\n  对 live 的 READY D 且 O 有槽：取得 O；启动 kernel(D,O)\n  对 live 的 READY H 且 D 有槽：取得 D；启动 H2D(H,D)\n  当 next<N 且 H 有槽和准入预算：\n    取得 H；启动 prepare(外部原始载荷,H)；next 加一\n  循环到没有可立即执行的动作；随后等待真实事件，不忙轮询\n\n处理 完成(uid,status,covered,ended,result)：\n  未知或已经结算的 uid 不改变任何当前对象；重复完成幂等忽略\n  找到 pending[uid]，先核对请求、端点代次和操作类型\n  若端点与在途记录不匹配：报告协议破坏并隔离，禁止发布/复用\n  若 ended 不能证明所有相关访问已结束：\n    停止该请求的新工作；保留 writer/readers 和 pending；等待真实排空\n  否则：\n    仅删除这个 uid 的源读责任和目的写责任，结算 pending[uid]\n    success = 状态成功且 covered 覆盖全部所需写范围\n    若失败或范围不完整：请求 live=false，不发布部分内容\n    若有目的且 success 且请求仍 live：\n      设置同代有效范围、布局和内容身份；phase=READY；hold=true\n    否则有目的时：hold=false，内容无效\n    若 kind=CPU 且 success 且 live 且 committed=false：\n      确认 result 是独立响应，不再借用 R\n      一次性提交响应；committed=true；请求进入成功终态\n    对本次涉及对象，按回收条件归还；唤醒推进\n\n处理 取消或终态失败(request)：\n  设置 live=false，禁止新阶段与未来响应提交\n  撤销该请求所有尚待消费的 hold，但不撤销已启动的读写责任\n  已在途准备、复制、kernel 和 CPU 消费仍按完成事件结算\n  无在途责任的无效对象立即回收；未知访问状态继续隔离\n  唤醒推进，让其他请求使用已经归还的容量\n\n结束：\n  所有请求已成功、失败或取消，且 pending 清空、各池无未归还对象才称排空\n  若访问结束无法确认，报告 uid、范围、代次和最后使用者，不宣称排空\n```\n\n零字节载荷可以省去实际 DMA，但仍需沿依赖发布明确的空范围完成；它不意味着后续计算、元数据或结果也为空。准备失败不能进入 H2D，目的空间不足不能截断后继续按完整对象发布。长度变化时先检查容量，再提交；不在 DMA 进行中改变描述符。\n\n多消费者扩展需要在启动任何消费者前登记所有独立 uid，再撤销待消费 hold。copy 完成两次不能抵消 archive 的责任。若发送继续借用 R 而没有复制到独立响应，发送也必须成为 R 的读者。增加消费者后，回收仍等待整个集合为空。\n\n代次检查保护账务身份，不能挽救已经发生的物理覆盖。真正仍在途的旧 DMA 不应遇到已复用的新代槽；若发生，说明更早的回收规则已被破坏，忽略旧事件无法恢复新内容。正常的“迟到旧完成”主要是重复或延迟送达的通知：其对应访问已经结算，新的 uid 和 gen 使它不能再次删除新代责任。uid 不复用；终态记录可在安全条件下清理，未知 uid 仍不得被解释成当前操作。\n\n该推进的资源依赖是 H → D → O → R → CPU，且不在等待时占有反向所需资源；每池有合适槽、调度公平、外部操作最终完成、CPU 消费不无限背压时可以继续推进。未知设备状态、永不结束的消费者或额外循环 workspace 依赖不满足此进度前提，应报告阻塞原因。\n\n## 槽位下界与一条完整映射轨迹\n\n对池 j，若每隔 P>0 启动一批，槽从取得到最后消费者结束的固定占用时间为 L_j，则半开占用区间为 [a_i,a_i+L_j)。稳定周期下至少需要\n\nn_j ≥ ceil(L_j/P)。\n\n当 L_j=0 时模型占用为零；当 L_j 恰好为 P 的整数倍时，先处理边界完成再重新取得，恰好 L_j/P 个槽可能足够。有限 N 批的实际同时存活数最多为 N，精确最小值应从这些区间的最大重叠计算。变长、排队和尾部延迟会改变 L_j，平均生存期不能保证安全；真实复用永远由完成责任决定。\n\n设 t_p=3 ms、t_h=2 ms、t_g=8 ms、t_d=1 ms，均为设定值。为得到周期 8 ms 的一条可重建轨迹，按每 8 ms 启动准备，而不是让 CPU 无限制提前准备。各阶段资源独立且槽位充足时：\n\n| 批 | CPU 准备 | H2D | kernel | D2H |\n|---|---|---|---|---|\n| A | [0,3) | [3,5) | [5,13) | [13,14) |\n| B | [8,11) | [11,13) | [13,21) | [21,22) |\n| C | [16,19) | [19,21) | [21,29) | [29,30) |\n\nH 使用 pinned 主机槽，D/O 使用相互隔离的设备地址范围，R 使用主机目的槽。A 的 H2D 命令进入复制 stream，其结束位置记录 h_A；计算 stream 等待 h_A 后读取 D_A。kernel 后记录 g_A；返回 stream 等待 g_A，才允许复制引擎读取 O_A、写 R_A。主机确认 d_A 完成后再读取 R_A。事件覆盖整个有效范围，且对象引用保护持续到最后访问。\n\n在 [11,13) 内，复制引擎将 B 的 pinned 字节写入 D_B，GPU 同时读取 D_A；它们使用不同设备输入槽。13 ms 后 A 的输入槽可以回收，但 O_A 仍被 D2H 读取，B 的 kernel 必须使用另一个输出槽。A 的 R 即使在 14 ms 已写完，也要等 CPU 消费结束才归还。若 CPU 消费被延迟，其占用时间和返回池需求都要增加。\n\n设备输入的固定占用是 [3,13)，L_D=10 ms；设备输出为 [5,14)，L_O=9 ms，因此各需要两个槽。每个输入 16 MiB、输出 1 MiB，这两个预留池合计 2×16+2×1=34 MiB。池内活对象已经包含在预留容量中，不再重复加一遍；另计模型、KV、workspace、主机池和 allocator 额外保留区。\n\n这条具体轨迹没有让 H2D 与 D2H 同时工作，因此单复制引擎也未必排除它；双引擎是一般独立方向模型的能力前提之一，不能反过来声称本例必须有两个引擎。八批在上述理想条件下为 14+7×8=70 ms，串行为 8×14=112 ms，首批仍需 14 ms。若 CPU 提前堆积多批，输入槽会经历更长等待，不能继续把占用时间固定为 10 ms。\n\n再构造复制引擎主导的反例：t_p=1、t_h=8、t_g=2、t_d=4 ms，N=5。错误套用独立方向公式得到 15+4×8=47 ms；单复制引擎光是复制工作就需要 5×12=60 ms，且首个复制不早于 1 ms，因此 T_5≥61 ms，直接排除 47 ms。61 ms 仍只是下界，不是已经构造出的最优调度。\n\n## 减少次数、分块与共享带宽\n\n小而频繁的 token IDs、lengths 和 sampling metadata 容易受提交与同步成本主导。设 B 字节分成 m 次提交，每次固定成本 c_s，有效路径带宽 B_eff；合并后增加 packing/unpacking 成本 c_pack，其他条件不变，则\n\nT_sep ≈ m c_s+B/B_eff，T_merge ≈ c_s+B/B_eff+c_pack。\n\n只有 (m−1)c_s>c_pack 时，合并才有该简化模型下的收益。若合并增加 padding、需要等待慢请求或改变原来的重叠，必须分别加入额外字节和等待；吞吐改善不保证单请求尾延迟改善。\n\n对 D 字节对象分成 q=ceil(D/b) 块，第 k 块有效范围为 [kb,min((k+1)b,D))。末块按实际长度处理，不能默认整除。若块之间没有计算依赖，可以对每块应用同样的准备、复制、消费与回收协议；若消费者必须取得完整对象，则先等待所有必要块的完整范围，再发布整体对象。任何一块失败都不能将混合旧字节的整体标为成功。\n\n设每次传输固定开销 α，分块会增加 qα 的提交/服务需求；小块可能较早启动计算，却增加事件、索引和尾块处理，大块减少次数却推迟首块可用并增加驻留。真实时间仍要用块依赖和共享资源日历求得，不能无条件把单对象时间除以 q。\n\n输入还可能先从 SSD 或远端存储到主存，再解码、转换和 H2D。存储部分完成、应用范围完整、布局转换完成和设备可读是不同边界。Linux 固定文档说明块请求可以乱序完成，iomap 还区分异步排队、传输字节数和部分完成；上游成功通知必须转换成当前对象的完整范围证明。\n\n对共享资源 r，每批实际承担 Q_r 字节，在同一并发条件下可持续带宽为 B_r，则 P≥Q_r/B_r。主机准备读取、转换写入、staging 读写及 DMA 读写若共享 DRAM，流量应合计。上游链路若按双向共享容量建模，也应合并相应方向；若硬件有独立方向容量，则分别列约束，不能一律把 H2D+D2H 除以单向带宽。\n\n在相应假设下，周期需要同时满足阶段、引擎及共享资源下界，但这些约束通常取最大值，不能把已经包含在阶段时间内的访存耗时再次相加。设共享 DRAM 每批累计搬运 128 MiB、并发可持续带宽为 8 GiB/s，资源下界为 15.625 ms，便排除了先前 8 ms 周期的可达性。增槽不能减少这项字节需求。\n\n## 同一候选的完整成本账\n\n| 成本 | 应记内容 |
