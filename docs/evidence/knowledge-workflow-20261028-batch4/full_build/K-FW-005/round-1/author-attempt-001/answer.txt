{"chapter": "# K-FW-005：CUDA Graph：捕获边界、计划状态与变长服务\n\nCUDA Graph 把一组设备工作和依赖从重复的提交路径中取出，定义一次、实例化后按固定地址与拓扑重放；服务动态性则由稳定缓冲中的值、图桶、计划缓冲和捕获外控制面承接。\n\n## 问题、对象与状态\n\n大量短 kernel 的服务步骤中，每个 kernel 都要经历参数准备、分派和驱动提交。设备执行很短时，这条 host 路径会占据相邻 kernel 的间隔。CUDA Graph 的动机不是减少矩阵乘、attention 分数或 KV 读取的算术，而是把重复的设备 DAG 的定义与执行分开：定义阶段记录节点和边；实例化阶段验证模板并建立可执行图；执行阶段用一次图 launch 提交整段工作。普通重放跳过大部分参数设置与逐 kernel 分派，但设备数学、访存、通信字节和依赖仍在。\n\n对桶 b 记 `G_b=(V_b,E_b,Π_b,A_b,Q_b)`：`V_b` 是 kernel、copy、memset、event、子图或条件节点等节点；`E_b` 是依赖边；`Π_b` 是节点参数、launch 配置和编译/分派选择；`A_b` 是重放持续引用的虚拟地址集合；`Q_b` 是工作队列、metadata、partial output 和输出槽的容量上界。实际第 t 步的请求集合为 `R_t`，其 token、位置、页表、有效长度、adapter 版本和 scale 写入稳定缓冲。普通静态图可写成 `Y_t=F_b(X_t; A_b,Π_b)`，其中地址与布局固定，内容可以变化；若使用条件节点或固定 grid 的工作队列，`F_b` 还能依据设备数据选择执行体或消费不同队列项，但容量仍受 `Q_b` 限制。\n\n必须区分三种“固定”。第一，图的拓扑、节点参数、launch 配置和虚拟地址在实例化后固定；第二，图中张量的形状、stride 与 dtype 每次重放相同；第三，地址里的内容可以在重放前更新。把一个 Python 整数改掉，不会自动改变捕获时写入 kernel 参数的值；若要改变节点参数，需要接口支持的节点更新或另一张图。相反，设备 kernel 从 length tensor 读取的值可以变化，前提是 kernel 本身和图容量接受该范围。\n\n状态至少包括：`bucket_state`（absent、capturing、ready、replaying、quarantined）、可执行图 `E_b`、私有池和稳定缓冲、`slot=(id,gen,state,last_read_event,consumer_event)`、计划 `plan=(sig,cta_queues,reduce_map,workspace_region)`，以及每个输出槽的消费者。输入是逻辑请求和其设备值；输出是本步 logits/attention 结果、写入的 KV 或后续采样输入。只有“图已实例化”并不表示某个槽的内容已就绪；只有“设备 kernel 返回”也不表示外部消费者已经读完输出。\n\n## 合法性：什么能进入捕获，什么必须留在图外\n\n捕获合法性首先来自 stream 捕获语义，而不是性能偏好。捕获应在非默认的源 stream 上开始；被捕获的 stream 不执行，而是把工作追加到内部图。多 stream 捕获可以由源 stream 经 event 分叉，再在结束前经 event 汇合到源 stream；等待的事件必须来自同一 capture graph，或由接口明确允许为外部事件。捕获期间禁止同步或查询被捕获 stream、event 以及覆盖它的更大执行句柄；同一进程同一时刻通常只允许一个 capture，且不能被未捕获的 CUDA 工作混入。违反这些条件的捕获可能直接失效，而不是得到一个稍慢的图。\n\n第二类合法性是控制流与形状。基于 CPU 数据的分支、host 读回、设备到 host 同步不能在捕获中执行；CPU 工作即使位于捕获上下文，也不会成为图节点，重放时会被省略。每次重放必须读写同一组虚拟地址，张量形状、stride 和布局固定。数据相关控制流若要进入图，必须使用接口支持的条件节点，或把决策写成固定容量工作队列中的数据，由固定 grid 的 kernel 消费；不能把普通 eager 分支假装成静态图。由此可知“batch 大小固定”不等于“总 query token 数固定”：prefill 的打包 query 行数、页索引数、tail 长度和 partial output 数都是独立容量维度。\n\n第三类合法性是地址与生存期。捕获期间的分配通常来自图私有池，私有池与图及捕获期间创建的张量同生命期。默认每次捕获一个私有池可以避免图之间互相覆盖；多图共享一个池只在它们总按捕获顺序重放、从不并发，且输出在可能被覆盖前复制时才安全。稳定地址解决的是 kernel 参数引用问题，不解决内容竞态。图引用的输入、metadata、workspace 和输出必须在整个在途区间保持有效；提前释放会让重放访问非法地址或读到被新对象复用的内容。\n\n第四类合法性是图更新能力。实例化后的拓扑固定在实例化时；整图更新要求更新图与原图拓扑相同、节点参数属于允许更新的类型，单个节点更新也只覆盖接口列出的参数。启用/禁用节点可以复用同一张图，但不会自动改变节点参数。形状、布局、kernel 类型、地址池或节点数变化超出更新规则时，必须重新实例化或重捕获。同一个 `cudaGraphExec_t` 不能与自身并发执行，对同一可执行图的多次 launch 按顺序排队；需要真正并发的两个重放，应使用不同的可执行图，并为它们分别准备 buffer 和 event。stream 只规定图与其他异步工作的外部顺序，不限制图内部的并行度。\n\n完整捕获与分段捕获是方案选择。完整捕获能减少更多 host 提交，但要求整段路径都兼容；动态调度、attention 计划准备、CPU grammar、数据相关的结果处理通常留在图外。分段捕获把稳定区域分别图化，保留控制边界，增加图间提交和中间缓冲，却降低对动态部分的约束。选择依据应是 host 开销位于何处、跨段中间状态多大，以及每段是否真正满足上述合法性；“使用 CUDA Graph”这个布尔值不能描述捕获覆盖。\n\n## 核心算法：捕获、计划与重放的状态机\n\n下面的伪代码给出一个可实现的骨架。它不规定具体框架 API，只固定输入、输出、顺序和失败边界。\n\n```pseudocode\n算法 CaptureBucket(b):\n输入：桶 key b（模式、B_max、Q_max、dtype、head 几何、page 容量、后端、adapter、投机长度等）\n输出：可执行图 E_b、私有池 P_b、稳定缓冲 A_b，或失败并回退\n\n若 b 的形状、后端或地址池没有固定：返回“不合法”\n预留 P_b 和 A_b，包括输入、metadata、workspace 与输出槽\n在副作用隔离的副 stream 上以 b 的代表形状预热；预热完成后再开始捕获\n在非默认源 stream 上 begin capture\n  只发出捕获安全的工作；所有指针来自 A_b\n  不读回 host 值，不改变张量 shape/layout\n  分支 stream 从源 stream 经 event 分叉，并在 end capture 前经 event 汇合\n  不调用会同步或查询被捕获 stream 的接口\nend capture\n若捕获结果为 invalid：丢弃临时图和 P_b；返回失败\ninstantiate；若失败：销毁可执行图并返回失败\n检查工作队列、partial output、输出槽和 metadata 的容量均不超过 Q_b\n把桶状态设为 ready，给每个槽登记 gen=0\n返回 E_b, P_b, A_b\n```\n\n```pseudocode\n算法 PrepareAndReplay(R_t, mode):\n输入：本步逻辑请求 R_t、模式 mode、模型/adapter 版本\n输出：本步输出槽和完成事件，或回退到 eager/拒绝\n\n1. 由 R_t 生成 BucketKey，检查请求数、query 行数、page 索引数、partial 上限和版本\n2. b ← 选择一个合法桶；若没有合法桶，按策略回退 eager 或拒绝\n3. plan ← PlanCache 查找 b 与 PlanSignature；若缺失或过期，按准备段重新生成\n   若 plan 超出固定 workspace/队列上界：不能截断；回退或拒绝\n4. slot ← AcquireSlot(b)\n   AcquireSlot 只返回 FREE 槽；若没有 FREE 槽，先等待/推迟，不能覆盖 in-flight 内容\n   slot.gen ← slot.gen+1；slot.state ← WRITING\n5. 把真实请求写入 slot 的输入、长度、页表和 metadata\n   未使用行填入 backend 明确支持的安全值；dummy 页不得与真实页混写\n6. 以 stream 顺序完成必要的 H2D/metadata copy\n   记录 input_ready=(slot.id, slot.gen)\n   slot.state ← READY\n7. 若同一可执行图已有更早 launch：按接口顺序排队；若需要并发，使用另一可执行图和独立槽\n8. launch E_b，参数指向 slot 的稳定地址；记录 release_event=(slot.id, slot.gen)\n9. 设备完成后 slot.state ← DEVICE_DONE\n   输出消费者只有在对应 release_event 完成后读取\n10. 输出被所有消费者读完，且没有迟到的旧代读写者时：\n    slot.state ← CONSUMED；随后 FREE\n   若等待超时或失败：保留对象和错误状态，不能把等待超时当作已释放\n```\n\n正确性不变量如下。其一，`E_b` 的每个指针指向 `A_b` 中同布局、同生命期的槽；其二，任何写入只发生在 `FREE` 槽，且守卫事件至少覆盖上一代最后读取；其三，输出槽只在所有消费者完成后复用；其四，`PlanSignature` 覆盖计划真正依赖的 batch 成员、query 分段、页索引、tail、mask、后端和几何；其五，容量不足时回退或拒绝，不截断页表、不丢弃 partial output；其六，同一可执行图不并发自身，并发图各自拥有事件和可写资源。\n\n## 变长批与图桶\n\n把容量 B 的图用于实际 b≤B 个请求，必须同时检查请求数、总 query token、页索引数和输出容量。桶 key 至少包含 `(model_id, mode, B_max, Q_max, P_max, dtype, Hq, Hkv, D, page_size, attention_backend, adapter_rank/layout, spec_len, mask_kind)`；只记录“batch=8”不足以解释图是否可复用。固定 batch 不固定总 query tokens：混合 prefill 的打包布局、每请求 query 段和 partial output 数需要另行表达。桶只承接所有维度都落在容量内的请求；越界时就切换合法图或普通执行，不能通过截断页表让重放勉强运行。\n\n填充行必须按所选 backend 的规则处理。长度为零未必被所有 kernel 接受；使用 dummy 页时，必须保证该页是独占的 scratch 或 kernel 明确忽略的区域，不能让 padding 行写入真实页。若 kernel 对零长度仍有未定义行为，应填一个有效但被 mask 的安全行，并验证输出路由只取真实行。采样参数、位置、KV 写入和 logits 路由都要按真实行映射；任何“shape 正确”都不足以发现把输出行交给了错误请求。\n\n桶选择不是简单的“最小容量”或“越多越好”。合法桶 b 的候选比较至少包括：该分布下的设备执行量 `D_exec(b,n)`、padding 增量 `D_pad(b,n)`、host 提交与计划成本、捕获摊销、图池驻留，以及对 KV 准入的挤占。若多个容量只在一个维度上不同，最小的合法桶通常减少 padding，但更多桶会增加图、workspace 和持久缓冲。设四个桶各额外占 64 MiB，合计 256 MiB；若同一资源池中每 token KV 为 128 KiB，这些字节的机会成本是 2,048 token 的 KV 容量。这是设定算例，不表示真实图一定占该数值。若多个桶共享私有池且从不同时重放，容量账应按最大活跃集合而不是简单求和；若它们可能并发，则按物理并集计。\n\n## Attention 计划与固定 grid 工作队列\n\n面向服务的 attention 接口常把依赖 metadata 的准备段与依赖张量的执行段分开。准备段消费 query 分段偏移、页索引区间和每条请求的末页有效长度，选择 kernel 变体，计算工作划分并写入 workspace；它在 host 上执行，可能包含设备长度读回、mask 打包或布局转换，通常不能进入图。执行段消费 query/key/value 张量和准备好的计划；当 batch 容量固定、metadata 缓冲在对象生命期内保留、workspace 地址稳定时，执行段可以进入图。计划在相同几何的各层间可以复用；batch 成员、query 分段、KV 长度、页索引、mask、adapter 或变体条件改变后，旧计划失效。\n\n三类 metadata 的单位不同：query 分段偏移以 token 行计，页索引区间以页索引数组中的位置计，末页长度以有效 token 计。计划缓存 key 必须覆盖这三类量，还要覆盖 head 几何、page 布局、dtype、mask 和 backend 特化。源 KV 未变不保证准备结果未变：batch 成员、总 query token、页索引、tail 长度或 kernel 特化条件都可能变。布局转换若需要完整复制（例如带块级 scale 的量化格式），其读写字节和临时缓冲应计入准备段，不能当成免费视图。\n\n若一个 query tile 的 KV 被切成多个区间，每个 partial 是 attention state：`LSE(I)=log Σ_{i∈I} exp(q·k_i)`，`O(I)=Σ_{i∈I} exp(q·k_i−LSE(I))v_i`。对不相交的 I、J，`LSE(I∪J)=log(e^{LSE(I)}+e^{LSE(J)})`，`O(I∪J)=(e^{LSE(I)}O(I)+e^{LSE(J)}O(J))/(e^{LSE(I)}+e^{LSE(J)})`。这要求分区不重叠、score 定义和 LSE 底数一致，空状态显式处理；不同分区树仍会改变浮点舍入。\n\n固定 grid 的工作队列是一种把动态任务放进静态图的表示。下面是一个整数化的计划骨架，来源于 FlashInfer 论文 Algorithm 1 的思想；具体实现的舍入、空集合和 partial 上界必须另行声明，不把该骨架当成所有接口的保证。\n\n```pseudocode\n算法 BuildWorkPlan(q_lens, kv_lens, Tq, C, alpha, beta):\n输入：每条请求的 query 长度 q_lens、KV 长度 kv_lens、query tile Tq、固定 CTA 数 C\n输出：每个 CTA 的工作队列、partial/final reduction map，或容量失败\n\n若 Tq<=0 或 C<=0：拒绝\n若某条 q_i>0 且 kv_i=0：拒绝；q_i=0 的请求可跳过\ntotal ← sum_i ceil(q_i/Tq) * kv_i\n若 total=0：返回空队列和空 reduction map\nL_kv ← max(1, ceil(total/C))       # 论文给平均分块长；这里给出整数上界选择\nW ← 空集合\nfor 每条 q_i>0 的请求 i:\n  for query tile t=0..ceil(q_i/Tq)-1:\n    lq ← min(Tq, q_i - t*Tq)\n    for 把 kv_i 切成长度不超过 L_kv 的区间 [kb,ke):\n      把 work(id,i,t,lq,kb,ke,len=ke-kb) 加入 W\n按 (-len, i, t, kb) 排序 W\nheap ← {(0,c) for c in 0..C-1}\nfor w in 排序后的 W:\n  (cost,c) ← 弹出 heap 中最小项\n  queues[c].append(w.id)\n  把 (cost + alpha*w.lq + beta*w.len, c) 压回 heap\nfor 每个 final (i,t):\n  若该 final 只有一个 work：直接写最终输出\n  否则：写 partial 区，并在 reduction_map 中登记确定性的合并顺序\n返回 queues、reduction_map 和 partial 数量；超上界则失败\n```\n\n排序和 heap 的并列规则必须显式。论文的调度以相同长度信息产生确定性的 CTA 队列和合并顺序，并避免原子累加；这不等于任意不同计划之间逐位相同，浮点归约树仍会改变舍入。固定 grid 也不自动保证归约顺序确定：固定 grid 只固定 launch 配置；归约顺序由队列、reduction map 和合并 kernel 决定。两者要分别证明。\n\n硬件映射上，捕获的 attention kernel 以 C 个 CTA 启动；每个 CTA 从固定 workspace 读取自己的队列项，队列项指出请求、query tile 和 KV 区间。K/V 最后一维保持连续，线程按 head 维合并读取到共享存储，再进入矩阵指令；graph 不会改变寄存器、共享存储或线程布局。CTA 数过少会留下空闲 SM，过多会增加每 CTA 的资源压力和队列开销；`C=k×SM` 是来源实例的起点，不是所有 GPU 和 tile 的最优常数。partial output 由后续合并 kernel 按 reduction map 读取；attention 与合并之间的依赖是图边或 kernel 边界。固定 workspace 偏移使每次重放的指针相同，计划内容异步复制到设备固定区段，再由固定 grid 的 kernel 消费。短 KV 的请求可以不分块直接写最终输出，省掉合并；长 KV 才进入 partial 区。partial 数量必须按所选切分策略建立上界，论文的 `2×CTA` 上界依赖其“只切长请求”和“每 split 最多两个 tile”的规则，换成别的策略要重算。\n\n## 时间所有权与并发\n\n图 replay 是异步提交。设 replay n 正在读取页表，CPU 或另一 stream 却把同一地址写成 n+1 的页表；即使地址稳定，图也会把两代状态混在一起。稳定地址解决捕获时的引用，不解决内容竞争。每个输入、metadata、workspace 和输出槽都需要代次与完成事件。\n\n槽的生命期可写为 `FREE -> WRITING -> READY -> IN_FLIGHT -> DEVICE_DONE -> CONSUMED -> FREE`。输入和 metadata 在设备最后读取后可以释放；输出要等外部消费者完成；若实现用一个复合槽，则保守地等两者都结束。`gen` 每次取得槽时递增；event 记录 `(slot.id, gen)`；迟到的完成不能释放新一代。单缓冲时，下一次写入会与在途读取重叠；双缓冲时，写入另一个槽可以让主机准备与当前重放并行。槽数由在途时间与准备周期决定：若槽被占用的时长为 L、重放周期为 P，在边界可立即复用时至少需要 `ceil(L/P)` 个槽；长尾仍要由真实事件保护，不能用平均 L 保证安全。\n\n多图共享同一私有池或同一 workspace 有额外限制。共享池若要求按捕获顺序、且从不并发，则两个图不能任意乱序重放；一个图的重放可能覆盖另一个图的输出，除非在覆盖前复制。共享 workspace 的写写冲突与输入事件是不同关系：一个输入 event 保护输入，不自动保护 workspace；两个图单独执行正确，不证明同时 replay 正确。并发时按最大活跃图集合计算容量，并按对象分别建立事件。\n\n取消请求也不能立即把图仍引用的 KV 页重新分配。业务取消可以先禁止新的提交和可见输出，然后等待图、传输和输出消费者的最后使用；代次防止迟到结果污染新请求，event 防止物理槽提前复用。卸载权重或切换 adapter 时，固定 staging 地址只有在旧 replay 的最后读取完成后才能覆盖。主机上存在新权重，不代表设备数据已就绪；设备地址仍有效，也不代表内容版本正确。\n\nLoRA 的固定 rank 桶可以承接较小 rank，前提是 padding 对低秩增量的数学贡献为零，scale、routing 和层选择一致。对于 `ΔW=sBA`，在 A/B 的 padding 位置放零可以使相应求和项为零；但如果后端按指针直接读取未初始化槽，或改变了 scale 的乘入位置，这个前提不成立。捕获了具体 adapter 指针时，切换 adapter 需要受支持的图更新、另一张图或固定槽填充；通过稳定 metadata 间接选择 adapter 时，仍要保证目标槽、rank、布局和在途代次满足契约。\n\n## 成本：捕获、提交、padding、驻留与同步\n\n设 eager 每步有 K 个需要提交的设备项，单个 host 提交成本为 h，另有计划、采样参数准备等 host 成本 p；图路径一次图 launch 的 host 成本为 g，metadata copy/选择等为 u，桶和计划查找为 q。则\n`H_eager ≈ K·h + p`，`H_graph ≈ g + u + q`，`ΔH = H_eager - H_graph`。\n设备侧仍为 `D_step = D_exec + D_pad + D_copy`。只有当主机路径限制在关键路径上时，`ΔH` 才会出现在完成时间里；在 host 与设备可重叠且无串行依赖的稳态，单步周期至少为 `max(H,D)`，但在单条自回归链上，采样反馈、下一 token 输入和必要同步仍构成依赖路径，不能把两个阶段简单相加，也不能把图 launch 当作消除了设备工作。更准确地说，应按事件图求关键路径：图边、stream 事件、输出消费者和 token 反馈谁在串行段上，谁才进入周期。\n\n一个设定算例：K=80，h=15 μs，则 eager host 项约 1.2 ms；图路径 g=50 μs、u=10 μs、q=5 μs，共约 65 μs。若设备执行约 0.9 ms，原来 host 路径约 1.2 ms 可能压住完成时间，图路径后设备约 0.9 ms 成为主项；若设备执行为 12 ms，则两种 host 路径都小于设备，单步墙钟主要由 12 ms 决定，图的收益不能从 1.2 ms 的 host 差直接外推。以上是成本模型，不是 GPU 测量。\n\n捕获和实例化是一次性冷成本。若捕获、预热和实例化合计 `C_b`，该桶预计重放 `N_b` 次，则每次摊销 `C_b/N_b`。例如冷成本 0.4 s、每次只省 0.3 ms，临界复用次数约 1,334 次；若该桶只出现 100 次，冷成本摊到每次约 4 ms，反而压过节省。桶频率、服务生命周期和版本变更都要进入这个除法；重建频繁时不能用总调用数计算摊销。\n\npadding 的成本不能只用浪费的槽位比例。容量 16 的桶承载 10 个有效行时有 6 个槽未承载有效请求，但 kernel 是否跳过、矩阵形状是否被补齐、attention 是否对 dummy 行执行，决定了 `D_pad`。若 padding 行仍执行矩阵和 KV 读取，设备工作量会增加；若 kernel 按有效长度跳过，增加可能很小。桶选择应对同一分布比较 `D_exec(b,n)+D_pad(b,n)`，而不是假设 padding 一定按比例耗时。\n\n驻留成本包括图私有池、每桶 workspace、metadata、输入/输出槽和并发在途缓冲。容量账应写为\n`M_total = B_fixed + B_kv + B_ws + max_live(Σ M_bucket) + B_slots + B_other`，\n其中并发共享池按最大活跃集合计，分开的池按并集计。更多桶减少 padding，却可能减少可准入 KV token 数，进而增加排队；图池与 KV 争同一显存时，吞吐和时延不能只看单步 kernel。通信方面，图可能减少集合通信的提交次数，但不会减少字节；collective 能否捕获取决于库版本和设置，不能从“图支持 kernel 节点”推出所有通信都可捕获。准备方面，计划生成、页表复制、mask 打包和布局转换仍在；同步方面，槽位 event、权重换入 event 和输出消费者等待仍在。\n\n## 条件变化后的保留、调整与放弃\n\n| 条件变化 | 保留的约束 | 调整候选 | 放弃/反转信号 |\n|---|---|---|---|\n| 设备已经饱和，host 提交不是关键路径 | 依赖与输出归属不变 | 保留 eager 或只捕获少数稳定段 | 图减少 host 时间但墙钟几乎不变 |\n| 短 kernel 多且 host 路径压住周期 | 地址、形状、依赖合法 | 增加桶覆盖高频形状，分段捕获 | padding 或槽位等待抵消提交收益 |\n| batch/长度集中 | 容量和版本检查不变 | 少量密桶；按真实分布摊销 | 长尾频繁越界，回退成本高 |\n| KV 容量紧张 | 图仍须有合法 workspace | 减少桶、缩小输出 slack、共享池但串行 | 新桶挤出 KV，准入和完成率下降 |\n| 计划每步变化但仍在固定队列上界内 | 计划签名完整 | 计划留图外，固定 grid 消费队列 | 队列/页索引越界，不能截断 |\n| 多 stream 并发 | 每个对象有最后使用事件 | 独立可执行图、独立 workspace/池 | 共享池乱序或并发导致输出污染 |\n| adapter/权重频繁切换 | 版本和布局契约 | 固定槽填充、受支持节点更新或新图 | 切换成本高于收益，改 eager |\n| 图更新接口只支持小参数变化 | 拓扑和地址池限制 | 单节点更新、启用/禁用节点 | 需要改 shape/布局，重新实例化 |\n\n## 诊断：竞争解释、区分实验与反证修正\n\n先固定逻辑输入、工作量、正确性和计时边界，再比较图与 eager。主机时间戳与设备时间域需要可靠关联；累计 kernel 时长不是墙钟关键路径；捕获、首次实例化和预热应与稳态分开报告。\n\n| 竞争解释 | 可区分预测 | 干预与观测 | 反证后的修正 |\n|---|---|---|---|\n| padding 让设备工作增加 | 更大桶在同一真实 batch 上设备时间上升，host 提交近似不变 | 固定输入比较精确桶与过大的桶；观察实际执行的 query 行/KV 区间 | 若设备时间不变，检查 kernel 是否跳过 dummy 行，不要继续归因 padding |\n| host 提交仍不是瓶颈 | 降低 launch 次数后墙钟几乎不变，设备区间仍占满 | 减少图覆盖但保持设备工作；比较 host 空档与设备时间 | 若图显著缩短墙钟，host 路径原先确实在关键路径 |\n| metadata 代次竞争 | 串行化后正确，双缓冲未加 event 时偶发混批 | 延迟写入下一代；记录 slot.gen、读事件和输出内容 | 若串行仍错，检查计划 key 或页表内容，不只怪双缓冲 |\n| 共享 workspace 冲突 | 单图正确，两图并发错误；分开 workspace 后恢复 | 两 stream 并发 replay，分别替换 workspace 和私有池 | 若换 workspace 无效，检查 KV 页写和输出槽 |\n| 图池共享顺序错误 | 按捕获顺序重放正确，交换顺序后输出被覆盖 | 交换两个桶的重放顺序；复制输出后再比较 | 若复制输出后仍错，检查输入槽是否也被共享 |\n| 权重/adapter 版本未就绪 | 等待换入完成事件后正确，地址始终有效 | 延迟加载完成事件；记录版本和最后读取 | 若等待后仍错，检查 graph 参数是否仍指向旧版本 |\n| 同一可执行图被当作可并发 | 两个 launch 实际串行；换成两个可执行图后才重叠 | 观察同一 exec 的排队与不同 exec 的时间线 | 若不同 exec 仍串行，检查 stream 依赖和共享资源 |\n\n反例一：单 metadata 槽在 replay n 读取页表时被写入 n+1。输出可能混合两代页表，且地址检查完全通过；必须用代次和最后读取 event，或至少用 stream 顺序的独立槽。反例二：为了适配图容量截断页索引数组。短测试可能仍产生 shape 正确的输出，但长上下文会漏读 KV；正确做法是回退或拒绝。反例三：padding 行使用与真实请求相同的 dummy 页并执行 KV 写入，会把无效行写到真实状态；必须使用独占 scratch 或确保 kernel 不写。反例四：两个图共享私有池但乱序重放，后一个图的输出可能覆盖前一个图的仍被消费者读取的缓冲；共享条件必须同时包含顺序、非并发和输出复制。\n\n验证应覆盖反复捕获/释放、跨桶切换、边界 batch、空请求、非整页、并发 replay、取消后迟到完成、卸载槽复用、adapter 更换和超容量输入。检查最终输出与独立 reference、持久缓冲代次、峰值分配、释放后的稳态占用和回退路径；不能只以一次 replay 的 kernel 时间判断图策略。CPU 状态模型可以检查覆盖、代次和容量不变量，但不能证明真实 GPU 的内存可见性、图内部调度、时钟或吞吐；这些需要目标设备上的独立测量。\n\n## 来源与推导\n\n- [S-TORCH-CUDA：PyTorch — CUDA
