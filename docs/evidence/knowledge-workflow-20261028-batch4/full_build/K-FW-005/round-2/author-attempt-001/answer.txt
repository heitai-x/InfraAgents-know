{"chapter":"# K-FW-005：CUDA Graph：捕获边界、计划状态与变长服务\n\nCUDA Graph 重放一组已捕获的设备工作；服务动态性通过稳定缓冲中的值、分桶和捕获外控制面承接。图降低的是重复提交与部分执行结构成本，不自动消除设备计算、主存流量、准备段或内容竞争。\n\n## 图固定的对象与可变内容\n\n把一次捕获记为图 `G=(V,E)`：节点是 kernel、拷贝、memset、事件等待/记录、条件节点或子图等操作，边是依赖。实例化得到可执行图 `E_G`，重放 `R(E_G)` 按同一节点参数和同一组虚拟地址提交工作。需要区分三类状态：\n\n- `A_G`：图参数中固定的虚拟地址集合。每次重放读写同一组地址，地址必须持续有效。\n- `κ_G`：捕获/实例化时确定的形状、stride、dtype、布局、kernel 变体、grid 拓扑与标量常量。\n- `D_t`：第 t 次重放前写入这些地址的内容，包括输入 token、position、页表、有效长度、adapter 槽和采样参数。\n\n因此，图固定的是地址、拓扑、形状和 kernel 序列，不是地址里的内容。图中某个 kernel 读取 length tensor，replay 时该 tensor 的值可以变化；但若变化改变 grid、页表项上界、dtype 或 kernel 变体，原图就不一定合法。把一个 Python 整数改掉不等于图节点参数已更新；把新数据拷入静态输入张量也不等于所有 metadata 和 workspace 已属于同一代。\n\n一个可重放状态可以写成 `(E_G, A_G, κ_G, D_g, g)`，其中 `g` 是内容代次。合法性至少要求：`κ_t=κ_G`；`A_G` 中每个被读地址在消费期间有效；`D_g` 已写完并被正确发布；所有设备读者只看到 `g` 代内容；输出只按 `g` 的行映射解释。地址稳定只解决第一个引用问题，不解决后三项。\n\n## 合法捕获、实例化与重放\n\n在 PyTorch 固定文档的语义范围内，capture 期间不得与主机同步，不得有基于 CPU 或一般 GPU 数据的动态控制流，不得运行未被捕获的 CUDA 工作；CPU 工作不被记录，重放时会被省略；每次重放读写同一组虚拟地址，动态 shape 被禁止；capture 必须在非默认 stream 上进行，且同一进程同时只能有一个 capture。跨 stream capture 必须从初始 stream 分叉、在结束前重新汇合，事件依赖也要属于同一 capture graph。违反这些条件可能报错，也可能产生静默数值错误。一般 CUDA 图另有条件节点和设备端图启动等能力，但某个框架是否暴露、是否允许某个控制流，必须按该版本接口核对，不能从“CUDA 支持图”推出“任意 Python 分支可捕获”。\n\n重放侧还有几项独立条件：\n\n1. 捕获后的图可以在任意 stream 上启动；stream 只规定与其他异步工作的顺序，不限制图内部并行度。\n2. 同一个可执行图不能与自身并发执行；对同一 `graphExec` 的多次 launch 会按顺序排队。若需要两个批次真正并行，需要不同的可执行图或不同的图实例，并给它们不同的输入、输出和 workspace。\n3. 捕获期间的分配通常来自图私有内存池。默认每次 capture 一个池；多图共享一个池只有在总按捕获顺序重放、从不并发时才安全，而且一张图重放可能覆盖另一张图的输出，除非消费者先复制。共享池节省容量，不提供并发隔离。\n4. 图内存节点的虚拟地址在分配节点生命期内固定，底层物理页可以按 GPU 顺序生命期复用或别名；这与框架私有池不是同一实现层，但共同结论相同：地址稳定不等于物理内容独占，也不等于上一代读者已经结束。\n5. 图更新不是任意改写。整图更新通常要求拓扑一致、依赖顺序可比；节点更新也有节点类型、函数上下文、内存类型等限制。即使允许更新一个指针，也仍需证明该地址当前属于正确代次。\n\n完整捕获能减少更多 host launch，但要求整段路径兼容；分段捕获把稳定区域分别图化，保留控制边界，代价是更多图间提交和跨段中间状态。选择依据是 host 开销在何处、跨段状态多大，而不是“是否使用了 CUDA Graph”这个布尔值。\n\n## 从请求到图桶：选择、填充与提交\n\n设请求 i 的需求向量为 `d_i=(mode, query_rows, page_slots, dtype, head_geometry, adapter_slot, spec_depth, mask_kind, backend)`，图桶 b 的容量向量为 `c_b`。若存在某个坐标使 `d_i` 超过 `c_b`，桶 b 对该请求不合法；不能截断页表、把超长历史映射到少量页或忽略 adapter 差异来强行重放。桶 key 必须覆盖真正影响 kernel 特化和地址布局的项；固定 batch 并不固定总 query token，混合 prefill 的打包布局、LoRA rank、投机长度和 attention backend 都可能需要另立桶。\n\n一个完整的选择与提交过程如下。\n\n```pseudocode\n算法 1：从活跃请求选择兼容图桶并提交一代重放\n输入：请求集合 R 及其需求向量 d_i；图桶集合 B；\n      每个桶 b 的容量 c_b、池占用 m_b、执行估计 D_b；\n      槽位集合 S；当前逻辑时刻 now\n输出：选中的桶 b、槽位 s、代次 g、输出行映射；或拒绝原因\n\n1. 对每个 i∈R 计算 d_i，剔除上游未就绪、版本不兼容或页表不完整的请求\n2. 候选 C = { b∈B | 对全部 i∈R，d_i ≤ c_b 且 b 的签名与请求契约一致 }\n3. 若 C 为空：尝试拆成多个兼容桶或拒绝；不得截断页表、长度或 adapter 状态\n4. 对每个 b∈C 估计：\n     W_b = 按容量 c_b 填充后的执行工作量\n     W   = 实际有效工作量\n     cost_b = D_b(W_b) + PlanCost(b) + CopyCost(b) + PoolShare(b)\n5. 选择 cost_b 最小的 b，并检查 KV、workspace、图池和槽位的峰值容量\n6. 从 S 取得一个槽 s，使 s.gen 的上一代读者全部完成；否则等待或降低本轮并发\n7. 在 s 的固定输入/metadata 区写入第 g 代内容：\n     真实行写入 token、position、页表和有效长度\n     填充行写入专用 dummy 页或按 backend 接受的有效零长度表示\n     输出行映射只登记真实行\n8. 需要重新准备的 metadata 在 capture 外生成，写入 b 对应的 plan 区；\n   在 consumer stream 上建立 plan 写完到 replay 的依赖\n9. replay b；把输出、KV 写入和副作用都绑定到 (g, s, 行映射)\n10. 只允许消费者读取已完成且代次匹配的输出；最后消费者结束后才标记 s 可覆盖\n11. 下一次 replay 重复第 6 步；host 调用返回不能当作设备完成\n```\n\n填充行必须按后端有效规则处理。长度为零未必被所有 kernel 接受；使用 dummy 页时，dummy 页不能与任何真实页别名，dummy 行的 KV 写入不能污染真实状态，输出也不能被路由给真实请求。若图内包含对全部行写 KV 的节点，必须给 dummy 行单独的写槽并丢弃其输出；仅在 host 侧把 marker 置零不能阻止设备写。多桶减少 padding，却增加图池、计划缓冲和持久 workspace 占用，从而挤压 KV 容量；因此“最小可行桶”不一定是总成本最低桶。\n\n## 准备段、执行段与固定 grid 数据流\n\n面向服务的 attention 接口常把准备与执行分开。准备段消费 metadata：query 分段偏移、页索引区间、每条请求的末页长度、mask 与 kernel 变体；它可能在 host 上执行，某些长度还要从设备读回，自定义 mask 可能需要打包。准备结果写入 plan/workspace。执行段消费张量和已准备好的 plan，运行 attention kernel、合并 kernel 或输出缩放。准备段通常不能进入图，因为其中包含 host 计算、设备读回或动态分派；执行段在固定 batch 容量、预分配 metadata 和 workspace 地址保持有效时，才可能被捕获。\n\n固定 grid 持久 kernel 可以把动态任务放进静态图，但数据流必须完整：\n\n1. CPU 计划器按请求长度和 CTA 数生成每个 CTA 的工作队列、partial-to-final 映射和 metadata。\n2. 计划写入 pinned 主机缓冲，再异步复制到设备 workspace 的固定区段；同一 stream 上的 replay 必须排在这次复制之后，跨 stream 则要有事件依赖。\n3. 固定 grid 的 attention kernel 从固定队列区读取工作描述，按页表读取 KV，把分区结果写成 `(O, LSE)` 状态到固定偏移。短 KV 请求可不分块，直接写最终输出。\n4. 固定 grid 的 contraction kernel 按映射合并部分状态。对不相交的集合 I、J，合并规则是：\n\n```pseudocode\nLSE(I∪J) = logaddexp(LSE(I), LSE(J))\nO(I∪J) = (exp(LSE(I))·O(I) + exp(LSE(J))·O(J)) / (exp(LSE(I)) + exp(LSE(J)))\n```\n\n5. 最终输出仍按真实 query 行映射写回；填充行、硬 mask 行和空分区必须有明确处理，不能把空状态的负无穷直接相减。\n\n这一表示来自固定论文 v0.2 的设计：计划在 CPU 上按 generation step 生成，复制到设备固定 workspace，attention 与 contraction 使用固定 grid 的持久 kernel。该设计把 workspace 各区段按上界分配：metadata 上界由并发请求数和累计请求长度给出，部分输出最多为 `2×#CTA` 个 tile，每个 tile 大小为 `Tq×Hqo×(D+1)`。这些是论文在特定算法和 A100/H100 条件下的设计事实，不是所有引擎的硬性上界，也不是本库实测。\n\n固定 launch 配置与确定归约是两个独立性质。固定划分粒度可以让归约顺序确定，却不保证 CTA 数不随 KV 长度变化；固定 grid 也不保证合并顺序确定。论文为避免原子累加的不确定性，选择了确定的映射和合并顺序；其他实现可以选不同策略。把“图兼容”直接写成“结果可逐位复现”是错误推断。\n\n## 代次、槽位与工作区的状态机\n\n图 replay 是异步的。replay n 还在读取页表时，CPU 或另一 stream 把它改成 n+1，会把两代状态混合。稳定地址解决 capture 的引用问题，不解决内容竞争。设槽 s 的第 g 代从开始写入到最后一个读者结束的生存期为 `L_s(g)`，启动周期为 `P_s`；所需槽数等于任意时刻重叠的代数上界：\n\n`N_s ≥ max_t |{ g : start_g ≤ t < end_g }|`。\n\n若每代等长 `L_s`、周期为 `P_s`，则 `N_s ≥ max(1, ceil(L_s/P_s))`。若到达不规则，必须按真实事件窗口计算，不能用平均周期替代长尾。槽内协议可写成：\n\n```pseudocode\n算法 2：槽位代次写入门控\n输入：槽 s，拟写代次 g，payload，读者注册表\n\n1. 等待 s 当前代的最后一个读者完成；若仍有读者，不得覆盖 s\n2. 若 g ≤ s.last_published_gen，拒绝本次写入，避免旧代迟到写入\n3. 只写 s 的输入、metadata 和 plan 区；不改动其他代的槽\n4. 设置 s.gen = g，发布 ready(s, g)\n5. 消费者读取前核对 (s, g)；最后消费者完成后登记 last_reader_done(s, g)\n6. 只有 last_reader_done 发生且输出已复制或消费后，s 才可交给下一代\n```\n\n双缓冲、代次槽或事件保护应覆盖输入、metadata、输出和 workspace 的整个在途区间；只保护输入不保护共享 workspace 仍会错误。多图共享同一私有内存池或同一 workspace，只有在其重放顺序和生存期兼容时才安全。并发 replay 与串行 replay 的容量模型不同；同一个 `graphExec` 不能与自身并发，所以“两个 stream 启动同一张图”通常只会串行，若观察到重叠必须核对是否使用了不同可执行图、不同槽和不同 workspace。\n\n取消请求也不能立即将图仍引用的 KV 页重新分配。取消先阻止新的业务提交，再等待在途 replay、输出消费者和必要的 KV 读者结束，最后回收物理页。业务取消通知不证明设备已停止；图重放返回也不证明输出消费者已读完。\n\n## 成本：提交、填充、准备与驻留\n\n设每轮有 K 个短 kernel，eager 路径每次提交与依赖解析成本约 h，图 replay 成本约 g，则主机侧可节省的主要项约 `K·h−g`。但只有当主机提交处于关键路径时，这部分才等量进入墙钟。若设备工作为 D、主机工作为 H，且二者可以重叠，稳态周期近似受 `max(H,D)` 与依赖链约束；若每步必须在 host 读取结果后继续，则还要加入该反馈依赖。图不改变长 GEMM 的算术量，也不自动减少 HBM 读取。\n\n设定 K=100、h=8 μs、g=0.05 ms，则主机项从约 0.8 ms 降到 0.05 ms，净省约 0.75 ms。若设备工作 D=1 ms 且不能充分重叠，粗略从约 1.8 ms 降到 1.05 ms；若 D=20 ms，则只从约 20.8 ms 降到 20.05 ms。两者都是设定算例，不是设备测量；它说明“图节省很多 launch”与“端到端加速很多”不是同一命题。\n\n填充成本要用同一候选、同一输入和时间范围列账。设桶容量为 `c_b`、实际需求为 `d`、执行成本为 `C_exec`，则填充的直接设备增量近似为 `C_exec(c_b)−C_exec(d)`（在成本随容量单调的范围内）。线性层常随行数近似线性；attention 还受可见 KV 长度、页表间接寻址和 partial workspace 影响，不能只按行数比例缩放。若填充增加 61 行却只节省 0.2 ms 提交，而填充执行增加 0.5 ms，则该桶在本轮为负收益。\n\n准备成本是另一项。设每步生成 plan 的成本为 `c_meta`，复制到设备为 `c_copy`，同一 plan 可被 L 层复用，则按层摊销约为 `(c_meta+c_copy)/L`。若每步计划都变化，不能跨步摊销；若两个在途 step 共用同一 plan 区，需要双缓冲，容量为 `2·S_plan`，并在每代之间建立完成依赖。计划缓存 key 必须覆盖 batch 成员、query 分段、总 token、页索引、tail 长度、mask、kernel 变体和布局；源 KV 未变不保证准备结果未变。\n\n驻留成本要计入图池、workspace 和槽位。设定四个桶各额外占 64 MiB，合计 256 MiB；若同一资源池中的 KV 每 token 占 128 KiB，这相当于 2,048 token 的容量。若另有两个在途 workspace 各 8 MiB，又相当于 128 token，合计机会成本约 2,176 token。这个算例只展示图池与 KV 的直接竞争，不表示真实图一定占该容量；多桶减少 padding，却可能降低可准入请求数并增大排队。\n\n## 条件变化后的保留、调整与放弃\n\n| 条件变化 | 保留的约束 | 调整候选 | 反转或放弃信号 |\n|---|---|---|---|\n| batch 在桶容量附近波动 | 地址、形状和行映射仍须合法 | 保持粗桶；或增加细桶减少 padding | 细桶的图池/workspace 挤出的 KV 容量使准入和完成率下降 |\n| 长度分布长尾明显 | 不能截断页表或历史 | 为高频形状设桶，长尾走 eager 或独立路径 | 长尾路径的主机提交或首请求等待超过收益 |\n| adapter、dtype、backend 改变 | 图 key 必须覆盖真正特化项 | 另立桶、受支持更新或固定槽间接选择 | 指针更新成功但内容版本或布局不匹配 |\n| 并发 replay 增加 | 同一 graphExec 不得与自身并发 | 不同图实例、不同槽和 workspace；或串行化 | 共享池/workspace 出现跨批复用污染 |\n| 取消率升高 | 已发出的图仍有读者责任 | 缩短在途、增加可插入边界、代次保护 | 图仍引用 KV 页却被回收，或无效执行超过新增有效输出 |\n| 设备内存紧张 | 地址稳定不等于容量免费 | 减少桶数、缩 workspace、降低并发 | 图池和双缓冲挤掉 KV，OOM 或驱逐增加 |\n| 主机不再是瓶颈 | 设备算术与流量未变 | 保留图作为低开销路径，但不期待大幅加速 | 图重放后墙钟几乎不变且设备区间不变 |\n| 固定 grid 负载不均 | 动态任务表示仍须合法 | 调整 CTA 数、工作队列和合并映射 | 空 CTA 增多、长尾变长或合并成本上升 |\n\n卸载权重时，图捕获的设备地址必须在每次 replay 读取时指向已经完成换入的正确层/版本。固定 staging 地址可以轮流装不同内容，但同一地址还被旧 replay 读取时不能覆盖；换入完成事件应在消费 stream 等待，最后一次读取完成后才允许下次填充。LoRA 路径若捕获了具体 adapter 指针，切换 adapter 需要使用受支持的图更新、另一图或固定槽填充；固定 rank 桶可以承接较小 rank，前提是 padding 对低秩增量的数学贡献为零，scale 与 routing 一致。\n\n## 反例、诊断与区分实验\n\n反例一：容量 64 的桶承载 3 个请求。若每步只节省少量 host 提交，而填充行使线性层和 attention workspace 明显增大，eager 可能更快。反例二：固定 grid 设为 512 个 CTA，但本轮只有 20 个工作块；大量 CTA 空转并增加部分输出和合并，固定 grid 的图兼容性不能抵消负载不均。反例三：两个图共享私有池且并发 replay；单图各自正确不证明同时正确，输出可能互相覆盖。反例四：只更新图节点指针，却让旧 replay 仍读该地址；指针合法不等于内容代次正确。反例五：固定划分粒度后宣称“归约一定确定”，但合并映射仍依赖未排序的完成顺序。\n\n区分实验应先固定逻辑输入、工作量、正确性和计时边界，再改变一个条件。\n\n| 竞争解释 | 可区分预测 | 干预与观测 | 反证后的修正 |\n|---|---|---|---|\n| 主机提交/驱动开销限制 | 图降低 host API 与 kernel 间空隙，设备
