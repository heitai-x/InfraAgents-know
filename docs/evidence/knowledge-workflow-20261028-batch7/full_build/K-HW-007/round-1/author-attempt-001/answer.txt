{"chapter": "# K-HW-007：Apple Silicon：统一内存、带宽与交互式推理\n\nApple Silicon 的统一内存让 CPU 与 GPU 访问同一物理内存池；MLX 数组不预先绑定设备，设备在操作执行时选择。它减少显式的设备间副本，却不消除读取、容量、依赖顺序和主机可见性。交互式推理的可用性由这些剩余成本共同决定。\n\n## 问题与对象：共享物理内存不等于零成本\n\n设物理分配 p 的字节数为 s_p，生命期为 [birth_p, retire_p)。birth 是容量实际被占用的时刻，retire 是逻辑持有者全部释放且已提交的异步访问全部结束后的可回收时刻。时刻 t 的物理容量为\n\nC(t) = Σ_{p∈Live(t)} s_p，  M_peak = max_t C(t)。\n\nLive(t) 按物理身份 p 去重。逻辑数组是视图\n\nv = (p, offset, shape, strides, dtype, version)。\n\n同一 p 上的多个视图、CPU/GPU 各一个引用、共享前缀页的多个读者，不会仅因逻辑引用增多就复制容量；只有产生新的物理分配才另计一份。反过来，数据相同但发生了 dtype、stride、连续布局转换或显式复制时，源和目标可能同时存活，必须分别计账。\n\n请求的已提交状态写成\n\nr = (x[0:n), k, KV, rho, phase, version)。\n\nx[0:n) 是已确认输入，k 是全部必要层 KV 已完成的连续边界，0≤k≤n；rho 是采样状态。token 已经追加到 x 不等于它的 KV 已经完成。一次图执行只覆盖其根集合的依赖闭包，不能把设备上的部分结果当成整个请求状态已经提交。\n\n成本至少有五本账：计算 F/P_eff、跨共享内存边界的字节 Q_j/B_eff、图构造与求值固定开销、主机同步与输出可见性、以及 M_peak 与驻留积分 A_C=∫C(t)dt。P_eff 和 B_eff 是匹配 dtype、shape、布局、并发和访问形态的条件化能力，不是无条件硬件峰值。A_C 的单位是 byte·s，不能直接加到毫秒延迟上。\n\n## 合法性与设备放置\n\n固定 Unified Memory 文档给出的事实是：Apple Silicon 的 CPU 和 GPU 可直接访问同一内存池；创建 MLX 数组时不必指定位置；设备在运行操作时选择。文档示例中，同一个加法可由 CPU 或 GPU 执行，两个没有依赖的加法可能并行；若 CPU 先产生 c，GPU 随后计算依赖 c 的 d，调度器会自动建立顺序，使后者在前者完成后开始。\n\n由此可保留的合法性结论与不能推出的结论必须分开：\n\n| 陈述 | 可保留的结论 | 不能推出 |\n|---|---|---|\n| 同一数组可被 CPU/GPU 操作 | 不必为该访问显式搬一份设备副本 | 每次操作没有访存、没有同步、没有固定开销 |\n| 无依赖的两个操作可并行 | 调度上允许重叠 | 两个执行各有独立完整带宽 |\n| 数组表达式已构造 | 计算图已有节点 | 结果已求值或已对主机可见 |\n| 调度器管理依赖 | 受跟踪的数组操作有顺序 | 框架外的原生指针、其他进程或未声明别名自动有序 |\n| 多个视图指向同一物理页 | 容量只计一次 | 每个读者的流量也只计一次 |\n| 权重量化降低存储 | 容量与每次读取的字节可能下降 | 端到端时间按同一比例下降 |\n\n合法执行至少要求：\n\n1. 访问范围与版本相容。两个操作读写同一物理范围且至少一个写时，必须存在 RAW、WAR 或 WAW 依赖；仅因它们在不同设备上就假定无冲突是不合法的。\n2. 生产者的完成先于消费者的读取。统一地址不取消这条关系；框架自动建立的依赖只覆盖其跟踪到的数组和操作。通过原生指针、外部库或其他进程读写时，需要显式同步、复制或序列化，并单独验证可见性。\n3. 目标设备实际支持该算子、dtype 和布局。来源说明的是统一内存与设备选择机制，不等于任意版本对任意算子组合都已优化或都已实现；不支持的组合应回退、转换或拒绝。\n4. 容量准入成立。M_peak 加上为系统、其他应用和在途转换预留的字节不能超过可用预算。若系统采用压缩或换出，容量数字可能暂时不报错，但交互延迟可能剧烈变化；这不是满足 SLO 的容量证明。\n5. 主机可见性按实际事件处理。打印、转 NumPy、memoryview、保存、读取标量 item 以及用标量数组做控制流，都可能触发求值或等待；构造数组表达式本身不是这些事件。\n\nCPU 与 GPU 同时工作还有一个容易遗漏的条件：并行只说明调度允许重叠，不说明共享内存系统能同时提供两份带宽。若 CPU 预处理和 GPU 推理都要访问同一内存资源，应把两侧需求合并后再估计下界，不能把两个孤立时间直接取最大值当作并发时间。\n\n## 惰性图、依赖和一次交互步\n\n固定 Lazy Evaluation 文档说明：MLX 操作先记录计算图，实际计算只在 eval 时发生；打印数组、转 NumPy、memoryview、保存、标量 item 和标量控制流都可能隐式求值；对同一数组重复 eval 可视为 no-op。文档还说明，过密的 eval 有固定开销，过大的未求值图也有开销；它给出的可用图规模是一个宽范围经验陈述，不是跨版本常数。\n\n把图写成 G=(V,E)，边 u→v 表示 v 消费 u 的结果。对根集合 R，依赖闭包为\n\nC(R) = R ∪ {u | 存在路径 u→…→r，r∈R}。\n\nEVAL(R) 的成功完成只覆盖 C(R)，不能证明另一个独立分支已经完成。来源的 loss 示例正说明这一点：在完整 eval 之前读取 loss 标量，只会做前向 partial evaluation；要连梯度计算和参数更新一起完成，必须把相应根也纳入求值。交互式推理中的同类错误是只把 logits 当作根，却漏掉新增 KV 的全层写入、随机状态发布或响应状态。\n\n为分析异步边界，使用下列状态名；它们是本库的分析状态，不声称 MLX 暴露同名 API：\n\n- CONSTRUCTED：图节点已经建立，未执行。\n- EVAL_PENDING：已提交 EVAL，等待根闭包完成。\n- DEVICE_COMPLETE：设备侧完成证书覆盖本次根闭包。\n- HOST_VISIBLE：主机读取、打印、保存或控制流所需的可见性已经建立。\n- COMMITTED：请求的 token、KV 边界、RNG、版本和响应记录已按同一事务安装。\n- OUTPUT_VISIBLE：已提交输出到达客户端或用户可消费的流。\n- RECLAIMED：最后一个逻辑持有者和异步使用者都已结束，物理容量可重用。\n\n若某实现把 EVAL 做成同步屏障，DEVICE_COMPLETE 与 HOST_VISIBLE 可能在同一事件发生；但不能反过来假定所有求值都异步，也不能把设备完成当成客户端已经收到输出。\n\n```pseudocode\n算法 UNIFIED_INTERACTIVE_STEP\n输入：模型 M；活动请求集合 R；物理预算 C；保留量 C_reserve；设备策略 σ；每请求片长 q_r\n输出：已提交 token/片段、等待或拒绝原因，以及更新后的请求状态\n\n1. 对每个 r∈R：\n   若 r.phase 属于 {CANCELED, FAILED, COMPLETED}：跳过\n   校验 r 的已提交状态、版本和缓存身份\n   b_r=r.k；e_r=min(r.n, b_r+q_r)\n   若 r.n=0：标记 REJECT_NO_INPUT；继续\n   计算新增 KV 字节 Δ_r=(e_r-b_r)*b_kv(r)\n   建立本步预留集合 P_r：新增 KV、工作区、图节点、输入/输出缓冲、必要的转换副本\n2. 按物理对象 p 合并 P_r 与当前活动对象，用并集计算 C_peak\n   若 C_peak+C_reserve>C：\n     按既定策略尝试等待容量、减小 q_r、减少并发、驱逐无引用缓存、转换表示\n     若仍不可行：推迟或拒绝该请求\n     不得把压缩或换出当作满足交互延迟目标的容量保证\n3. 对每个获准的 r：\n   建立图 G_r\n   对每个操作 o：\n     读取输入视图及其 version；选择 d=σ(o,r,M)\n     若 o 需要不同 dtype、stride 或连续布局，则加入显式转换节点\n       转换结果是新物理对象时加入 P_r，并重新检查容量\n     若 o 与同一物理范围上的先前操作存在 RAW/WAR/WAW：\n       加入依赖边 u→o\n     否则不因设备不同而假定无依赖\n4. 确定本步根集合 R_roots：\n   新增 KV 的全层写入、所需 logits、采样随机状态、请求状态发布、响应记录\n   每个改变已提交状态的副作用必须是根或由根覆盖\n5. 调用 EVAL(C(R_roots))\n   等待全部根完成\n   若根包含主机标量、打印、保存或控制流条件：再等待 HOST_VISIBLE\n6. 仅在完成证书覆盖全部根且版本/资格未变时：\n   若需要采样：token, rho_next=SAMPLE(logits, rho)\n   原子提交 r.k=e_r、必要的 r.n、r.KV、r.rho、r.version、r.phase\n   发布响应记录；设备完成但尚未主机可见的结果不算用户可见\n7. 失败或取消：\n   不安装未提交候选；保留旧已提交状态\n   已提交读写仍受保护，直到所有使用者结束\n   记录失败证据和未结束使用者，不把超时改写成完成\n8. 返回提交/等待/拒绝事件；回收只在最后一个使用者结束后进行\n```\n\n该算法把“选择设备”“建立依赖”“求值根闭包”“主机可见”“业务提交”和“物理回收”分开。实际引擎可以把多个请求合并求值、把同一权重的读取合并，或把采样留在设备上；只要根闭包、完成证书、版本和最后使用者条件等价，这些实现选择不改变本章的合法性边界。\n\n## 容量、带宽和驻留账\n\n对普通全注意力模型，令层数为 L、KV head 数为 H_kv、每 head 通道数为 d_h、每元素字节为 b_a，则每 token 的全层 K/V 有效载荷主项为\n\nb_kv = 2 L H_kv d_h b_a。\n\n因子 2 来自 K 和 V。设定 L=32、H_kv=8、d_h=128、b_a=2，则 b_kv=131072 byte=128 KiB/token。四个请求各持有 4096 token 的未共享 KV 时，KV_live=4×4096×128 KiB=2 GiB。若两个请求共享同一段 1 GiB 前缀且物理页确实相同，容量只计 1 GiB；若两个读者都实际读取该前缀，流量仍按两个读者累计，除非 cache 或合并读取另有证据。\n\n容量准入不能只算权重。令 W 为当前权重物理字节，KV_committed 为唯一物理 KV，增量、工作区、图、编译产物、队列、缓存保留和系统预留分别为 delta_live、workspace、graph、compile、queues、retained、reserve，则\n\nM_peak ≈ max_t |W ∪ KV_committed ∪ delta_live ∪ workspace ∪ graph ∪ compile ∪ queues ∪ retained| + C_reserve。\n\n只有确属不同物理对象才相加；若 workspace 已包含某个增量或中间量，不能再计一次。作为设定算例，取预算 C=16 GiB、W=12 GiB、四请求 KV=2 GiB、workspace=0.75 GiB、graph 与队列合计 0.5 GiB、系统及其他应用预留 1 GiB，则列项总和为 16.25 GiB，已经超过预算；减少到三个请求时 KV=1.5 GiB，总和为 15.75 GiB，虽然可行但只剩 0.25 GiB 给分配粒度、转换副本和在途峰值。这些数字是容量推导，不是目标机器测量。\n\n带宽账要区分逻辑有效字节、实际事务字节和 cache 命中。对一次 decode 或一段 prefill，若每个请求的逻辑历史读取为 n_r 个位置，暂时忽略 head 重用、融合和 cache，则\n\nQ_step ≈ Q_W + b_kv Σ_r n_r + b_kv Σ_r Δn_r + Q_CPU + Q_other。\n\nQ_W 是本步实际读取的权重主项，Δn_r 是新增 KV 位置数；共享前缀不会自动减少各读者的逻辑读取。实际设备事务量可能因 GQA 复用、分块、layout、cache 和重复读取而不同，不能把 Q_step 当成已经测得的内存事务。若这些需求主要落在同一共享内存资源上，则\n\nT_mem_lb = Q_shared / B_eff。\n\n设定 W=12 GiB、四请求 KV 读取=2 GiB、CPU 预处理及其他共享流量=0.5 GiB、B_eff=200 GiB/s，则单遍下界为 14.5/200 s=72.5 ms；忽略 CPU 项会得到 70 ms。这个差值是共享资源账的一部分，不是完整端到端延迟；实际还要加入计算、图求值、同步、采样、排队和输出。\n\n固定开销也要在同一时间范围中计。若 m 是本步 eval 屏障数，T_eval_fixed 是每次求值的固定开销，T_sync 是主机同步或控制流等待，T_queue 是排队，则允许计算与访存重叠时有近似\n\nT_step ≈ max(F/P_eff, Q_shared/B_eff) + m T_eval_fixed + T_sync + T_queue。\n\n若某两个阶段实际串行，应把 max 改成相应求和，不能一边声称重叠一边又把全部时间相加。图构造还有 O(|V|+|E|) 的准备成本，过大的图还会增加常驻元数据和调度开销；过密的 eval 则增加固定屏障。两者要按同一候选比较，不能只缩短单次数学时间就宣布端到端更快。\n\n固定 Unified Memory 文档在 M1 Max 上报告过一个设定示例：4096×512 的 matmul 与 512×4 上 500 次 exp，全部放在 GPU 时约 2.8 ms，matmul 放 GPU、exp 循环放 CPU 时约 1.4 ms。它说明在该版本、该形状和该分工下，较小的 elementwise 工作可能更适合 CPU；该摘录没有给出重复次数、误差、完整求值边界、主机同步和背景负载，因此不能把约两倍收益外推到其他形状、其他模型或真实服务。\n\n驻留积分 A_C=∫C(t)dt 描述容量被占用了多久，适合比较缓存保留、长会话和排队策略；它不直接是延迟。一个缓存保留对象可能提高 A_C 却降低后续读取，一个已经逻辑释放但仍在 DMA 或最后读者中的对象可能不降低当前 M_peak，却会延长可回收时间。两者要分别记录。\n\n## 条件改变后的保留与放弃\n\n| 条件变化 | 保留的机制 | 调整候选 | 放弃或修正信号 |\n|---|---|---|---|\n| 权重与 KV 能在预算内共存 | 共享物理内存、无显式设备副本、依赖跟踪 | 调 batch、片长、求值边界和缓存 | 峰值超出预算、系统预留不足或输出仍超时 |\n| CPU 预处理与 GPU 推理并发 | 两侧可在无依赖时重叠 | 限制并发、调整输入队列和分工 | 两侧同时变慢，或共享流量下界超过 SLO；不能只用孤立时间取最大值 |\n| 小 elementwise 循环 | CPU 可能避免 GPU 固定开销 | 按实测比较 T_CPU+T_sync 与 T_GPU+T_sync | 形状增大后 GPU 追上，或 CPU 被其他主机工作挤占 |\n| 长上下文 | KV 的逻辑位置和模型语义不变 | 限制并发、缩短无效输出、量化 KV、分块 prefill | KV 读取或容量成为主项；仅改权重不再缩短关键路径 |\n| batch 增大 | 一次调用可摊薄权重读取 | 增大 batch 提高吞吐 | ITL、KV 容量或尾延迟超过目标；吞吐收益不等于单请求更快 |\n| 需要不同 dtype 或连续布局 | 设备仍可访问共享池 | 插入显式转换或保留原生布局 | 转换副本与流量超过收益，或转换改变了数值契约 |\n| 惰性图过密或过大 | 图构造与求值边界可调 | 合并 eval、拆稳定子图、限制未求值图 | 固定屏障主导或图元数据/驻留主导；只测单个算子不足以判断 |\n| 系统内存压力上升 | 物理容量仍需准入 | 降低并发、释放无引用缓存、拒绝新请求 | 压缩或换出造成延迟尖峰；不能把不报错当作满足交互目标 |\n| 外部原生访问或未跟踪别名 | 显式同步或复制仍可用 | 序列化访问、建立外部完成事件 | 框架自动依赖未覆盖该访问；数据竞争或可见性错误不能归因于统一内存 |\n| 量化降低权重字节 | 容量可能下降 | 比较量化、解包和尺度读取的总成本 | 字节下降但时间不降，检查解包、布局回退和实际事务 |\n\n这些选择都由同一候选、同一输入和同一时间范围决定。没有一种设备分工、batch、片长或量化格式在所有这些条件下都最优。\n\n## 反例、区分实验和检查边界\n\n反例一：把“没有显式 H2D”当成“没有内存读取”。即使 CPU 和 GPU 使用同一物理池，GPU 计算仍要从内存层级取权重和 KV；CPU 预处理也读写同一池。省掉副本只删除了一类传输，不删除 Q_W、Q_KV、Q_CPU 和同步。\n\n反例二：把同一物理页的多个逻辑引用当成多份容量，或反过来把多个读者的流量当成一份。前者会过度拒绝，后者会低估带宽需求。容量按唯一物理对象计，流量按实际消费者和实际事务计，两者不能互相替代。\n\n反例三：只求值 logits 就宣布请求状态已提交。若新增 KV 的全层写入、RNG 或响应发布不在根闭包内，后继步骤会读到缺失或旧状态。根闭包和完成证书必须覆盖本步全部必要副作用，而不是只看一个标量结果。\n\n反例四：用 M1 Max 的 2.8 ms 与 1.4 ms 证明所有 CPU/GPU 分工都能约两倍加速。该来源只覆盖一个形状和一个版本；真实收益受 elementwise 规模、图固定开销、共享带宽、主机负载和求值边界影响。它也不能证明把大矩阵搬到 CPU
