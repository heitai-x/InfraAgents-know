# v2.2-r1：探索边界与专题归属复审

审查日期：2026-10-24。原分支基线：`f640148464929f803a53b55e27ee4cbb83dc8657`。修订版：`base-gpt-6-astra-2026-04-30-v2.2-r1`。固定来源上限仍为 2026-04-30，114 项来源未增删。

## 结论与责任

上一份本地 v2.2 提案存在两个实际设计问题：把“提高可执行性”部分写成了通用构建方法；没有先充分检查既有专题归属，就为 CPU–GPU、接口和分布式执行等内容另建了章。用户指出的问题成立。来源可靠、算例正确、读取通过，都不能为这两项设计决定提供充分依据。

“从空工程构建并优化完整推理引擎”仍是研究任务。它描述任务起点和最终对象；允许哪些库、目标模型、外部行为、质量、资源和性能指标由具体 Task 固定。知识 base 不自行规定先完成什么模块、什么时候才能研究性能、必须拆成几个组件、每个角色必须提交什么中间文件。

修订后的活动目录恢复为 **108 篇原专题**，相对原分支基线深化 **11 篇**，其余 **97 篇**不变。上一份提案的六个新设主题均撤回，有效技术增量归入已有章节。当前是本地可审阅修订，未推送远端。

## 运行时强制与内容引导需要分别判断

所提供的本地 InfraAgents 运行时没有把 U01–U07 编译为阶段状态机，也没有消费上一版 JSON 中的 `expected_outputs`、`required_validation` 或 `runtime_entry` 来限制构建方案。`knowledge_used` 的校验针对声明的条目、版本、读取记录与用途；它并不验证候选实现是否遵循文章中的架构。可不声明使用知识。编辑模板不是运行时指令，冻结的 DESIGN/DIAGNOSIS 由运行时按选定 catalog 生成。

这些代码事实只说明没有这类显式门禁。正文、catalog 摘要、检索词和重复出现的内容仍可能影响模型选择。尤其把单请求、状态、并发、接口与优化排列成一条通用路线时，模型可能把一个例子当成默认施工方案。因此本次实际修改了正文、专题划分、摘要和问题表，没有只添加“非强制”声明。

这个行为风险有内容与接口审查依据，但没有测量过影响大小。本轮没有执行模型或 Agent 对照实验，不能断言旧版必定使所有 Agent 走同一路线，也不能断言修订后不存在探索偏置。初始证据见 [探索边界审计](knowledge_exploration_boundary_audit.json)，修后语义复核见 [内容复审](knowledge_exploration_revision_review.json)。

## CPU–GPU 原本已有，增量应当原位补充

旧基线的 K-HW-003 已讲主机准备、传输、流水、缓冲和生命周期；K-ALG-020 已讲异构计算放置；K-ALG-008 已讲异步调度；K-FW-003 已讲 stream、event 与分配器。共享内存、NUMA 和时间线也有独立专题。把这些再包装成 K-HW-015，会重复解释同一机制、分散主条目，并可能在检索上下文中使同一种实现思路出现多次。

本次保留的是原章缺少的具体关系，而不是新的 CPU–GPU 总章：在明确的固定时间、独立资源及足够缓冲假设下，从稳态周期推到有限批完成时间；按每个缓冲池的占用寿命与发射周期估计必要槽位；多个阶段使用同一资源时按实际共享流量计算带宽下界。旧三阶段模型作为新表达的特例存在，不再并列重复算例。

这些推导也不要求实际引擎一定使用四个组件、双缓冲、独立传输线程或固定执行域。真实任务可以改变放置、批形状、表示、依赖和执行方式，随后重新判断模型前提。归并后的条件与算术由非作者复核，见 [CPU/通信归并复审](knowledge_communication_postmerge_review.json)。

## “可执行”通过哪些细节提高

本轮保留的改进包括张量地址式中的元素/字节单位、view 与物理布局的区别、重叠写的条件、具体缓存 API 的索引语义、collective 的参数及容量对应、组提交与设备完成的区别、ASGI 发送返回与远端消费的区别，以及取消通知被满数据队列阻断的等待环。它们让 Agent 可以实现一个假设、辨别错误、估计成本和设计观察，不要求事先选择一套工程组织。

一条知识需要区分四种性质：Task 要求；所选数学函数或固定版本 API 的语义；有假设的机制与成本解释；一个条件下的设计示例。只有相应前提成立时，相关技术约束才适用。跨 stream 的生产/消费依赖属于运行时正确性关系，不等于要求开发者先写完生产者模块才研究消费者。独立数值参考也不意味着所有早期 microbenchmark 必须等待完整服务实现。

改写后的 [使用场景文档](../../knowledge-use-cases.md) 和 [schema2 问题示例](../../actionable-knowledge/use-cases.json) 没有执行顺序、必选入口或封闭候选集合。七个问题只是当前非穷尽示例，不是七个必须走完的阶段。正文允许整体原型、编译先行、接口与实现共同演化等方式，也允许没有列出的方案；这些例子同样不是新白名单。

复核还修正了相邻旧文中的泛化：单机方案不会自动增加集群或存储服务要求；下界筛选不必先于实验；没有统一的说明链要求；在线服务的 offered workload、吞吐和用户时延只用于相应 Task；任务要求资源有界时，约束的是总在途工作，可以由准入、额度或其他机制实现。固定任务的最终正确性和性能要求没有被降低。

接口与算子的归并后独立复核见 [交叉审查](operator_service_merge_cross_review.json)。各报告记录实际阅读范围；例如 Triton 本轮交叉复核仅涉及尾部归属链接，未声称重新审完其全部原始实现。

历史 v2.2 证据保持原状，仅证明当时被检查的内容。当前验证单独写在本目录，不覆盖旧通过记录。撤回登记见 [withdrawn-chapters.json](../../actionable-knowledge/withdrawn-chapters.json)。

## 对后续研究的含义

知识 base 的价值应通过目标 Task 的引擎完成情况、质量、性能和总成本来判断，同时观察 Agent 是否把建议误作要求、能否依据反证改变设计、能否采用未列出的合法方案。可以由研究者在相同任务、模型、工具和预算下做对照；不要向被评估 Agent 增加“必须产生多种架构”或“必须偏离示例”的任务。

路径相同不能单独判定探索失败，路径不同也不能单独判定创新成功。本次修订解决已发现的流程化表达和重复归属问题，为这样的研究保留条件；尚未证明探索能力、RSI 收益或科研新颖性有所提升。
