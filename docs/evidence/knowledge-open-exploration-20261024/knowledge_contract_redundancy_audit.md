# 三篇新增“契约”章的重复与探索约束审计

**明确建议：三篇均归并已有知识对象，撤销本轮独立新章身份；只保留真正增加解释力的细节。** 这不是删除有用约束或否定接口语义，而是避免把已有机制再次包装成三套通用契约。此前来源与算术审查通过，不能推出新增章节具有独立必要性。

基准为 f640148464929f803a53b55e27ee4cbb83dc8657。完整读三篇当前正文；逐篇读取基准中的算子、attention、streams、数值、图、服务、请求身份、取消、主机运行时、模型生命周期、恢复、并行、collective、传输与拓扑等相关章节。详细 SHA、真实阅读范围与每节归属见 JSON。本审计阶段只读，没有改仓库。

## “契约”怎样影响探索

三个不同层次需要分开。任务给定的模型函数、质量与服务目标决定最终验收；某个具体库的 shape、数值或完成保证只在选择该 API 时适用；组件数量、批次视图、线程/进程划分、数据结构和调用接口则是可以重做的内部设计。把第三类称为不可改变的“契约”，会把一个早期实现假设提升成任务要求。

FW-013 的大部分边界是物理和数学事实，架构约束风险较低。但其三层张量描述不应变成三种必须实现的结构，更不能把当前后端支持域当成自定义 kernel 的不可突破边界。

API-021 风险更明显：三种接口表中的固定批次视图、请求引擎和一次执行，是常见组织形式，不能据此要求所有专用引擎拆成三个组件。单体执行、融合控制、在线增量接口与不同并行组织都可以表达相同外部任务。取消、设备完成和资源回收可以作为观察事件存在，不必各自对应一个 API 或服务层。

SYS-022 的“在实现前……两个以上适用候选”没有来自数学或任务的必然性，应直接去掉固定数量与先后顺序。“可交付产物是一张……边界表”也只能作为可选表达。真实探索可能先有试验性实现、再发现接口需要改变；可以在同一轮同时研究正确性缺陷和性能机会，最终交付仍按原任务要求验收。

数据未就绪不能读、在途地址不能被无序覆盖等关系应保留。这些条件不是替 Agent 指定架构；不同同步、复制、共享、重算和融合设计都可以满足它们。应解释违反关系如何导致错误，以及哪些不同设计能改变成本，而不是要求所有任务生成同一组文档或走同一步骤。

## 最小实施建议

FW-013：把仿射地址式、转置视图算例和必要别名展开并入 ALG-016；把固定 FlashAttention cache_batch_idx 写入边界并入 FW-006。删除 margin、workspace、graph 和预打包公式的第二份叙述，不为保留 20/12/240 或 64/128 的设定数字额外扩章。

API-021：精确的 ASGI Body/Start 发送边界归 SYS-008；同步推进与后台运行的条件比较、控制通知与数据争满队列的反例归 SYS-015。原身份、取消和恢复章已经给出的关系不重复搬写；三接口表可直接撤去。

SYS-022：count、rank布局、每rank输入输出容量以及100r+i验证构造归SYS-005；nonblocking提交细节与该章本轮扩写去重；带启动项的理想ring时间关系及算例归HW-002。其余并行、状态迁移和RDMA正文保持原主章。此分布式判断与communication_content独立对照结果一致。
