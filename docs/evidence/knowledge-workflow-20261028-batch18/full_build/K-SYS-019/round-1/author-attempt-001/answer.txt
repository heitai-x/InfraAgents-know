{"chapter": "# K-SYS-019：部署环境：版本契约、可见设备与真实资源边界\n\n部署描述必须回答一个可检验的问题：这一次执行实际跑在哪些资源上，凭什么它是合法的。镜像、宿主内核与驱动、设备暴露、用户态库、cgroup 层级、文件与网络路径、故障域共同决定答案。容器能够启动只说明进程被创建；它不证明设备真正注入、限额没有被祖先收紧、编译产物与设备能力相容，也不证明代表路径执行过。\n\n本章把“环境”整理成可核对的命题，给出映射链、有效资源折叠、峰值与准入、就绪范围与代次失效的算法，再讨论条件化成本、条件变化后的取舍和区分实验。\n\n## 环境身份与环境代次\n\n把环境写成一个多元组\n\n𝒳 = (α, ρ, δ, μ, β, γ)，\n\n其中 α 是制品与执行身份（权重清单版本、配置、tokenizer/processor、量化与布局元数据、执行器与编译器版本、用户态计算与通信库版本）；ρ 是宿主侧身份（内核版本与配置、驱动版本、容器运行时与低层运行时、设备插件版本）；δ 是设备暴露声明（资源名、副本或访问名额数、注入方式、设备 ID 策略、共享方式）；μ 是逻辑序到物理身份的映射；β 是资源边界（cgroup 层级参数、有效 cpuset、有效配额、内存上限、pids、文件描述符、共享内存与 I/O 限额）；γ 是路径与故障域（挂载、命名空间、网络可达范围，以及与设备共享的机架、供电、交换与存储出口）。\n\nδ 与 μ 必须分开。同一组设备暴露声明在不同下发顺序下会产生不同的 μ；只看 δ 会把“两张卡可用”误当成“这次请求拿到的是我核对过的那两张卡”。\n\n环境代次 ε 是 𝒳 的抽象身份：只要任一可能改变合法执行集合的字段变化，ε 就递增。权重替换、库升级、设备重排、cgroup 限额收紧、挂载点改变都各自产生新的 ε。缓存的就绪证书、编译产物、探测结果和路由决定都绑定在具体 ε 上；𝒳 变了却不换代次，等于用旧证据放行新环境。\n\n## 相容关系是偏序，不是一个标量\n\n合法性由两个对象之间的谓词给出，而不是由版本号比较给出。设制品 α 要求一组条件 R_α（驱动能力、设备计算能力、指令与内存模型、库 ABI、内核接口、设备内存下限、布局与对齐），环境提供一组能力 K_𝒳。执行合法当且仅当 R_α(K_𝒳) 成立，并且观测到的能力集合确实属于这次执行由 μ 选出的设备。\n\n需要保留三条反直觉性质。\n\n第一，逐维匹配。用户态库版本满足下限，不能推出驱动侧接口仍存在；驱动存在，不能推出某个 kernel 路径在目标计算能力上被支持；单卡前向通过，不能推出多卡通信路径可用。\n\n第二，相容不对“更新”单调。新版本可能移除旧接口或改变默认数值行为，因此 K 满足 R 不意味着任意 K′ ⊇ K 也满足 R。不能用版本号大小替代组合验证。\n\n第三，相容一般不可传递。α 与 B 相容、B 与 C 相容，不能推出 α 与 C 相容。\n\n编译产物绑定的是能力集合与编译条件，不是设备型号名。复用编译缓存要核对两件事：目标能力集合仍满足编译时假设的每一条依赖，以及影响该产物的编译条件（布局、常量折叠、捕获地址、算子选择）没有变化。把已编译文件拷到另一类设备上，只有在这两项成立时才合法。\n\n## cgroup 层级：有效值是折叠，不是本级设置\n\ncgroup v2 的资源沿层级自顶向下分配：子组只能分配父组已经获得的资源，祖先限制无法被子组突破。三类接口的折叠方式不同。\n\n配额型（cpu.max 形如 Q τ，表示每个周期 τ 最多消费 Q 的 CPU 时间；memory.max 为字节上限）取路径上的最小值。设 π(n) 为从根到 n 的节点链（含 n 自身），则\n\nP_eff(n) = min( |E_cpuset(n)| , min_{a∈π(n)} Q_a/τ_a )，\nB_eff(n) = min_{a∈π(n)} M_a。\n\nQ 与 τ 必须同单位；Q 为 max 表示该层不额外收紧。P_eff 只是长期时间上界，它不保证任一时刻有线程可运行，也不保证 cache、内存带宽或 NUMA 局部性。\n\n集合型（cpuset.cpus、cpuset.mems）中，空值表示继承最近的非空祖先，因此\n\nE(n) = ∩ { S_a : a∈π(n), S_a ≠ ∅ }。\n\n这个写法依赖“空值即继承”的语义；若某平台把空集解释为“没有可用 CPU”，公式要改回逐层求交且空集吸收的形式。\n\n三个必须读取有效值而非写入值的地方：cpuset.cpus 在热插拔下保持不变，真正生效的是 cpuset.cpus.effective，它受祖先与在线状态共同限制；cpuset.mems 写入非空值会触发页面迁移，来源明确说明迁移有成本且可能不完整，所以设置成功不等于页面已在新节点，稳态数据路径要读 memory.numa_stat；内存记费跟随分配它的组而不是进程当前所在组，迁移进程不会搬走已记费内存。\n\n父子组的 memory.current 是包含关系（含后代），因此把父子组的 current 或峰值相加会重复计数。同理，memory.events 是层级汇总，memory.events.local 才是本级事件；看到 high 事件时先确认它是本级还是后代触发，再决定归因。\n\n## 设备暴露与逻辑序号：一条完整映射链\n\n从集群资源声明到框架里的 device 序号要经过至少六次转换，任何一次都足以让“0 号卡”指向另一块物理设备。\n\n1. 资源声明：资源名（例如 nvidia.com/gpu，或 mixed MIG 策略下形如 nvidia.com/mig-<slice_count>g.<memory_size>gb 的资源名）与申请数量。\n2. 分配结果：一串 grant。每项携带物理身份（UUID；MIG 下还要带实例标识），共享方式下多个 grant 可以指向同一物理资源。time-slicing 的 replicas 是访问名额数，不是独立设备数。\n3. 注入通道：固定来源列出 envvar、volume-mounts、cdi-annotations、cdi-cri 四种方式把设备清单交给运行时。通道改变的是传递方式，不改变逻辑序由下发顺序决定这一点。\n4. 设备 ID 策略：uuid 或 index。README 明确说 index 适用于重启后挂上不同物理 GPU 的重部署场景，这等于承认同一 index 在不同时刻可以指向不同物理卡。\n5. 容器内可见集合：运行时按注入的设备清单设置可见范围，容器内的设备序号从 0 重新编号。\n6. 框架层再过滤：框架自己的可见设备变量还会再筛一次，逻辑序第二次重排。此时 torch.cuda.device(i) 里的 i 是最终逻辑序。\n7. 执行器记录：执行器必须从第 2 步取物理身份，不能从第 6 步反推。torch.cuda 的当前设备与容器逻辑序是同一坐标系的不同层，不能互相替代。\n\n```pseudocode\n算法 RESOLVE_DEVICE_MAP(grants, injection, id_strategy, framework_filter)\n输入：grants 是有序 grant 列表，每项 = (slot, physical_id, share_group)\n      physical_id 是设备物理身份；share_group 非空表示同一物理资源的访问名额\n      injection ∈ {envvar, volume-mounts, cdi-annotations, cdi-cri}\n      id_strategy ∈ {uuid, index}\n      framework_filter 是框架层有序子集（可为恒等）\n输出：逻辑序到物理身份的映射 μ，或拒绝及原因\n\n1 核对 grants 非空；每个 physical_id 属于本节点当前枚举集合\n  若 id_strategy = index，把序号按当前物理枚举序解析为物理身份\n  若枚举集合与发证时记录不同，拒绝并递增环境代次 ε\n2 V ← [g.physical_id for g in grants]，保留下发顺序\n3 若所用注入通道不保证顺序，则只发布集合 {V}，不发布 μ\n  并要求调用方在容器内重新读取实际可见集合后再建立映射\n4 V′ ← framework_filter(V)，下标从 0 重新编号\n5 μ(i) ← V′(i)\n6 核对不变量：\n    |μ| = |V′|；集合 {μ(i)} 等于集合 V′\n    每个物理身份 p 对应的逻辑下标集合，等于 p 在 V′ 中的位置集合\n    distinct_physical(μ) = |{μ(i)}|，在共享方式下可以小于 |μ|\n    容量只按 distinct_physical 计一次，不按 |μ| 计\n7 返回 μ 与 distinct 集合；不把逻辑 0 当作物理 0\n```\n\n一个展开算例。设节点有 1 张 80 GiB 物理 GPU，配置 replicas=2 的 time-slicing，某实例申请 2 个 rank，每 rank 声明 45 GiB 权重加 KV。插件会给出两个 grant，都指向同一物理身份。表面账“2 个名额 × 80 GiB = 160 GiB，装得下 90 GiB”是错的：两个 rank 共用同一份显存，正确条件是\n\nΣ_{i∈共享组} d_i ≤ C，\n\n即 45 + 45 = 90 > 80，容量不可行；而且两个 rank 位于同一物理设备，一次设备故障会同时失去它们，故障域没有变成两个。\n\n同一组声明下的合法变体是：每个客户端只申请 1 个 rank、各 40 GiB，合计 80 GiB 刚好等于容量。这通过了容量检查但没有余量，任何超过 40 GiB 的瞬时峰值都会撞上同一个 OOM 边界。访问名额数不创造显存，只创造竞争。\n\n## 有效资源、峰值与容量准入\n\n容量准入必须逐 rank 检查，因为总量足够不能推出每个 rank 足够：两个 rank 的需求都放不进各自的可达设备时，把两张卡的总容量相加不会让它们变得可行。\n\n加载与运行的峰值按“同一时刻的唯一物理存储”取并集：\n\nPeak = max_t Σ_{s∈U(t)} |s|，\n\nU(t) 是时刻 t 仍存活的唯一存储集合。共享引用只计一次，预留池与其内部存活对象不重复相加，allocator 的 allocated 与 reserved 是观测口径而不是两个可加项。\n\n设定时间线：t0–t1 驻留源权重 24 GiB 与 staging 4 GiB，共 28 GiB；t1–t2 源权重、转换目标各 24 GiB 加 staging 4 GiB，共 52 GiB；t2–t3 只剩目标 24 GiB 与图池 3 GiB，共 27 GiB。峰值是 52 GiB。把三个阶段峰值相加得 107 GiB 是重复计同一份权重；只报最终态 27 GiB 会漏掉加载期超限。宿主有 512 GiB 也不能使一个上限 48 GiB 的服务自动加载成功。\n\n```pseudocode\n算法 ADMIT_RANKS(实例需求, 层级表, 设备表, 环境代次 ε)\n输入：每个 rank r 的节点位置 node(r)、需求向量 d_r（设备显存、主存、CPU 时间、\n      进程数、描述符、共享内存等）、该 rank 的可见设备集合\n输出：可行与账本，或逐维违反、限制来源祖先与解除条件\n\n1 对每个 rank 计算 e(r) ← 沿 node(r) 的祖先链折叠有效资源\n  CPU 按 min(|E_cpuset|, min Q/τ)；内存按 min M；集合按非空交集\n2 对每个 rank 逐维检查 d_r ≤ e(r)，并记录限制来自哪个祖先\n  设备维只计该 rank 实际可见的物理设备，不按集群空闲总数计\n3 检查共享组：对每个物理设备 p，若 p 上有 k 个访问名额被本实例或其他实例占用，\n  要求 Σ d_i ≤ C_p，且共享方式声明的隔离边界仍成立\n4 检查故障域：实例的 rank 集合不能全部落在同一个已声明会共同失效的域\n5 计算峰值：对每个时刻取唯一存储的并集，不把各阶段峰值相加\n6 全部通过才返回可行与账本；否则返回具体维度、来源祖先和使该项变化的合法路径\n```\n\n共享方式改变合法性而不只是改变性能。固定 README 明确说明：time-slicing 下不同工作负载共享同一底层 GPU 时没有额外的隔离，一个工作负载崩溃会带走其他工作负载；MPS 由控制守护进程按份额限制显存与计算，但该版本只支持完整 GPU 且与启用 MIG 的设备不相容；mixed MIG 策略产生的资源本身还可以再配置 time-slicing，因此一个 MIG 资源名仍可能承载多个访问者。资源名相同不能推出隔离相同。\n\n## 健康、就绪与可接收容量\n\n三件事必须分开：进程能否推进必要工作（活性）；某个 (v, g) 在某个环境代次与某个公开范围上是否被验证（就绪）；此刻还能不能接一个新请求（瞬时容量）。\n\n就绪证书写成\n\nC_g = (v, g, ε, Ω, Π)，\n\nΩ 是允许公开的请求范围（模型、dtype、输入几何、上下文上限、adapter 路径、受验证的回退路径、共享方式假设），Π 是验证证据（制品核对、能力探测、代表路径、边界用例）。证书绑定 ε，因此环境变化不是重启一下，而是哪些 Ω 失效。\n\n```pseudocode\n算法 PUBLISH_READINESS(g, v, ε, Ω, Π)\n1 核对 Π 覆盖 Ω 的每个执行变体；未覆盖的变体不得进入 Ω\n2 核对 v 的制品身份与 α 一致；ε 与当前环境代次一致\n3 若任一必要 rank 的 e(r)、μ(r) 与 Π 记录不同，拒绝发布，只更新证据\n4 发布 C = (v, g, ε, Ω, Π)；准入门仍关闭，直到路由切换\n5 环境代次从 ε 变为 ε′：\n    对每个变体 t∈Ω，若 Π 中 t 的证据依赖的字段发生变化，标记 t 失效\n    若失效集合为空，仅更新 ε\n    若失效集合非空，令 Ω′ 为 Ω 去除失效变体；Ω′ 非空则收窄发布\n    Ω′ 为空则撤销证书\n6 收窄或撤销只影响对应范围；已接受的请求保留原绑定与原预留\n```\n\n活性与就绪的关系同样要限定。端口能连接、HTTP 返回成功、插件进程没有退出，都不能单独证明权重完成加载、通信组完整、设备可用、代表路径正确。反过来，KV 满、队列长、范围外请求被拒也不等于进程失效：把暂时过载当成失效并反复重启，会清空热状态、重复加载并放大存储压力，把容量问题变成可用性问题。无法恢复的设备或执行组错误才应退出相应可用集合，并按恢复协议重建。\n\n## 六类成本与条件化选择\n\n| 成本 | 本章对应的对象 | 易漏项 |\n|---|---|---|\n| 计算 | 设备能力探测、cgroup 有效值读取、制品与布局核对、代表路径执行 | 设备初始化本身的开销；探测触发的驱动初始化 |\n| 访存 | 页面迁移字节、加载峰值并集、页表与元数据 | 迁移可能不完整留下的跨节点页 |\n| 通信 | 制品拉取、多节点共同验证与屏障 | 多个副本同时拉同一制品对同一出口的竞争 |\n| 准备 | 锁页、挂载、编译、图捕获、注册 | 升级后的重新注册与重新验证 |\n| 同步 | 探测与初始化引入的同步点、屏障、排空等待 | 探测污染后续派生进程；排空期仍在途的访问 |\n| 驻留 | 新旧版本并存、每设备副本、共享组、图池 | 同一 backing 的多种用途被重复相加 |\n\n就绪延迟可以写成一个保守模型：\n\nT_ready = max_r ( q_r + L_r^load + L_r^probe + L_r^verify ) + T_group。\n\n各项在 r 内部可能重叠；若确实重叠，应改用依赖图，而不是把四项相加当作上界。T_group 只计真正位于这些工作之后的共同验证或屏障，已包含在 L_r 内的不能再加一次。\n\n环境核对的选择不是“缓存一定更好”，而是由合法性先决定、再由算术决定。\n\n设每请求完整探测的成本为 c_probe、请求数为 N；缓存后每请求只核对代次的成本为 c_check、环境变化次数为 M、每次变化的重新验证成本为 c_verify，则\n\nC_naive ≈ N·c_probe，\nC_cached ≈ N·c_check + M·c_verify。\n\n设定 c_check = 5 微秒、N = 5×10^5、c_verify = 8 秒、M = 20，得 C_cached ≈ 2.5 秒 + 160 秒 = 162.5 秒；若 c_probe 真的只需 50 微秒，则 C_naive ≈ 25 秒。在这组设定量下缓存反而更贵。\n\n这个反例说明：缓存的价值不能只用算术辩护。真正的约束是探测可能有副作用。固定文档指出，默认的可用性判断会调用运行时接口，从而初始化驱动；此后派生的子进程会因 CUDA 初始化而失败，改用基于 NVML 的检查可以避免污染，但该检查的保证更弱，可能通过而随后初始化失败。也就是说，完整探测不是纯读操作，它会改变进程状态并与推理争用设备。在这种情况下，缓存不是优化而是保持路径合法的必要条件；反之，如果目标平台上探测既便宜又无副作用，逐请求核对更简单，也应被接受。\n\n排空成本单独列账：\n\nT_drain = T_最后在途请求完成 + T_重新注册 + T_重新验证。\n\n固定来源明确建议在升级插件前排空 GPU 任务，并不保证任务在滚动升级中存活。因此不能把插件重启而容器还在当作环境等价；容器存活只说明进程未退出。\n\n## 条件变化后的保留、调整与放弃\n\n驱动、设备插件或运行时更换会影响整个节点，不只影响一个服务进程：ε 在节点级递增，受影响的是所有依赖该层的证书。应停止新准入、完成或迁移已有工作、确认最后访问结束后再释放旧环境，而不是假设滚动升级期间任务继续可用。\n\n用户态库升级要按依赖闭包判断。若
