# K-MODEL-015：推荐推理：稀疏表、特征交互与请求批量

推荐模型的容量通常由大 embedding 表占据，计算则分布在不规则 lookup、特征交互和稠密网络。参数很多不代表每个请求都读取全部权重，也不代表请求只做几次廉价查表；设计需要同时掌握访问分布和后续计算。

## 输入特征和表共同定义函数

一个请求包含连续特征及多个类别特征。连续值的缺失填充、裁剪、变换和顺序必须与模型一致。类别值先经过词表、哈希或其他映射，得到表 ID、行 ID 及可选权重。相同整数在两个表中不代表相同含义；特征 schema、映射版本、embedding 参数和 dense 参数需要作为一套可兼容制品使用。

一个 bag 可以包含多个索引。求和、均值、带权求和、顺序编码是不同函数，重复 ID 的 multiplicity 也有含义。例如求和 bag [a,a,b] 的结果为 2E[a]+E[b]，不能通过集合去重变成 E[a]+E[b]。如果为了缓存和搬运合并重复读取，应在消费时恢复次数或权重。空 bag、未知类别和缺失字段的规则应显式定义，不把任意零行当作全部模型的默认语义。

DLRM 固定论文给出的结构是：类别特征经 embedding/bag 聚合，连续特征经 bottom MLP 投影到共同维度，再做成对点积交互；交互结果与 dense 向量拼接后，经 top MLP 和输出函数给出概率。这是一个完整参考结构，其他推荐模型可能使用不同交互或序列网络，不能共用未声明的张量解释。

## 从 lookup 到交互的形状账

设有 F 个类别表，公共 embedding 维度 d，batch 为 B，每个请求第 j 个表平均取 lⱼ 行，元素字节数 s。无缓存且不计重复的有效行字节为 BΣlⱼds；真实内存流量还受 cache line、对齐、随机访问与 miss 重复影响。表容量为 ΣVⱼds，另加量化元数据、索引和缓存副本。

Bag 在表侧聚合后，每个请求只需 Fd 个数，而把所有原始行送到计算侧则需 Σlⱼd 个数。是否提前聚合取决于算子语义、分片方式与设备能力。跨行分片的一个 bag 需要合并各分片 partial sums；求均值还需合并有效计数，不能对各分片均值直接等权平均。

DLRM 的 F 个类别向量与一个 dense 向量形成 F+1 个输入，若只取互不重复的非对角点积，共有 F(F+1)/2 项；与 d 维 dense 向量拼接后，top MLP 输入维度为 d+F(F+1)/2。交互顺序属于权重接口，改变三角展开次序而不重排对应权重，会使每一列数值看似合理但结果错误。

## 放置策略取决于表大小与访问偏斜

整表驻留 GPU 减少跨设备延迟，但可能挤压 batch、工作区和其他模型。DRAM 驻留、GPU 热行缓存适合容量超过显存且热点较集中的情况；均匀访问或热点快速迁移时，cache lookup、填充和淘汰可能抵消收益。SSD 可以容纳更大冷表，随机小读的尾延迟及读放大却需要独立验证，不能用顺序带宽估算全部 lookup。

按表分片容易保持 bag 的局部聚合，但大表和热表会导致容量或带宽不均。按行分片可以摊开单个大表，却增加索引路由与部分结果合并；按列分片会让每个向量涉及更多设备，并影响后续点积。复制热点表或行能降低读压力，但增加容量和版本切换成本。

当 embedding 分片而 dense 部分复制时，各 dense 执行器需要收齐本批请求对应的所有特征。通信对象通常是查表后聚合的向量、请求身份和必要计数，不是训练中的梯度。DLRM 论文含训练并行部分，其中梯度 all-reduce 不属于只读推理的必需路径；推理应单独计算前向通信与版本一致性。

## 持续更新、缓存和请求状态

长驻状态包括参数表、特征映射、热点缓存和路由元数据；单请求状态包括输入特征、bag 边界、分片完成情况、交互缓冲和输出身份。一个 bag 的一部分返回，不能使整个请求提前进入 dense 阶段。取消后应停止尚未提交的 lookup，已在途读取完成前不得复用返回缓冲。

如果表允许更新，需要定义一个请求读取哪个版本：固定快照、具有明示一致性边界的增量版本，或业务允许的陈旧读。更新缓存行时，旧请求仍可能持有引用；直接复用地址而未区分代次会混合新旧参数。增量模型与旧 dense 头是否兼容必须由制品契约决定。TTL 只能控制年龄，不能证明语义兼容。

离线 embedding 训练、在线特征生成和标签回流会影响推理质量，但这里的系统边界是已确定模型的服务。延迟统计应从可归属的入口开始，明确是否包含远端特征获取。否则模型前向优化可能被入口查询或结果排序完全淹没。

## C12-D：大表推荐服务的完整验证场景

设定 26 个表，每表 1,000,000 行、64 维、FP16，参数表总量为 3,328,000,000 字节，约 3.10 GiB，尚未计 dense 权重与缓存元数据。B=256，每请求每表平均 4 个 ID，无命中时有效行读取为 26×256×4×64×2=3,407,872 字节，即 3.25 MiB；bag 聚合后为 851,968 字节，即 0.8125 MiB。一次批的交互含 351 个点积/请求，约 5,750,784 次乘加，top MLP 的输入维度为 415。

候选 A 将全部表驻留一张容量足够的 GPU，dense 同设备；候选 B 将表放在 DRAM 或按表分片，发送聚合结果给 dense GPU。A 的主要约束是显存和其他工作竞争，B 的主要约束是随机访问、主机聚合、传输和慢分片。若按表分在两个设备且 dense 请求均匀分配，各设备一半聚合结果需跨设备发送；这里的字节可按实际请求—表位置逐项求和，不能再把完整表容量算作每批通信量。

为实现建立独立小参考：表行 a=(1,2)、b=(3,4)，bag [a,a,b] 求和应为 (5,8)；另设 dense=(2,1)，两向量点积为 18。分别验证空 bag、缺失、权重、重复 ID、跨分片求和、均值计数、交互展开和输出 sigmoid/任务头。先比较完整 FP32 参考，再独立评估允许的低精度差异。

工作负载应同时包含热点稳定、均匀随机、热点迁移及多值长度长尾，保留请求到达和特征相关性。质量用固定标签集的 log loss、AUC 及业务规定的排序指标，数值容差用来定位实现差异；不能用“全预测未点击”的高 accuracy 代替有区分力的评估。性能报告完成请求/s、p99、特征获取与各阶段耗时、缓存命中对应的实际字节以及慢分片情况。

当热门行稳定且缓存足够时，B 可能以更低显存获得可接受时延；当访问均匀、batch 很小或尾延迟收紧时，A 或更高复制率可能更合适。增大 batch 能提高 dense 效率，但增加 lookup 并发、排队与响应尾部；只有满足同一质量、到达过程和服务目标的方案才可直接比较。
