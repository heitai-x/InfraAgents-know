# 专家知识写作约定

一个专题应让读者能够理解系统、推导设计，并在条件变化时重新选择方案。篇幅由问题需要决定；使用能解释主题的章节结构。

## 以对象与机制展开

先明确对象是什么、输入输出如何定义、哪些信息依赖哪些前置状态。数学模型解释计算，布局解释数据组织，状态关系解释生命周期，时间线解释并发。公式中的符号、轴、单位和假设需要完整，使读者能够独立复算。

随后推导设计分支：为什么采用某种表示、它减少了哪项成本、又增加了哪项成本。用具体算例展示权衡，再说明与其他机制组合后哪些条件改变。模型、平台和版本不同的地方直接写在相应推导处。

## 由主题选择表达

Attention 适合从公式到 IO 和归约；缓存适合从依赖等价到布局、共享和恢复；调度适合从就绪关系到资源预算和时延；平台适合从存储/执行资源到数据流；引擎索引适合把机制映射到固定版本的模块责任。

可观察现象、区分实验和反例来自这些机制的预测。它们为理解提供支持，不取代正文。以“注意同步”“先检查配置”等通用提醒结束，尚未解释缺少哪条依赖、配置怎样改变函数或成本。

## 来源与原创推导

把论文机制、文档语义、经源码核对的算法、自己的代数推导和项目观测分别归到具体依据。允许公式、算法步骤与标注为 pseudocode 的伪代码，写清初始化、依赖、状态更新、完成条件和成本；现成项目源码、可执行命令和原始日志留在工程产物中。数值算例明确为设定条件下的计算，不冒充实测。内容深度与来源处理按[知识库构建与修订方法](../../docs/knowledge-method.md)执行。

作者与审阅者可按[知识内容审查](../../docs/knowledge-review.md)追问算法、布局、组合状态、联立成本与区分实验。已有问题修复后按当前正文关闭；内容充分、软件模型成立、运行时可读取和实际 Agent 构建效果分别陈述。

正文保留稳定的机制、检查覆盖与未验证边界。本轮工具能力、V8/JavaScript 探针过程和“尚待协调者执行”等进度写入作者说明或证据记录，不进入长期正文。实际 Python 检查是否通过，以绑定脚本和输入的执行记录为准，不预先写成通过；正文需要说明执行状态时，链接对应证据并保留其适用范围。

## 修订保持知识连续

新增主题提供完整论证；已有主题只替换或新增受影响的完整二级章节。原标题是精确定位键，三级以下结构属于该节。未受影响的论证、公式、布局和关联由运行器保留。修改标题意味着新增章节；需要纠正原节时保持原标题。

RSI 的 mechanism 字段容纳这些非代码 Markdown 章节；claim 用作导航摘要，conditions 表达适用范围，其他字段保存预测、证据与后续检验。摘要不能替代正文。争议与弃用保留完整解释，便于后续修正与恢复。

正文与“来源与推导”构成本地阅读链：来源条目提供已核对的机制、定义和本库推导关系，原始网址仅作出处元数据。运行中的来源说明随知识快照保存，无需通过 WebSearch 补全本文。

论文 PDF、说明文档与必要图片提供本地原文阅读入口。源码经核对后提炼为算法与设计知识，原始实现留作溯源证据；混合资料保留其中的可读文档。来源说明不能以整份源码链接代替知识，详见[资料阅读入口](../../references/index.html)。

## 可执行性与探索边界

把技术对象、输入输出、单位、版本、依赖和副作用写清，使读者能形成实现或实验。参数、shape/stride、数值、工作区、完成点和错误语义按主题需要展开；不要求每篇填满相同字段或给出统一交付物。

任务约束、数学/API 语义、经验假设和设计示例分别表述。所选机制的依赖关系可以约束合法执行，但不自动规定实现、调试和性能探索的先后次序。已有具体接口也只是固定版本的事实，不要求新引擎沿用该组件划分。

候选和使用场景不穷尽设计空间。读者可以不用所列机制、提出不同表示或把原来分开的部分融合；以任务要求和实际机制语义检查合法性。验证层次界定证据适用范围，不把局部、集成和系统三个词写成必经施工阶段。

新增内容先查明现有专题的覆盖。已有对象的深化修改其受影响完整二级节，跨主题说明优先链接；只有独立技术对象才新增章节。问题入口用于帮助检索，不新增角色义务、固定候选数量或知识使用考核。
