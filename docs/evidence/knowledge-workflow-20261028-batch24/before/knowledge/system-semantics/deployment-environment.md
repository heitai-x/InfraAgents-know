# K-SYS-019：部署环境：版本契约、可见设备与真实资源边界

部署描述必须回答一个可检验的问题：这次执行实际跑在哪些资源上，凭什么它是合法的。镜像、宿主内核与驱动、设备暴露、用户态库、cgroup 层级、文件与网络路径及故障域共同决定答案。容器能够启动只说明进程被创建；它不证明设备已经正确注入、祖先预算仍有余量、编译产物与设备能力相容，也不证明目标执行路径已被验证。

本章把环境身份接到实际枚举、有效资源、共同容量账和就绪资格。容量检查的输出可以是明确违反、声明模型内可行或证据不足，不能把未知填成足够。

## 环境身份与环境代次

把环境写成

𝒳 = (α, ρ, δ, μ, β, γ)。

α 是制品与执行身份：权重清单、配置、tokenizer/processor、量化与布局元数据、执行器与编译器、用户态计算与通信库。ρ 是宿主侧身份：内核及配置、驱动、容器运行时与低层运行时、设备插件。δ 是设备暴露声明：资源名、访问名额、注入方式、设备 ID 策略与共享配置。μ 是每个执行进程中逻辑序号到稳定设备身份的实际映射。β 是资源边界：控制器启用状态、cgroup 层级参数、有效 cpuset、CPU 额度、内存及其他资源限额。γ 是实际路径和共同依赖：挂载、命名空间、网络、NUMA、存储出口，以及设备、主机、机架和供电等故障域。

δ 与 μ 分开记录。两个共享访问名额可以指向同一设备；名额列表也没有自动给出 CUDA 的枚举顺序。同一进程的逻辑 device 0 在重启后仍叫 0，不证明其稳定身份未变。

环境代次 ε 标识一次受管理的环境配置。任何可能改变合法执行集合的字段变化都产生新 ε。设备重建时还要区分设备实例代次，避免把重新创建的 MIG 实例当作旧对象。证书、编译缓存和探测结果绑定其实际依赖及 ε；环境变化后先判断哪些证据仍有效，再决定复用。

ε 不是阻止外部变化的锁。读取多份文件也不是内核事务；配置、热插拔或分配在取证过程中变化时，应丢弃不一致快照并重读。运行时仍需响应真实设备故障和资源收紧。

## 相容是制品与环境之间的谓词

设 A 为制品与执行配置的对象域，X 为环境描述的对象域。定义二元谓词

Compatible : A × X → {真, 假, 未知}。

给定 α∈A 与 𝒳∈X，将 α 的要求展开为 R_α：驱动接口、设备计算能力、指令与内存语义、库 ABI、布局与对齐、数值策略及必要容量。逐项核对这次执行由 μ 选出的设备与运行路径。任一必要要求已被反证则为假；全部要求在声明范围内得到支持才为真；必要信息缺失则为未知。

这里没有把相容定义成偏序。它的两端属于不同对象域，不能将“制品依赖库、库依赖驱动”当作同一种关系，套用传递性。即使每条接口分别可用，组合路径仍可能受 ABI、设备能力或执行选项约束。

版本号大小也不构成能力包含关系。新版本可能删除接口或改变默认数值策略；设备型号相同不能证明库、驱动与路径相同。用户态库满足某个版本要求，不推出某个 kernel 支持当前设备；单卡前向通过，不推出多卡通信路径可用。

编译产物复用要求当前环境满足其全部编译假设，并且真正影响产物的条件保持相容。运行时参数替换而 ABI、布局不变时，未必需要重编译；常量折叠、预打包格式或捕获地址改变时，相关产物需要重建。拷贝已编译文件或比较型号名都不能代替这些判断。

## cgroup 层级：请求值、有效值与共同预算

[Linux cgroup v2](../sources/S-LINUX-RESOURCES.md) 按层级分配资源。控制器必须实际启用；某层没有相应接口，不等于获得独占资源。子组可以设置上限，但上限不是父组向每个子组分别承诺的一份资源。

cpu.max 的 Q、τ 均以微秒表示，Q/τ 的单位为 CPU 秒/秒。Q 为 max 时该层不额外设限。对节点 n，令 π(n) 为根到 n 的祖先链，则普通 CPU 带宽规划中的单消费者必要上界是

P_path(n) = min(|E_cpu(n)|, min_{a∈π(n), Q_a≠max} Q_a/τ_a)。

无有限额度时，第二项为无穷。memory.max 的路径上界为

B_path(n) = min_{a∈π(n)} M_a，

M_a 的单位为字节，max 按无穷处理。这两个量都没有扣除其他消费者。CPU 上界不保证瞬时运行机会、独占物理核、cache、内存带宽或固定 FLOP 供给；memory.max 也不是内存预留保证。

### 有效集合递推与回退

固定 Linux 6.12 摘录明确规定：cpuset 请求为空时继承父级可授予集合；请求非空但其中没有任何资源能够授予时，也按空请求处理。cpuset.cpus.effective 和 cpuset.mems.effective 均有这个分支。

先限定一个可重建的静态模型：使用普通 member 层级，控制器已启用；在线集合固定，没有新增或变化的 exclusive/root/isolated 分区分配。根的可授予集合 O 来自本次在线有效资源快照。对 CPU 或内存节点分别递推：

E(root)=O；J_n=S_n∩E(parent(n))；

E(n)=J_n，当 S_n≠∅ 且 J_n≠∅；否则 E(n)=E(parent(n))。

S_n 是请求集合。算法必须先得到父有效集，再决定本级是否回退，不能把路径上所有非空请求一次求交。

```pseudocode
算法 FOLD_SET(根有效集合 O, 根到目标的请求列表)
E ← O
对每一级请求 S：
    parent ← E
    J ← S ∩ parent
    若 S 非空且 J 非空：E ← J
    否则：E ← parent
    核对 E ⊆ parent
    若 J 非空：核对 E ⊆ S
返回 E，以及各级采用请求或回退的分支
```

父有效集为 {0,1}、子请求为 {2} 时，J=∅，子有效集回退为 {0,1}。它不是请求 {2} 的子集。条件化不变量是：有效集总在父可授予集合内；只有请求实际获得资源的分支才要求它在请求集内。若父可授予集合本身为空，回退不会创造资源。

分区配置会改变可授予集合和排他关系，不能用上述普通层级模型重建任意分区。存在 root/isolated、exclusive 分配或分区有效性变化时，需同时核对 cpuset.cpus.partition、exclusive.effective 及相关祖先；远程分区尤其不能机械套用普通父子交集。真实环境以当前 effective 文件及分区状态为准。热插拔会改变 effective，而请求文件可能保持原值；变化后重读并使相关旧证据失效。

设置 cpuset.mems 非空值可能触发页面迁移，来源说明迁移有成本且可能不完整。设置成功不证明页面已经全部迁到目标节点，实际放置还需结合 memory.numa_stat。内存记费也不随进程迁组自动迁移：应使用对象实际记费归属，不能只看进程现在在哪个组。

memory.current 包含后代，因此不能把父子 current 相加。memory.events 是层级事件，memory.events.local 是本级事件。memory.high 引入节流和回收压力，越过 high 本身不调用 OOM killer；memory.max 在无法回收时可进入 OOM 路径，某些情况下用量还可能暂时超过限额。规划预算、事件归因和瞬时观测应分别解释。

## 设备暴露与逻辑序号：从授权到实际枚举

[NVIDIA device plugin v0.16.1](../sources/S-NVIDIA-PLUGIN.md) 描述资源暴露和设备清单传递。其 envvar、volume-mounts、cdi-annotations、cdi-cri 是注入通道；uuid/index 是传给运行时的身份策略。README 没有保证 grant 列表顺序就是 CUDA 枚举顺序，也没有保证同一设备的重复共享引用变成多个 CUDA ordinal。

完整链条需要分别保存下列对象。

1. 集群资源请求：资源名、访问数量和共享配置。mixed MIG 可以暴露 profile 资源，profile 名称本身不说明是否又配置了 time-slicing。
2. 授权 grant：每项包含访问名额身份及其稳定设备身份。整卡使用 GPU 身份；MIG 需包含实例身份和所属物理 GPU，不能只保留父卡 UUID。
3. 宿主身份解析：index 必须按本次设备清单解析成稳定身份。固定 README 指出 index 策略可以用于重启后挂上不同物理 GPU 的场景，因此历史 index 不能当作稳定身份。
4. 注入后的实际枚举：容器可见范围由运行时落实。记录观测所在的进程、环境代次、逻辑序号和稳定身份，不从 grant 顺序猜测。
5. 最终进程枚举：CUDA_VISIBLE_DEVICES 等可见性配置生效后，在实际执行进程中记录最终 ordinal—稳定身份对应关系。若需要检查过滤前后的变化，使用分别取得的枚举记录或已有固定契约；不临时修改已初始化进程的变量并假定它会重新枚举。
6. rank 绑定：将执行 rank 绑定到其进程中已核对的 ordinal，再由 μ_r 找到实际设备。rank 数、访问名额数和一个进程的 ordinal 数是不同数量。

下面选择“每个稳定设备实例在一个枚举中出现一次”的映射模型。若目标运行时另有别名合同，应先补足该合同；不能用重复 grant 自行制造别名。

```pseudocode
算法 RESOLVE_DEVICE_MAP(grants, inventory, policy, observations, ε)
输入：本次授权；带代次的宿主清单；最终所需设备集合策略；
      实际执行进程的枚举记录，或尚未取得记录
输出：READY(μ,设备集合,ε)，WAIT_ENUMERATION，或拒绝及原因

1 验证 grant 与宿主清单属于当前节点实例和配置代次
  index 身份逐项查本次清单；无法唯一解析则返回待取证，不发布 μ
2 A ← grant 所授权的稳定设备实例集合，去除共享访问名额的重复引用
  F ← policy 要求最终暴露的集合；核对 F ⊆ A
3 未取得最终进程枚举：返回 WAIT_ENUMERATION；本次调用结束
4 检查枚举记录属于当前执行进程和 ε
  ordinal 必须完整、无重复且为 0…N−1；稳定设备身份必须可核对
  此模型中重复稳定身份、未知身份或缺失身份均拒绝
5 μ ← 枚举记录中的 ordinal—稳定身份对应关系
  核对 image(μ)=F；额外暴露和缺少必要设备分别报告
6 对每个 rank 核对其进程身份、所选 ordinal、μ 对应身份与计划相同
  不满足则拒绝；全部满足才返回 READY
```

若某条完整、固定的运行时合同保证顺序转换，可以使用该合同推导中间映射，但仍需记录合同版本及最终核对范围。本章所供 README 不承担这个顺序保证。

例如授权名额按 [GPU-a,GPU-b] 给出，容器枚举观测却为 [(0,GPU-b),(1,GPU-a)]，最终策略仅保留 GPU-b，最终进程枚举为 [(0,GPU-b)]。正确 μ 是 {0↦GPU-b}。按 grant 顺序取第一个得到 GPU-a，或忽略过滤仍返回两个设备，都会与实际枚举或策略冲突。

共享情形另作展开：两个客户端分别取得指向 GPU-x 的一个 time-slicing 名额，各自进程都显式枚举到 [(0,GPU-x)]。这是两个进程各有一个逻辑设备，它们共同依赖一张物理 GPU；不能据此构造某个进程有 ordinal 0、1。设该设备可用于本账本的容量为 80 GiB，两个客户端各需 45 GiB 私有存储，则 45+45=90>80，必须拒绝。错误的名额容量账会得到 2×80=160 GiB 并放行。

若各需 40 GiB，物理总容量检查恰好通过，但没有剩余裕量；额外 workspace、驱动或在途峰值必须已经计入需求或预留。多个 rank 是否允许共用一张设备，还需核对执行器和通信合同，容量通过不证明执行组合法。

## 峰值、共享祖先与容量准入

逐 rank 检查能发现局部设备装不下，却不能证明共同容量够用。准入必须同时检查祖先预算、实际物理资源域和已有消费者。

### 同时存活的唯一对象

对资源域 d，令 U_d(t) 是时刻 t 存活且记费到该域的唯一存储对象集合。每个对象带分配身份、代次、大小和记费归属，则

Peak_d = max_t Σ_{s∈U_d(t)} |s|。

同一 backing 的别名只计一次；预留池已经覆盖的内部对象不再相加。allocator 的 allocated 与 reserved 是不同观测口径，不能作为两份物理存储相加。相同内容的独立副本仍计两份。

设加载时间线为：t0–t1 源权重 24 GiB 与 staging 4 GiB，共 28 GiB；t1–t2 源与目标各 24 GiB，加 staging 4 GiB，共 52 GiB；t2–t3 目标 24 GiB 与图池 3 GiB，共 27 GiB。峰值为 52 GiB。把阶段总量相加得到 107 GiB，不能作为这条轨迹的实际峰值；只报最终 27 GiB 又会漏掉加载超限。宿主有 512 GiB 不能使一个 memory.max 为 48 GiB 的组自动加载成功。

对每个内存祖先 a，同一时刻的规划账为

D_a(t)=Σ_{s:charge(s)∈subtree(a)} |s| + R_a^unmaterialized(t) + H_a(t) ≤ M_a。

第一项按唯一对象统计，包含已有占用；第二项只计尚未物化、未被第一项覆盖的承诺；H_a 是尚未被其他项覆盖的必要余量。不能把当前占用、覆盖该占用的全额预留和父子 current 再次相加。共享页的记费归属不明、其他消费者账本缺失或必要峰值未知时，不能输出完整容量可行。

父上限 48 GiB，两个子组各上限 32 GiB，两个 rank 同时各需 30 GiB。各自均有 30≤32，父组却需 60>48。即使每个 rank 都小于路径最小上限，仍须拒绝。已有 20 GiB 占用再承诺 30 GiB 也会超过父组；只看新候选的空闲快照会漏掉这一项。

### CPU 的时间单位与实际运行集合

CPU 需求定义为指定规划窗口 W 内的 CPU 时间 D_r，先换成 p_r=D_r/W，单位为 CPU 秒/秒。例：分词每请求 10 ms CPU，其他主机工作 6 ms CPU，150 请求/s 需要 150×0.016=2.4 CPU 秒/秒；每 100 ms 最多消费 200 ms 的额度只支持长期上界 2。

本节采用普通调度、无额外 burst、固定在线集合与持续份额的规划模型。Q/τ 是长期带宽上界；不同周期的补充时刻和短窗口瞬时节流没有被它消除。若要承诺某个短窗必须完成多少工作，还需按实际周期、剩余额度与调度状态检查，不能直接用 W×Q/τ 当任意窗口的保证供给。

每个有限额度祖先 a 都要满足

Σ_{r∈subtree(a)} p_r + p_a^existing ≤ Q_a/τ_a，

已有消费者若已经包含在 r 集合中，不能再放进 existing。两个子组各需 1.5 CPU 秒/秒，父上限 2，各自单独检查通过，合计 3 仍须拒绝。

只汇总 cgroup 还不够：两个兄弟组都只能运行在 CPU 0，各需 1 CPU 秒/秒，即使父额度为 4，也不能同时获得 2。对同一主机建立份额分配变量 x_{r,c}，要求

Σ_c x_{r,c}=p_r；x_{r,c}=0，当 c∉E_r；Σ_r x_{r,c}≤1。

E_r 还应包含线程亲和等真实限制。所有已承诺消费者都进入同一资源域。可以建立最大流：源到消费者容量 p_r，消费者到其允许 CPU 的边容量至少为总需求，每个 CPU 到汇容量为 1。最大流等于总需求，才存在这个连续份额模型中的放置。它不证明任意线程并行结构能实现该份额，也不证明延迟 SLO。

### 共同准入与故障承诺

```pseudocode
算法 ADMIT_RANKS(plan, snapshot, ledger, fault_contract, ε)
输入：逐 rank 执行与设备计划；同一规划窗口的需求与峰值轨迹；
      有效资源快照；已有占用和承诺账；可选故障承诺
输出：REJECT、UNKNOWN，或 MODEL_FEASIBLE 与条件及预留账

1 验证身份、单位、非负需求、快照代次和全部必要 rank
  设备映射仍待枚举时返回 UNKNOWN；不进入可提交状态
2 逐 rank 核对能力、路径、可见设备及单消费者必要上界
  CPU 使用 min(有效 CPU 数,路径 quota 比值)，不能只检查 quota
3 对候选与已有消费者按资源域合账：
    CPU：统一窗口，逐共享祖先汇总份额，再检查实际 CPU 集合分配
    主存：按唯一对象及记费归属，逐祖先、逐重叠阶段核对峰值
    设备：按实际 μ 的设备实例汇总唯一存储和未物化承诺
    MPS：另外逐客户端检查该版本配置的份额上限
    pids、描述符、共享内存、I/O 等使用各自真实计数域和单位
4 任一已知预算违反：返回 REJECT，列出维度、域、需求、上限和来源
  未发现违反但其他消费者或必要资源账缺失：返回 UNKNOWN
5 对 fault_contract 要求的每个场景 F：
    移除失去任一必要 rank、设备、存储、控制或路径依赖的完整执行组
    检查剩余独立副本的版本、状态、路由和承诺容量
    共用资源导致服务率不能相加时，使用共同资源模型
    不满足声明目标则拒绝；依赖或容量未知则返回 UNKNOWN
6 未声明故障目标时，记录共同失效风险，不额外要求单实例容错
7 在预留协调域内重验 ε 与账本代次，取得全部必要承诺后发布结果
  竞争导致条件变化则重算；无法完成共同预留时不发布半份可执行准入
返回 MODEL_FEASIBLE，仅表示所声明预算模型内存在可行承诺
```

第 7 步可以由一个串行拥有者、锁或等价协议实现。跨节点多步预留应先取得临时资格，再共同确认；失败撤销尚未启动的预留，已提交访问仍需排空。读取 cgroup 文件本身不会自动实现这个事务。

故障检查针对服务声明，不能要求“一个实例的 ranks 不得全部位于同一故障域”。合法单 rank 实例和追求近距离通信的单节点 TP 组，都可以普通准入。它们只是不自动满足节点失效后继续服务的承诺。

若一个必要 TP 组分布在节点 A、B，失去任一必要 rank 后整个组都不可作为完整服务容量。把 ranks 分散不等于创建独立副本。设三个独立副本各有 40 请求/s 的已验证容量，目标到达为 70 请求/s；失去任一副本后剩余 80，仅通过平均容量检查。若两个副本共用会同时失效的供电域，该场景只剩 40，必须调整放置、余量或故障时降载承诺。尾延迟和恢复时间仍需另证。

## 共享机制决定哪些账必须重算

固定 v0.16.1 README 中，time-slicing 的 replicas 是底层 GPU 的访问引用，不提供额外显存或故障域隔离，也不保证申请多个名额获得同比算力。客户端可以创建多个 GPU 进程，因此不能从客户端数量直接推出等份吞吐。

MPS 使用控制守护进程限制客户端显存和计算。该版本配置 q 个份额时，每客户端受约 1/q 总显存和计算能力上限约束；只支持完整 GPU，与启用 MIG 的设备不相容，且与 time-slicing 配置互斥。这些是配置契约，不是实测吞吐保证。

因此 time-slicing 至少检查每个实际设备的物理总账；MPS 除总账外，还要检查每客户端上限。设可计账容量为 80 GiB、两等份 MPS，每客户端上限 40 GiB。60+20=80 满足总容量，但 60>40，仍须拒绝；改成 40+40 才通过此容量模型。实际实现保留、控制守护进程开销和峰值需进入预算。

MIG 的容量按实际设备实例及 profile 核对，不能把父整卡容量发给每个实例。实例之间是否共同依赖同一物理 GPU、主机或出口，还需在故障图中保留。mixed MIG 资源可以再配置 time-slicing，因此同名资源不推出相同隔离边界。

## 健康、就绪与可接收容量

健康回答进程能否推进必要工作；就绪回答特定制品与执行组在某环境上是否具备接收某范围请求的资格；瞬时容量回答现在是否还能接一个请求。三个判断不能合成一个 ready 布尔量。

就绪证书可写成

C_g=(v,g,ε,P,Ω,Π)，

v 是制品身份，g 是加载实例，P 是完整 rank、设备与布局计划，Ω 是允许公开的请求范围，Π 是绑定实际依赖的验证证据。Ω 应能判定模型、dtype、模态、输入几何、上下文上限、adapter、图桶和受验证回退路径。代表输入通过只证明该路径上的观察；向范围推广还需要执行契约、形状 guard 和容量边界。

```pseudocode
算法 PUBLISH_READINESS(v,g,ε,P,Ω,Π)
1 关闭新准入门；核对制品身份和全部必要 rank 的完成证据
2 核对实际 μ、有效资源、依赖和 Π 的身份一致
3 对 Ω 中每个变体核对执行合同、guard、容量边界与所需证据
  必要项未知或失败时，不把该变体放进公开范围
4 范围非空且共同条件成立：发布 READY 证书；路由切换后才开放准入
5 环境变为 ε′ 时，先使旧 ε 的新准入资格过期
  逐变体比较证据依赖：已证明未受影响者可以重绑定 ε′
  受影响者重新验证；失败或未知者从 Ω 去除
  剩余范围非空则收窄发布，否则撤销证书
6 已接受请求保留原版本与资源责任；不因收窄而改绑到新实例
  设备失效或资源收紧使继续执行不安全时，停止相关新提交并按恢复合同处理
  不能用“保留原绑定”声称失效资源仍能履行执行
```

端口能连接、HTTP 成功、插件进程未退出，都不能独立证明权重、执行组和目标路径就绪。KV 满或排队长时，可以暂停准入；若把暂时过载当成进程失效并反复重启，会清空热状态、重复加载并放大存储竞争。无法恢复的设备或组错误则需退出相应可用集合，按[恢复协议](serving-recovery.md)重建。

共享内存、文件描述符、任务/线程数、I/O 和网络范围也进入环境合同。增加 GPU 数量可能同时增加 tokenizer 进程、IPC 缓冲和并发制品读取，先耗尽这些资源；不能用 GPU 尚有空间证明其他维度足够。

## 六类成本与有条件的时间模型

| 成本 | 同一部署方案中的对象 | 易漏项 |
|---|---|---|
| 计算 | 制品与能力核对、集合折叠、容量账、代表路径 | 初始化、哈希、布局转换和重新验证 |
| 访存 | 加载读写、页面迁移、元数据与页表 | 迁移不完整留下的远端页，额外 staging |
| 通信 | 制品分发、rank 共同验证与控制消息 | 多副本对同一 NIC、缓存或存储出口的竞争 |
| 准备 | 挂载、锁页、注册、编译、图捕获与预热 | 变化后失效产物的重建及失败清理 |
| 同步 | 初始化、组建立、屏障、排空与路由交接 | 提交返回不等于完成，最慢必要 rank 决定发布资格 |
| 驻留 | 权重、KV、图池、旧版本、共享组与在途对象 | 同一 backing 重复计数，取消后尚未释放的责任 |

若有 R 个 rank、层级深度 H，直接逐 rank 折叠需 O(RH) 次层级访问，公共祖先可以在一致快照内缓存。G 个 grant 和 N 条枚举记录的身份去重与核对可用散列表做到期望 O(G+N)。有 K 个阶段快照、O 个存储记录时，直接逐阶段逐祖先计账约为 O(KOH)，可通过事件增量维护减少工作，但回收和代次必须保持正确。CPU 份额检查可用最大流；算法成本随消费者、允许边和 CPU 数增长，不能把探测与规划成本当成零。

就绪计时从共同准备触发到全部必要条件可发布为止，所有时间项单位为秒。q_r 是触发到 rank r 可开始本地准备的前置等待；L_r 是从该时刻到本地准备完成的依赖图完成时间，包含加载、探测、验证、编译与预热中实际需要的工作及内部等待。T_group 只计全部本地工作之后的共同验证或屏障。

只有在 rank 的资源相互独立、没有遗漏跨 rank 依赖，且组阶段确实在其后时，才可写

T_ready=max_r(q_r+L_r)+T_group。

若加载、探测、验证被强制串行，L_r=L_r^load+L_r^probe+L_r^verify，编译与预热按实际依赖另计。每项必须以相邻完成边界计量，避免内部等待被重复加入。

允许重叠时，用共同依赖与资源图求完成时间。对已经加入资源顺序的无环图，任务 j 的固定时长 t_j≥0，完成时间为

F_j=max_{i∈pred(j)}F_i+t_j。

无前驱时从其可开始时刻计；最终完成时间取全部必要终点的最大值。共享资源尚未排定时，需要选择合法资源顺序或有效服务份额，单有依赖图关键路径并不保证可实现。

重叠不会使串行求和自动失去上界意义：若阶段时长是固定非负值或可信上界，串行调度合法，且等待、争用及额外依赖均被覆盖，则全局合法串行计划的总和可以给出保守上界。串行化若违反通信匹配、超时或驻留条件，就不能直接使用。孤立带宽估计也不是争用后的时长上界。

展开一个跨 rank 反例。两个 rank 各从同一 SSD 读取 4 GiB，SSD 持续服务能力设为 1 GiB/s；每个随后在各自独立设备上验证 2 秒。均为设定量。把每个 rank 的孤立时间写成 4+2=6，再取最大值 6 秒，会漏掉共享 SSD 至少服务 8 秒。

| 工作 | 一个合法计划的区间 | 依赖与资源 |
|---|---|---|
| 读取 A | [0,4) | SSD 独占服务 |
| 读取 B | [4,8) | 与读取 A 共用 SSD |
| 验证 A | [4,6) | 依赖读取 A，独立设备 |
| 验证 B | [8,10) | 依赖读取 B，另一设备 |

该计划完成于 10 秒；全部四项串行的 12 秒也是满足这些假设的保守计划。6 秒既小于此计划，也小于 SSD 服务量下界 8 秒，不能当上界。若额外存在跨 rank 验证或屏障，应加入同一图；已经加入的事件不再单独相加。

探测缓存的成本也需条件化。设 N 次请求的完整探测成本为 c_probe，每次代次检查为 c_check，M 次环境变化各需 c_verify，则

C_naive≈N·c_probe，C_cached≈N·c_check+M·c_verify。

设 c_check=5 微秒、N=5×10^5、c_verify=8 秒、M=20，缓存方案为 162.5 秒；若 c_probe=50 微秒，逐次方案为 25 秒。这组设定量反驳“缓存算术上必然更便宜”。

合法性还受探测副作用影响。固定 PyTorch 文档说明，默认 is_available 会经运行时调用初始化 CUDA 驱动，影响随后 fork 的使用；NVML 路线成功时可避免这项污染，但保证更弱，且 NVML 发现失败会回退到运行时检查。设置环境选项不等于保证没有初始化副作用。应按进程创建方式选择探测位置、时机及缓存策略，不能把一个历史成功布尔值当作当前执行路径验证。

排空时间从停止新准入计到最后必要访问和责任结束。重新注册与验证只有确实在排空之后串行发生时才再相加；恢复可以并行时仍使用共同图。固定插件文档建议升级前排空 GPU 任务，不保证任务在滚动升级中存活，容器未退出不能证明环境等价。

## 条件变化后的保留、调整与放弃

更换驱动、设备插件或运行时可能影响整个节点。应保留制品和已证明不依赖变化字段的知识，更新节点环境代次，关闭受影响的新准入，完成或恢复已有工作，并对相关路径重新验证。不能因为插件重新注册了设备，就复活旧实例的映射与证书。

用户态库升级按依赖闭包判断。接口、ABI、数值策略和编译假设未受影响时，可以保留相应布局与产物；改变实际依赖时重建受影响部分。若组合不再满足要求，放弃该组合或选择已验证回退，而不是用更大的版本号解释合法性。

设备重排或 uuid→index 策略变化后，保留不受影响的制品，重新解析授权身份、取得实际枚举并建立 μ。只记录历史 index 的日志不能回答逻辑 0 是否仍为同一设备。MIG 重建还要核对实例及父卡依赖。

独占改成 time-slicing 或 MPS 时，先按变化后的 μ、设备实例、客户端和共享组重算账本。共享模式名称本身不改变设备数量或故障域数量。若原工作仍分布在原来的 k 张卡上，就逐卡保留容量账；只有把原来分布于 k 张容量 C 的设备上的工作合并到同一张卡时，才从分设备条件变成该卡的 Σd_i≤C。即便原总量小于 kC，也不能推出合并可行。

time-slicing 检查物理总容量与竞争风险；MPS 还检查客户端份额。80 GiB 两等份下的 60+20 不能因总量相等而放行。故障域由实际共同依赖决定：同卡工作共同依赖该卡，不同卡仍可能共同依赖主机或供电。容量限额不能自动证明故障独立。

CPU 或内存收紧后，保留身份和最后使用规则，重算祖先预算、实际 CPU 分配与峰值。提高线程数不能突破 quota；迁移进程不能抹去旧内存记费。若旧承诺已无法兑现，应停止相关新提交并按服务合同降载、恢复或终止，不能仅更新证书数字。

公开范围部分失效时，可以收窄 Ω，让其余证据仍有效的请求继续服务。共享变化后，数值路径证据只有在其依赖确实不受影响时才可保留；容量、性能和隔离结论均需单独重核。整个范围无法合法执行，或修复后的成本超过可接受预算时，应放弃该部署组合。单一受控机器可以选择直接部署；多租户、多版本与弹性场景需要更明确的责任与代次合同，部署载体不改变这些合法条件。

## 区分竞争解释与反证修正

| 观察 | 竞争解释 | 区分实验 | 反证后的修正 |
|---|---|---|---|
| 容器启动但前向失败 | 未注入设备；身份错误；库与驱动不相容；kernel 不支持；通信组失败 | 固定制品，核对授权、最终枚举与稳定身份；先单设备最小前向，再完整组路径 | 身份缺失先修暴露；单卡通过而完整组失败时检查通信及共同依赖 |
| 子组请求了 {2}，有效值却是 {0,1} | 固定语义回退；读错组；热插拔或分区变化 | 固定父有效集与 member 配置，分别请求空集、{2}、{1,2}；同时保留请求和 effective | 前两者相同而第三者为 {1} 支持回退；不符则查实际层级、在线状态与分区，不能直接判写入失败 |
| 每个 rank 都够，合起来 OOM 或节流 | 共享祖先预算；其他消费者；峰值漏算；记费归属错 | 保持单 rank 需求，比较单独与共同运行；记录父级 current、事件和已承诺对象；CPU 同时看节流 | 仅并发失败支持共同账问题；父账仍有余量时查实际设备域、对象峰值和其他限制 |
| 线程池增大但吞吐不增 | quota；cpuset/亲和过窄；锁或内存带宽 | 联合读取 cpu.stat、effective 和亲和，只放开一个维度 | quota 不变但扩有效集改善，支持放置解释；两者均无效时撤回单纯 CPU 额度不足解释 |
| 外部工具有空闲但分配失败 | allocator 保留；MIG 容量；MPS 客户端上限；在途峰值 | 固定身份，比较 allocated/reserved、实例容量、客户端限额和唯一对象时间线 | 总卡空间足够而客户端超份额时修客户端预算；保留高不自动等于泄漏 |
| 同一模型两台机器速度不同 | μ 指向不同设备；NUMA；共租户；功率或时钟 | 固定稳定设备，只改 CPU/NUMA；固定放置，只改共租户；记录逐阶段等待 | 性能随设备、放置或竞争分别移动才支持对应解释 |
| 升级后仅部分请求失败 | 旧证书；编译依赖失效；未覆盖变体；旧实例仍接流量 | 固定请求类型，分别核对 ε、实例绑定、产物与 guard；只替换受影响项 | 身份纠正无效时转查产物与路径，不能把关联直接写成因果 |
| ranks 分散却不能承受节点故障 | 必要组被当副本；副本共享依赖；剩余容量不足 | 分别移除一个必要 rank、一个完整组和一个共同供电域，重算完整组集合 | 必要 rank 丢失后应移除整组；独立副本不足则调整承诺或部署 |
| 多副本冷启动比 max_r 估计慢 | 共享 SSD/NIC；跨 rank 等待；编译或探测副作用 | 固定字节，比较串行与并发加载，记录共同出口服务量和各完成事件 | 总出口服务量已解释延迟时修共同模型；若不饱和则查依赖和初始化 |

这些是诊断设计，不是目标设备实验结果。先固定对象身份、请求与完成边界，再做单因素干预；不同环境中的两次总耗时差不能直接归为 kernel 优化或共享方式收益。

## 检查覆盖与未验证边界

配套 tools/check_k_sys_019_full.py 是确定性、离线、只读的 Python 标准库 CPU 符号模型。检查范围按实际编入脚本的机制限定。

集合检查对三元素在线全集、全部在线子集及三层请求组合，比较集合递推与逐资源布尔参考；核对父集约束和仅在获得请求资源时成立的请求集约束。非空不相交请求必须回退。旧的非空交集算法和只看本级的变体在同一输入域中被检出。此模型用于 CPU 集或内存节点集的普通静态层级，不模拟分区。

CPU 检查同时使用 quota 和有效集数量，包含 quota 大于 cpuset、共享祖先份额超额，以及兄弟消费者争用同一 CPU。最大流的连续份额可行性与独立的消费者子集容量判据交叉核对。内存检查按唯一对象及记费归属汇总祖先，包含 48/32/32 GiB 下 30+30 的反例、已有占用与未物化承诺、别名去重、元数据冲突和账本不完整返回未知。逐 rank 单独放行、忽略 cpuset 和重复计共享对象的错误均有触发输入。

设备检查使用显式给定的容器与最终进程枚举，包含待枚举、与 grant 顺序不同、最终过滤、共享名额去重、未授权身份、缺设备、重复身份和 ordinal 缺口。按 grant 顺序猜映射、忽略最终过滤和按名额扩容量的负对照均实际调用并与同一观察核对。共享检查包含 45+45>80，以及 MPS 两等份下总量合法但客户端 60>40 的反例。

故障检查移除失去必要依赖的完整组，包含无容错目标的单实例、跨节点必要组、独立副本和共同域。范围检查明确包含 dtype、模态、上下文越界、代次不匹配和收窄后仍合法的请求。只看模型名和只看 ranks 分散的变体会错误放行指定反例。

峰值检查用独立的存储粒度集合核对 28/52/27 GiB 时间线；成本检查核对共同 SSD 的合法 10 秒计划、8 秒服务量下界，以及 6 秒孤立估计的不足。它不因此成为一般资源调度器或性能预测器。

以上是模型覆盖说明，执行是否完成及其结果由绑定当前脚本和输入的实际记录承担。脚本不读取真实 cgroup，不执行 CUDA、设备注入、CDI、MIG、MPS、fork 或故障恢复，不验证内核实际 effective 值、真实设备身份查询、GPU 可见性和隔离强度，也不测量存储、网络、设备性能、SLO 或 Agent 使用效果。短周期 CPU 调度、动态热插拔、任意分区、真实共享页记费、分布式预留和完整生命周期并发仍需各自证据。
