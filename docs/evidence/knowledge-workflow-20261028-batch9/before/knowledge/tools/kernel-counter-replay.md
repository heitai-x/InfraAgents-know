# K-TOOLS-003：Kernel 计数器：吞吐、访存与 Replay 语境

计数器回答的是：指定逻辑工作在某个范围、时间窗和采集环境中，产生了多少事件。它不能单独回答瓶颈是什么。有限的硬件计数资源可能迫使工具多次执行工作；内存恢复、cache 清空、时钟控制和串行化又会改变被观察的环境。因此，要把原始计数、派生量、replay 状态和正常服务结果连接起来。

本章输入是时间线选出的代表实例、需要区分的机制假设、事件计划和可用采集模式；输出是带身份与范围的样本、直接指标或有条件的估计、拒绝合并的原因，以及下一项区分实验。计数用于解释资源限制，正常执行用于确认完整服务收益。

## 计数对象、时间与派生量

定义逻辑 kernel 实例 X=(进程角色,设备,上下文,stream,launch 序号,kernel 名,grid,block,shape,执行阶段)。跨应用重跑时，进程号和地址可能改变，必须另建运行身份与逻辑实例的映射。只按 kernel 名聚合，会把同名不同 shape、不同阶段或不同次 launch 混在一起。范围级结果则以 R=(应用运行中的逻辑范围,设备/上下文,范围内工作集合) 为对象，不能冒充其中某一个 kernel 的计数。

每个原始样本至少记录：逻辑对象、实际运行身份和 pass、事件及单位、采集范围、开始/结束、聚合层级、cache/clock 策略、并发集合、工具模式、计数支持与错误状态。pass 编号必须连同实际运行身份解释；两次应用运行各自的 pass 0 不是一次同时观测。硬件计数、软件插桩和启动参数也要分开，软件插桩可能改变执行时间。

CPU 复用需要三个不同的时间量：

- T_wall 是观察窗口经过的墙钟时间。
- T_enabled 是该事件的逻辑 time_enabled，即读数接口定义的启用时间。
- T_running 是该事件实际占用计数资源的 time_running；复用时可以小于 T_enabled。

对尚未缩放的计数 C_raw，perf 复用缩放的目标是估计逻辑启用期间的事件总数：

C_hat_enabled = C_raw × T_enabled / T_running，r_mux = T_running / T_enabled。

这要求 T_running>0，且实际计数片段能代表逻辑启用期间的事件率。T_running=0 表示没有可供外推的计数，不能返回零或除以默认比例。T_enabled=0 也没有本式的估计目标。时间必须来自同一事件及同一读数语义，不能把线程 CPU 时间、显式启用时长或墙钟随意替换进去。对聚合的多个 CPU/事件，先保留各自的时间与缩放语义，再按合法范围聚合；它们的累计时间可能超过一次墙钟。

设单事件窗口 T_wall=1 s、T_enabled=1 s、T_running=0.25 s，原始计到 250；代表性成立时，缩放为 1000。若 T_enabled=0.4 s、T_running=0.1 s、原始计到 100，则启用期间估计为 400。把后一个样本再按 T_running/T_wall 外推，会得到墙钟全窗假设下的 1000，已经改变估计目标。线程未运行、阻塞或事件未启用期间，不能未经说明补出事件活动。

perf 的输出可以已经缩放；导入时必须保存 raw/scaled 标志及运行比例，已缩放值不再乘一次 T_enabled/T_running。运行比例小不必然证明估计错误，运行比例大也不能证明短 burst 被准确覆盖。如果高事件率只出现在被调度计数的片段，任何时间比例都不能从缺失片段恢复真值。

派生量还要保留资源边界。对链路 j，定义有效需求字节 D_use,j、事务字节 D_tx,j，以及同一范围的完成时间 T：B_use,j=D_use,j/T，B_tx,j=D_tx,j/T。D_use,j>0 时，放大 A_j=D_tx,j/D_use,j，效率 E_j=D_use,j/D_tx,j；这些定义只有在有效需求与事务属于可比较的请求集合时才有解释。cache 复用可能使 DRAM 字节低于上层请求字节，此时不能把跨层比值称为同一层的合并效率。

计算吞吐 F/T 必须说明算术计数规则、dtype 与执行路径。occupancy O=W_active/W_max 描述活跃 warp 与可驻留上限之比，不是有效工作比例。工具的百分比也要保留分母：burst 峰值和 sustained 峰值不同；S-NCU 说明 sustained 百分比在边缘情况下可能超过 100%，不能一律裁剪为 100%。

## 合法组合与 replay 模式选择

派生比率分为三类。

| 类别 | 条件 | 可输出的结论 |
|---|---|---|
| 同 pass 直接比率 | 分子分母确实来自同一次执行、同一范围和兼容事件语义；分母为正 | 这次被采集执行的比率，仍带工具环境标签 |
| 跨 pass 估计 | 同一逻辑实例已正确匹配；输入、完成工作、cache/clock 和并发策略受控；重复观察未显示相关非平稳性 | 明确标为估计，保留原始 pass、点估计和观察变化范围 |
| 不可合并样本 | 实例、范围、单位或状态不匹配，匹配不确定，或已观察到显著工作变化 | 保留原始值和失败原因，停止该派生量 |

因此，hits 来自 pass 1、queries 来自 pass 2，并不自动非法。S-NCU §2.2.3 明确支持正确识别并合并同一 launch 的多个 application replay pass；§2.3.4 指出，工作分布改变、短工作未达稳态或自旋等固有变化会让跨 pass 命中率产生显著误差。相反，线程范围 instructions 与系统范围 cycles 即使同时采集，也不能称为该线程的 IPC。

跨 pass 的状态控制不是只恢复内存。相同内存可以配上不同 cache、时钟、工作分布或外部响应。应重复采集关键事件与共同锚点，例如完成工作量、输入身份、输出检查值、执行时长和与假设有关的分布信号；检查事件组顺序改变后结论是否变化。时长稳定只是证据之一，不能证明内部工作完全相同。所供文档中的一般稳态时长提示不是适用于所有 kernel 的硬门槛。

一种可复核的估计方法是：对固定工作量，分别保留各次 H 和 Q，采用 mean(H)/mean(Q) 作为点估计；当所有 Q>0 时，报告 [min(H)/max(Q), max(H)/min(Q)] 作为这些观察支持的保守经验包络。它不是统计置信区间，也不包含未观察到的状态。若 H=(80,82)、Q=(100,102)，点估计为 81/101，包络为 [40/51,41/50]。若计数变化与 pass 顺序、时长或工作量显著相关，就不能仅用更宽的包络掩盖非平稳采集。

减少指标有助于降低 pass 数，也提高相关计数同 pass 取得的机会，但硬件约束可能使它们无法同时采集。此时可输出经过验证的估计，或明确选择保守策略而保留 unresolved；不能承诺改成一个事件组就一定解决。对 hits/queries 这种有明确取值范围的指标，越界结果应保留原始证据并停止解释，不能夹到 [0,1] 后继续归因。

四种 replay 模式具有不同的执行对象和状态推进。

| 模式 | 一个 pass 执行什么 | 后续 pass 如何重建状态 | 主要选择条件 |
|---|---|---|---|
| kernel replay | 同一个 kernel 实例 | 多 pass 时，首 pass 前保存可访问 GPU 内存，首 pass 后确定写集；以后从原始备份恢复写集 | kernel 自包含，恢复机制覆盖其副作用，不依赖缺失的主机响应或必要并发 |
| application replay | 完整应用 | 每次重新运行应用，由应用重建主机与设备依赖；工具不做 kernel 写集保存恢复，再匹配对应 launch | 应用活动及设备/上下文/stream/range 归属足够确定，能匹配同一逻辑执行 |
| range replay | 捕获的 CUDA API 与 kernel 范围 | 捕获范围，按范围保存和恢复必要主机/设备状态，再重放整个捕获序列 | 必须保留范围内并发，且范围满足捕获与恢复契约 |
| application-range replay | 完整应用中的选定范围 | 每次重跑应用并匹配逻辑范围，由应用重建状态；不显式捕获范围或进行工具内存恢复 | 需要范围并发，或捕获不支持其 API；应用本身可以正确重复执行 |

kernel replay 的不变量是每次执行前，相关内存内容都等于原始 M_0，而不是上一 pass 的输出。首 pass 保存量可能远大于写集；备份优先放在合适的可用存储，设备空间不足时可能转到主机。单 pass kernel 采集不做这套保存恢复。恢复内存不会恢复硬件 cache，cache 策略必须另行声明。

application replay 默认 grid 匹配在同一进程、同一设备候选内比较 kernel 名和 grid；同属性的多次 launch 按执行顺序区分。这个工具匹配键不能证明两次调用语义相同：同名同 grid 的 prefill/decode、不同输入或顺序变化仍需作者核验。实际进程身份的跨 run 对应、上下文与 stream 归属都要记录；匹配失败时停止派生。

range replay 的范围包括起止标记之间来自各 CPU 线程的 CUDA 调用与 launch。应用负责线程间同步，保证捕获集合符合预期；范围起点必须能够同步所有活跃 CUDA 上下文，范围内不能出现固定工具版本不支持的 API。其捕获基于受支持的 Driver API，Runtime API 能否捕获取决于其内部生成的调用，不能仅凭接口名称判断。应把 API 列表与具体限制委托给固定版本的 Supported APIs 检查，出现不支持调用就终止该范围采集。

被设备写入、工具随后要恢复的主机地址必须仍然有效，且没有释放或改作其他对象；普通堆/栈分配生命周期并不全由工具截获。缩窄范围可减少跨生命周期恢复。若不能保持地址有效，应改用适合的 application-range 或其他符合文档限制的采集方式，不能在失效地址上继续恢复。application-range 不要求范围内 API 能被显式捕获，但目标上下文必须在定义范围起点的线程上 current，并在整个范围保持 active；逻辑范围仍须跨应用运行匹配。

需要正确并发执行的 kernel，不能用强制串行化的单 kernel 结果替代；范围指标属于整体工作，通常不能按各 kernel 时间比例分摊。图作为整体采集可以保留必要并发与节点间 cache 关系，但部分指令级指标不可用。MIG shared compute instance 的共享单元可能禁止采集；green context 的不可归因指标不随其 SM 数缩放。共享 L2、DRAM、PCIe、NVLink 还可能包含其他引擎活动，不应当作本实例独占需求。

## 从代表实例到可复核结果的算法

```pseudocode
算法 CollectAndValidateCounters
输入：时间线 TL；目标逻辑实例 X 或范围 R；假设 H；事件计划；模式与预算
输出：原始样本；直接指标或跨 pass 估计；失败原因；下一项区分实验

从 TL 定位实际 shape、阶段、进程/设备/上下文/stream 与完成边界
为每个假设列出预期信号、竞争解释和可控干预
核实事件语义、单位、聚合层级、支持情况及 raw/scaled 状态
按硬件兼容性安排事件组；P 表示实际采集 pass 数，额外预热另记
若没有待采事件：返回空采集结果，不制造零计数
选择模式，核实其正确性前提并估算准备、重复执行和状态成本
预算不足时减少问题或改选模式；估计成本不冒充严格必要下界

若模式为 kernel：
    建立目标实例的原始输入状态 M_0
    若 P>1：在首 pass 前由工具保存可访问 GPU 内存为原始备份 B_0
    对 p=0 到 P-1：
        若 p>0：从 B_0 恢复首 pass 确定的写集；等待恢复完成
        应用并记录 cache、clock 和串行化策略
        在目标 kernel 实际执行范围启用本组计数，执行同一实例并收集结果
        若 p=0 且 P>1：取得工具确定的写集，不用 M_1 替换 B_0
        保存输入/输出身份、完成状态、原始计数和物理执行身份

若模式为 application：
    对 p=0 到 P-1：
        从相同外部输入、配置与随机状态启动一次完整应用运行
        由应用执行主机准备、设备依赖、目标 launch 及后续工作
        采集本组事件；建立本 run 的 launch 到逻辑 X 的映射
        不执行 kernel 写集恢复
        若目标缺失、歧义、顺序变化或运行失败：停止受影响指标的派生

若模式为 range：
    检查起点上下文可同步、跨线程范围边界和 API 支持
    保持将被恢复的主机/设备对象及地址生命周期
    在原应用到达起点后，捕获完整范围和必要状态；首个采集 pass 执行该范围
    对其余 pass：
        按工具的范围恢复契约恢复必要状态，等待恢复完成
        重放捕获的完整 API/kernel 序列，保留范围内完成依赖与并发
        收集范围级计数，不把它标成单 kernel 计数
    若捕获、恢复、地址有效性或完成检查失败：停止派生

若模式为 application-range：
    对 p=0 到 P-1：
        启动并执行一次完整应用，由应用重建全部依赖
        检查定义范围线程的目标上下文为 current，且范围内保持 active
        匹配逻辑 R，在其范围内采集本组事件
        不显式重放捕获序列，不执行工具写集恢复
        范围匹配或应用执行失败时停止派生

对每个样本：
    保留对象、run/pass、范围、事件/单位、策略、错误及时间标签
    CPU raw 计数只在时间有效且代表性成立时按 enabled/running 缩放
    已缩放值直接保留；零 running 或未知缩放状态标为 unresolved
对每个派生量：
    拒绝实例、范围、状态或事件语义不匹配的组合
    同次执行且同范围采集时计算直接比率
    否则核验 replay 匹配、状态控制、重复事件与共同锚点的稳定性
    条件成立时输出估计标签、点估计和观察包络；否则保留 unresolved
将结果与独立工作/字节账、时间线及无 profiler 服务结果对照
输出支持项、被反证项、未知项及下一项干预；不裁剪异常原始计数
```

这个流程的状态链是：实例已定位 → 模式前提满足 → 状态已重建 → 工作已完成 → 样本身份已核对 → 指标可解释。工作完成前不能把 host API 返回当作计数窗口结束；匹配成功也不能跳过状态与稳定性核验。错误样本可以作为诊断证据保存，但不能继续进入后面的瓶颈推断。

## 条件化成本与资源账

采集耗时与被采 kernel 的耗时是不同对象。令 P≥1 为一个目标的采集 pass 数，T_exec,p 为每次在所声明工具环境下的 kernel 执行时间，T_aux,p 包含该 pass 未与其余项重叠的配置、清 cache、读取计数与同步成本。对 kernel replay，若采用全部串行的记账假设，可写近似预算：

T_kernel,serial ≈ T_setup + Σ_p(T_exec,p+T_aux,p) + I(P>1)[S_save/B_save + Σ_{p=1}^{P-1} W_restore,p/B_restore,p]。

S_save 是原始备份字节，W_restore,p 是第 p 次重放前恢复的字节。B_save 与 B_restore,p 是相应设备内存或设备↔主机路径的估计速率，单位 byte/s；不默认它们相同。P=1 时括号中的保存恢复项严格为零，这是上述 kernel replay 策略的单 pass 特例。各 pass 时间可以不同，不能无条件用 P 倍一次时间替代。此式是给定串行假设的预算模型，不是经证明的必要下界；可持续速率也不是硬件能力上界。

设多 pass 需保存 1 GiB、每次恢复 4 MiB、P=4，则状态流量为首次 1 GiB 加后续 12 MiB，保存驻留量还取决于备份位置。kernel 很短时，保存、cache 清空或一次性指标配置可能主导采集。设备备份与原分配是两个物理对象；备份溢出到主机后，还要计入链路、主存容量与路径变化，不能继续沿用设备内复制速率。

application replay 的预算应另写为 T_setup+Σ_p T_application,p，其中完整应用成本包括主机准备、文件访问、目标以前的工作、目标与后续执行，以及采集干预。它不支付上述工具写集恢复，却可能重复远多于目标 kernel 的工作。application-range 同样按完整应用运行记账，采集对象则是范围。

range replay 另计首次捕获、范围必要状态保存、每次范围恢复和完整范围执行；保存对象可以含主机内存，范围执行时间包含并发，因此不是范围内各 kernel 时长之和。单 pass kernel 不保存恢复的文档保证不能扩展为所有 range 捕获都没有状态管理成本；range 的捕获与内部准备按实际工具记录列账。

允许重叠时，先把保存、恢复、执行、配置和等待画成依赖图，再标出共同的复制引擎、内存与链路。恢复所需输入必须先于消费者执行，但与其无关的主机工作可能重叠；共享同一复制路径的活动不能各自领取全带宽。例如两个独立准备活动分别需 4、6 个时间单位，执行需等两者完成后再花 2；独立资源上的可行完成时间为 8，串行相加为 12。把 12 写成必要下界会错误拒绝这个合法时间线。

若另有真正的资源能力上界 U_j，可以用资源总需求 D_j/U_j 和依赖路径上的必要时间构造下界；其最大值仍不保证存在达到该时间的调度。使用实测可持续速率得到的则是相应条件下的理想估计，需要目标采集校准。

| 成本 | 需要保持的边界 | 常见漏算或重复计费 |
|---|---|---|
| 计算 | 同一工作、dtype、指令路径与执行窗 | 把峰值百分比当有效 FLOP/s；漏插桩工作 |
| 访存 | 有效请求、各层事务、方向分别记录 | 混加 L1/L2/DRAM 字节；重复惩罚放大 |
| 通信 | PCIe、NVLink 等实际链路及共享上游 | 用 HBM 带宽估计主机备份；忽略其他引擎 |
| 准备 | 指标配置、编译、捕获、保存与 cache 策略 | 将 profiler 首次准备算成服务稳态 |
| 同步 | 恢复完成、上下文同步及关键路径等待 | 把重叠区间相加，或删除必要前驱 |
| 驻留 | 原分配、备份、工作区及同时存活对象 | 原地址别名重复计容量；遗漏主机溢出备份 |

occupancy 的资源账可写为每 SM 的 CTA 上界：N_cta≤min(⌊S_sm/S_cta⌋,⌊R_sm/R_cta⌋,⌊T_sm/T_cta⌋,⌊W_sm/W_cta⌋,B_max)。零需求资源不参与除法。这里 S、R、T、W 分别对应 shared、寄存器、线程和 warp；R_cta、S_cta 要使用目标实际分配量及粒度，实际还受每 block 上限、cluster 和调度约束。它是可驻留上界，不保证网格有足够 block 或 achieved occupancy 达到该值。

设一个明确的资源模型：128 线程、每线程 37 个寄存器、warp=32，每 warp 按 256 个寄存器取整，则每 warp 需要 1280 个，每 CTA 为 5120 个。65536 个寄存器允许 12 CTA；若每 CTA shared 为 16384 B、SM 预算 102400 B，则 shared 只允许 6 CTA。只看寄存器会错估驻留。较少 warp 减少通过 warp 切换隐藏延迟的余地，但更多驻留还可能增加 cache 争用、排队和同步，不能由 occupancy 单项决定速度。

## 从地址、段与 cache 到吞吐解释

S-CUDA-BEST 对 CC≥6.0 的标量访问给出 32 B 段模型。考虑一次只读访问：32 个 lane 各读不同的一个 32-bit 字，地址为 addr(w,λ)=base+4(32w+λ)+o，其中 base 按 32 B 对齐，λ=0…31，o 为字节偏移。

当 o=0，warp 0 覆盖字节 [0,127]，使用段 0…3；当 o=4，覆盖 [4,131]，使用段 0…4。偏移情况下，lane 0…6 在段 0，7…14 在段 1，15…22 在段 2，23…30 在段 3，31 在段 4。该单次请求在这个段边界上有 D_use=128 B、D_tx=160 B，因此 A=160/128=5/4，E=4/5。这里尚未把缓存命中转换成 DRAM 事务。

相邻 warp 1 覆盖 [132,259]，访问段 4…8。若两 warp 间相关段保留且只考察这些冷读的填充，两个请求分别记五段，共 320 B 请求段字节；唯一填充段为九个，共 288 B。这是指定 cache 条件下的地址集合推导，说明上层请求段求和与下层实际填充可以不同，不是目标 GPU 实测。

来源 §9.2.1.3 中的 4/5 是偏移拷贝相对对齐基线的预期吞吐，约 9/10 是该 V100 例子观察到的相对吞吐，文档将偏差联系到相邻 warp 对过取 cache line 的复用。它们不是事务放大，9/10 也不是从计数器测得的 DRAM 字节效率。吞吐还受时钟、指令、写路径与重叠影响，不能从相对速度直接反推实际 DRAM 字节。

若改为 stride=2、o=0，地址为 8λ，每 warp 的 128 B 有效字分布到八个 32 B 段，单请求段模型为 256 B、效率 1/2。改变 stride 后应重建请求集合、段集合和缓存复用，不能沿用原倍数。请求、sector 与 wavefront 也不同：S-NCU 的 L1TEX 模型允许同一个请求含四个 sector，而由一个或多个 wavefront 处理；多个 wavefront 在该流水阶段依次推进。四个 sector 不能唯一决定周期，也不能代表四次 DRAM 读取。

CPU 也需分开工作与速度。两段设定分别为 2×10⁹ instructions、1×10⁹ cycles，以及 1×10⁹ instructions、0.75×10⁹ cycles，IPC 为 2 和 4/3。第二段 IPC 较低，却使用更少 cycles；融合或 SIMD 减少指令时，这完全可能对应同等有效工作的改善。墙钟还取决于频率、调度、等待和并发。instructions 与 cycles 应固定线程/进程、CPU 集合、cgroup、权限过滤和时段；事件分组尽量同时调度，分组过大又可能无法调度或需要复用，需要按具体 PMU 取舍。

## 条件变化后的保留、调整与放弃

| 条件变化 | 保留的关系 | 调整或放弃 |
|---|---|---|
| 事件组增加 | 逻辑实例和事件语义 | 重算 pass、保存恢复与重复应用成本；不能同采时评估跨 pass 估计，不保证单组重跑可行 |
| cache 敏感或分析热态 | 输入身份与完成工作 | 默认清 cache 的隔离结果不能代表应用热态；改选保持前驱状态的采集并重复验证 |
| 时钟固定、热降频或分区限制 | 事件与时间分开 | 记录实际时钟；工具设置可能失败或被热限制覆盖，旧吞吐参数失效 |
| kernel 必须并发 | 完成依赖及范围级结果 | 使用符合前提的 range/application-range，放弃单 kernel 归因 |
| 主机响应参与 kernel | 完整应用的因果链 | kernel replay 可能缺少响应；应用重跑仍须控制外部输入和匹配 |
| range 出现不支持 API 或主机对象失效 | 逻辑范围与正确执行 | 停止捕获恢复；缩窄范围或改用合法的 application-range |
| application 活动不确定 | 原始样本身份 | 匹配歧义或工作变化时停止估计；不能按同名同 grid 强行合并 |
| graph 作为整体 | 图内依赖与并发 | 重核可用指标；不把节点间保留 cache 的结果当普通隔离 kernel |
| MIG/green context 或其他引擎共享 | 可归因单元的计数 | 不支持的共享指标停止采集；不可归因值不解释为单消费者需求 |
| 转到 AMD 等平台 | 问题、单位、范围和假设 | 重核 wave、VGPR/SGPR、LDS、事件与工具模式；不复制 CUDA 的 lane/bank 常数 |
| CPU 范围或聚合层级变化 | IPC 与缩放目标 | 重核迁移、SMT、权限过滤及各事件时间；不把聚合 enabled 与一次墙钟混用 |
| 工作很短或存在 burst/自旋 | 原始工作身份 | 减少事件、分阶段或延长同类工作；新的长窗结论不自动代表原短窗 |

## 竞争解释与区分实验

先由时间线确定代表 kernel 与 shape，再用小事件集回答具体问题。比如重复读、spill、tile 资源或矩阵路径，分别需要独立工作账、生成资源报告及对应事件；源码声明支持 dtype 不能证明本次 dispatch 使用预期指令。

| 观察 | 竞争解释 | 区分干预与预测 | 反证后的修正 |
|---|---|---|---|
| DRAM 带宽和计算都低 | 并行度不足、依赖长、访问不规则、启动或串行化 | 固定工作，改变网格/资源预留，联合观察 issue、驻留、事务和总时间 | 驻留增加仍不提高事务率时，降低 occupancy 解释权重 |
| cache 命中高但慢 | cache 流水、wavefront、依赖或共享端口受限 | 固定工作改变布局与工作集，分别记录请求、sector、wavefront 和时间 | 字节减少而时间不降时，不继续单靠命中率解释 |
| 跨 pass 比率漂移或越界 | 错误匹配、输入变化、工作分布/时钟变化、其他引擎 | 核对实例序号，重复关键事件和共同锚点，交换组顺序；能同采时作直接对照 | 任一相关稳定性条件失败就停止派生；不能夹值后归因 |
| profiler 下更快或更慢 | cache/clock、串行化、插桩与准备改变 | 分别改变相应策略，比较 kernel 与范围，最后回到无 profiler 服务 | 差异只在采集环境成立时，限制结论范围 |
| 高 occupancy 反而更慢 | cache 争用、同步、更多排队或工作不均 | 保持工作和实现，使用受控资源预留改变驻留，记录总网格与等待 | 驻留不变时，不能继续用驻留下降解释 |
| local memory 流量增加 | spill、动态局部数组或原有线程私有存储 | 核对资源报告与生成程序，缩短临时量生命期后再比较相同计算 | 没有对应流量变化时，降低 spill 解释权重 |
| perf 缩放后差异很大 | running 片段偏置、事件组调度、阶段混合或重复缩放 | 少事件同组对照，分阶段保留 raw/enabled/running，核对导出状态 | 时间比例不能代表事件活动时，停止全窗外推 |
| IPC 降低但服务更快 | 指令工作减少、cycles 减少、频率或阶段改变 | 同范围同时看 instructions、cycles、墙钟和完成工作 | IPC 单项不能判定退化 |
| 字节下降但服务无收益 | 瓶颈位于同步/排队，或只减少容量副本 | 固定请求与历史，分别看唯一容量、各消费者请求、链路事务和端到端时间 | 只证实容量时收回带宽或延迟结论 |

一条组合轨迹可以同时触发几种边界。设输入经异步 I/O 到主机缓冲，再复制到设备，目标 kernel 会原地更新输出，并需要另一个 kernel 并发提供进度。首先按 I/O 身份确认已完成范围，不能把排队返回或部分完成当成输入完整；复制完成并建立消费者可见性后，设备工作才可开始。S-LINUX-IO 支持队列与乱序/部分完成的区分，不提供本目标存储速率。

若强行单 kernel replay，即使正确恢复写集，并发伙伴缺失仍会改变工作或导致停滞。应把两者及所需依赖纳入合法范围，或重跑完整应用。range 的首次捕获保存必要状态；后续从范围原始状态恢复并重放完整序列，不能只恢复其中一个 kernel 的输出。范围内如有设备写主机缓冲，地址必须存活到恢复结束。若栈地址已失效，采集在派生前失败；不能把一次正常退出当作恢复正确的证明。application-range 则由每次应用重新建立 I/O、主机和设备依赖，但外部文件内容、请求顺序与目标范围仍须固定或核验。

随章 tools/check_k_tools_003_full.py 是标准库、离线、只读的标量检查。它从时间输入推导 perf 缩放，允许符合证据契约的跨 pass 估计并拒绝错误匹配及非平稳样本；以独立单次函数参考检查四种模式的简化状态推进；以逐字节地址集合核对段数，以可行驻留枚举核对资源公式，并给出重叠反例。错误的 enabled/墙钟比例、重复缩放、遗漏原始恢复、只恢复单 kernel 状态及把串行预算当下界都实际进入负对照。

这些模型不实现真实 CUDA API 捕获、并发调度、工具内存追踪或 PMU。当前仅完成 V8 独立标量复算；新 Python 脚本未在本轮执行，需协调者隔离运行并保留结果。没有目标 GPU replay、CPU PMU、真实缓存事务、同步可见性、服务性能或 Agent 使用效果的实测证据。
