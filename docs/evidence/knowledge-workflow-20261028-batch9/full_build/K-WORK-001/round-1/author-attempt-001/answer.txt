{"chapter":"# K-WORK-001：服务指标：事件边界、Token 间隔与用户时间\n\n一个延迟指标是两个有身份的事件之间的时间差；指标名字相同而事件定义、时间域或分母不同，会得到不同结论。服务指标还要说明观察对象是客户端可见内容、服务端发送、设备执行还是任务最终完成，不能把这些边界混成一个数。\n\n## 问题、事件对象与不变量\n\n生成服务的可观察过程是异步的：请求先被接收，随后排队、预处理、执行和流式交付；模型已经产生 token、服务已经写入发送缓冲、客户端已经显示字符是不同事件。指标系统的任务不是给这些事件改名字，而是保存足够身份，使每个数值可以还原为一条明确的差分或聚合。\n\n一次观测至少写成\n\n`e = (r, g, k, t, d, s, p)`。\n\n其中 `r` 是请求或会话身份，`g` 是尝试或输出代次，`k` 是事件类型，`t` 是时间读数，`d` 是时间域（客户端、服务进程、设备或外部压测器），`s` 是作用域（连接、请求、批或设备队列），`p` 是负载身份（内容、token 范围、chunk 序号、usage 或空事件）。时间统一采用同一单位；跨时间域时另行保存偏移界限，而不是把两个读数直接相减后称为精确延迟。\n\n本章使用的请求记录 `REQUEST_RECORD` 至少包含：逻辑请求身份、尝试代次、到达时间、准入结果、首次执行时间、首个模型 token 时间、首个用户可见内容时间、最后内容时间、协议结束时间、客户端完成时间、输出 token 数、内容 chunk 表、终止原因（完成、拒绝、取消、超时、失败）以及质量与 SLO 判定。状态的含义必须区分：已接收不等于已准入，已产生 token 不等于已交付内容，协议完成不等于客户端已经消费，取消标志也不等于设备上的最后访问已经结束。\n\n本章依赖以下不变量。\n\n1. 事件有稳定身份。重试、旧代次、迟到回调、同一物理工作的重复导出不能自动合并成一条事件；合并前必须证明它们是同一逻辑事件。\n2. 内容事件与元数据事件分开。空角色消息、心跳、usage、响应头、预览标记和真正的首个内容不是同一事件。\n3. token 与传输 chunk 分开。一个 chunk 可以包含零个、一个或多个模型 token；客户端只能直接观测 chunk 到达时，不能凭空恢复 chunk 内部的 token 时间。\n4. 时间差只在同一时间域或已证明的偏移区间内解释。trace 身份可以连接因果，不自动提供时钟同步。\n5. 分母与聚合对象显式保存。`N=1` 没有 token 间隔；每请求平均、按间隔合并、每请求分位数和全局分位数回答不同问题。\n6. 窗口内的拒绝、失败、取消、超时和未完成请求不能从账本中消失。吞吐、成功率和 goodput 的分母必须与实际观察集合一致。\n\n## 事件时间轴与指标定义\n\n记客户端发送为 `t_0`，服务接收为 `t_R`，开始执行为 `t_X`，首个模型 token 为 `t_M`，首个用户可见内容为 `t_1`，最后一个用户可见内容为 `t_N`，协议结束为 `t_F`，客户端确认完成为 `t_C`。所有时间使用同一单位，例如毫秒；若使用不同时间域，只保留带界限的区间。\n\n常用定义如下。\n\n- 客户端 TTFT：`TTFT_client = t_1 - t_0`。它包含网络、排队、预处理、首步执行、内容过滤和首个 chunk 的交付。\n- 服务内部首内容延迟：`TTFT_server = t_1 - t_R` 或 `t_1 - t_X`，取决于起点。它不能与客户端 TTFT 共用同一个名字后直接比较。\n- 请求完成延迟：`L_request = t_F - t_0`；客户端总时间：`L_user = t_C - t_0`。后者还包含最后封包、传输、解析和客户端提交。\n- 设输出有 `N` 个用户可见内容 token，且有精确 token 时间。平均 TPOT 为 `TPOT_avg = (t_N - t_1) / (N - 1)`，仅当 `N > 1`。`N=1` 时没有 token 间隔，应报告 TTFT 或请求完成延迟，并把 TPOT 标为未定义，不能除以零或写成零。\n- 第 `i` 个 token 间隔为 `ITL_i = t_i - t_(i-1)`，`i=1..N-1`。p99 ITL 是这些间隔上的尾部分位数，不是平均 TPOT 的 p99，也不能由平均 TPOT 推断。\n- 单请求的输出 token 速率若定义为除首 token 外的生成量除以生成持续时间，则为 `(N - 1) / (t_N - t_1)`，仅在 `N>1` 且时间可解释时有意义。\n\n传输 chunk 带来额外边界。设第 `k` 个内容 chunk 在 `τ_k` 可见，携带 `m_k` 个 token，累计 token 数为 `C_k = Σ_{j≤k} m_j`。若 chunk 内没有逐 token 时间，则 `τ_k` 只能给出该 chunk 的可见时刻；chunk 内 token 的时间属于一个不可直接区分的区间。此时可以从 chunk 时间构造一个明确命名的近似量：`chunk_ITL_k = (τ_k - τ_(k-1)) / m_k`，但它不等于精确逐 token ITL，除非 `m_k=1` 或另有均匀间隔等假设。\n\n一个特别容易被误算的边界是：所有 `N>1` 个 token 都在同一个 chunk 中。此时用首 chunk 和末 chunk 的端点相减会得到零，再除以 `N-1` 会报告零 TPOT；这不是快，而是 token 时间不可观测。正确做法是保留 TTFT 和 chunk 可见时间，把精确 TPOT 标为不可用；若要报告近似值，必须把它命名为 chunk 级估计并说明假设。\n\n## 从协议事件到内容 token：合法映射\n\n首个内容事件必须由任务和协议共同定义。文本流中的角色消息、空 delta、usage、结束标记和工具调用元数据通常不是用户可见内容；stop string 检测、detokenization 缓冲、内容过滤和代理压缩又可能让模型已经产生的 token 暂时不可见。指标应同时保存模型 token 时间、服务端内容事件时间和客户端收到时间，而不是只保留最后一个。\n\nASGI 的固定规范说明：`http.response.start` 不要求立即刷新，服务器可以等到第一次 Response Body 再发送响应头；成功处理 `http.response.body` 的 send 返回时，数据已经交给服务器发送缓冲，但这不确认远端客户端已经消费。断开通知与发送失败还可能存在时间上的竞争。因此至少有三个边界：服务端准备发送、服务器发送缓冲接受、客户端收到并解析。用户 TTFT 应绑定任务定义的首个有效内容；若只测服务端发送函数返回，就不能声称测到了用户体验。\n\n一次内容映射合法，需要满足以下条件。\n\n1. 逻辑输出 token 数 `N` 有明确身份：固定模型、tokenizer、模板、特殊 token 规则和输出过滤条件。不同 tokenizer 或不同模板产生的计数不能直接混用。\n2. 内容 chunk 的累计 token 范围从 0 开始连续、不重叠、不遗漏；重复 chunk、倒退范围或缺失中间内容应被拒绝或标为不完整。\n3. chunk 时间随序号非递减；协议结束时间不早于最后内容时间。跨时间域时不直接要求两个读数满足该不等式，而使用已证明的因果关系或偏移区间。\n4. 若提供逐 token 时间，其数量必须等于 token 数，且时间非递减。若没有逐 token 时间，`N>1` 的多 token chunk 只能提供 chunk 级时间，不得伪造精确 TPOT。\n5. `N=0` 时 TTFT 未定义，但请求仍可以有完成、拒绝、空结果或错误状态；空输出是否算成功由任务定义，不能自动计为一次有效生成。`N=1` 时 TTFT 和请求延迟可定义，TPOT 未定义。\n6. 取消、超时和断开后，已经交付的内容可以计算部分 TTFT 或部分间隔，但没有完整请求完成指标。迟到结果必须携带原尝试代次；不能写入新请求的槽位。\n\n若客户端只能从 chunk 观察内容，需把 chunk 作为观测单位，并额外记录 `m_k`、累计 token 范围和内容身份。这样可以恢复首内容时间、输出 token 总量和 chunk 级间隔，但不能单独恢复 chunk 内每个 token 的精确时间。\n\n## 指标计算算法与状态推进\n\n下面的算法把事件校验、尝试过滤、chunk 合并和指标定义连成一条可复现路径。输入是同一逻辑请求的候选事件和策略；输出是记录、未定义原因和可用于聚合的间隔。\n\n```pseudocode\n算法 BuildRequestMetrics(events, r, policy)\n输入：请求 r 的候选事件；policy 指定时间域、内容事件类型、尝试选择与是否要求精确 token 时间\n输出：REQUEST_RECORD；或拒绝原因\n\n检查 r、时间单位和 policy；建立 seen_event_ids\n选择本次尝试 g；属于其他 g 的事件只保留在诊断集合，不进入 r 的状态\n初始化 status=RECEIVED、send=空、first_content=空、last_content=空、chunks=空\nfor 每个同 g 且未重复的事件 e，按时间和稳定事件优先级处理：\n    若 e 的时间为负或不可比较：拒绝\n    按 e.type 推进状态：\n        SEND：只允许一次；记录 t0；状态仍为 RECEIVED\n        ADMIT：只允许在首次内容前；记录准入结果\n        START：只允许在 ADMIT 后；记录 tX\n        MODEL_TOKEN：只记录模型侧时间，不作为用户内容\n        CONTENT：要求 status 未终止；要求 token_count 为正整数\n                 要求 token_start 等于已收 token 数，或可按 chunk 顺序恢复连续范围\n                 记录 chunk 时间、token 数、可选逐 token 时间；更新 last_content\n                 若这是首个有效内容，记录 first_content；状态转为 STREAMING\n        FINAL：只允许一次；要求不早于最后内容；记录 tF；状态转为 COMPLETED\n        CANCEL/TIMEOUT/ERROR：只允许在 FINAL 前进入对应终止状态；记录原因\n        其他空角色、心跳、usage：不改写内容状态\n    若事件导致已终止状态出现新内容或第二个 FINAL：拒绝或标为身份冲突\n\n校验 chunks：累计 token 连续、时间非递减；若存在逐 token 时间，数量匹配且非递减\nN=已收 token 总数\nif N=0：TTFT=未定义；reason=no_content\nelif 首个有效内容不存在：TTFT=未定义；reason=no_content_event\nelse：TTFT=first_content-send\n\n若全部 chunk 有逐 token 时间：exact_times=按 chunk 顺序展开\n否则若全部 chunk 的 token 数都是 1：exact_times=各 chunk 时间\n否则：exact_times=不可用；exact_TPOT=未定义；可另报 chunk 级估计\nif N>1 且 exact_times 可用：\n    exact_TPOT=(exact_times[N-1]-exact_times[0])/(N-1)\n    exact_ITL=相邻 exact_times 的差\nelse if N=1：exact_TPOT=未定义；reason=no_token_interval\nelse if exact_times 不可用：exact_TPOT=未定义；reason=chunk_only_multi_token\n\n请求完成延迟=最后一个有效终态时间-send；若没有终态则标为未完成\n返回记录；未定义原因必须随记录保存，不能在聚合时静默当作零\n```\n\n状态推进的关键不是字段齐全，而是拒绝不可能的组合：同一内容范围出现两次、最后内容晚于最终响应、旧尝试事件混入新尝试、`N=1` 却产生 TPOT、只有多 token chunk 却声称精确逐 token 间隔，都应进入诊断而不是产生看似正常的数值。\n\n聚合和窗口账务也不能只取成功样本。下面的参考过程先建立到达队列，再统计完成、拒绝、未完成和联合合格结果；每请求平均与合并间隔分开计算。\n\n```pseudocode\n算法 AggregateAndWindow(records, policy)\n输入：已按请求身份去重的 REQUEST_RECORD；观察到达窗 [W0,W1)；排空截止 T_end；分位数定义\n输出：每请求指标、宏平均、合并间隔、窗口计数、goodput 与未定义覆盖\n\n检查 W0<W1、T_end>=W0；建立 seen_request_ids\ncohort=空\nfor record in records：\n    若 record.id 重复：拒绝\n    若 W0<=record.offered<W1：把 record 加入 cohort\n\noffered=cohort 的数量\nadmitted=cohort 中已准入的数量\nrejected=cohort 中未准入的数量\ncompleted=已准入且终态时间<=T_end 的数量\ngood=已准入、终态时间<=T_end、success 与 quality 同时为真的数量\nincomplete=已准入但无终态或终态晚于 T_end 的数量\n\n对 cohort 中每个 record：\n    若 record.TPOT 可用：加入 macro_values\n    若 record.ITL 是精确 token 间隔：把全部间隔加入 pooled_values\n    若 record.ITL 不可用但存在 chunk 级估计：加入 chunk_values，并保留其不是精确间隔的标记\n\nmacro_mean = macro_values 的算术平均；同时报告可用请求数和总请求数\npooled_mean = pooled_values 的算术平均；同时报告间隔数和是否只覆盖部分请求\n若 pooled_mean 可用：ratio_of_sums 的倒数关系只在同一组精确间隔上有意义；不能把 macro_mean 的倒数当作同一吞吐\nquantile(p, population) 必须声明总体和分位数定义；例如 nearest-rank：排序后取第 ceil(p*m) 个值\nwindow_goodput = good / (T_end-W0)，前提是 T_end>W0；若分母不同则另命名\nwindow_offered_rate = offered / (W1-W0)\nsuccess_over_offered = good / offered，前提是 offered>0\n返回所有计数、覆盖和未定义原因；任何空总体都返回未定义，不返回零\n```\n\n## 聚合、窗口与未完成样本\n\n设第 `r` 个请求有 `N_r` 个输出 token，且精确时间可用，则每请求平均为 `m_r=(t_(r,N_r-1)-t_(r,1))/(N_r-1)`。宏平均给每个可用请求相同权重：`M_macro=(1/R')Σm_r`，其中 `R'` 是有定义的请求数。合并间隔平均则按间隔数加权：`M_pooled=Σ(N_r-1)m_r/Σ(N_r-1)`，它让长输出贡献更多间隔。两者的差异不是测量误差，而是聚合对象不同。\n\n设定三个请求：第一个 2 token、首末间隔 10 ms；第二个 11 token、首末间隔 100 ms；第三个 2 token、首末间隔 30 ms。每请求平均分别是 10、10、30 ms，宏平均约为 16.67 ms；合并 12 个间隔后总间隔时间为 140 ms，合并平均约为 11.67 ms。若只报告一个数，必须说明是每请求等权还是间隔加权。\n\n分位数同样要说明总体。对有序值 `x_(1)..x_(m)`，nearest-rank 的 `p` 分位数可取 `x_(ceil(pm))`；另一种插值定义会给出不同数值。每请求 TPOT 的 p99、所有 token 间隔的全局 p99、每请求 p99 再平均，三者不能互相替代。空总体必须报未定义；`p99` 只由少量尾部样本支持时，还应报告样本量和不确定性。\n\n窗口账务常见两种口径。固定到达窗口 `[W0,W1)` 后继续排空到 `T_end`，分母可写为观察时间或到达窗长度，但必须明确；固定完成窗口只统计在窗口内完成的请求，则早先到达的请求也可能进入分母。两种口径不能共用同一个“每秒”标签。\n\n设定 10 s 到达窗口内发出 100 个请求，10 个被拒绝，90 个获接收，其中 80 个在窗口内完成，72 个同时满足质量与全部时延条件。按该到达窗和联合合格定义，goodput 为 `72/10=7.2` 个合格请求每秒，合格请求占全部发出请求的比例为 72%，占获接收请求的比例为 80%。只保留 80 个完成请求会改变分母；把拒绝和未完成请求删掉会让系统看起来更好，却没有解释 offered workload。\n\n联合 SLO 也要直接统计交集。TTFT 合格率 95% 与 ITL 合格率 95% 不保证同一批请求中有 95% 同时合格；两个边缘比例不能替代联合条件。质量不合格、输出被截短、分辨率降低或音频时长缩短，都可能让延迟和吞吐变好，但任务已经改变。\n\n## 条件化成本\n\n指标系统的成本至少分为六类。\n\n- 计算成本：逐事件校验是 `O(E)`；对无序事件排序是 `O(E log E)`；计算每请求平均是 `O(N)`；对 `M` 个间隔或请求求精确分位数通常要排序，成本 `O(M log M)`。直方图或草图可降低内存和排序成本，但引入分桶误差和合并规则。\n- 访存与驻留成本：保存逐 token 时间需要 `O(N)` 个时间戳和身份；只保存 chunk 需要 `O(C)`。设定 10,000 个请求、每个 100 个 token，若每个精确时间戳用 8 字节原始整数，约 8,000,000 字节，即约 7.63 MiB，尚未计对象头和索引；若每请求平均 20 个 chunk，chunk 时间约 1.6 MB 原始数据。保留原始 trace、输出内容和请求身份还会增加驻留。\n- 通信成本：客户端指标、服务端指标和设备 trace 可能经不同通道汇总；序列化、批量上报和时钟校准都消耗网络或主机时间。跨机报告还需保存偏移界限，不能用一次往返时间的一半替代单向延迟。\n- 准备成本：固定 tokenizer、模板、内容过滤规则、事件 schema、请求身份映射和分位数定义都需要准备；准备版本改变可能改变 token 计数或内容边界。\n- 同步成本：在内容 flush、chunk 发送、trace 采样和窗口关闭处加入同步，会改变队列和重叠。用于诊断的详细采集应与其造成的扰动一起报告；正常运行指标不能把 profiler 的同步开销当成服务成本。\n- 关键路径成本：指标聚合若在响应路径上执行，可能推迟 chunk 发送并恶化 ITL；离线聚合不改变用户路径，但增加保留与读取成本。事件采样降低开销，却可能漏掉尾部事件和取消边界。\n\n这些成本不能只相加成一条时间。事件校验、内容发送和分位数计算可以重叠；共享存储、网络和 CPU 又会互相竞争。报告至少应说明观察到的 `E`、`C`、`N`、保留窗口和聚合方法，使读者能判断成本模型是否适用于当前负载。\n\n## 条件变化后的保留、调整与放弃\n\n| 条件变化 | 应保留 | 应调整 | 应考虑放弃 |\n|---|---|---|---|\n| chunk 变大或服务端合并多个 token | 首个有效内容和协议完成事件的定义 | 把精确 ITL 改为 token 级采集；否则明确报 chunk 级估计 | 单 chunk 多 token 时放弃精确 TPOT，不能报零 |\n| 输出长度分布改变 | 每请求与合并间隔两种口径 |
