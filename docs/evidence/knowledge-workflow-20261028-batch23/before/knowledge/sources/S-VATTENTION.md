## 来源支持的机制与定义

§5 将虚拟地址预留与物理页映射分开。每个 worker 为其负责的各层分别建立 K/V 虚拟张量，请求占其中不重叠的子区间；虚拟范围按支持的最大批量和上下文预留，物理内存按需求分配和映射。因此原有连续 kernel 仍沿连续虚拟地址取数，不能把预留虚拟范围大小当作已占物理显存。

§5.2–5.3 的迭代流程是：确定当前请求及其需要的 KV 范围，确保当前范围已有可访问的物理 backing，再进入模型计算；结束的请求允许释放或保留 backing。底层映射/访问权限调用要求粒度和对齐，不能仅更新长度就访问尚未映射的尾部。各层的 K 与 V 分别取整，碎片不能只按全模型总字节取整一次。

§6.1 为减小物理粒度修改了开放部分的驱动，增加 64/128/256 KB 分配选择；论文所述既有 CUDA 接口的粒度是其版本背景。小粒度支持依赖该扩展，不能推断任意 CUDA 环境都有同样能力。§6.2 将未来页映射与当前计算重叠，并通过延迟回收和提前准备重用 backing；每轮仍检查本轮所需映射是否真实完成，来不及时同步完成。隐藏映射延迟没有消除映射工作、后台线程或提前保留的容量。

该设计避免应用 token 块表，不等于消除 GPU 虚拟地址翻译、TLB 或底层页表。论文也没有由连续虚拟地址自动证明跨请求前缀共享、无复制迁移或任意 graph metadata 生命周期安全。

## InfraAgents 如何据此推导

将连续地址、应用块池和映射粒度作为分配器的不同方案，分析尾部开销、生命周期与调度预算。完整推导见 [分页 KV](../algorithms/paged-kv-capacity.md)：按每个区域的粒度计算物理容量，分别测 kernel 消费、主机准备和映射等待；背景映射能否隐藏取决于下一次需求前的可用时间，不能从“异步调用”直接推断零关键路径成本。

## 适用边界

v1 中更小粒度的实现依赖扩展；不能当作任意设备的标准 CUDA 接口能力，也不能推断已具备 SSD 卸载或前缀共享。 来源版本资格不证明模型训练集包含该资料；seed 不构成本项目实测有效性的声明。


## 整篇复核后的使用限制

较小物理页在此版本依赖扩展；按需映射仍需在每轮消费前确认完成，预映射和延迟回收只是隐藏开销的策略。实验中的旧 kernel 与框架对比不证明任何当前后端排序，也不证明所有 workload 的碎片都可忽略。
