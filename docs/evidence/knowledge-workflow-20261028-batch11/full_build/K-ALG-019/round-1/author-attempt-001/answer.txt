{"chapter":"# K-ALG-019：权重与专家卸载：重用、路由与在途版本\n\n权重卸载不是“把放不下的参数搬到更慢的存储”这一动作本身，而是在有限容量下重新安排参数读取、计算位置与结果提交。稠密层的读取顺序大体固定，MoE 的专家由输入路由决定，激活稀疏模型又依赖输入相关的神经元激活；三者共享“按需取数”的表象，却没有同一个工作集合、合法性条件或收益公式。\n\n## 问题、对象与合法状态\n\n设模型版本为 `m`，一组参数对象按 `(m, layer, expert, representation, shard)` 标识。本层输入为 `X`，输出为 `Y`。对稠密层，权重 `W_m` 覆盖全部必需输出；对 MoE 层，router 对每个 token 产生选中集合 `S_τ`、门控权重 `g_{τ,e}` 和目的副本 `π_G(τ,e)`，每个选中专家贡献一次：\n\n`z_τ = Σ_{e∈S_τ} g_{τ,e} E_e(x_τ),  y_τ = u_τ + z_τ`，\n\n其中 `u_τ` 是模型规定的 residual 或宿主路径，不应被省略后再与完整输出比较。`G=(attempt, layer, routing_generation, placement_generation)` 冻结一次层调用的路由版本与放置版本；`routing_generation` 绑定 router 参数、选择规则、平局规则和本轮选择快照，`placement_generation` 绑定专家副本目录、每个副本的权重版本和可执行布局。\n\n一个权重对象在某一时刻至少有如下与执行有关的描述：\n\n| 对象 | 必须记录的内容 | 不能由什么替代 |\n|---|---|---|\n| 版本身份 | `m`、层/专家、表示、分片、放置代次 | 文件名、路径或“已加载”标签 |\n| 有效范围 | 已完整可见的逻辑区间；不是已提交的读取字节数 | 读取请求长度、DMA 入队成功 |\n| 驻留位置 | 设备或主机上的真实副本及尺寸、对齐和布局 | 逻辑张量大小 |\n| 访问责任 | 哪些 in-flight 计算、传输或消费者仍会读取该对象 | 请求完成、host 调用返回 |\n| 提交状态 | 该层是否已收齐全部必需贡献并可按本轮快照发布 | 单个专家完成或 GPU 利用率 |\n\n状态机的核心顺序是：`未驻留 → 已预留 → 传输中 → 完整且可见 → 可执行 → 计算中 → 结果已消费 → 可回收`。失败路径为 `失败排空 → 隔离/释放`，迟到的旧代完成事件不能推动新代状态。一个专家只有在完整范围、正确版本和正确布局均可见后才能执行；部分加载可以发布已经完整且相互独立的专家，但整层输出只有在所有必需贡献都到达后才能提交。\n\n容量账按同一时刻同时存活的唯一存储计：设备权重、主机权重、在途 staging、转换临时区、每请求激活/KV、接收缓冲、返回部分和、元数据和池的保留容量。共享只读页只计一次；预留目的空间与仍在途的源副本不能因为“尚未使用”而重复忽略；旧版本在最后一个读者结束前也不能释放。\n\n## 稠密层：层间重用与成本下界\n\n稠密 forward 必须执行规定的全部层。设一层（或所有必须在该轮加载的权重）字节数为 `W_o`，每个生成迭代至少需要一次可用的权重读取，链路有效带宽为 `B`，一次推进 `n` 个独立请求，则仅权重传输的每轮下界为\n\n`T_load ≥ W_o / B`，每个输出 token 的摊销下界为 `W_o / (B n)`。\n\n第二个量是吞吐摊销，不是每请求的 ITL。即使 `n` 很大，单个请求仍需等待该轮完整计算、同步和输出，`W_o/(Bn)` 不能替代“从提交到可见 token”的延迟。实际每轮还有 KV、激活、host 准备、布局转换、量化解包和 kernel 启动；下述账本只有各项自身采用同一候选、同一输入和同一时间窗时才可相加。\n\n层间重用的候选是把当前层权重留在设备，轮流处理多个微批后再换下一层，以摊薄 `W_o`。对于 `n` 个微批，粗串行模型是\n\n`T_round ≈ max(W_o/B, T_comp) + T_sync + T_other`，\n\n其中 `max` 只在存在可重叠通信且确有独立工作覆盖时成立。若权重传输、专家计算和结果提交互相依赖，则不能把全部未重叠项相加后又称它们已经隐藏。\n\n```pseudocode\n算法 DENSE_LAYER_REUSE\n输入：请求集合 R；每层权重槽；设备容量；链路预算；本轮目标\n输出：本轮输出，或容量/失败原因\n\n1 固定模型版本、层顺序和每层完整的逻辑权重范围\n2 按容量与 deadline 选 n 个可一起推进的请求\n3 对每一层 l：\n     a 选择驻留权重或准备从主机/磁盘读取；先预留完整目的槽\n     b 只把尚未完整的层标为 LOADING；记录源版本和目的槽 lease\n     c 对 n 个微批执行依赖允许的独立计算\n     d 完成可见后消费权重；仍在读取的旧读者保护旧槽\n     e 所有消费者结束后才允许下一层覆盖该槽\n4 每层和每个请求均按提交边界发布；输出不能按完成顺序错配\n5 返回结果；失败时停止新接纳，排空已提交访问后回收\n```\n\n这里至少有三个容易混淆的完成事件：主机读取调用返回、目的缓冲对设备可见、最后一个消费者结束。前者不证明数据传输成功，中者不证明旧槽可以复用，后者也不证明业务输出已提交。\n\n## MoE：路由并集与读取稀疏性\n\n一个 token 只用少数专家，不表示一个 batch 只访问少数专家。设 `E` 个专家，每 token 选择 `k` 个不同专家；在请求彼此独立、每 token 均匀选择且不含热点的设定下，单个专家未被选中的概率是 `(1−k/E)^B`，因此 `B` 个 token 触及的专家数期望为\n\n`E_touch(B) = E [1 − (1 − k/E)^B]`。\n\n这是均匀独立路由的设定，不是实测热点模型。`E=64,k=2` 时，`B=1` 为 2，`B=16` 约为 25.5，`B=64` 约为 55.6；若每专家 128 MiB 且全冷，则 batch 扩大仍可能把权重读取推近全专家。若出现非均匀热点、连续 token 相关性或共享专家，必须改用相应分布；Mixtral 的论文实验甚至报告了较深层连续 token 选择同一专家的时间局部性，这既可能帮助缓存，也可能加重专家并行热点。\n\n缓存策略应以“下一次合法使用前能否获得完整版本”为目标，而不是以命中率为目标。候选至少包括：\n\n| 候选 | 优点 | 条件与新增成本 |\n|---|---|---|\n| 固定热门专家驻留 | 准备简单，热点稳定时命中高 | 热点漂移会持续缺失；副本占容量 |\n| 按近期路由更新 | 适应局部变化 | 迁移和旧版本排空有滞后；抖动会浪费带宽 |\n| 需求加载 | 不预取无用专家 | 当前 token 等待 I/O；可能阻塞整层 |\n| 预测预取 | 可能隐藏延迟 | 错预取占带宽与容量，仍需为真命中准备合法路径 |\n\n`E_touch` 只说明逻辑上可能触及多少专家，不能直接当作 HBM 事务。实际读取还要按 `(rank, expert, version)` 统计，并计入 tile 重读、cache 命中、复制副本及分组 GEMM 的 padding。\n\n## 激活稀疏：预测、近似与函数差异\n\n激活稀疏讨论的是输入相关的神经元或激活值是否为零。PowerInfer 的动机是热点神经元在输入间反复激活，冷神经元由 CPU 直接计算，以减少把冷权重搬到 GPU 的流量；其预测器来自离线激活统计，在线执行仍可能出现预测误差。预测为不活跃而实际有贡献，会改变函数；预测为活跃但实际为零，只是多做了工作。\n\n因此必须分开三个命题：\n\n1. 已知为零的精确跳过：若模型或算子契约能证明该贡献恒为零，可以合法跳过；\n2. 预测性跳过：用输入相关预测器替代真实贡献，属于允许近似的算法，必须报告质量、分布外输入和反例；\n3. 标准 MoE 的确定路由：按 router 选中的 `S_τ` 与门控权重执行，不能把“低概率专家”任意当作零。\n\n链路传输的冷权重 `W_c` 与 CPU 直接计算的代价也不同。前者约为 `W_c/B + T_GPU`，后者约为 `A/B + T_CPU + T_sync/combine`，其中 `A` 是输入、结果和必要同步的实际交换量。若 CPU 计算所需激活与结果远小于权重，或 CPU 已经在计算其他部分，后者可能更优；但 CPU 算力、主存争用、batch 增大和结果合并都可能使选择反转。\n\n## 卸载执行与版本所有权\n\n下面的伪代码把路由、权重准备、部分专家计算和最终提交串起来。它故意不规定某个具体 DMA 引擎、stream 或库接口，只要求每种资源都有明确的完成事件。\n\n```pseudocode\n算法 OFFLOAD_MOE_LAYER\n输入：本轮 token X、固定 router 契约、权重目录、容量预算\n输出：完整层输出，或带原因的失败/隔离结果\n\n1 冻结 G 和每个 token 的 S_τ、g_τ，以及每个 e 的权重版本 v_e\n2 对每个选中项建立 logical item=(G,τ,e,目的 rank, v_e)\n   记录 origin、token 身份、专家身份和门控值；相同 token 不能按本地序号去重\n3 按目的端和专家 e 计数，计算每个桶的输入范围\n   为接收 hidden、描述符、专家中间量、返回部分和和输出预留容量\n   若容量不足：按合法计划分块或失败，不得静默删除 item\n4 对每个需要的 (e,v_e) 检查完整覆盖：\n   若完整驻留：标记 READY\n   否则预留完整目的槽，发出可验证的读取；标为 LOADING\n   任何部分读取、旧版本或错误布局都不得标记 READY\n5 当某个专家完整且可见后，将它的 READY 版本发布给本层\n   对每个 item：\n       若在 GPU 上，执行对应专家；若在 CPU 上，执行同一函数的 CPU 路径\n       记录完成身份、覆盖范围和权重版本\n6 目的端对每个 token 可合并多个专家贡献；合并记录必须保留\n   covered 集合与每个贡献的 gating，不能把不同 token 的本地 t 合并\n7 origin 建立 Expected=S_τ，Seen=∅，输出累加器=0\n   对每个返回：\n       验证 G、token、e、v_e 和 covered 与本轮一致\n       要求 covered 与 Seen 不交、贡献恰好一次\n       Seen ← Seen ∪ covered；累加该贡献\n8 仅当 Seen=S_τ 时提交该 token；缺失、重复、版本错误或非有限门控均失败\n9 所有 item 的物理访问结束后，才释放旧权重槽和返回缓冲\n   旧版本在迟到读者结束前仍被保护；新版本不能覆盖旧版本\n```\n\n正确性不变量是：每个逻辑 item 恰好贡献一次；每个贡献使用本轮冻结的版本和门控；每个 token 的合并能恢复到 origin 身份；任何失败都不产生“缺项的完整输出”；资源释放必须等最后一个读者。\n\n## 成本：准备、传输、计算、同步与驻留\n\n设 hidden 维为 `d`、专家中间维为 `f`、每 token 选 `k` 个专家。每个门控三矩阵专家的权重主项为 `W_e ≈ 3 d f b_w` 字节，单 item 算术主项为 `6 d f` FLOPs；`B` 个 token 有 `N_items=Bk` 个 routed item（固定 `k` 且无 shared 专家时）。一个不含通信的桶，其算术强度约为 `2 n_e / b_w` FLOP/byte，其中 `n_e` 是该桶实际行数；`n_e` 很小或很多专家都只收到一行时，专家 GEMM 更像低复用 GEMV，权重读取和启动开销可能成为主项。\n\n跨设备或跨 rank 的传输下界可按 source 不等于 destination 的端点发送量计：设 `N_remote` 为远端 item 数，`D_remote` 为远端 `(token,destination)` 对数，每行 hidden 为 `d b_h` 字节，返回向量为 `d b_y` 字节，则粗略端点主项为：\n\n| 组织 | dispatch | return |\n|---|---:|---:|\n| 逐 item 往返 | `N_remote d b_h` | `N_remote d b_y` |\n| hidden 去重、逐 item 返回 | `D_remote d b_h` | `N_remote d b_y` |\n| 逐 item 发送、目的端预合并 | `N_remote d b_h` | `D_remote d b_y` |\n| 去重并预合并 | `D_remote d b_h` | `D_remote d b_y` |\n\n本地 item 不进入这个网络账；若把全本地项的输入算进“dispatch 流量”，会把内存重排误当成网络发送。返回按 chunk 分多次时，应改用实际返回条数。上述公式也不计协议头、重传、padding、计数消息、下一层布局转换和经过入口的转发边。\n\n驻留账在同一时刻取并集：设备权重、主机权重、staging/转换缓冲、每个 rank 的接收 hidden、描述符号、专家中间激活、返回 partial、完成集合、分组 GEMM workspace 和未释放的旧版本。未融合的两层上投影可能产生约 `2Σ_{r,e} n_{r,e} f` 个中间元素；融合或分块缩短其生存期，但不改变“在峰值时刻没人读取才能释放”的规则。\n\n准备成本包括：router 计算、计数与前缀和、索引/描述符、布局重排、核选择、量化解包和预热。计数分桶可接近 `O(N_items+E)`，比较排序可能达到 `O(N_items log N_items)`。同步成本包括等待专家权重、计数交换、跨 rank 返回、共同提交和失败排空；可重叠的通信只在有独立工作覆盖等待时降低关键路径。\n\n## 条件变化后的保留与放弃\n\n| 条件变化 | 保留的依赖 | 应重算或放弃的选择 |\n|---|---|---|\n| batch 增大 | 每 token 仍选相同路由，贡献恰好一次 | 专家并集、接收缓冲、KV、热点和分组 GEMM 行槽；权重读取可能先摊薄后转而被专家并集压回 |\n| 热点集中或漂移 | 固定专家函数和版本身份 | 驻留集合、副本与预取；漂移时按迁移成本、旧版本排空和命中滞后重新比较 |\n| hidden 或 `d/f` 改变 | 逻辑专家定义和门控不变 | 权重字节、链路 payload、算术强度和 staging 容量 |\n| 在链路与 GPU 之间选择 | 函数和版本契约不变 | 搬权重、搬输入/结果、CPU 计算；batch 小、CPU 算力足够时计算放置可能更优 |\n| 低精度或打包改变 | 逻辑模型和参考质量不变 | 解包、尺度和布局转换成本；若表示近似改变函数，需重新做质量验证 |\n| 取消或路由重算 | 已提交的访问仍需排空 | 未提交 item 可以丢弃；迟到结果不能解除新代资源责任 |\n| 全部权重可驻留 GPU | 计算图和路由规则不变 | 卸载项的收益消失；继续人为搬运会把准备成本加回来 |\n\n一个常见反例是“batch 越大，权重读取越省”。均匀独立路由下，`E_touch(B)` 随 `B` 增大而增大，且每 token 还需要选择、通信和 combine；只有在增加的重用覆盖新增的专家并集时，摊销才成立。\n\n另一个反例是“专家被加载了一部分也可以先算”。一个专家若按行/列分片或按低位块读取，只有完整逻辑范围与匹配 scale 才构成可执行版本；拿部分字节执行会产生看似有输出但语义错误的专家贡献。\n\n## 诊断、反例与区分实验\n\n| 观察 | 竞争解释 | 区分实验 | 反证后的修正 |\n|---|---|---|---|\n| 输出缺失某个专家 | 路由漏项、加载未完成、返回身份错配 | 固定路由，逐项记录 Expected、READY、Seen 和 covered；只删一个远端返回 | 覆盖完整才有资格提交；不能以 GPU 利用率代替逐项账 |\n| 专家加载完成后仍有旧 token 污染 | 旧版本被新版本覆盖，或槽按物理地址复用 | 新旧版本交错，延迟旧读者，让迟到完成事件到达 | 旧代完成不能解除新代 lease |\n| 固定热点命中率很高但请求变慢 | 缓存命中没有覆盖关键路径、入口拥塞或专家桶过小 | 固定路由，仅改变副本布局，记录每桶行数、dispatch、专家计算和返回 | 命中率不是收益；瓶颈可能在通信、启动或 combine |\n| 大 batch 后每 token 权重读取下降 |
