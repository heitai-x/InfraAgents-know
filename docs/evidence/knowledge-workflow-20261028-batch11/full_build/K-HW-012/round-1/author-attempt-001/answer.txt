{"chapter":"# K-HW-012：存储 I/O：请求粒度、队列和加载流水\n\nSSD 的标称带宽只是某次访问模式下的能力；推理实际获得的是经过文件布局、页缓存、块层排队、设备传输、主存 staging、H2D 和消费者同步之后的供给速度。本章把一次加载拆成对象身份、文件范围、请求排队、完成匹配、布局转换、设备传送和缓冲释放，说明哪些字节必须到齐、哪个完成事件能解除何种责任，以及条件变化后哪些阶段会反转。\n\n## 问题、对象与完成边界\n\n设一个加载对象为 O=(a,t,R,g,z)。a 是固定制品版本；t 是张量或参数逻辑名及其源 shape、dtype、轴序和目标布局；R 是一组带文件身份的源范围；g 是本次加载尝试的代次；z 是目标物理槽的 lease 代次。一次文件请求可写成 X=(O,f,o,l,dest,g,z)，其中 f 绑定不可变文件内容版本，[o,o+l) 是该文件中的字节范围，dest 是本次尝试中的目的缓冲。路径字符串相同不证明文件内容版本相同；旧完成事件也不能因为地址相同而解除新 lease 的责任。\n\n合法性至少包括：源范围在固定 a 和 f 内且运算不溢出；目标范围容量、对齐和表示相容；同一槽没有被旧代次消费者继续读取；全部必需范围完成之后才发布对象；发生错误或短读时，只把已完成部分记为部分完成，不用旧缓冲填充缺失部分。缓存命中、mmap 成功、read 调用返回、H2D 入队、设备 kernel 完成和最后消费者释放是不同事件。\n\n| 状态 | 已经成立 | 尚不能推断 |\n|---|---|---|\n| RESERVED | 目的槽和转换工作区已为本代预留 | 文件字节已到 |\n| SUBMITTED | 请求已进入文件或块层路径 | 设备已服务或字节已完整 |\n| PARTIAL | 某些范围已有成功字节 | 整个对象可发布 |\n| HOST_READY | 必需源范围都到达主机缓冲且错误状态已知 | 布局转换和 H2D 已完成 |\n| CONVERTED | 目标表示已形成 | 设备 DMA 已完成且消费者可见 |\n| DEVICE_READY | H2D 完成且消费依赖已建立 | kernel 已读完并允许复用 |\n| CONSUMED | 所有声明的消费者最后访问结束 | 写入已持久化 |\n| FAILED | 失败范围和仍存活责任已知 | 其他无关对象必然失败 |\n\n## 文件布局、逻辑范围与可执行目标\n\n文件范围不是张量布局。权重可能按 shard、tensor 或目标设备分片保存，执行器却按层、专家或 tile 消费；一个逻辑读取范围可能跨多个文件或物理 extent，非连续表示还可能产生多个小读取和后续重排。设源 shape 为 s、轴排列为 p、目标 shape 为 u_k=s_{p_k}。行主序下源线性下标为 L_s(c)=Σ_i c_i∏_{j>i}s_j，目标线性下标为 L_u(q)=Σ_i q_i∏_{j>i}u_j；源段地址可写成 (a,f,o_t+e_sL_s(c))，目标地址为 base_t+e_dL_u(q)。这要求源数据、轴序、dtype 和目标基址都属于同一版本；坐标式正确也不能推出量化分组、字节序或 QKV 分段正确。\n\n把相邻请求合并成大块可以摊薄提交、元数据和队列开销，但会过读不需要的数据、增加暂存和首块等待。一个逻辑读取计划应区分有效字节、实际文件读取字节、块层物理请求字节、主机到设备字节和最终被消费者使用的字节。连续大权重可用固定块流水；随机专家块可能必须按实际路由读取，错误预取会占用带宽和容量但不改变模型函数；长 KV 范围还要与层计算和页缓存复用一起计算。\n\nServerlessLLM §4.1 报告的加载优化格式把每个 GPU 的目标张量分组到独立文件，索引记录 tensor.name、GPU id、offset 和 size，运行时用 base+offset 恢复张量视图，并把张量对齐到内存字；§4.2 用固定大小内存块池、直接文件访问、锁页内存和多阶段任务队列减少重复复制与碎片。这些是论文所述系统设计，不是所有文件格式、文件系统或设备的普遍保证。\n\n## 缓存、映射与直接 I/O 的合法性\n\n缓冲读取利用页缓存。页缓存命中可以减少存储事务，但应用仍然支付复制、检查和暂存；写入页缓存的返回也不等于脏页已经写回存储。mmap 让文件范围进入虚拟地址空间，但映射成功既不代表内容已驻留，也不代表首次访问不会缺页等待。多个进程可能共享只读文件页，而转换后的私有布局仍可能各持一份副本。\n\n直接 I/O 绕过页缓存，让应用管理块池、并发和复用，但有对齐、文件系统和具体路径约束。Linux 6.12 的 iomap 文档还指出：直接读和直接写可能在发起 I/O 前刷新相应页缓存，直接写前后可能使页缓存失效；请求可能短读、部分完成，某些路径可回退到缓冲 I/O，异步请求可能返回已排队状态，调用者要用已积累的进度继续。直接 I/O 不自动等于异步，不自动等于零复制，也不自动等于存储设备直接把数据送入 GPU。\n\n判断缓存还是直接 I/O，应固定字节和对象，分别观察冷缓存、热缓存、读取 CPU 时间、实际存储字节、主存峰值和后续消费者等待。热页缓存读速不能被记成 SSD 带宽；直接 I/O 也不保证比 mmap 快，因为它可能增加页缓存刷新、对齐检查、锁页或应用内部复制。\n\n## 请求粒度、队列深度与吞吐\n\n设每次请求大小为 b 字节，平均服务时间为 S(b)，则单服务路径的请求率为 1/S(b)，数据率为 b/S(b)。一个常用分解是 S(b)=S0+b/B_eff+W，其中 S0 包含提交、寻址和完成处理，B_eff 是当前访问模式下的可持续传输率，W 是排队等待。b 很小时可能先达到 IOPS 或 CPU 提交上限，b 很大时则可能受设备、链路、主存或 PCIe 上游带宽限制；超过对齐或消费者粒度的大块还会增加过读和尾块浪费。\n\n若目标数据率为 X，请求大小为 b，则请求到达率为 λ=X/b。由 Little 关系，平均在途请求数至少为 N≈λE[S(b)]；整数槽位取上界。设目标 4 GiB/s、平均完成时间 1 ms、请求大小 1 MiB，则 λ=4 GiB/s÷1 MiB=4096 次/s，4096×0.001=4.096，至少需要 5 个在途槽。4 个槽在此均值模型下只能提供 4×1 MiB÷0.001 s=3.90625 GiB/s，低于目标。这是带宽时延积的起点，不是实际设备曲线。\n\n队列稳定性还需要 ρ=λE[S]<1。对到达近似泊松、服务独立同分布的 M/G/1 FIFO 模型，W_q=λE[S^2]/(2(1−ρ))；它说明仅用平均服务时间不能解释尾延迟，服务时间方差和突发到达会抬高峰值。多个模型冷启动、权重预取和 KV 读取还共享同一 SSD、主存和 PCIe 上游，优先级应连接消费 deadline、可避免的重算收益和公平性；盲目增加深度可能只增加排队、取消排空和驻留。\n\n## 加载流水：算法、状态与缓冲复用\n\n把一块数据的路径写成 read→convert→H2D→consume。convert 可能在 CPU 上完成，也可能在设备上以 kernel 完成；若在设备上完成，就必须先完成 H2D，且不能在转换结束前把目标当作可执行权重。每个阶段都需要独立的资源、缓冲和完成关系。下面给出加载对象从预留到回收的抽象推进算法；它不指定具体文件、CUDA 或驱动 API。\n\n```pseudocode\n算法 LoadBlocks(plan, events, pools)\n输入：固定制品版本 a；按消费顺序排列的块 B_0...B_{N-1}，每块含源段、目标范围、代次、消费者集合和 deadline；各池容量与释放条件；完成事件队列\n输出：每块状态、失败范围、仍需保护的槽和未完成责任\n\n初始化：对象状态为空；每个池槽记录 lease、拥有者和最后消费者；队列按 deadline 与公平约束组织\n若 plan 为空：返回成功、无在途责任\nfor i=0..N-1:\n    校验源范围属于 a、目标表示相容，并等待 B_i 所需槽和工作区\n    预留主机槽、设备槽和转换区，记录 lease_i 与本代范围\n    提交 B_i 的读取请求；状态 SUBMITTED\n    若提交失败：释放尚未发布的预留，标记 FAILED_i，保留错误原因\nwhile 仍有在途读取、转换或 H2D:\n    取下一完成事件 e，按对象、文件、范围、尝试代次和 lease 匹配\n    若 e 属于旧代次或重复通知：只结算其资源，不推进当前对象\n    若读取只完成部分范围：把已完成前缀记入 PARTIAL，未完成范围继续在途\n    若读取失败：只把对应范围标为 FAILED，禁止发布整个对象\n    若全部必需源范围 HOST_READY：\n        执行布局转换；失败时保留部分输出和失败原因\n        状态 CONVERTED，提交 H2D，并登记主机源缓冲的最后读取者\n    若 H2D 完成且消费者依赖已建立：\n        状态 DEVICE_READY，向 B_i 的消费者发布同一版本内容\n        登记每个消费者的读取责任\n    若所有消费者最后访问结束：\n        状态 CONSUMED；归还设备槽、转换区和主机槽\n    若发生取消：停止提交新工作，但保留已发起 I/O、DMA 和 kernel 的排空责任\n若所有块 CONSUMED 且无在途责任：返回成功\n否则：返回未完成对象、失败范围、隔离槽和仍需保护的资源\n```\n\n正确性不变量是：主机源缓冲在 H2D 实际读取结束前不得复用；设备输入在 kernel 最后读取结束前不得复用；转换输出在消费者取得正确版本前不得发布；旧代次完成事件不得释放新 lease；部分范围齐全前不能把未写区域混入新张量；零字节块可以立即满足载荷条件，但仍要建立版本、索引和消费者关系。取消只禁止后续业务推进，不会自动撤销已提交的物理操作。\n\n若各阶段使用独立资源、缓冲足够且没有额外跨块依赖，第 i 块第 k 阶段的完成时间可递推为 F[i,k]=max(F[i−1,k],F[i,k−1])+t[i,k]，边界为零。对 N 个大小相同、阶段时间相同的块，T_0=0，T_N=Σ_k t_k+(N−1)max_k t_k；它不是各阶段工作量的简单相加。若转换和 H2D 共用主存控制器或 PCIe 上游，或 CPU 读取与转换共用串行 worker，就必须加入资源边，递推中的独立资源假设不再成立。\n\n固定周期 P、固定生存期 L_j 的缓冲池至少需要 n_j≥⌈L_j/P⌉ 个槽；它只是所述周期下的必要条件。设 L=9、P=4，则需要 3 个槽：块 0 在 0 开始并到 9 才释放，块 2 在 8 开始时若只有 2 个槽就会复用块 0 的槽，形成覆盖。实际长度不一、完成乱序或取消排空时，必须按真实完成事件复用，平均值不能保证安全。多个池要分别计算主机读缓冲、转换输入输出、设备输入和设备输出，池的 reserved 与池内 active 槽也不能重复相加。\n\n## 硬件映射：文件范围到设备消费\n\n一次标准加载至少经过以下路径。第一，按固定清单和索引定位 (a,f,o,l)，校验范围与目标布局，申请主机块。第二，文件路径可能由页缓存满足，也可能发起直接 I/O；页缓存命中只是减少存储事务，用户缓冲仍需复制或映射。第三，进入块层后，请求可先进入软件暂存队列，相邻 sector 的请求可以合并，I/O scheduler 可以重排以改善公平或性能；随后进入硬件派发队列，受设备队列深度限制，不能立即派发的请求留在临时 dispatch 列表。设备完成时用 tag 通知对应的块层请求；块层和设备协议不保证完成顺序，应用必须按对象、范围和代次匹配。\n\n第四，主机必需范围全部到达后，执行必要的解包、转置、校验或设备端转换。若转换在 CPU 上，会产生源和目的两份暂存；若转换在 GPU 上，则先完成 H2D，再由 kernel 读取源并写目标，转换 kernel 完成前不能发布目标。第五，H2D 的完成只表示复制对相应执行依赖可见；源缓冲要保护到 DMA 实际读完，设备输入要保护到 kernel 最后读取。第六，消费者完成后再回收槽，不能以主机 API 返回或入队成功代替最后访问。\n\n绕过主机 staging、让外部 DMA 引擎直接访问 GPU 内存是这条路径上的另一条设计轴。NVIDIA GPUDirect RDMA 文档把网络接口、视频采集设备和存储适配器列为第三方设备示例；它要求设备共享同一上游 PCIe root complex，要求 IOMMU 为 1:1 或 pass-through 等平台条件，并通过注册、BAR 映射和页表把 GPU 内存暴露给外部设备。注册和 pin 可能很贵，文档提到可达毫秒级，因此常用 lazy unpinning 和 registration cache；撤销映射的回调要等待未完成 DMA，并可能阻塞数毫秒，必须避免死锁。\n\n更关键的是内存序：固定文档 §2.7 说明，只有 CPU 发起的 CUDA 同步或工作提交 API 能为 GPU 观察到 GPUDirect 操作提供顺序。外部 DMA 写入即使已经能被主机读回，若依赖它的 GPU kernel 在 DMA 对启动线程完成前已经开始，kernel 仍可能读到旧值、部分值或乱序值；此时并发 kernel 与 RDMA 写构成数据竞争。要让 kernel 看到新数据，必须让 DMA 写相对于发起依赖 kernel 的 CPU 线程完成。直通路径去掉一次主机中转和相应主存带宽占用，但不改变 SSD IOPS、请求粒度、排队、校验和格式转换；本库没有归档该路径的吞吐实测，不能把它写成无条件更快。\n\n写入还要区分应用缓冲可复用、数据已到存储栈、数据已满足持久性。缓冲写返回可能只落入页缓存；writeback 失败也可能在之后才通过同步接口报告。可重建的 KV 缓存与不可丢失的制品、提交记录应有不同的持久性合同；声称跨进程或机器故障恢复时，必须说明发布点、校验点、旧版本读者和持久化边界。\n\n## 条件化成本：从单块到整模型\n\n| 成本 | 应计算的对象与条件 | 常见漏算或重复计费 |\n|---|---|---|\n| 计算 | 索引、范围校验、合并、解包、转置、校验和、设备转换 kernel | 把存储带宽当成全部加载成本；漏掉转换和启动 |\n| 访存 | 页缓存、主机 staging、目标张量、设备输入、转换读写 | 逻辑有效字节与实际过读、复制、读写方向混算 |\n| 通信 | NVMe、PCIe、网络和共享上游；每请求固定开销与字节项 | 把热缓存读速记成 SSD 带宽；忽略多个模型共享链路 |\n| 准备 | open、索引解析、池分配、锁页、注册、编解码器或 kernel 准备 | 把一次性准备摊成零；忽略取消失败后的排空 |\n| 同步 | 队列等待、事件等待、fsync、回调、最后消费者完成 | 用 API 返回代替设备完成或持久化 |\n| 驻留 | 在途槽、旧版本、页缓存、转换暂存、dispatch 列表 | 把 reserved 与 active 相加；把共享只读页重复计数 |\n\n设定 16 MiB 块，SSD 顺序读 4 GiB/s、主机到设备 16 GiB/s，纯传输时间分别为 16 MiB÷4 GiB/s=3.90625 ms 和 16 MiB÷16 GiB/s=0.9765625 ms。如果转换、CPU 调度和共享主存带宽另需时间，它们不能被这两项吸收。设四阶段时间分别为 8、3、2、5 ms，独立资源且缓冲足够时，四块完成时间为 18+(4−1)×8=42 ms；完全串行为 4×18=72 ms。42 ms 是设定整数时间的流水预测，不是目标机器实测；若转换与 H2D 争用同一 PCIe 或主存资源，42 ms 可能不可达。\n\n对更多块或更大模型，端到端时间应由依赖图、资源下界和有限排空共同决定。若资源 r 每块承担 Q_r 字节、在该并发条件下可持续带宽为 B_r，则启动周期还必须满足 P≥Q_r/B_r；例如 CPU 转换和 DMA 共用主存时，两者的读写流量要合并。多 rank 或多模型加载时，可把每个 rank 的排队 q_r 和本地流水 L_r 放入同一完成时间 T_ready=max_r(q_r+L_r)+T_barrier，但前提是 barrier 之后才需要共同发布；各 rank 的字节服务时间不能简单相加替代本地流水。\n\n容量账按唯一物理对象统计。主机读缓冲、设备槽、转换工作区和未释放旧版本各有生存期；同一 backing 的别名只计一次，共享只读页只计一次，确实复制的两份分别计。池的 reserved 已经包含其中 used 时不能再次相加；在途但尚未发布的对象必须占用容量。新旧模型并存、取消排空和失败重试都会出现在峰值中。\n\n## 条件变化后的保留、调整与放弃\n\n模型常驻且只冷启动一次时，复杂直接 I/O、注册缓存和深流水的准备成本可能难以摊销；频繁模型切换、多模型共享 SSD 或主存接近上限时，分块流水和可回收槽更重要。数据频繁复用且页缓存足够时，保留缓存路径可能更便宜；单遍大制品、缓存污染严重或需要应用精确控制驻留时，可比较直接 I/O 与有界块池。\n\nSSD 变快后，瓶颈可能移到 CPU 转换、页缓存刷新、锁页、PCIe
