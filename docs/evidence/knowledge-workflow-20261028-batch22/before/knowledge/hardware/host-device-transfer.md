# K-HW-003：主机准备、DMA 与流水缓冲

输入流水的吞吐取决于准备、传输和计算阶段的平衡；数据可见性和缓冲所有权决定能否正确重叠。设计输入路径、研究 CPU–GPU 协作或定位等待时，都可以从对象大小、当前驻留、生产与消费关系出发。局部原型可用于比较传输或缓冲方案；未知时间和带宽可以先作为带范围的设定量，随后再用目标环境的观察修正。

当前问题需要哪些事实，取决于要比较什么：小 metadata 的提交次数、大对象的实际字节、数据是否重复使用、主机与设备是否争用同一资源，以及任务允许怎样的输入和结果语义。所选路径应能解释哪些对象保持驻留、哪些需要 staging、何时可读与何时可复用；它可以体现在原型、设计说明或现有实现中，不要求统一的工程产物格式。

## 准备不是一次复制

文本服务包含解析和 tokenization，多模态还包含媒体解码、采样、resize、特征整理。CPU 输出通常要整理成连续数组，必要时经 pinned staging，再由 DMA 到设备。每一步可能持有一份副本，峰值主存和锁页容量都进入资源预算。

pageable 主存的异步传输可能经过额外 staging；pinned memory 提供 DMA 所需的稳定物理页面，但锁页本身有成本，也占用系统不可自由换出的内存。将所有主存永久锁页会改变其他进程的可用容量。锁页分配或注册的范围、是否能重复使用及实际源/目的位置，都影响完整准备成本，不能仅按复制 API 的名字推断路径。

## 流水周期与有限批完成

设固定形状的一批依次经过准备、H2D、GPU 计算与 D2H，时间为 \(t_p,t_h,t_g,t_d\)；H2D/D2H 分别是主机到设备、设备到主机。若四阶段使用独立资源，不同批可并发，缓冲充足且没有其他跨批依赖，理想稳态周期为

\[
P_0=\max(t_p,t_h,t_g,t_d).
\]

不计返回传输时可取 \(t_d=0\)，得到准备、传输和计算的三阶段模型。在这些确定性条件下，完成 \(N\) 批的时间为

\[
T_N=t_p+t_h+t_g+t_d+(N-1)P_0.
\]

第一批仍经历各依赖阶段之和；有限任务还要包含流水排空。为准备 \(n+1\)、传输 \(n\)、计算 \(n-1\) 同时存在，需要不同缓冲代次，不能仅靠一块可变数组实现重叠。逐 token 反馈、额外 CPU 输出处理、长度变化及共享资源会改变这个模型；公式是有条件的设计预测，不能直接作为服务尾延迟承诺。

## 何时减少传输次数更有效

小而频繁的 token IDs、lengths 和 sampling metadata 可能受调用与同步成本主导，合并提交比只减少字节更有效。合并还可能增加 packing/unpacking，需结合长度变化和消费者布局比较。大图像或 KV 状态则更接近带宽问题；分块流水还要计入每块启动、尾块和额外缓冲。将采样留在设备可以减少逐 token D2H 同步，却需要在设备/主机之间明确 EOS 与输出交付时机。

缓存输入特征可减少重复 processor 和传输，但缓存身份必须涵盖处理配置；保持设备副本还需明确输入版本和失效条件。实际管线的最慢阶段也可能随并发改变：单请求 GPU 忙，多个媒体请求却让 CPU 解码饱和。各阶段队列长度与完成时间能够区分这种迁移。

## 多级输入与共享带宽

输入还可能从 SSD 或远端存储进入主存，再完成解码、转换、锁页 staging 与 H2D。每段需要分别记有效字节和实际传输字节；布局转换可能读写整个对象，多个阶段又可能共享主存控制器或同一 PCIe 上游链路。理想流水取最大值的模型只有在资源与依赖允许时成立。

设资源 \(r\) 每批累计承担 \(Q_r\) 字节，在该并发条件下可持续带宽为 \(B_r\)，周期还必须满足 \(P\geq Q_r/B_r\)。同一资源上的 CPU 读取、转换读写、DMA 等流量应按实际路径合计，不能把孤立测得的全部带宽同时分给每个阶段。结合上面的阶段模型，\(P\geq\max(P_0,\max_r Q_r/B_r)\) 是相应假设下的必要下界；额外依赖、有限槽位和争用仍可能使周期更大。

小 metadata 应先分析提交次数和同步，大权重/KV 应先分析可持续带宽。若同时预取权重、读取媒体和执行 CPU 冷部分，原先单独测得的 DMA 带宽不一定仍可用。[存储 I/O](storage-io.md) 与 [计算放置](../algorithms/heterogeneous-execution.md) 需要使用同一份资源预算。

## 缓冲池的槽位与代次

主机发送缓冲在 DMA 读取完成前保持不变；设备输入在 kernel 读完前保持不变；D2H 输出在传输完成后才能由 CPU 消费。返回一个异步句柄与数据已经可读是不同事件，数据访问必须依赖完成关系。

一个槽位依次承担读取目的、转换输入、传输源和待回收对象。真正的回收点是所有消费者结束，而不是最后一个主机函数返回。I/O 可以乱序完成，CPU 取消也不能倒转已提交的 DMA；完成记录必须保留对象、范围、请求与代次。[Stream 与分配器](../frameworks/streams-allocator.md) 进一步区分生产消费顺序与最后使用前的存储保护。

对缓冲池 \(j\)，若一个槽从占用到最后消费者完成的固定时间为 \(L_j\)，每隔 \(P\) 启动一批，且完成边界允许立即复用，至少需要

\[
n_j\geq\left\lceil L_j/P\right\rceil.
\]

主机输入、设备输入、设备输出可能有不同的生存期，应各自计算。该关系给出所述固定周期下的容量必要条件；长度或完成时间变化时，平均生存期不足以保证安全，复用仍由真实完成控制。

预留缓冲数可以由阶段时延、吞吐和每批字节估计。任务要求过载下资源有界时，需要使总在途工作满足相应预算；缓冲池、上游准入、端到端额度或其他机制可以承担这一作用。过深队列可能增加等待与取消成本，甚至挤出本来能驻留的 KV。发生输入读取或转换错误时，不向下一阶段发布部分旧/新混合的数据，并让已在途工作完成资源清理。

## 设定算例：阶段、槽位与共享带宽

设准备为 3 ms、H2D 为 2 ms、GPU 计算为 8 ms、D2H 为 1 ms。它们是设定值，不是硬件实测。在前述独立资源和足够缓冲条件下，八批串行为 \(8\times14=112\) ms，理想流水为 \(14+7\times8=70\) ms，第一批仍为 14 ms。

设备输入从 H2D 开始到 GPU 读完占用 10 ms，按 8 ms 周期需两个槽；若设备输出从 kernel 开始保留，到 D2H 完成占用 9 ms，也需两个槽。每批设备输入设为 16 MiB、输出为 1 MiB，则这两个池共需 \(2\times16+2\times1=34\) MiB，另计模型状态、workspace、主机池及其他并发工作。增加到八个槽不会把 8 ms 的计算阶段缩短。

若 CPU 分片和 DMA 在同一 DRAM 资源上每批累计搬运 128 MiB，而该并发条件下的可持续带宽为 8 GiB/s，资源下界为 \(128\ \mathrm{MiB}/(8\ \mathrm{GiB/s})=15.625\) ms。此时不能同时维持先前设定的 8 ms 周期；增加槽位不能消除这项带宽需求。减少流量、改变计算放置或改善资源亲和是可比较的方向，真实流量与带宽仍需在相应环境观察。

这个例子能分别提出三个检查：阶段是否有足够独立工作以接近 8 ms；两个池的不同最后使用时刻是否确实容许各两个槽；共享资源是否已使 8 ms 不可达。若缩为单槽，可能出现等待增加，但不应允许覆盖尚在使用的对象。

## 共享路径的替代方案

物理共享内存、映射主机页和可迁移统一内存有不同的字节与可见性关系，见 [共享内存路径](shared-memory-paths.md)。选择零显式复制路径时，仍需检查实际远端读取、缺页和 CPU/GPU 竞争；不能仅凭应用没有调用复制接口就认定传输成本为零。

对当前对象，可以比较简单复制、有界 staging 或满足平台条件的共享路径。一次性输入、GPU 重复读取、CPU 仍需频繁读取的对象可能适合不同选择。write-combining 主机内存的主机读代价与普通 cacheable 锁页内存不同，不能仅以 H2D 指标决定全部对象的分配方式。具体 stream、分配器和平台默认行为按固定版本核对，相关执行顺序见 [Stream 与分配器](../frameworks/streams-allocator.md)。

## 用具体反例检查所选路径

验证分别改变输入大小、重复次数、CPU 准备强度和设备消费速度，观察各队列、实际完成时间及缓冲峰值。若更深流水只增加队列而未减少设备空洞，说明限制可能来自共享资源或必需依赖，应缩小在途预算或重分配工作。

| 所选机制的边界 | 应成立的关系 | 可区分的观察 |
|---|---|---|
| 锁页分配或注册 | 范围、额外副本和锁页预算与所用对象相符 | 分开比较一次性小对象与重复大对象，检查锁页成本是否摊薄 |
| H2D 与源复用 | DMA 读完前源保持该代次内容 | 延后传输并连续使用不同内容，检查过早覆盖 |
| H2D 与 kernel 消费 | 消费者依赖所需复制完成 | 改变复制完成顺序，核对消费者内容与身份 |
| D2H 与主机读取 | CPU 在复制完成后读取；取消保留在途清理责任 | 延后 D2H，检查是否读到上一轮内容或提前回收 |

局部原型可以用精确输入和独立转换参考检验这些关系，也可以为布局、提交次数或缓冲大小建立 microbenchmark。把路径接入真实消费者时，可核对相邻组件的布局、完成与复用是否相容；完整引擎的收益按 Task 原定的质量、性能和资源边界评价。对于相应服务任务，固定 offered workload、完成吞吐与用户时延可以构成比较口径，其他任务按其自身指标判断。这些证据回答不同范围的问题，局部结果不会自动成为系统结论。

有限任务的完成时间包含管线排空，不能用“所有复制已提交”代替完成。稳态测量可使用明确窗口，但要记录两端的在途工作，并追踪未完成任务的结果。诊断时的同步和 profiler 扰动应与正常路径的性能区分。若方案只减少提交时间，却增加队列等待、锁页峰值或取消后的排空时间，这个反例应进入其适用条件。
