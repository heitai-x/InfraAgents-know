# K-SYS-008：服务协议：接收、流式背压与终止语义

推理服务将内部生成状态映射为可观察的网络事件；接收、执行完成和客户端收到结果是不同的完成点。

## 问题、不变量与设计轴

问题：生成是逐 token 产生、可能很长、可被中途放弃的过程，而客户端通过有限带宽、会断开、会重试的连接消费它。协议层要回答的是"一个请求在外部有哪些可观察状态，内容以什么粒度交付，客户端慢或消失时内部资源怎样受约束，重试时什么算同一个请求"。

不变量：每个对外事件都能映射到确定的内部状态（已接收、已准入、首内容、终止原因）；交付的内容与模型输出的 token 序列按约定的切分一一对应；发送缓冲有界，慢客户端不能无限占用主机内存或拖住设备侧进度；终止（完成、取消、错误、超时）各自有明确的资源回收路径；重试身份使重复提交不被当成两条独立请求。

成本项：每事件的序列化与系统调用、发送缓冲驻留、连接数对执行域的占用、背压传播到调度器的延迟、以及为"恰好一次交付"保存的提交记录。

设计轴：内容粒度（逐 token / 按时间窗合并 / 按语义块）；背压位置（协议层丢弃 / 暂停生成 / 准入拒绝）；终止语义（取消即停 / 排空后停 / 允许迟到结果）；兼容目标（既有 API 子集 / 自定义协议）；重试身份（客户端 ID / 服务端幂等键 / 无）。SSE 流式加有界队列是常见的一点；无流式整段返回在短输出场景同样合法。轴上未列点同样合法。

## 使用场景与协议选择

设计对外接口、接入真实客户端，或探索流式输出、取消、会话续接与滚动更新时，需要解释用户能够观察到什么。目标协议的版本及支持子集、模型/前处理身份、输入输出范围、客户端消费方式和重试要求，共同决定输入解释、内容事件、终止原因与资源责任。哪些行为属于交付要求由当前任务决定；请求身份与执行完成的关系分别见 [请求身份](request-batch-identity.md) 和 [取消与完成](cancellation-resource-completion.md)。

一次请求只在全部计算结束后返回结果时，普通请求—响应可以保持较简单的交付语义，但用户无法观察中间内容；需要逐步交付文本、音频或进度时，可以采用明确事件格式的 HTTP 流；需要在同一连接上持续输入、打断和接收内容时，可以选择 WebSocket 或另一种明确支持双向通信的协议。选择双向连接不会自动提供会话一致性，选择流式传输也不会自动降低模型的首内容计算时间。

本地 ASGI 规范区分 HTTP 的单请求 scope 与 WebSocket 的连接 scope。同一 HTTP/2 连接可以承载多个请求，不能用连接身份代替请求身份；一个 WebSocket 会话内若有多个任务，也要定义各自的请求、回合和输出归属。协议版本、服务声明支持的行为与模型版本应分别识别。

## 一条请求的外部状态

参数验证、排队接收、开始执行、产生首个有效内容、持续输出、最终终止构成可观察协议。返回 HTTP 成功状态通常只说明响应开始，后续流仍可能失败。每条流需要明确的终止事件和原因，否则客户端无法区分正常结束与连接中断。

流式 chunk 是传输单位，不一定是模型 token。一个 chunk 可包含多个 token、空角色信息或 usage 元数据；TTFT 应绑定协议定义的首个内容事件。压缩、代理缓冲和客户端解析还会改变收到事件的时间。

固定 ASGI 规范要求：成功处理 http.response.body 的 send 返回时，本次 body 已交给服务器发送缓冲；它没有确认远端应用已经消费。http.response.start 没有同样的即时 flush 要求，服务器可以等到第一次 Response Body 再发送响应头。生成、交给发送缓冲和客户端收到是可分别观察的事件；它们可以发生在同一调用链，也可以跨越线程或进程，不据此要求引擎拆成固定组件。

## 背压的资源含义

若生成快于客户端消费，输出队列增长。无限队列让慢客户端持有大量文本/音频和请求状态，最终影响其他用户。限制队列、暂停后续生成或断开超时消费者是不同服务策略，应该由延迟与可靠性目标决定。

暂停生成并不一定能释放 KV；完整请求状态仍需保留。对音频，过大队列还增加用户打断后的尾音。背压因此既是网络机制，也是调度和容量变量。

## 取消、错误和重试

客户端断开、发送失败、内部超时和模型异常都应进入同一请求终止账务，避免重复释放。重试是否允许复用请求 ID、是否可能重复输出、是否支持恢复已确认前缀，是协议明确承诺的功能，不能由客户端盲目重发推断。

请求追踪可以跨 API、tokenizer、scheduler、runner 和输出阶段传播上下文。batch 是多请求聚合，需额外记录请求与执行批的映射。敏感原始输入不必全部写 trace，状态身份和摘要即可支持许多因果分析。

## 兼容 API 的实际含义

字段名字相同只说明表面结构。采样默认值、token 计数、流式 delta、工具调用结构、错误格式、取消和结束原因共同定义行为兼容。服务验收应以具体协议的输入输出实例和状态转换为准。内部 engine 能生成文本，与一个完整可消费的服务接口之间还有这些确定的语义关系。

## 接收协议要连接实际执行域

入口事件循环将请求交给分词线程/进程、调度器和模型 worker 时，每条队列都应携带请求版本、deadline、取消状态和缓冲所有权。[主机运行时](host-runtime.md)比较执行域组织；在协议层，关键是队列满时能明确等待、拒绝或终止，而不是已经接受后无限隐藏排队。

租户限额应同时覆盖输入字节/长度、待处理工作、活跃状态和输出积压。只限制连接数不能阻止单连接携带大输入，按请求数平均也不能限制长上下文 KV。配额不足和模型版本未就绪可以有不同的可重试语义，错误响应需说明这次请求是否已经被接收及是否已有对外结果。

## 滚动发布与连接生命周期

服务发现和路由将新请求绑定到具体就绪版本；已有流式连接保持其请求版本和提交顺序。滚动发布先撤销旧实例的新准入，再排空或按明确协议迁移；关闭监听端口不等于现有生成、IPC 和设备操作全部结束。遇到最长排空时间时，最终错误或恢复能力必须与客户端契约一致。

重试协议需要明确请求身份与去重范围。如果服务只能重新执行，就应披露可能重复已产生的内容；若支持从已确认位置恢复，还需保存对应模型、输入、采样/约束状态和输出序号。内部算子重新计算的幂等性不能自动提供网络交付的恰好一次语义。

## 服务故障状态验证

从参数验证前、进入队列后、首内容前、已交付若干内容后、最终结果已计算但未发送等边界分别断开连接或终止 worker。逐项核对客户端看到的事件、服务端提交记录、可否重试与最终资源账。慢客户端测试需要同时运行正常客户端，检查背压是否限定在预定队列和租户范围内。

发布测试保留一条旧版本长流，切换新请求到新版本，再注入新实例预热失败和旧实例排空超时。成功条件包括结果版本可识别、未就绪实例不被路由、每条流有可解释终态、没有迟到旧消息污染新连接。TTFT 继续以首个有效内容计算，不能因发布期间先发空 chunk 就宣称满足目标。

## 参数、计数与内容如何保持同一语义

输入适配应明确缺省值、显式空值与非法值分别意味着什么。最大输出 token 数与“输入加输出”的上下文上限不是同一个数；文本输入的 token 数依赖固定 tokenizer、模板及特殊 token 规则。若外部接口支持 token ID 和文本两条入口，还要说明它们怎样形成相同的规范化输入，避免模板或特殊 token 被重复应用。相关推导见 [Tokenizer 与 I/O](tokenization-io.md)。

采样、停止条件和结构化输出能力按声明的子集处理。未实现的参数应被明确拒绝或按已披露规则处理，不能仅因为字段能够解析就声称支持。停止序列可能跨越多个 token 或传输 chunk；如果协议规定不向用户展示停止文本，输出层需要保留足够的待确认内容，并将该缓冲延迟计入可见时间。流式与非流式的最终内容应在同一停止规则下比较。

输出账应分别记录模型生成、正式提交和客户端收到的范围。usage 信息可以有自己的计数定义，但必须说明是否包含被丢弃的候选、停止内容或取消后的在途计算。不能以“模型执行过多少 token”替代用户收到的内容，也不能因为最终字符串一致就省略流内重复和乱序检查。

## 一个慢客户端的容量算例

以下参数全部为设定，不是服务实测。观察引擎到传输适配层之间的一处有界队列，假设编码后字节的实际入队速率为 8000 B/s，下游从这处队列的实际出队速率为 2000 B/s，允许积压 64 KiB，初始积压为零。在两种速率暂时保持不变、忽略额外封包开销的条件下，队列净增长为 6000 B/s，达到上限所需时间为

\[
t_{\mathrm{full}}=\frac{65{,}536\ \mathrm{B}}{(8000-2000)\ \mathrm{B/s}}\approx10.92\ \mathrm{s}.
\]

远端客户端消费 2000 B/s 本身不足以推出这个本地出队速率：下游发送缓冲仍有空间时，可以先吸收更多字节。只有背压已传导到这处队列，并在观察窗口确认其出队速率时，才能将相应值用于此式；端到端积压还需计入其他缓冲。

若 128 个请求都达到该上限，仅这个输出层就保留 8 MiB。若每个暂停请求另占 6 MiB 私有模型状态，则还有 768 MiB 状态驻留；该状态大小是独立设定，不能由输出字节数推算。发送缓冲、序列化副本和共享前缀还应另按实际所有权计账。

因此可以比较三个合法候选：持续暂停直到消费者恢复，限制暂停时间后终止，或采用任务允许的其他交付方式。暂停保留继续服务的机会，却延长状态占用；超时终止释放未来工作，但必须披露用户可见失败；默默丢弃未声明可丢弃的生成内容会改变任务。选择反转取决于客户端恢复分布、请求价值、资源压力和服务承诺。

验证预测包括队列在达到额度前的增长斜率、饱和后的生成节奏、取消后的在途消耗，以及正常客户端是否受到额外影响。分别观察引擎出队、服务器发送和客户端读取，可以避免把不同缓冲边界的速率与完成事件混用。

## 验收必须包含未完成和被拒绝的请求

局部协议检查覆盖参数、默认值、事件格式、结束原因和解析边界；集成检查覆盖模板到模型输入的映射、增量到最终内容的重建、断开与内部取消的联系。系统检查则使用实际到达过程、混合长度、慢消费者、取消和版本更新，观察完整请求集合与资源变化。

例如一个设定的 10 s 测量窗口内发出 100 个请求，10 个被拒绝，90 个获接收，其中 80 个在窗口内完成、10 个仍未完成；已完成请求中有 72 个同时满足任务规定的质量与全部时延约束。按此窗口和该任务的合格定义，合格完成率为 7.2 请求/s，合格请求占全部发出请求的比例为 72%。这两个量不同，且均不能通过只保留 80 个完成请求来重新定义分母。窗口结束后应继续记录尚未完成请求的结局，排空阶段与稳态窗口分别标明。

固定 GenAI-Perf 文档把 goodput 定义为满足指标约束的完成请求率；如果任务还要求质量或协议正确性，就要把额外门限明确加入资格定义。其 README 将 TTFT 写为首个 response，当前任务若采用首个有效内容，必须核对哪些流事件被解析器计入，保留空事件、首内容与终态的区别。修改刷新频率、代理缓冲或流事件格式后，应重新确认该映射，不能仅比较同名指标字段。
