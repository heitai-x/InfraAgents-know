# K-WORK-011：集群放置：资源向量、拓扑、执行组与故障域

单实例的计算与容量方案确定后，还要找到能够同时满足它的设备集合。集群总空闲资源足够只是必要条件；拓扑、逐设备内存、CPU/NUMA、网络、存储局部性和故障后的剩余容量共同决定部署是否可行。

## 资源向量与可行集合

一个实例的需求可表示为逐 rank 的 GPU 类型与内存、CPU 时间/核集合、主存、临时存储、NIC 与带宽，以及 rank 之间的连接要求。设备算力、容量和网络不能直接相加成一个没有单位的总分。先排除不满足硬约束的位置，再比较剩余候选的排队、成本与干扰。

总 GPU 内存不能替代每 rank 预算：参数切片之外，部分张量可能复制，workspace 与 KV 也会不均衡。相同型号但不同链路、NUMA 或 quota 的设备，实际执行成本不同。编译与内核支持属于能力约束；某台机器能安装相同容器，不证明它能执行同一指令路径。

[Borg](../sources/S-BORG.md) 区分配额准入、资源可行性和位置评分，并讨论紧凑装箱与碎片、包局部性、故障域之间的关系。这些是集群层机制；将其用于 GPU 推理时，仍需加入设备组、状态和通信约束，不能把论文中的 CPU 混部效果当作推理性能保证。

## 共同启动与控制状态

TP/PP/EP 组中的 rank 需要形成相容的执行集合。可以先预留整个组，再加载和建立通信；也可以分阶段取得资源，但要限制部分取得后长期占用且无法完成的情况。这里的 gang 准入指整组满足启动条件后才作为服务容量公开，不要求所有操作在同一个物理时刻发生。

控制面拥有期望的副本、放置和版本；节点报告实际分配、加载与执行状态。计划基于旧观察时可能失效，提交放置必须重新检查资源与代次。路由读取的是已就绪实例集合，不能直接把“调度已决定”当作“模型可计算”。调度器故障与已有数据面是否继续工作，也需要明确约定。

## 碎片与两种放置比较

设定四个节点各有 4 张同型 GPU，目前每个节点各剩 2 张空闲，总空闲为 8 张。新服务 A 的验证方案要求同一节点 4 卡，另一服务 B 每副本只需 1 卡。A 仍然不可放置，B 可在这些空位运行；为 B 填满全部余量又可能延长 A 等待完整节点的时间。

候选一保留即将释放的完整节点给 A，把 B 放到其他位置，代价是暂时留空部分卡。候选二将 A 改为两个节点各 2 卡，需重新核对跨节点通信、组装与故障条件。只有在新的执行布局和 SLO 验证通过后，第二种方案才是合法替代；不能用总空闲数量跳过这一验证。迁移已有任务以消除碎片，还要计入迁移带宽、排空及受影响服务的代价。

紧凑放置可为大型实例保留完整空间，也可能集中争用 CPU、NIC 与 SSD。分散放置减少局部干扰和相关失败，但可能扩大通信距离、减少权重缓存命中或造成小碎片。[多模型放置](multi-model-placement.md) 与[路由迁移](../algorithms/routing-and-migration.md)决定这些代价是否值得支付。

## 故障域与可用容量

副本是功能上的替代，只有分散到适当故障域才具有相应容错价值。同一节点的两个模型实例可能同时失去 CPU、驱动或网络；不同节点但共用机架网络、供电或存储出口，也仍有共同故障。执行组内部追求近距离通信，独立副本之间追求故障分散，二者需要分别设计。

设定三个副本组各能处理 40 请求/s，正常到达为 70 请求/s。丢失任一组后剩余 80 请求/s，仅从平均服务率看仍有余量，尾延迟是否达标仍需测量。如果两个副本共用同一故障域且会同时失去，剩余只有 40 请求/s，就无法维持这个到达率。此时要增加独立余量、调整放置或承诺故障时的降载/拒绝。

超售也需按资源区别处理。空闲 CPU 时间可能通过节流交回，但正在使用的 GPU 权重与 KV 不能凭降低调度权重立即消失。把内存容量超售给不可抢占的请求，会将配额争用转成 OOM；可借用容量应绑定明确可撤回的状态和代价。

## 可区分方案的验证

以具体部署描述检查每个 rank 的容量、设备身份、通信集合和允许的路径，再用保留轨迹比较放置方案。记录待调度原因、碎片、启动各阶段、网络/存储热点与逐租户 SLO。模拟或注入一个 rank、一台主机、一个共享存储出口不可用，确认故障后哪些组仍完整、路由何时停止指向旧代次，以及剩余容量的实际工作量。

模型很小、独占实例长期低负载时，混部收益可能占优；大模型需要完整高速设备组、严格尾延迟或强故障隔离时，保留空间和拓扑约束更重要。集群设计的目标是兑现推理契约，而不是单独优化装箱率。
