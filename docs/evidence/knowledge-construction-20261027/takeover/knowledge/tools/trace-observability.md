# K-TOOLS-001：可观测性：执行事件与采集事件的映射

trace 是由采集范围和工具机制生成的观测，不是系统全部执行事实的无损副本。

## 观测模型

系统先发生事件，采集器在被启用的 domain、进程和时间窗口中记录它，再由导出器转换成表或文件。任何一层的缺失都会让最终查询看不到事件。表不存在、表存在但空、窗口外、过滤后为空、无法关联，是不同状态。

缺少 kernel 表只支持“这份导出未提供该表”，不能推出“设备未执行”。证明没有执行需要覆盖相应进程、设备、窗口和事件类型的观测能力。相反，看到 kernel 也不说明它属于目标请求，仍需关联上下文。

## 覆盖矩阵怎样帮助推理

记录所需信号、采集是否启用、原始记录是否存在、导出是否成功和查询范围，可以明确每个结论依赖什么。主机 API、设备 kernel、memcpy、通信、NVTX 和 OS 调度各回答不同问题；一个工具的默认输出不能自动覆盖全部。

可以构造两份采集材料作区分：一份明确启用并取得目标设备事件，另一份未启用该类采集。后者缺少相应表，只能说明该观测路径未覆盖；是否执行须由其他独立信号判断。这里给出验证关系，不声称已经完成一次项目实验。

## 缺失也可形成下一步信息

若候选原因是 CPU 阻塞，但只有 GPU kernel，下一次观测需要补主机线程/调用区间；若候选是请求错配，单个 GPU 利用率指标不足，需要请求到 batch 的映射。高质量采集由问题的可区分预测决定，避免无目标收集庞大 trace。

## 推理全路径需要哪些信号

观测范围应覆盖候选瓶颈，而不是默认围绕 GPU 展开。先为任务确定完成边界，再把输入处理、等待、计算、状态迁移和输出交付接成同一条路径。

| 需要区分的问题 | 需要取得的观测 | 单独不足的信号 |
|---|---|---|
| CPU 计算不足或线程排队 | 线程运行/等待区间、实际执行范围、工作量 | 进程总 CPU 百分比 |
| 本地或跨 NUMA 访存 | 分配/线程放置、可用的内存域计数和受控放置对照 | 一个总 cache miss 值 |
| 磁盘慢或软件队列深 | 提交、派发、完成、字节数、合并范围与队列占用 | 文件读取调用的单一总耗时 |
| 传输慢或接收方未就绪 | 发送/接收范围、完成、消费许可、源/目的等待 | 网络字节数或本地 CQE |
| 设备计算或输入供给 | 输入就绪、设备排队、kernel/copy 及主机准备 | GPU utilization |
| 输出慢或客户端背压 | 内容生成、封包、发送、对端可见与队列长度 | 内部 token 生成速率 |

表中信号是所需证据的定义，不保证任一 profiler 自动提供全部信息。工具权限、设备事件支持和采集范围需要在实际环境确认；无法取得的部分应明确保留为未知。

## 区分逻辑请求与物理工作

文件读取可能由页缓存满足，多个逻辑读取可能合并为一个块请求；一个缓存对象也可能同时服务多个推理请求。因此逻辑 token、张量字节、系统调用字节、块层字节与设备传输字节应分别统计。对同一个物理读取，既可以报告其服务了多少逻辑消费者，也必须在物理流量中只计一次。

反过来，一次逻辑请求可能触发重试、格式转换、临时副本和多跳传输，物理流量可以大于用户输入大小。归因时保留对象范围和转换身份，才有可能解释放大来自布局、缓存未命中还是失败重传。[Linux I/O](../sources/S-LINUX-IO.md) 的软件/硬件队列区分提供一项具体边界依据。

## 让一次采集能够反驳假设

存在竞争解释时，用它们的不同预测选择观测；已有充分证据指向具体关系时，可直接检查该关系，无需为满足数量要求补造假设。例如长 TTFT 可能来自权重加载，也可能来自已就绪实例的准入等待。前者预测冷启动时存储与转换路径增长；后者预测模型已驻留但请求排队增长。只采集最终 TTFT 无法裁决，应补两者之间的交接事件。

使用短窗口先确认目标进程和事件确实可见，再扩大到足够覆盖触发与回收的区间。检查事件丢失、缓冲溢出和导出过滤；若采集本身改变队列稳定性，应缩小采集范围并以无 profiler 的重复测量为性能依据。带有观测缺口的材料仍可支持局部结论，但不能把缺口对应阶段的成本视为零。
