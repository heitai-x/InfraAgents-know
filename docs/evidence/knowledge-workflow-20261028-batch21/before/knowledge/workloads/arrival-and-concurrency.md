# K-WORK-002：到达过程与并发：排队、反馈和饱和点

负载生成器定义了系统受到的压力；闭环并发和独立到达率回答不同容量问题。分析需要把计划、就绪、发送、准入、执行、业务结束和物理排空连成一条可核对的时间线。完成吞吐、排队长度和并发只有在人口、边界和窗口一致时才能相互解释。

## 对象、时间边界和两套状态

到达过程定义请求何时进入考察范围；并发是某一时刻处于指定范围内的请求数。必须说明计数的是等待发送、已准入、正在执行，还是仍持有物理资源的请求。

对一次尝试 i，记录以下时刻，单位统一为秒：

| 符号 | 含义 |
|---|---|
| pᵢ | 原始计划或最早允许到达的时刻 |
| rᵢ | 时间与依赖都满足、可以进入发送就绪队列的时刻 |
| sᵢ | 实际发送时刻 |
| gᵢ | 本次发送所占生成器槽位的最后使用结束时刻 |
| aᵢ | 服务端实际确认准入的时刻 |
| bᵢ | 所考察服务资源首次开始执行的时刻 |
| fᵢ | 首个可见内容到达所选观察端的时刻 |
| cᵢ | 成功达到所选业务完成边界的时刻 |
| xᵢ | 成功、失败、拒绝、取消或超时导致业务结束的时刻 |
| dᵢ | 所考察物理访问全部结束的时刻；多资源时还要分别记录各自的最后使用 |

独立开放请求通常有 rᵢ=pᵢ。带依赖的请求则有 rᵢ=max(pᵢ，上游要求的完成时刻＋思考或工具等待)。此时 sᵢ−pᵢ 同时包含依赖阻塞和生成器等待，只有 sᵢ−rᵢ 才能归入就绪后的迟发。严格闭环客户端可以在上游完成后才创建下一计划，此时新计划的 p 本身随响应变化。

请求身份应包含逻辑请求、尝试序号和生命期。重试增加尝试，不增加原始逻辑任务；重复通知不增加完成量。批次行号、连接号和复用后的请求字符串都不能单独充当生命期身份。

业务状态和物理责任分开维护：

| 业务状态 | 语义及后继 |
|---|---|
| PLANNED | 计划已创建；等待时间或依赖，满足后进入 READY |
| READY | 已就绪但未发送；取得发送槽后进入 SENT |
| SENT | 已实际发送，尚未得到确定的准入、拒绝或发送失败结论 |
| QUEUED | 已确认准入，等待服务；可启动、取消或超时 |
| RUNNING / OUTPUT | 已开始执行，或执行结果等待所选业务完成边界 |
| COMPLETED / FAILED | 业务成功或失败终态 |
| REJECTED | 本次业务在准入阶段被明确拒绝 |
| CANCELLED / TIMED_OUT | 业务取消或超时终态；停止后继提交和业务发布 |

物理账另外保存发送槽、待决远端请求、已预留对象、执行引用和输出消费者。业务终态不可被迟到完成覆盖，但终态请求仍可能占内存、连接和设备工作区。取消 QUEUED 请求必须移出可启动集合；取消 RUNNING 请求不能提前释放在途对象。

“完成”可以指服务端生成结束、客户端收到最终响应或质量判定通过。一次比较必须选择其一，或分别报告多个边界。首个流式 chunk 也不必等于一个模型 token；首内容、最终响应和 token 数分别记录。

合法观测须声明到达模型、身份、队列纪律、准入与重试规则、业务完成边界、物理回收条件、窗口及未完成处理。跨主机时间差需要时钟映射与误差范围；无法对齐时，不能把不同机器的时间戳直接相减。

## 闭环、开环和到达方差

开环按外部时钟产生请求，服务变慢不会自动降低后续计划率。闭环客户端收到响应后再思考并发送下一请求，服务变慢会降低实际请求率。这是反馈结构的差异。

固定 N 个持续循环的客户端，平均响应时间为 R、平均思考时间为 Z，在稳定、同一人口口径下，交互响应关系为

N=X(R＋Z)，因此 X=N/(R＋Z)。

它来自每个客户端在响应与思考两阶段的循环时间账；R 随 N、调度和资源争用变化，不能把式子当作独立的容量预测。设 N=8，R=0.20 s，Z=0.05 s，则 X=32 请求/s；若 R 增至 0.75 s，X 降为 10 请求/s。固定并发测试会自动减压，不能据其吞吐断言系统承受同速率的开放到达。

固定间隔、Poisson、突发和真实 trace 即使平均 λ 相同，尾延迟也可能不同。Poisson 间隔为指数分布，均值为 1/λ、方差为 1/λ²；固定间隔没有这种间隔方差。真实流量还可能存在租户、长度、共享前缀和相邻到达之间的相关性。平均 λ 不保留短时峰值、持续时间或突发间隔。

多轮服务可以把会话开始建模为开放到达，在会话内部保留响应、思考和工具调用依赖。逐轮随机打乱可能制造原本不存在的并发；聚集相同前缀可能制造过于理想的缓存局部性。trace 缩放须同时解释时间变换和依赖、长度、租户、前缀关系如何保留。

## Little 关系与有限窗口的精确核算

对同一人口和系统边界，在长期平均存在、流量守恒且没有持续积压增长的条件下，平均系统内数量 L、通过该边界的长期流率 λ、平均逗留时间 W 满足

L=λW。

W 是均值，不能换成 p99。稳定条件下，到达率与全部离开率相等，因此同人口的长期离开率可以代替到达率；如果所有离开都是成功完成，完成率也可以使用。如果人口包含失败、取消和超时，成功完成率就不能自动替代全部离开率。另一种合法做法是单独定义成功请求人口，同时只积分成功请求的驻留，不能仍用全部请求的 L。

平均 20 请求/s、平均逗留 0.5 s 对应平均 10 个系统内请求；这不是最大并发，也不是尾延迟保证。

有限窗口有不依赖稳定性的样本路径恒等式。对窗口 [u,v)，T=v−u>0，令 eᵢ、ℓᵢ 为同一人口的进入和离开时刻；未离开者令 ℓᵢ=∞。每个请求贡献

hᵢ=max(0,min(ℓᵢ,v)−max(eᵢ,u))。

于是

∫ᵤᵛN(t)dt=Σᵢhᵢ，L̄=Σᵢhᵢ/T。

请求在窗口前到达、窗口内离开，只贡献窗口内那段；窗口末仍未完成，也贡献已经发生的驻留。仅在窗口开始为空、所有计入的到达都在窗口内离开且结束为空时，才可直接写成 L̄=(A/T)·(ΣWᵢ/A)。一般窗口应先用区间交集核算，并检查 N(v)−N(u)=窗口进入数−窗口离开数的端点约定。

混用全部到达率与已完成请求均值时，偏差方向不固定：

- 窗口 [0,10)，A 的区间为 [0,9)，B 为 [9.9,10.9)。真实面积为 9.1 请求·秒，L̄=0.91；全部到达率 0.2 请求/s 乘已完成均值 9 s 得 1.8，发生高估。
- 同一窗口，A 为 [0,1)，B 为 [1,20)。真实面积为 10 请求·秒，L̄=1；相同算法得到 0.2，发生低估。

这两个反例说明：删失问题不能靠统一增加或减少一个修正量解决。需要保留身份、进入、离开以及窗口内交集；尚未完成者不能伪造成成功，也不能从驻留面积中删除。

## 排队公式的合法范围

对单服务台、工作守恒、无限队列、先来先服务、独立到达与独立同分布服务时间，令 S 为服务时间、λ 为到达率，ρ=λE[S]。稳定要求 ρ<1。

若到达为 Poisson，服务时间为指数分布，令 μ=1/E[S]，M/M/1 给出

W=1/(μ−λ)，Wq=ρ/(μ−λ)，L=ρ/(1−ρ)。

若保留 Poisson 到达，但允许一般服务时间分布，且 E[S²] 有限，M/G/1 的平均排队时间为

Wq=λE[S²]/(2(1−ρ))，W=Wq＋E[S]。

二阶矩解释了为什么相同平均服务量仍可能产生不同等待。对 c 个相同服务台，λE[S]<c 是相应模型的必要负载条件，不是尾延迟或联合 SLO 的充分条件。

LLM 服务常违反这些假设：batch 组成改变每请求服务时间；长 prefill 阻塞短 decode；有限 KV 形成准入边界；抢占改变队列纪律；共享前缀和会话使服务时间相关。此时不能把模型公式直接作为真实尾部预测，也不能无证明地称其为下界。应建立随 batch、长度、缓存和调度变化的服务曲面，并用事件轨迹核对模型失配。

## 突发、残余积压和排空

在请求可连续近似、工作守恒且服务率 μ 固定的流体模型中，一段持续 τ、到达率为 λb 的区间，其结束积压为

B=max(0,Q₀＋(λb−μ)τ)。

Q₀ 是区间开始的积压。对从空队列开始且 λb>μ 的突发，B=(λb−μ)τ。突发后到达率为 λ₀，若 B>0 且 λ₀<μ，净排空时间为

D=B/(μ−λ₀)。

B>0 且 λ₀≥μ 时没有有限排空时间；B=0 只表示当时无积压，不表示之后任意基础流量均稳定。

设 μ=100 请求/s，突发 λb=160 请求/s、持续 2 s，B=120 请求。之后 λ₀=60 请求/s，需要 3 s 排空。若只间隔 1 s 又出现同样突发，残余为 80，请求积压随后增至 200。每次突发都重置为空队列会低估后续压力。

逐区间参考算法应守恒：本段到达量为 λΔt，可服务量为 μΔt，实际服务量为 min(Q＋λΔt,μΔt)，新积压为旧积压＋到达−实际服务。对分段常数流体，它可核对段末积压；真实离散请求、不可抢占工作和组批需要另建服务模型。

优先级可以重新分配等待和拒绝，不能创造总容量。分块可缩短不可抢占段，却增加调度、重复读取和状态保存。完成吞吐达到平台而队列继续增长，只说明有限窗口中的完成率达到某个平台，不能证明稳定容量。

## 从输入事件到可推进的完整算法

下面给出一套可实现的审计与生成模型。实测模式消费真实发送、准入、启动、完成和释放事件，不依据名义延迟伪造时间戳；模型模式则必须显式输入发送槽持有时间、准入延迟、服务规则和回调规则。两种模式使用相同账本，但模型事件不构成设备观测。

输入包括带生命期的尝试计划、无环依赖图、生成器槽数、准入策略、服务容量、取消/超时及完成边界。输出包括逐事件日志、每请求时间线、业务终态、物理引用、队列与驻留面积、各阶段计数。

```pseudocode
初始化：
    验证单位、非负持续时间、身份唯一、依赖存在且无环
    建立计划表、依赖反向边、未满足依赖数、就绪 FIFO 和服务等待队列
    建立发送槽账、准入决定账、业务终态账、逐对象物理引用账
    建立已消费通知凭据集合；设置观察窗口与端点规则

按时间与声明的稳定次序消费事件：
    在更新状态前，以旧状态累计上一事件至本事件的窗口内面积
    验证请求生命期、事件来源和通知凭据；重复通知走幂等路径

    PLAN / 时间就绪：
        创建 PLANNED 记录，保留原始 p
        时间和全部依赖满足时，记录 r，进入 READY 并加入就绪 FIFO
        否则登记等待的依赖或定时器，不能只留下无唤醒来源的标志

    依赖完成：
        仅按声明的成功/内容/质量边界解除相应依赖
        更新反向边及未满足数；时间也满足的请求进入 READY
        依赖失败则按既定规则结束或转入显式恢复，不无限等待

    推进发送：
        有空发送槽时，取仍为 READY 且未结束的请求
        原子取得槽与发送凭据；实际交付发送后记录 s，进入 SENT
        模型模式按输入规则产生未来事件；实测模式等待真实回调
        不能在 SEND 时直接填入 a

    TX_DONE / 发送槽最后使用结束：
        按凭据至多归还一次槽；立即重新推进就绪 FIFO
        槽持有到发送结束还是完整响应，必须预先声明

    ADMIT / REJECT_DECISION / 确定发送失败：
        从真实决定事件记录 a 或拒绝/失败，不回填为 s
        每次尝试只有一个确定的准入决定；不确定发送结果保持待决
        已准入且业务仍有效：进入 QUEUED，保留所需容量责任
        业务已取消/超时：保持原终态；迟到准入仍记入准入账并请求清理
        迟到拒绝只结束待决责任，不覆盖已有取消终态
        活跃请求被拒绝或确定失败：设置相应业务终态

    推进服务：
        从可执行且未结束的等待请求中选择候选
        校验输入与资源就绪；取得服务槽、预留和执行凭据
        记录 b，进入 RUNNING；执行视图绑定原请求生命期
        无合法候选则等待具体事件，不提交空工作或忙等

    CANCEL / TIMEOUT：
        若尚无业务终态，原子设置 CANCELLED 或 TIMED_OUT，记录 x
        从 READY 和可启动队列移除，停止未来提交与业务发布
        不撤销已提交物理访问；重复终止不重复计数或释放
        通知依赖方按失败规则推进；尝试清理已满足回收条件的对象

    PHYSICAL_DONE：
        按执行/消费者凭据确认对应最后使用，至多归还一次物理引用
        归还该资源后立即推进等待者；部分资源完成不代表全部排空
        已取消/超时的请求只做物理清理，不转为成功或执行失败
        仍有效的请求按结果进入 OUTPUT、业务成功或失败路径

    业务完成事件：
        只有达到预定完成边界且尚无终态时才设置 COMPLETED 或 FAILED
        记录 c 或 x，按约定解除依赖；重复通知不重复发布和计数
        业务结束不等于所有输出消费者或发送对象已结束

    每次状态变化后：
        推进新就绪请求、发送 FIFO 与可执行服务队列，直到没有即时进展
        仅当逻辑拥有权撤销、全部已提交访问结束、最后消费者退出时回收对象

窗口结束：
    先累计到端点的面积，再按声明规则取得快照
    冻结业务计数与物理账；不等待未来完成来改写窗口事实
    单列逻辑 remaining、物理在途、draining、未决准入和生成器 backlog
```

该算法保证进展需要额外条件：资源最终释放、依赖最终有确定结果、准入与服务选择不会无限饿死可执行请求。算法必须在释放槽、依赖解除和服务完成时唤醒等待者；仅记录“阻塞”并不能保证活性。有限硬容量、永不返回的远端调用或无界输出背压都会使等待持续，必须报告为未决或调整策略。

draining 表示业务已结束但仍有物理责任的请求，是业务终态人口的子集；remaining 表示尚无业务终态，两者不重叠。仍在物理执行中的 remaining 请求另计 physical_inflight，不能全部叫 draining。

对固定计划队列、无静默重试的人口，有互斥业务恒等式：

planned=completed＋failed＋rejected_business＋cancelled＋timed_out＋remaining。

发送尝试的决定账则是：

attempted=admitted＋rejected_decisions＋definite_send_failures＋pending_decisions。

两个拒绝计数可能不同：取消后收到拒绝决定，增加 rejected_decisions，但业务仍属于 cancelled。准入后取消也仍属于 admitted。跨窗口使用“初始人口＋本窗口新增−本窗口离开”核算，不能把窗口前的在途请求凭空消掉。

## 一条贯通迟发、取消和窗口截断的轨迹

以下是设定的单发送槽、单服务台模型，不是服务实测。发送槽从 s 持有 1 s，与服务执行独立；服务按准入队列顺序运行且不可抢占。依赖等待成功完成。每个回调后立即推进队列；同一时刻的模型回调顺序为物理完成、发送槽释放、计划、取消/超时、准入决定，再以稳定序号打破同类平局。

窗口为 [0,6)，快照包含 t=6 已处理的回调。I 在窗口前已启动；其余请求如下。表中横线表示截至快照没有相应事件。

| 请求 | p | r | s | a 或拒绝 | b | 业务结果与 x | 物理完成 d |
|---|---:|---:|---:|---:|---:|---|---:|
| I | −2 | −2 | −2 | −1.5 | −1.5 | 成功，1.5 | 1.5 |
| A | 0 | 0 | 0 | 1.5 | 1.5 | 取消，2 | 3.5 |
| B | 0.25 | 0.25 | 1 | 1.5 | — | 排队取消，2.5 | 无执行 |
| R | 0.5 | 0.5 | 2 | 拒绝，2.25 | — | 拒绝，2.25 | 无执行 |
| C | 0.1 | 1.5 | 3 | 3.5 | 3.5 | 成功，4.5 | 4.5 |
| U | 3.25 | 3.25 | 4 | 4.5 | 4.5 | 超时，5.5 | 窗口外，14.5 |
| D | 0.2 | 4.5 | 5 | 5.5 | — | remaining | — |

C 依赖 I，D 依赖 C。C 在 1.5 就绪时，B 正持有发送槽，R 已在就绪 FIFO，因此 C 到 3 才发送。C 的 s−p=2.9 s 中，依赖等待为 1.4 s，就绪后迟发为 1.5 s。B 的 s=1<a=1.5，证明发送和准入不能合并。

A 在 2 取消，但服务台到 3.5 才释放；B 在 2.5 排队取消后不再启动。3.75 收到 A 的重复物理完成通知，不得释放正在被 C 使用的服务槽。U 在 5.5 超时后仍执行，D 已准入却不能启动。

这批计划从其创建开始累计的快照为：planned=7、attempted=7、admitted=6、拒绝决定=1；成功=2、失败=0、业务拒绝=1、取消=2、超时=1、remaining=1。draining=1，是 U；A 已排空。它们是包含窗口初始请求的队列累计快照，不是全部发生在 [0,6) 的事件增量。

准入至业务结束的窗口面积为

1.5＋0.5＋1＋1＋1＋0.5=5.5 请求·秒。

物理服务台在整个窗口持续占用，面积为 6 请求·秒。A 的取消后区间 [2,3.5) 与 U 的超时后区间 [5.5,6) 合计 2 请求·秒排空面积。若用业务终态立即释放服务槽，会错误提前启动后继。

再条件化地假设每次准入分配一个独占 1 MiB 对象，业务结束且全部服务访问结束后才能回收，没有额外输出消费者，则驻留面积为 5.5＋2=7.5 MiB·秒，平均 1.25 MiB，峰值 2 MiB。只按逻辑剩余人口记账会漏掉取消与超时后的 2 MiB·秒。这是对象生命期算例，不是实际 KV 大小或内存测量。

## 生成器供给与六类成本

生成器容量必须按同一种资源的供需比计算。设可用 CPU 份额 Pg 的单位为 CPU 秒/秒，每尝试 CPU 工作量为 d_cpu 个 CPU 秒/尝试；发送槽数为 Cg，每尝试持有 d_slot 个槽秒；每尝试网络流量为 D 字节，链路可用率为 B 字节/秒。平均必要条件分别是

λ_attempt·d_cpu≤Pg，λ_attempt·d_slot≤Cg，λ_attempt·D≤B。

需求为正时可改写为 λ_attempt≤min(Pg/d_cpu,Cg/d_slot,B/D)。零需求项不作除法。连接占用到完整响应的系统，d_slot 必须包含该墙钟持有时间，不能仍使用仅发送的时间。重试率进入尝试流率，而非只用逻辑任务率。

CPU 秒是各线程 CPU 时间之和。一个发送槽内，10 个 CPU 各运行 0.1 s，一次发送消耗 1 CPU 秒、持槽 0.1 槽秒；若 Pg=10、Cg=1，两项上界均为 10 次/s。将 Cg=1 除以 1 CPU 秒得到 1 次/s，是单位混用。即使平均条件成立，CPU 配额节流、同步和瞬时突发也可能使计划时刻无法兑现。

| 成本 | 条件化账目 | 需要避免的混算 |
|---|---|---|
| 计算 | 计划生成、序列化、分词、服务计算、采样、日志处理 | 生成器 CPU 与服务端 CPU 分开；每项工作只计一次 |
| 访存 | 请求表、输入、KV、输出、事件日志的读取与写入 | 逻辑对象字节不同于设备事务；共享物理对象去重 |
| 通信 | 请求、流式响应、完成与取消消息、跨机状态传输 | 建连与重试另计；chunk 数不直接等于 token 数 |
| 准备 | trace 解析、数据采样、tokenizer、连接预热、模型 warmup | 冷启动与稳态窗口分开，不能悄悄移出目标计时 |
| 同步 | 槽位归还、依赖唤醒、回调、时钟映射和输出背压 | 回调延迟不自动等于设备执行；重叠段按关键路径计时 |
| 驻留 | 已准入排队对象、在途 KV/工作区、待消费输出和待决尝试 | 取消后引用未清零不能扣除；预留池与池内对象不重复计容量 |

对无共享、按请求归属的对象，稳定平均驻留更一般地写成 λ·E[∫mᵢ(t)dt]。只有大小恒定或具备相应独立条件时，才能简化成 λE[W]E[m]；大小与停留时间相关时不能把两个均值直接相乘。共享缓存应按唯一物理对象生命期计算。

实现上，V 个请求、D 条依赖、E 个事件的反向边唤醒可累计为 O(V＋D) 次依赖处理；就绪 FIFO 的取放可为摊销 O(1)。模型事件堆通常需要 O(E log E) 时间；已有有序日志的面积扫描为 O(E)。全量日志占 O(E) 空间，在线状态与依赖表另占 O(V＋D)。观测开销可能改变发送节奏，需要采集开关对照，不能将审计器的模型复杂度当作服务开销实测。

## Coordinated omission 与计划兑现

闭环客户端等待慢请求结束才生成下一请求，会减少停顿期间的到达。这适合描述固定用户循环，却不能代表独立用户仍持续到来的开放流量。如果仍按开放到达解释只对已发送请求统计的尾部，就出现 coordinated omission。

设开放计划在 [0,12) 每秒到达一次，共 12 个请求。另一条单客户端闭环轨迹在 t=0 发出请求，首请求耗时 10 s，之后每次耗时 1 s，则实际发送在 0、10、11，共 3 次。两者不是同一个 offered workload；相对开放计划少了 9 次到达，不能只比较三个实际请求的服务延迟。

对独立计划，分别报告 s−p、c−s、c−a 和 c−p；它们对应发送前迟发、发送后响应、准入后逗留及相对计划的总响应。对依赖请求再报告 r−p 与 s−r。补救不是给所有请求加固定延迟，而是保存原计划和实际事件。

重放器落后时，可以保留原计划、显式迟发并报告计划未兑现，也可以判定生成失败；不能静默拉长时间轴后继续声称提供了原压力。事后合成遗漏样本需要额外到达与服务假设，不等价于真实独立到达下的队列观测。

## 条件变化后的保留与调整

| 条件变化 | 可以保留 | 必须重算或放弃 |
|---|---|---|
| 平均到达率改变 | 身份、事件边界、守恒账 | 重算各资源需求和队列趋势，不能只外推旧 throughput |
| 方差、突发长度或间隔改变 | 区间面积算法 | 重算残余积压和排空；放弃只凭平均 λ 的尾部判断 |
| 闭环用户数或思考时间改变 | N=X(R＋Z) 的人口口径 | 重测 R(N)，不能把旧闭环吞吐迁移为开放容量 |
| 长度与服务分布改变 | 所选完成边界 | 重算服务二阶矩、batch 和驻留；重新检查队列假设 |
| 准入、取消和重试改变 | 逻辑任务与尝试身份 | 重算尝试放大、各决定率、业务终态和排空责任 |
| batch、缓存或抢占改变 | 请求归属和物理回收不变量 | 重建服务曲面；放弃固定 μ 或独立服务时间假设 |
| CPU 配额、连接池或网络改变 | 计划时间轴 | 分资源重算供给，生成器跟不上时放弃原压力声明 |
| 会话依赖或 trace 变换改变 | 明确的依赖语义 | 重算 r、局部性和会话完成单位，不能逐轮任意打乱 |
| 完成或窗口边界改变 | 原始逐事件日志 | 重新聚合，不能直接比较两个不同人口的延迟或吞吐 |

## 区分实验、反证和检查范围

容量扫描先在低负载建立服务与固定准备时间，再逐步增加外部压力；每个点同时保留 planned、ready、attempted、准入决定、各业务终态、remaining、队列斜率、驻留与分阶段延迟。完成吞吐平台而积压持续增长的点不能作为稳定 SLO 容量。

| 观察 | 竞争解释 | 区分干预、预测与修正 |
|---|---|---|
| 吞吐平台且尾延迟上升 | 服务饱和；生成器供给不足；拒绝掩盖过载 | 固定计划和服务条件，增加生成器资源；若 s−r 显著下降且实际压力提高，原点先受生成器限制；发送准时而准入后队列增长则转向服务解释 |
| 相同平均 λ、不同尾部 | 到达突发；服务方差；cache 或长度关系变化 | 固定请求服务量和初始状态，只改变到达间隔；积压若随突发对齐支持到达解释，服务量同时改变则撤回单因素结论 |
| 取消后吞吐似乎立即提高 | 合法移除排队工作；提前回收在途对象；减少了 offered 工作 | 记录取消位置、物理最后使用和后继启动；在途访问结束前复用同一对象直接反证回收合法性 |
| GPU/CPU 平均利用率低但队列增长 | 单资源饱和；准入等待；依赖未就绪；输出背压 | 按请求阶段记录等待，只改变一个对应资源；平均利用率本身不能排除局部瓶颈 |
| 完成延迟很好、成功比例低 | 拒绝或超时筛掉慢请求；窗口删失；质量失败 | 恢复完整人口与未完成请求，按联合成功条件报告 goodput；仅幸存样本快不能证明总体容量改善 |
| 固定并发下停顿后恢复很快 | 闭环自动减压；真正有排空余量 | 用独立计划重放相同请求量，保留 p、r、s；若开放队列持续增长，应限制闭环结论的适用范围 |
| 重复通知后后继异常提前启动 | 重复释放槽位；错误生命期归属 | 注入同凭据重复通知和旧生命期通知；资源数与业务计数应保持不变，异常则修正幂等与身份处理 |

实验比较要固定任务、输出质量、长度、准入和窗口规则。若干预同时改变 batch 或后续生成内容，需报告这些变化，不能继续解释为单一资源的改善。差异落在独立重复的不确定范围内时，结论是未区分。

随章 tools/check_k_work_002_full.py 是标准库、只读、离线的确定性事件模型。它从模型输入产生有身份的日志，再用独立给定的时间线和逐请求窗口交集核对发送、准入、业务终态、物理执行、排空与条件化驻留；包含窗口初已有请求、窗口末未完成、零时长失败、同时到达、空输入和重复完成。它还以逐区间流体守恒核对突发公式，用两个相反方向的删失反例核对 Little 窗口说明。

负对照进入同一个审计器：取消后计成功、遗漏拒绝、把发送当准入、发送槽释放后不推进和提前记录物理完成。另有只累计到达、不扣服务的突发错误。检查通过只支持这些模型机制，不证明真实发送器、线程可见性、网络、GPU、时钟映射或端到端 SLO。检查脚本、输入绑定与实际执行结果见[检查记录](../../docs/evidence/knowledge-workflow-20261028-batch9/K-WORK-002/round-2/check-0.json)。
