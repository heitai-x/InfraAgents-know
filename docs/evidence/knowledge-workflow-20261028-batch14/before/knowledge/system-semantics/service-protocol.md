# K-SYS-008：服务协议：接收、流式背压与终止语义

推理服务将内部生成状态映射为可观察的网络事件；接收、执行完成和客户端收到结果是不同的完成点。协议必须定义内容边界、背压责任、终止原因与重试身份，使慢客户端、取消、失败和版本切换能够进入同一条可追溯的状态链。

## 请求、内容与完成边界

设逻辑请求为 q，执行尝试为 g，协议流为 s，固定模型与输入解释档案为 v。q 关联用户的一次逻辑操作，g 区分重试或恢复的实际执行，s 标识承载输出的流。HTTP/2 同一连接可以承载多个请求 scope；一个 WebSocket 连接也可以承载多个应用任务。连接、逻辑请求、尝试与输出流不能共用一个身份。

模型 token 经过固定 decoder、停止规则和输出适配，形成合法内容字节串 C。传输 chunk 可以合并或切分这些字节，不必与 token 一一对应。应用事件携带 `(q,g,v,seq,payload,kind)`；seq 从 0 连续递增，kind 区分内容与元数据。序号属于应用事件，不能要求 ASGI 服务器或代理保留应用每次发送的底层网络分包。

每个尝试分别记录以下前沿。

| 量 | 定义 | 不足以证明的事实 |
|---|---|---|
| accepted_end，A | 已成功进入协议适配层的累计内容字节数 | 已发送或已被客户端接收 |
| committed_end，C_s | 顺序 send 成功返回的累计内容字节数 | 远端应用已经消费 |
| acked_end | 应用协议明确确认的接收前沿；无确认则未知 | 已播放、已展示或已完成业务提交 |
| played_end | 媒体客户端明确确认的播放位置 | 服务端设备资源已经释放 |

A 是累计历史，不因取消丢弃队列而回退。发送前沿只在对应发送成功返回时推进。发送异常可能发生在部分字节已流出之后，因此“未成功提交”不能一律解释为“远端一定没有收到”；失败操作的交付范围需要保留未知状态。不能根据服务器日志中的 C_s 静默重放失败块。

还要区分两个终止对象：业务决定 `terminal` 与终止帧发送状态 `end_state`。业务决定至多一次，原因可为 FINAL、CANCELLED、TIMEOUT、FAILED 或 PEER_CLOSED；终止帧可以尚未开始、发送中、成功提交或发送失败。FINAL 可以表示服务端已正常生成并提交全部内容，但如果结束帧发送失败，客户端仍没有完整成功证据。服务端业务完成数与客户端合格完成数必须分别统计。

本章采用以下不变量。

1. 每次尝试最多确定一个业务终止原因，最多启动一次终止帧发送。迟到完成与重复通知只结算自己的责任，不改变既定原因。
2. 成功接收的应用事件序号连续；内容发送按序启动，客户端成功解析的内容保持合法输出的前缀。正常结束不能越过尚未发送的事件，包括零字节元数据事件。
3. 业务终止后不再接收新内容，也不再登记新的内容发送。终止前已经登记启动的发送仍可在终止后完成；这属于在途结算，不能误判为新内容提交。
4. 字节预算和事件数量都有上限。仅限制内容字节不能约束无限空事件产生的对象和 framing 成本。
5. 取消停止未来生成与提交资格，不证明已提交 kernel、DMA、发送或借用缓冲的最后访问已经结束。物理回收继续依照[取消与完成](cancellation-resource-completion.md)的责任账。
6. 在一个外部事件处理结束的稳定边界，若尚无业务终止且有待发送事件，就必须已有在途 DATA。生成完成通知不能成为启动首个内容发送的必要条件。

## 合法条件与协议选择

固定 ASGI HTTP/WebSocket 规范提供具体的接口边界。

- HTTP scope 覆盖一次请求；HTTP/2 同连接的不同请求应有不同 scope，并复用回各自 stream。
- `http.response.start` 后至少需要一个 response body。服务器可以等首次 body 才将响应头刷入发送缓冲，因此 start 的 send 返回不能命名为“客户端已收到响应头”。
- `http.response.body` 的 send 返回前，数据必须进入服务器发送缓冲；它不确认远端消费。`more_body=false` 且没有声明 trailers 时完成响应；声明 trailers 时，还需履行 trailers 契约。
- 关闭连接上的 send 应抛出服务器特定的 OSError 子类，但该行为自子规范 2.4 引入，旧实现未必保证。并发代码可能先遇到 send 异常，之后才收到 disconnect。
- WebSocket connect 必须先得到 Accept 或 Close，才能继续传递 receive 数据。接受前 Close 会拒绝握手并返回 HTTP 403。连接内多任务的取消、序号和终态仍由应用定义。

本章算法选择无 trailers、应用结束标记随最终 body 发送的协议子集。普通 HTTP body、SSE、增量 JSON 和 WebSocket message 需要各自的编码器；不能将抽象终止帧当作 ASGI 自带的业务事件。使用 trailers 或多路业务消息时，应扩展对应状态，而不能提前把 body 结束当作全部协议完成。

逐 token 推送降低适配层等待，却增加事件数、编码、唤醒与 framing。按时间窗或语义块合并减少调用次数，但推迟首内容和尾部交付。短输出且允许等待时，整段请求—响应同样合法；需要持续输入与打断时可以使用双向协议。流式传输本身不降低模型首内容计算时间，双向连接本身也不提供会话一致性。

字段兼容必须覆盖行为：缺省值、显式空值、非法值、采样默认值、工具调用结构、usage、停止原因、取消和错误格式。未实现参数应拒绝或按已披露规则处理。最大输出 token 数与输入加输出的上下文上限分别核对；文本与 token ID 入口必须固定 tokenizer、模板和特殊 token 规则，见[输入输出语义](tokenization-io.md)。

停止串可能跨 token 或 chunk。若契约不展示停止文本，输出适配必须先完成停止判断，再接收可交付字节，不能先发送后从最终字符串删除。usage 应说明是否包含停止内容、丢弃候选和取消后的在途计算；它不等于客户端收到的内容长度。

## 接收、准入与重试身份

入口先确定可信租户身份、协议能力和规范化输入，再决定是否接受执行。规范化摘要 d 覆盖实际决定函数的模型、adapter、processor、模板、输入、采样与约束配置。仅比较文本会漏掉版本或默认值变化。

有幂等键时，命名空间至少为 `(tenant,key)`；没有键的请求各自获得独立身份，不能把所有空键放进同一去重记录。以下为一种明确的接受策略。

```pseudocode
算法 Admit(meta, normalized_input)
输入：可信租户、可选幂等键、输入摘要 d、版本 v、deadline、资源需求
输出：拒绝信息，或唯一拥有准入责任的尝试 (q,g)

验证协议子集、参数范围、输入上限与 deadline
若非法：返回 REJECT，说明未启动模型工作

若存在幂等键：
    在权威记录域内原子执行：
        若 (tenant,key) 已存在：
            若摘要不同：返回 CONFLICT
            若记录仍活跃：返回 IN_PROGRESS，关联原 q 与 g
            若记录已结束：返回其结果状态或契约允许的重放入口
        否则创建 {q,g,d,v,ADMITTING}
否则创建独立的 q 与 g

取得版本 v 的就绪引用，并预留准入所需的资源额度
预留必须返回具体责任句柄；不能只检查余额后再无条件扣减
若版本或容量不满足：
    撤销本次已取得的全部预留与引用
    将本次接受决定记为 REJECTED，保留是否可重试的原因
    返回拒绝信息

在同一责任域内将记录推进为 ADMITTED
将身份、版本、deadline、取消通道和缓冲责任交给执行路径
返回 (q,g)
```

原子创建防止两个重复提交同时启动。它不等于跨进程崩溃后的持久恢复协议；若要求该保证，记录持久性、执行授权与故障恢复必须共同实现。本章不以一个内存字典证明分布式恰好一次。

同键同摘要的活跃请求返回进行中，不能启动第二次生成。同键不同摘要必须冲突。结束后是否重放完整输出、只返回状态或要求新键，由接口明确规定；准入拒绝后也不能静默删除记录并使并发重试意外变为第二个接受决定。允许的重试窗口、记录容量与 TTL 必须一致，活跃记录不能仅因普通 TTL 到期就丢失唯一性。

恢复已确认前缀需要输出游标和前缀身份，并保存相容的模型、输入、随机、停止及输出状态。没有客户端确认时，只能披露接收未知或可能重复，不能由 send 返回推断恢复位置。请求 ID 和 trace ID 都不是授权凭证。

## 有界输出与单写者发送算法

采用一个串行状态拥有者处理 Offer、生成结束、取消、deadline 和发送完成事件。网络等待不占住状态锁：状态域先登记一个发送票据，再由适配器异步发送，完成事件回到状态域结算。每条流最多有一个在途发送，因此不需要用乱序完成猜测连续前沿。

设字节容量为 Q，低水位为 L，事件容量为 M，事件低水位为 J，满足 `Q>0，0≤L<Q，M≥1，0≤J<M`。事件 e 的计费大小 w(e) 包括实际保留的编码缓冲；内容字节长度另记为 b(e)。合成检查用 `w(e)=b(e)`，生产系统还需计对象、编码膨胀与副本。

队列占用包括待发送事件和在途内容事件，后者直到发送访问结束才归还额度。暂停采用滞回：一次接收因容量不足被拒绝后，必须等字节与事件占用都降到低水位，才允许重新接收；“下一小块已经能装下”不是恢复条件。

Offer 的成功顺序是先完成所有权转移和累计前沿更新，再调用 Drive，最后返回 ACCEPTED。Drive 只登记发送，不等待网络。即使适配器立即成功或失败，结果也必须排成后续完成事件，不能重入尚未返回的 Offer。启动适配器时的异常同样转成该票据的失败完成；不能在已接收后向生产者返回 PAUSED，让同一块被重复提交。

```pseudocode
算法 StreamAttempt(q,g,v,Q,L,M,J)
输入：按固定输出语义产生的事件、生成结束、取消/超时、发送完成
输出：顺序内容发送、唯一业务终止、交付状态与资源责任结算

初始化：
    pending = 空 FIFO
    inflight = NONE
    settled_ids = 空集合
    next_seq = 0；next_send_id = 0
    accepted_end = 0；committed_end = 0
    discarded_bytes = 0；uncertain_bytes = 0
    paused = false；resume_epoch = 0；producer_done = false
    terminal = NONE；end_state = NOT_STARTED
    delivery = UNKNOWN

函数 Occupancy()：
    返回 pending 与在途内容事件的计费字节和、事件数

过程 Offer(payload,kind)：
    若 terminal != NONE：返回 TERMINAL
    若 producer_done：返回 PRODUCER_CLOSED
    构造有界事件 e，其内容长度为 b，保留成本为 w
    若 w>Q：返回 TOO_LARGE；调用者拆分或明确失败
    (bytes,count) = Occupancy()
    若 paused 且 bytes<=L 且 count<=J：paused=false
    若 paused：返回 (PAUSED,resume_epoch)，不分配 seq、不增加累计前沿
    若 bytes+w>Q 或 count+1>M：
        paused=true
        返回 (PAUSED,resume_epoch)，不接收该事件
    e.identity=(q,g,v,next_seq)
    next_seq += 1
    pending.Append(e)
    accepted_end += b
    此处 e 的持有责任已转入协议层；生产者不得再修改或重送它
    Drive()
    返回 ACCEPTED

过程 ProducerDone()：
    若 terminal != NONE 或 producer_done：只记重复/迟到诊断
    否则 producer_done=true
    Drive()

过程 Decide(reason)：
    若 terminal != NONE：只记诊断，返回既有 terminal
    若 reason==FINAL：
        若 not producer_done 或 pending 非空 或 inflight!=NONE：返回 WAIT
    terminal=reason
    paused=false
    若 reason!=FINAL：
        将 pending 全部移入 discarded，累计其内容字节
        清空 pending，归还其不再被读取的缓冲额度
        撤销未来生成与接收资格，通知模型协作停止
    唤醒容量等待者，使其观察终止而不是继续等待恢复
    已有 inflight 继续保留，直到其实际访问结束
    发出幂等的业务终止通知；设备与借用缓冲另按责任票据清理

过程 Launch(kind,event_or_reason)：
    要求 inflight==NONE
    id=(q,g,next_send_id)；next_send_id+=1
    原子登记 inflight={id,kind,event_or_reason}
    若 kind==END：end_state=SENDING
    在状态域外启动适配器发送：
        必要时恰好发送一次 Response Start
        DATA：编码并发送该事件，more_body=true
        END：编码 terminal 与 usage，最终 body 的 more_body=false
    将成功或失败携带原 id 排入后续状态事件；不在持锁状态等待网络

过程 Drive()：
    若 inflight!=NONE：返回
    若 terminal==NONE：
        若 pending 非空：
            e=pending.PopFront()
            Launch(DATA,e)
            返回
        若 producer_done：Decide(FINAL)
    若 terminal!=NONE 且 end_state==NOT_STARTED 且 delivery!=BROKEN：
        Launch(END,terminal)

过程 OnSendComplete(id,result)：
    若 id 已结算：只记重复诊断，返回
    若 inflight 不匹配 id：只记身份错误，保留现有责任，返回
    op=inflight；inflight=NONE；将 id 加入 settled_ids
    若 op.kind==DATA：
        若 result 成功：committed_end += op.event 的内容长度
        否则：
            uncertain_bytes += op.event 的内容长度
            delivery=BROKEN
            若 terminal==NONE：Decide(PEER_CLOSED)
        仅按该发送的真实访问结束契约释放对应缓冲
    否则：
        若 result 成功：end_state=SUBMITTED
        否则：end_state=FAILED；delivery=BROKEN
    若 terminal==NONE：
        (bytes,count)=Occupancy()
        若 paused 且 bytes<=L 且 count<=J：
            paused=false
            resume_epoch+=1
            发布容量恢复通知，携带 resume_epoch
    Drive()

过程 WaitForCapacity(observed_epoch)：
    在同一串行状态域内检查并登记等待：
        若 terminal!=NONE：立即返回 TERMINAL
        若 not paused 或 resume_epoch!=observed_epoch：立即返回 RETRY
        否则登记等待者，之后由恢复或终止通知唤醒
    等待发生在状态域外；醒来后重试原未被接受的事件

过程 Cancel、Deadline、ModelFailure 或 Disconnect：
    分别 Decide(CANCELLED)、Decide(TIMEOUT)、Decide(FAILED)、Decide(PEER_CLOSED)
    Disconnect 同时标记 delivery=BROKEN
    调用 Drive()
```

Launch 的票据登记是本章发送启动的线性化点：登记后由适配器履行这张责任，取消不再将它作为尚未启动的 pending 丢弃。实际系统若还要在另一个执行域撤销已登记但尚未执行的发送，应另给交接与撤销协议，不能直接归还其缓冲。

适配器持有自己的 start 已发送状态；start 成功返回仍不证明响应头已刷出。start 或 body 任一步失败，都结束该发送操作，不盲目重发。实际异常若不能证明借用访问已经结束，应继续保留物理责任；上面完成事件的释放分支只适用于已给出最后访问证据的适配器。

正常发送时，累计内容满足 `A=C_s+P+I+D+U`：P 是 pending 内容字节，I 是在途内容字节，D 是从未启动发送便被丢弃的内容，U 是失败发送中交付范围未知的内容。正常 FINAL 时 P、I、D、U 均为零。这个式子是责任分类，不是远端接收字节公式；U 的全部内容长度只表示未知操作覆盖范围。事件数也应做同样分类，才能覆盖零字节事件。

业务终止与发送完成的两个顺序都合法。若先取消、后完成已启动的 DATA，既定原因保持 CANCELLED，结算该 DATA 后才尝试结束帧。若 DATA 失败先被处理，则 PEER_CLOSED 获得业务终止，之后取消只记诊断。若全部内容排空后先选中 FINAL，随后结束帧失败，业务决定仍为 FINAL，交付标为 BROKEN；客户端成功统计不能把它计入完整 FINAL。

生成结束后禁止再次 Offer，避免 done 与最后一块接收竞争。最后一块必须先被接受，再发布 ProducerDone；被 PAUSED 拒绝的块仍归生产者，等待恢复后重试，不分配新 seq。容量通知不预留额度，醒来仍要重新检查。检查状态与登记等待必须在同一状态域完成，否则恢复恰好发生在两者之间时可能丢失唤醒。空输出直接从 ProducerDone 到 FINAL；TTFT 未定义，不能写成零。空元数据事件可以入队，但占事件额度，也必须在 FINAL 前排空。

数据队列满不能阻断取消与发送完成通知。控制事件应有可达且能获得处理机会的路径，状态域也不能被同一个阻塞发送占住。协议暂停还必须传到实际生成边界：若模型已提前提交 K 份工作，需要给这些在途结果预留有界空间。仅在 Offer 拒绝时设置标志，却继续无界生成和编码，不构成端到端背压。

## 滞回轨迹、反例与成本

取合成参数 `Q=8 B，L=4 B`，事件容量暂不成为瓶颈。内容块长度依次为 `3、3、2、1、1、3、2 B`，总计 15 B。以下相邻 Offer 之间暂不投递发送完成；发送启动本身不归还额度。

| 动作 | 未提交占用 | 接收结果、发送与暂停状态 |
|---|---:|---|
| 接受 seq 0，长度 3 | 3 B | Offer 内启动 DATA 0；生产者尚未完成 |
| 接受 seq 1、2 | 8 B | DATA 0 仍在途，另外两块 pending |
| 尝试 seq 3，长度 1 | 8 B | PAUSED，进入滞回 |
| DATA 0 成功完成，再尝试 seq 3 | 5 B | 完成回调启动 DATA 1；仍 PAUSED，虽然 5+1≤8 |
| DATA 1 成功完成，再尝试 seq 3 | 2→3 B | 发布恢复通知并启动 DATA 2；重试被接受 |
| 接受 seq 4、5 | 7 B | 继续接受，不启动第二个并行发送 |
| 尝试 seq 6，长度 2 | 7 B | PAUSED |
| DATA 2 成功完成，再尝试 seq 6 | 5 B | 回调启动 DATA 3；仍 PAUSED |
| DATA 3 成功完成，再尝试 seq 6 | 4→6 B | 第二次恢复，回调启动 DATA 4，重试被接受 |
| 发布 ProducerDone，继续投递已有发送的完成 | 逐次降到 0 B | DATA 4、5、6 依次完成，最后启动并完成 END |

这条轨迹包含四次 PAUSED 返回、两次恢复和七次 DATA 启动。将“有空间即可接受”作为参考，会把两次合法暂停误判为失败；删除滞回是另一种策略，不能冒充原策略的修复。相反，在占用 8 B 时仍接受 1 B 才是真正的超限反例；接受第三块 2 B 后恰好达到 8 B，并没有触发溢出。

发送推进还有一个独立的反例：删除 Offer 成功尾部的 Drive，依次接收 3、3、2 B 后占用达到 8 B，下一块 1 B 返回 PAUSED。此时 pending 非空、inflight 为空、发送启动数为零。生产者不能发布 ProducerDone，传输也没有可以完成的已启动操作，合法有限输出便停滞。测试驱动此时直接取走队列或调用 flush，会掩盖缺失的启动依赖。

修订后的推进可以按事件归纳：首次成功 Offer 在返回前登记 DATA；后续 Offer 若已有 inflight，只增加 pending；每次成功 DATA 完成先结算旧票据，再通过 Drive 启动下一个 pending。因此暂停不阻止排空，生成结束也不是排空前提。在有限合法事件、生产者收到恢复后会重试、适配器操作最终完成且完成事件公平处理的假设下，队列最终下降到两个低水位，最后一块能够被接收并完成 FINAL。网络永久不返回、控制事件被饿死或生产者不重试时，这个条件化活性结论不成立，应由 deadline、断开证据或明确的失败策略处理。

令 q(t) 为同一队列边界的计费字节占用，生产与出队速率为 r_p、r_d，单位均为 B/s。暂未暂停且 `r_p>r_d` 时，从初始 q0 到容量 Q 的流体近似为 `t_full=(Q-q0)/(r_p-r_d)`。有限大块可能因装不下而提前阻塞，事件数量也可能先达到上限；这个式子不替代离散接收规则。这里的出队须对应额度真正归还的完成边界，不能只计从 pending 移到 inflight。

设定入队 8000 B/s、出队 2000 B/s、初始零、容量 65536 B，则净增长 6000 B/s，约 10.92 s 到达容量。这是设定算例。远端客户端消费 2000 B/s 不足以推出本地出队也是该值：服务器、TLS 或代理仍能先吸收字节。只有背压已经传到所观察队列，才可使用同边界的 r_d。

从高占用 q_hi 排空到 L 的暂停时间，在无新入队且 r_d 稳定时近似为 `(q_hi-L)/r_d`；事件低水位可能再增加等待。降低 L 会减少短周期启停，但增加恢复等待和保留状态的时间。若背压传播延迟为 τ，且额外生产速率有界为 r_p，还需容纳约 `r_p τ` 加最大在途突发的结果，或在启动前取得信用额度；没有这项上界，就不能从本地 Q 推出全路径内存有界。

各类成本分别列账。

- 准备：规范化、输入摘要、协议能力校验和幂等查询；摘要扫描成本随实际输入字节增长。构造编码帧还可能产生转义膨胀与临时副本，容量检查前的暂存也要有界。
- 计算与同步：N 个事件的固定编码、排队、锁或消息处理、唤醒成本，加随内容字节增长的工作。终止判定、发送开始和完成结算需要一致顺序，跨域后还需 IPC 与上下文切换。Offer 调用 Drive 只增加本地状态判断及至多一次发送登记，不把网络等待串入生产者持锁时间。
- 访存：复制路径每复制 D 字节，逻辑上至少读取与写入各 D 字节；若有 k 次复制，约为 2kD 的逻辑搬运，不能直接称为 DRAM 事务或设备实测。借用减少复制，但延长原缓冲责任。
- 通信：编码内容 D_enc 与每事件封装 h 形成约 `D_enc+N h` 的应用传输量，底层分包、重传和压缩另计。固定有效带宽下，传输服务时间有相应字节/带宽下界。
- 驻留：输出缓冲、事件对象、在途编码副本、连接状态及暂停请求的 KV/其他私有状态。它们按真实物理并集计数，共享存储不重复相加。

若每事件 CPU 时间为 c_e、每字节处理时间为 c_b，则串行编码服务需求约为 `N c_e+D_enc c_b`。编码与发送串行时按依赖相加，充分流水时受两阶段较慢者及共享资源限制；不能把独占吞吐和理想重叠同时用于同一预测。连接等待消耗墙钟与驻留，不应直接记成 CPU 秒或设备秒。

128 个请求各保留 64 KiB 输出，仅该层为 8 MiB；每个请求另有设定的 6 MiB 私有模型状态，则还有 768 MiB。暂停生成不释放这些状态。实际 Q 若只含 payload，还须增加最多 M 个事件的元数据及在途副本；若 Q 已包含同一编码缓冲，则不能再次把它加进峰值。

伪代码的 settled_ids 若逐项保留到流结束，会另有 O(N) 的票据历史。单写者、单在途且发送 ID 严格递增时，可用连续已结算水位识别旧完成，将常驻去重状态压缩为常数；详细历史若用于审计，应采用有界或外部记录。Q 和 M 本身不约束无限保留的日志与诊断集合。

幂等记录也有容量。N_id 条、每条 s_id 字节，占用约 `N_id s_id`；缓存完整结果重放还增加输出副本。记录到达率 λ_id 与保留期 T 可以估计稳态数量，但还需硬容量和活跃记录规则，不能依靠 TTL 宣称无条件有界。

## 慢消费、取消、重试与发布的组合

以下是一条设定轨迹，不是服务实测。尝试 g1 已提交 seq 0、1，seq 2、3 等待发送；之后 seq 2 开始发送，在途操作持有自己的票据和缓冲。客户端取消先进入状态域，业务原因成为 CANCELLED，seq 3 被丢弃，后续生成资格撤销，但 seq 2 的额度不能提前归还。

若 seq 2 随后成功返回，C_s 包含它；这证明终止前启动的操作已进入服务器发送缓冲，不证明客户端已消费。适配器可以随后发送 CANCELLED 结束帧。若 seq 2 失败，则其覆盖范围进入未知交付，连接标记 BROKEN，CANCELLED 原因不变，也不再假装已经发送结束帧。重复完成只命中同一票据，不得归还另一发送的额度。

用同一字节预算可以复算一条最小取消轨迹：连续接收 3、3、2 B，首个 3 B 已在途，其余 5 B pending。此时取消，只能立即丢弃 5 B，仍保留 3 B 在途责任。若该发送成功，最终 `A=8，C_s=3，D=5，U=0`；若失败，则 `A=8，C_s=0，D=5，U=3`。两者业务原因都保持 CANCELLED，后一种没有可用连接提交结束帧。若发送失败先于取消被处理，业务原因则为 PEER_CLOSED。不能先排空全部内容，再声称该实验验证了取消时丢弃 pending。

客户端随后用同一幂等键重试，应得到原尝试状态或契约允许的恢复入口。没有确认游标时，从头发送可能重复内容，从 C_s 后继续也可能漏掉客户端未收到的内容。因此重执行与断线续传是两种不同承诺。音频还需区分接收与播放；服务端停生成后，客户端播放队列可能继续发声，打断体验需客户端丢弃旧代次未播放数据，见[语音生成](../models/speech-generation.md)。

选择持续暂停、限时终止或断开慢消费者，取决于恢复时间分布、请求价值、共享状态压力与交付承诺。快速恢复且状态充裕时可保留暂停；大量暂停请求挤占 KV 并伤害正常请求时，应调整准入、暂停期限或交付方式。静默丢弃未声明可丢弃的内容会改变任务语义。

HTTP/2 或 WebSocket 多任务共享连接后，单流额度仍需与连接总额度共同约束。每流有界不能阻止无限创建流；共享发送器也可能使一个慢流影响其他流。应同时检查每流、每租户和连接总预算，不能仅限制连接数。

滚动发布先撤销旧实例的新准入，再排空已有请求。新请求只能绑定已就绪版本，旧流保持原版本和顺序。新实例预热失败不能计入可接收容量；关闭监听端口不证明旧请求、IPC、发送及设备访问已经结束。最长排空时间到期后，按同一状态机终止或按另有证明的协议迁移，不临时发出伪造 FINAL。插件升级建议排空 GPU 任务，也不等于插件负责完成业务流或资源清理。

请求上下文可以跨入口、输入处理、调度、执行与响应传播。OpenTelemetry 提供关联机制，batch 与请求的多对多映射还需附带身份。只记录必要的版本、序号、摘要和责任事件即可支持许多诊断；trace 结束不能充当网络接收或设备完成证书。

## 竞争解释与区分实验

| 观察与竞争解释 | 可控干预与预测 | 反证后的修正 |
|---|---|---|
| 首内容一直不发送：生成尚未完成、接受后未推进或适配器阻塞 | 生产者尚未完成时只接受一块，分别记录接受、发送登记和完成；再填满队列 | 接受后无发送登记支持推进缺失；有登记无完成才继续检查适配器。外部直接 flush 会破坏这项区分 |
| 客户端 TTFT 高：模型慢、stop 等待、发送聚合、代理缓冲或解析慢 | 固定输入与模型，记录首稳定内容、入队、send 返回、代理转发与首有效客户端事件；只改变刷新策略 | 模型时间未变而客户端改善，不能归因模型加速；沿首个变化边界修正 |
| 小块明明能装下却暂停：合法滞回或恢复通知遗漏 | 固定 Q=8、L=4，在占用 5 与 4 时各尝试同一小块，并记录恢复代次 | 5 时暂停、4 时恢复支持滞回；状态已恢复但生产者仍睡眠，检查等待登记与通知竞争 |
| 输出字节有界而内存仍增长：空事件、编码副本、暂停状态或日志历史 | 固定 payload 总字节，增加空事件数；再分别限制事件数、在途副本、历史和活跃请求 | 随空事件数增长支持元数据预算缺失；随暂停请求数增长先核对私有状态 |
| send 成功但客户端缺内容：代理截断、结束帧丢失或接收确认口径错误 | 内容提交后、结束帧前后分别断开，比较服务端与客户端日志 | 服务器成功不能覆盖客户端缺少结束标记；保留交付未知 |
| 取消后仍见发送完成：合法在途结算或取消后启动了新发送 | 延迟一条已登记 DATA 的完成，再取消；另在取消后尝试登记新 DATA | 原票据可结算，后者必须拒绝；不能只按完成时间判定违规 |
| 取消后资源不归还：设备在途、发送借用、控制阻塞或泄漏 | 分别延迟设备最后访问、发送访问结束和完成通知处理 | 归还随哪项延迟变化就查哪条责任；业务终态不能代替物理完成 |
| 重试重复输出：去重失败、明确重放或失败发送已部分交付 | 同键同摘要、同键不同摘要、结束后重放及发送异常后重试分别对照 | 第二次活跃生成支持去重错误；合法重放仍需披露重复，不称恰好一次 |
| 慢流影响正常流：共享发送器、连接总额度、KV 或执行域竞争 | 一个慢客户端与一个正常客户端并行，分别改变输出额度、状态额度和执行域 | 只有输出额度改变时恶化支持输出共享解释；只随 KV 改变则调整暂停驻留模型 |
| 200 被当作完成或空事件降低 TTFT | 分别注入首内容前失败、首内容后失败、空角色事件与空输出 FINAL | 200 不能替代完整结束；空输出 TTFT 未定义，元数据不算首有效内容 |

条件变化后保留的是身份、顺序、容量和完成证据；可以调整的是块大小、水位、合并窗口、复制/借用、等待期限与执行域。输出变成音频或视频时，保留字节预算还不够，需增加可播放区间和时间额度；改用双向连接时，需增加回合与打断身份。若测量反驳原来的瓶颈预测，先修正解释，再选择优化。

## 检查方法、统计与证据范围

配套文件为 `tools/check_k_sys_008_full.py`，只使用 Python 标准库，确定性、离线、只读。被测模型保存 pending、单个 inflight 及累计计数；独立审计从接受、发送登记、完成和终止历史重建事件集合，不读取被测 FIFO 或占用计数来决定参考接收结果。每个外部事件结束后比较状态快照，同时检查稳定边界的推进义务。固定七块预期序列另外核对滞回行为。

模型中的假适配器只在 Launch 时获得一个操作。测试驱动只能投递这些已登记操作的完成，不直接取走 pending，不调用内部 Drive，也不额外 flush。专门的 3、3、2、1 B 回归要求第一次接受就在 ProducerDone 之前启动 DATA；队列满后，第一项完成留下 5 B 并维持暂停，第二项完成留下 2 B 并恢复，之后原块重试成功。删除 Offer 中的 Drive 或删除完成回调中的 Drive，都必须被同一稳定边界规则检出。

检查还构造不同容量与低水位、空输出、零字节事件数量限制、生成结束后的接收关闭、FINAL 排空屏障、取消时仍有 pending 和在途数据、旧票据重复与错误身份、DATA 失败、END 失败、取消与完成的两个事件顺序，以及单块过大。取消例在未完成任何 DATA 时取消，再结算已启动的 3 B，核对立即丢弃 5 B 与在途占用没有混算。

故障变体实际删除发送推进、接收后丢块、超过容量仍接受、忽略滞回、重复结算完成字节或提前 FINAL，交给同一审计规则拒绝。正常模型必须先通过，负对照还要命中预定错误条件，不能借正常路径已有错误冒充辨别力。

这个检查验证的是单流、串行事件处理、操作完成具有完整访问结束证据的有限逻辑模型。它将网络和最后访问抽象成可控制的完成事件，不实现真实 ASGI 适配器、线程等待唤醒、传输分包、借用内存可见性、幂等存储或崩溃恢复。真实服务仍需控制取消、DATA 完成、disconnect 与 END 发送的顺序，检查票据和实际访问覆盖是否一致；有限模型不能证明网络最终一定取得进展。

系统检查保留 offered 全体、拒绝、准入、取消、超时、失败和未完成请求。设定 10 s 内发出 100 请求，其中 10 拒绝、90 接受；80 在窗口内完成、10 未完成；完成者中 72 满足预先声明的全部约束，则合格完成率为 7.2 请求/s，合格占 offered 比例为 72%。只保留完成请求会改变分母；窗口后继续观察未完成结局，并区分稳态与排空阶段。

固定 GenAI-Perf 文档以首个 response 定义 TTFT，以符合指标约束的完成请求率定义 goodput。任务若要求首个有效内容、质量或协议完整性，需要明确增加相应判据，核对解析器实际计入的事件。修改刷新、代理或事件格式后重新核对映射，同名字段不保证同一观察边界。

检查通过须绑定实际运行的脚本字节与记录，旧脚本的通过不能代替改动后的执行。这些检查属于有限 CPU 协议模型；它们不是 ASGI 服务器、网络、GPU、KV 回收或性能实测，也不证明知识改善了 Agent 的构建效果。真实设备最后访问、HTTP/2 多路复用、WebSocket 多任务、客户端播放和滚动发布仍需各自证据。
