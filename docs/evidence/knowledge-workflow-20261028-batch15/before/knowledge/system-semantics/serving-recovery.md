# K-SYS-014：推理服务恢复：提交边界、执行组与重试身份

恢复首先要确定哪些工作已经成为外部可依赖的结果、哪些状态仍可信，以及谁有权继续提交。检测到超时或重新启动进程，都不能独立回答这些问题。

## 三个边界分别记录

计算边界表示哪些输入位置已经生成完整模型状态；确认边界表示投机/搜索后哪些 token 属于保留路径；外部提交边界表示服务已经按协议发布的内容。它们可能不同。prefill 末行可以产生一个 token，但该 token 自身的 KV 未必已经计算；网络发送返回也不等于客户端已消费。

恢复描述至少包含请求与尝试身份、模型/adapter/输入配置、已确认 token、可重建的共同状态位置，以及需要继续的随机、grammar 和输出状态。只保存 KV 字节无法恢复任意请求；只保存 token 也不自动恢复任意递归模型、分支状态或已经发生的外部动作。

可重算的模型状态与不可重复的业务结果分开处理。固定前缀可以帮助重建 KV，但跨 backend 重算是否逐位一致取决于数值契约。若协议需要断线续传，应有明确的游标、去重与确认规则；否则应报告失败或重新请求，不能默认已经获得“恰好一次”交付。

## 故障矩阵决定恢复路线

| 故障位置 | 首先确认 | 合法的恢复或终止方式 |
|---|---|---|
| 输入处理进程失败 | 是否已准入、输入是否可重放 | 从固定输入重做未提交部分，清理预留 |
| 单个计算 rank 退出 | 执行组是否还拥有一致状态 | 停止受影响组，从共同提交点重建或明确失败 |
| KV 传输部分完成 | 目标范围和源副本的有效性 | 撤销未提交目标，重传或从可恢复前缀重算 |
| 源在接管期间失效 | 目标是否完成且已获提交权 | 按协议完成接管；否则使用其他副本或重建 |
| 磁盘/压缩读取失败 | 哪些对象可重建、哪些记录必须保留 | 失效对应缓存；不能把未完成解码当作可用状态 |
| 客户端断线 | 哪些内容已发出、协议能否确认消费 | 依协议取消、续传或失败，不猜测客户端进度 |

每条路线同时说明输出处理和资源清理。最后一个错误通常只是连锁超时，诊断要保留最早失败、rank 状态、操作序号和已经完成的范围。

## 执行组恢复与单请求恢复不同

TP/EP 等组内的 ranks 必须执行相容的操作序列。一个 rank 的失败不能让其他 ranks 继续把局部结果当作完整层；请求取消也不能让某个 rank 单独跳过 collective。根据固定通信库的错误处理契约终止或重建受影响资源，并让调度器停止向失效组提交新工作。

重建可以重新加载模型、重建 communicator/执行上下文，再恢复合法状态。已经失效的设备句柄、注册区、页表和图对象不能仅因地址看起来相同就继续使用。较大的执行组能处理更大模型，但故障影响范围与恢复时间也随组织方式改变。

## 迁移期间只允许一份提交权

[Llumnix v1](../sources/S-LLUMNIX.md) §4.2 描述了分阶段复制、目标预留和迁移异常处理；它利用 append-only KV 隐藏部分复制时间。窗口覆盖、递归状态和可回滚分支不自动满足这个前提，需冻结或另行保存恢复版本。

应用需要明确源端何时停止提交、目标何时获得提交权，以及确认丢失时如何判断。新尝试带独立代次，旧节点的迟到消息不能重新获得当前请求的提交权。多个控制节点也必须提供一致的授权规则，不能各自根据本地超时决定同时接管。

最后源副本释放与目标提交之间的窗口必须有恢复依据。可以保留源直到确认、依赖已经完整的其他副本，或允许从持久输入重算；选择取决于故障模型与成本。内存内迁移本身不能保证机器同时失效后仍有持久恢复能力。

## 重试预算和过载反馈

重试可能与原任务同时消耗资源，且常发生在系统已过载时。控制并发尝试、总时间预算和退避，避免把一次网络或节点故障变成请求放大。幂等传输 ID 处理重复范围，逻辑请求 ID 处理重复提交；它们是不同层次。

恢复后需重新检查 deadline、质量和容量。如果剩余时间已无法满足任务，不应无条件重试直到某次成功再隐藏此前失败。故障恢复实验与正常稳态性能分开报告，也要度量恢复期间对其他请求造成的影响。

## 验证可观察的不变量

在预留后、部分传输后、目标发布前后、输出提交前后分别注入失败。检查请求终态唯一、输出序号连续、旧代次不覆盖新状态、未完成缓冲不被复用，以及资源最终回到声明的稳态基线。对随机生成，明确要求相同轨迹还是相同分布；对可重算缓存，检查恢复位置和其他状态族的交集。

低失败率、短请求可能适合失败后重做；长请求、严格交互连续性或昂贵状态可能需要更多检查点、副本与接管协议。多种方案都要把恢复成本计入 SLO 与容量，而不是只比较无故障时的速度。
