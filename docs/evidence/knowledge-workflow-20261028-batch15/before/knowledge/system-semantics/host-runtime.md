# K-SYS-015：服务主机运行时：执行域、队列与缓冲所有权

推理服务的 CPU 工作包括接收与解析、tokenization、调度、张量准备、提交、结果处理和响应编码。它们有不同的阻塞方式、并行度和生命期，必须与模型算子共享同一份主机资源预算。

## 问题、不变量与设计轴

问题：设备每步只需要主机提交几次工作，但主机还要同时处理连接、分词、调度决策、采样后处理和响应编码；这些工作有的阻塞在 I/O，有的占满一个核，有的必须与设备完成事件同步。要回答的是"哪些工作放在哪个执行域，域之间用什么通信、容量多大，缓冲属于谁、何时可回收"。

不变量：每个阶段的队列有界，溢出有明确的拒绝或等待语义；缓冲在同一时刻只有一个写者，跨域传递时所有权转移；取消能到达等待中的任一阶段；主机总 CPU 与内存不超过实际额度（容器 quota、cpuset）；设备提交不被与设备无关的主机工作阻塞。

成本项：跨域通信（锁、队列、IPC 序列化）、上下文切换与缓存污染、每阶段服务时间与并行度的乘积、缓冲驻留（对象大小 × 同时存活数）、以及为了隔离付出的额外进程与复制。

设计轴：执行域划分（单事件循环 / 线程池分阶段 / 多进程 / 混合）；通信方式（共享内存队列 / 管道 / 消息）；队列容量的依据（对象大小与存活范围 / 固定深度 / 按时间）；背压方向（上游拒绝 / 下游丢弃 / 两端协商）；设备提交线程（专用 / 与调度合一）。单进程事件循环加专用提交线程是小 batch 交互服务的常见点；多进程分词与编码在 CPU 占比高时出现。轴上未列点同样合法。

## 何时重新设计执行域

从单请求实现扩展到多请求服务，或观察到设备空闲但请求仍在等待、长输入延迟其他连接、增加 worker 后尾延迟反而上升、取消无法到达等待中的阶段时，主机运行时提供一组可调查的机制。每阶段的工作量与服务时间、真实 CPU/内存额度、原生库线程、设备提交方式和队列占用，可以随原型、profiling 与实验逐步获得，用来区分阻塞、资源争用和通信成本。

执行域划分改变共享状态的更新与协调方式、跨域消息的字节、借用缓冲的生存期以及关闭时的未完工作。顺序执行、锁或原子操作协调的共享状态、消息传递可以形成不同实现，其取舍来自实际争用、搬运和错误传播成本。外部可观察行为见 [服务协议](service-protocol.md)；具体文件和符号位置由当前实现确定。

## 执行域与有界通信

事件循环适合协调大量等待中的连接和完成通知；一个长时间占用该执行域的解析或分词任务会延迟其他连接处理。线程池可以隔离阻塞工作，但是否获得 CPU 并行还取决于运行时和所调用的原生库。进程池增加隔离和独立执行能力，同时引入 IPC、序列化、地址空间和模型副本问题。线程数或进程数本身不是吞吐量。

一个可分析的划分是：网络接入处理请求；输入处理形成带身份的 token/模态张量；调度组织就绪工作；模型执行消费资源；响应处理交付结果。这些是可合并或拆分的责任，既可以在同一调用链完成，也可以跨线程或进程。跨域后，需要解释请求与数据如何对应、谁可更新共享状态以及何时可重用缓冲；具体协调机制随设计变化。

推进方式也可单独选择。由调用方驱动一次工作并消费结果，便于控制观察点；长期执行域接收请求并持续推进，则可能重叠准备、设备执行与结果处理，同时增加排队、通知和在途状态。两种方式都可以支持批处理，也可以混合使用。把同步调用改成返回等待对象，本身没有增加独立工作；收益取决于哪些依赖可以重叠，以及为此增加多少缓冲和协调成本。

任务要求在过载下保持资源有界时，需要约束能够同时进入各阶段的总在途工作。队列容量、上游准入、端到端额度或其他资源管理机制都可以承担这一作用，不必为每条队列设置独立上限。计量单位可以是项数、字节、token 或估计工作量；仅限制请求数会把 100 个短提示与 100 个长视频当作相同负载。若上游生产速率持续高于下游消费速率且没有其他限制，持续积压会增加内存和尾延迟。达到所选预算边界时，可以等待、拒绝或采用任务允许的降载方式，同时保持 deadline 与取消的可达路径。

## 统一计算 CPU 与内存预算

设阶段 j 每请求平均消耗 cⱼ 个 CPU 秒，分配 pⱼ 个有效核，单看该阶段的稳定性必要条件为 λcⱼ<pⱼ。它忽略了方差和排队，因此不足以保证尾延迟。多个阶段共用 CPU 时还要满足总预算，另计模型内部线程、垃圾回收、通信和操作系统工作。

设定 tokenization 每请求占用 8 ms CPU，输入域有两个有效核，其理想上限为 250 请求/秒；事件循环还有每请求 1 ms 的不可重叠 CPU 工作，理想上限为 1000 请求/秒。假设模型可以处理 500 请求/秒，当前输入域已经限制整体。把模型线程翻倍不会消除这个瓶颈；若大量长提示使分词成本翻倍，输入容量还会下降。

主机内存要计入连接缓冲、未分词输入、token 数组、共享 IPC 段、pinned staging 和待发送输出。共享内存省去一次复制，但生产者不能在消费者结束前重用它；进程异常退出后，也需要由明确的资源拥有者回收。复制路径虽然多搬字节，却可能简化生命期并改善隔离，应比较数据大小、频率与错误处理成本。

## 从取消到可回收

| 请求位置 | 取消后的动作 | 仍需保护的对象 |
|---|---|---|
| 尚在输入队列 | 移除或跳过该代请求 | 仍被其他阶段读取的输入缓冲 |
| 正在分词或预处理 | 标记结果不再提交，必要时协作停止 | 原生调用在用的输入与输出 |
| 已提交模型执行 | 禁止后续调度与客户端提交 | 在途 DMA、kernel、通信和 KV |
| 输出等待发送 | 终止发送，释放已无读者的结果 | 网络层尚未完成的缓冲访问 |

取消标志不能倒转已发起的 DMA，也不能保证一个阻塞调用立即返回。迟到结果携带原请求及代次，不能写进已复用的槽位；最终清理要汇合各执行域的完成事件。对断开连接的响应行为以 [本地 ASGI 规范](../sources/S-ASGI.md) 的相应版本为准，不能把发送函数返回等同于客户端已经消费数据。

## 背压如何连接到模型调度

慢客户端会让输出积累。若每个请求的输出缓冲有上限，服务可以暂停该请求后续生成或按协议终止；暂停又会延长 KV 占用时间。因此网络背压也参与容量准入。批量刷出多个 token 降低封包开销，但增加可见延迟，并改变 ITL 事件位置；不能在没有说明口径时与逐 token 刷出比较。

主机轮询减少唤醒延迟，却占用核和功耗；阻塞等待节省空闲资源，却引入唤醒与调度延迟。完成通知的批处理也存在同样取舍。对延迟敏感的小请求，调度和序列化可能占主导；对大张量，复制与内存带宽可能占主导。两类负载应通过测量决定执行域和缓冲设计。

## 观测与反例

沿同一请求记录各阶段入队、开始、结束、提交和取消事件，区分排队时间与 CPU 服务时间。检查 CPU 实际可用额度、进程/线程数、上下文切换、主存流量和分配次数，避免用“CPU 总利用率不高”排除单一执行域饱和。

验证应包括长输入阻塞短输入、慢客户端、突发到达、队列饱和、分词失败、worker 退出和各阶段取消。比较纯复制与共享缓冲、单域与分域、请求并行与算子并行时固定任务语义和资源总预算。改善单阶段吞吐而使模型饥饿、内存峰值或请求尾延迟恶化，说明资源划分仍需调整。

## 有效核数与线程组织的候选比较

可见的 CPU 数量不等于可持续使用的 CPU 时间。Linux 固定 cgroup v2 文档中，cpuset.cpus.effective 表示实际获准使用的在线 CPU，cpu.max 表示一个周期内可消费的 CPU 时间上限；后者与前者约束不同。还需考虑祖先层级、其他竞争者及实际节流，才能估计当前执行域的可用预算。

设定某服务允许在 8 个 CPU 上运行，CPU 时间额度为每 100 ms 消费 400 ms，且没有更严格的祖先限制。其长期 CPU 时间上限相当于 4 个核，并不保证任何一个线程随时都能获得运行时间。设每请求前处理需要 10 ms CPU，网络与解析需要 2 ms，调度和响应需要 3 ms；在 200 请求/s 下，这三项合计消耗 3 CPU 秒/s。若模型提交、通信及其他后台工作另需 1.2 CPU 秒/s，总需求为 4.2，已超过设定额度，增加 worker 数量不能消除这项约束。

可以比较较少请求 worker 配合适量算子线程，以及更多请求 worker 配合更少算子线程。前者可能改善每次模型调用并减少跨域通信，后者可能提高独立请求的并行机会；原生库是否释放语言运行时限制、算子是否真正并行、cache 和 NUMA 局部性都会改变结果。两个并行 worker 各自允许 4 个算子线程，表示可能同时争用更多执行机会，不表示获得了额外 CPU 配额。

验证需要同时保留各阶段 CPU 服务时间、等待时间、cpu.stat 的使用/节流记录、线程活跃情况和客户端尾延迟。固定 PyTorch CPU 指南提供 NUMA、OpenMP 线程与亲和性的调节依据，但其示例设置不能直接代替当前任务测量。若设备执行已经饱和且主机充足，增加主机并发的收益可能很小；若单执行域阻塞明显，适当拆分可能比扩张模型线程更有效。

## 队列容量必须连接对象大小与同时存活范围

| 队列或缓冲 | 合适的容量观察量 | 容量满时应传播到哪里 |
|---|---|---|
| 尚未完成输入解释 | 原始字节、媒体大小及待处理工作 | 入口读取、请求准入或输入期限 |
| 已完成前处理 | token/张量字节、已保留请求数 | 前处理生产者与模型准入 |
| 已提交的一次执行 | 在途批数、借用输入与暂定状态字节 | 调度器与状态分配器 |
| 待交付输出 | 内容字节、媒体时长或事件数量 | 响应消费者、后续生成与新准入 |
| 完成与取消通知 | 尚未处理的控制事件及其责任 | 相应状态拥有者，避免被数据队列永久阻塞 |

有界数据队列也可能阻断终止路径。例如，执行线程必须把结果写入已满队列后才检查取消，而输出线程在等待取消确认时停止取走结果，两者会彼此等待。让等待入队可被取消、由仍可运行的控制路径处理取消，或在排空期间持续消费结果，形成不同解除依赖的方案。独立控制队列或预留通知容量有助于保持消息可达，但仍要保证处理通知的执行域没有被同一个阻塞操作占住。

设定输入队列最多保留 512 个请求，每个原始输入上限 64 KiB，则该层原始字节上限为 32 MiB。若前处理结果还允许另有 512 个、每个最多 4096 个 4 字节 token ID，则该层为 8 MiB；128 个输出队列各保留 64 KiB，又增加 8 MiB。在三类对象能够同时达到上限、且互不共享存储的设定下，这三项合计为 48 MiB，尚未包含 Python/容器元数据、模态张量、IPC、pinned 缓冲与模型状态。

如果处理阶段在生成新表示后立即交还原表示，可以缩短两份对象同时存活的时间；如果只是传递共享内存句柄，同一物理字节不应在物理容量中重复加算，但每个使用者仍有独立生命周期。进程之间复制模型、序列化中间张量或保留调试快照，会产生新的物理副本，应另列。平均请求很小不能证明有界内存，必须用准入允许的输入与同时存活关系计算。

队列上限还会影响延迟。例如固定 worker 服务时间为 5 ms、前面已有 20 个需要串行服务的任务时，忽略其他延迟的等待已为 100 ms；若剩余 deadline 小于此值，继续进入同一队列不会使请求按时完成。真实任务有不同工作量，需按其可估计服务需求与不确定性判断，不能把此设定算例当成所有输入的等待预测。

## 进程输出、超时与关闭也是运行时路径

将预处理或执行放到子进程后，控制消息、结果、stdout/stderr 和进程状态是不同通道。固定 Python subprocess 文档说明，只等待进程结束而不消费有容量限制的输出管道，可能因管道写满形成死锁；一次通信超时也不一定终止子进程。长期 worker 还应避免把无界日志全部缓存在内存中。具体排空方法依赖所用运行时，本章不要求一种统一函数调用。

关闭顺序由对象责任决定：停止新准入，告知拥有者停止未来工作，继续处理能够解除引用的完成事件，最后确认进程与设备相关操作已到达可回收边界。数据队列饱和时，关闭和取消通知仍必须可达。对于无法立即中断的原生调用或设备提交，可以撤销其结果提交资格，再等待完成；将等待超时标成清理成功，会使下一代 worker 继承未知责任。

局部验证检查队列容量、消息归属和重复完成；集成验证在输入、执行、输出分别设置迟到与取消，并加入正在正常运行的邻居请求；系统验证覆盖突发、长短混合、慢消费、日志洪峰和 worker 异常。最终检查各执行域的待办数、实际 CPU 时间、队列字节及共享/私有资源，而不是只用主进程的“活跃请求为零”判定排空。设备上的完成与内存条件参见 [CUDA stream 与分配器](../frameworks/streams-allocator.md)。
