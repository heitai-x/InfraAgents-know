# K-HW-014：通信传输：注册、完成、可见与回收

推理通信既搬运 tensor，也传递执行责任。提交成功、传输完成、接收方可消费、应用接管和物理地址可复用是不同事件。本章把这些事件连接成一个可实现的保守协议，再说明哪些优化需要补充证明。

输入是稳定的源内容、目标需求清单、两端分配描述、可用传输能力和容量预算；输出是绑定同一内容身份的目标可读视图，或者明确的失败及待排空责任。传输层可以证明某段字节的操作完成，但模型状态是否完整、请求由谁继续执行，仍需上层协议判断。

## 对象、范围和完成证据

区分三类身份：逻辑内容身份 C，例如模型版本、请求、层、位置、head 和表示；传输身份 T=(逻辑传输 ID,尝试代次)；分配身份 X=(进程或设备实例,物理槽,分配代次)。一次操作再绑定 QP 实例、WR ID、源和目标 X、字节范围及分片序号。地址、lkey、rkey 都不能替代 C 或 X。

设目标副本 d 需要 D_d 字节，需求域 U_d=[0,D_d)。冻结计划将其切成不相交范围 I_j=[a_j,b_j)，要求各范围并集恰为 U_d。实际空需求显式记录 EMPTY；不能把丢失的分片当作空工作。每个目标物理副本都要单独覆盖，即使其逻辑内容相同。

目标范围的状态依次为 PLANNED、POSTED、ARRIVED、VISIBLE、PUBLISHED。POSTED 只表示接受了对应操作；ARRIVED 表示适配层取得成功且范围匹配的到达证据；VISIBLE 表示消费者所需的排序关系成立；PUBLISHED 表示应用安装了完整视图。失败后可以保留 ARRIVED 字节，但不能将部分新内容发布为完整状态。

对分配 X，分别保存逻辑拥有者集合 L_X、尚未证明最后访问结束的操作集合 U_X，以及待解决隔离原因 Q_X。关闭未来授权后，只有 L_X、U_X、Q_X 全为空，才允许复用。完成按操作身份幂等结算：同一 WR 的重复记录不能解除另一个 WR 的保护。接收完成仅结束 NIC 对接收区的那次写入；转换 kernel 和模型消费者仍有各自的访问责任。

若一个源对象同时是发送缓冲和最后恢复副本，它有两种不同责任。发送读取结束可以解除本次读保护，恢复拥有者仍可能保留整份内容，直到应用接管合同允许释放。

## 注册与操作类型限定合法访问

verbs Memory Region 由保护域、地址范围和访问属性定义。普通本地 SGE 使用有效 lkey；远端 READ、WRITE 和 atomic 使用相应 rkey 及访问权限。REMOTE_WRITE 或 REMOTE_ATOMIC 还要求 LOCAL_WRITE。应检查长度、偏移、地址计算溢出、SGE 数量和设备能力，不能仅以注册返回非空推断任意操作合法。

| 操作 | 数据目的位置与必要资源 | 完成解释与边界 |
|---|---|---|
| SEND/RECV | 接收侧事先提供与协议匹配的接收 WR 和合法容量 | 发送 CQE 结算发送侧使用；接收 CQE 用于接收侧范围检查，两者不能互换 |
| 普通 RDMA WRITE | 发起者指定远端已授权地址、范围和 rkey | 不能假定目标应用自动收到接收 CQE；目标到达证明须由另行核对的协议提供 |
| RDMA WRITE with immediate | 同时涉及远端写入和 immediate 通知约定 | 必须核对 transport、接收资源及通知含义；immediate 不代替完整数据清单 |
| RDMA READ | 本地目的范围及远端可读范围均有效 | 本地读取操作完成不说明远端应用已处理某个请求，也不自动结束其他远端访问 |

固定 rdma-core v54.0 文档列出的操作支持矩阵不同：例如 READ 支持 RC/XRC_SEND，不能套到 UC 或 UD。UD 接收还保留前 40 字节 GRH 区，payload 从偏移 40 开始，即使没有 GRH，也不能把前 40 字节当 payload。本章后续算法选择 RC SEND/RECV，避免把这些差异藏在统一的“发送成功”后面。

基线为每个发送 WR 请求完成记录，逐个结算。普通非 inline 缓冲按固定文档，在请求执行结束且取回相应 CQE 后才允许复用。合法的 inline SEND/WRITE 把 payload 放入 WQE，调用返回后原 payload 缓冲即可复用；描述符、其他对象和应用恢复责任不因此全部结束。减少 signaled WR 的方案需要额外证明覆盖关系与错误路径，本章不从“后一个完成了”推断任意此前操作均可回收。

注册缓存只能复用仍有效的映射，不能复活原分配。GPUDirect 固定文档给出两条失效跟踪路线：拦截分配/释放，或者使用 Buffer ID 检查释放和重分配。一次 tag 检查与随后提交之间仍必须保有分配资格；否则检查之后发生释放，仍会产生竞争。CUDA 指南所供摘录还指出，对已调用 cudaFreeAsync 的分配查询指针属性具有未定义行为，因此不能把释放后的属性查询当作通用回收检测器。

```pseudocode
算法 ACQUIRE_REGISTRATION(X,range,access)
输入：仍受分配拥有者保护的 X、非空范围、所需访问属性
输出：有效映射和本次使用票据，或拒绝

在分配与注册缓存协调域内：
    核对 X 仍有效且范围在分配内，阻止与本次取得竞争的释放
    查找同一设备/地址空间、分配身份、覆盖范围和访问权限的缓存项
    若失效、被撤销或身份不同，关闭旧项的新使用入口
    对仍有在途访问的旧项保留隔离责任，不覆盖它的账本
    若无有效项，按平台支持的方式注册；失败则拒绝
    登记唯一使用票据并增加该项实际使用集合
返回映射与票据；操作结算后只解除这张票据

缓存淘汰或映射撤销：
    关闭新使用入口，移除可发现性
    等待相关已接受访问终止，按对应 API 释放映射资源
    无法取得访问终止证明时保持隔离，不把缓存删除当作排空
```

Desktop GPUDirect 文档的典型 BAR 映射粒度为 G=64 KiB。对非空 [a,a+D)，对齐范围为 [⌊a/G⌋G,⌈(a+D)/G⌉G)。D=0 时不为不存在的 payload 建立映射。实际 BAR 消耗还取决于共享映射和驱动保留，不能把每个重叠注册的对齐长度直接相加。Tegra 的分配和对齐规则不同，不能复制 Desktop 参数。

映射撤销回调必须关闭使用并清理在途 DMA；固定文档特别提醒，回调中等待 GPU 工作可能死锁。需要按驱动合同安排排空，不能将“等待全部 CUDA 工作”机械塞入回调。

## 一个可恢复的 RC 分片传输算法

以下选择合作端点、固定计划、每次尝试独占的数据 QP，以及连续 wire 分片。它不处理恶意端点，也不把 RC 可靠传输扩大为跨进程事务。控制消息绑定完整 T 和两端实例身份；每个接收 WR 在主机账本中绑定预定分片，不依赖 CPU 直接读取 GPU payload 来猜归属。

设最大分片 q>0，n=⌈D/q⌉，I_j=[jq,min((j+1)q,D))，j=0…n−1。接收窗口有 w 个槽；按 j 递增发布接收描述和发送授权，同一 QP 上的 SEND 序列遵守该顺序。只在槽的 NIC 写入及全部转换读者结束后，才能为后续 j 重新使用它。这样，接收队列的顺序匹配与逻辑分片身份相容。不同 QP 不共享隐含顺序。

```pseudocode
算法 TRANSFER_RC(T,C,source,target,D,q,w)
输入：稳定源快照、目标需求和布局描述、有效实例身份；q>0,w>0
输出：目标完整可读句柄，或失败及仍受保护的范围

1 核对 C、表示、有效长度和目标需求；冻结全部分片与布局转换计划
  目标预留私有最终区、接收槽及必要工作区；源保留恢复拥有者
  D=0 时共同记录 EMPTY，验证身份与应用提交资格后走步骤 8
2 两端取得所需注册；源完成生产并建立 NIC 读取所需的顺序
  为每个将尝试提交的 WR 先登记身份、范围和访问保护
  接收方按 j 递增选择可用槽，建立接收 WR 与 j 的固定绑定
3 提交接收 WR：
    全部成功：相应项记 POSTED
    在 bad_wr 处立即失败：只将此前前缀记已接受
    失败项及其后项记本次调用未接受
    包装层丢失结果：相关项记接受未知，保留保护并转步骤 9
  只对已确认接受的接收项发出对应授权
4 发送方按计划顺序处理已授权 j：
    核对授权绑定 T、目标实例、槽代次、范围和长度
    在登记保护后提交 SEND；按实际接受前缀记录结果
    无授权或窗口用尽时等待，不越过计划发送别的 payload
    立即错误、异步错误或超时转步骤 9
5 两端持续 poll CQ，并按操作身份和成功状态处理完成：
    发送成功：结算该 WR 的本地发送读取，不修改目标到达账
    接收成功：以接收 WR 绑定恢复 j，核对成功 byte_len 等于预期长度
      标记 I_j 为 ARRIVED；不能以消息数代替范围覆盖
    重复记录只命中已结算项；未知身份、错误状态或长度不符转步骤 9
6 接收方对 ARRIVED 分片：
    按平台合同建立外部写入到 CUDA 消费者的顺序
    登记转换读写保护，启动该分片的布局转换
    转换完成并建立后续消费者依赖后，记 I_j 为 VISIBLE
    转换最后读取结束后允许接收槽用于后续分片，重新执行步骤 2–3
7 发送完成与接收到达独立结算；直到全部需求完成或失败
  接收方按原始目标需求检查覆盖、长度、表示和全部辅助元数据
  封闭本次接收计划；确认无仍可能改写最终结果的本次操作
8 在应用协调域中重新核对 T、实例、分配代次和发布资格
  完整且可见时安装目标视图，交接目标逻辑拥有者并返回 READY
  应用接管确认按上层协议发送；源仅在该合同允许时解除恢复拥有者
  所有对象仍须等待各自最后实际使用结束后才能回收
9 失败：关闭新提交、授权和发布入口，保存已接受与接受未知集合
  未发布目标保持不可消费；源恢复副本继续受保护
  对已 post 但没有匹配消息的 RECV 也保留责任
  等待逐操作完成或取得可信的访问终止证明
  只回收已无拥有者、访问者和隔离原因的范围；其余返回 DRAINING
```

接收部分 post 失败时，不能向源发出整批授权。发送部分 post 失败时，已经接受的前缀仍会执行，接收侧尚未匹配的 WR 也不会因源函数返回错误而自动消失。重建或销毁通信资源如何终止访问，必须由适配层以实际平台合同兑现；没有证明时保留隔离，比凭超时把槽交给新对象更保守。

账本登记、提交返回处理和 CQ 消费需处在同一可证明的协调关系中。CQE 可能在提交线程处理返回值之前被另一线程取到，因此账本应允许“先见完成、后结算提交结果”，不能在 post 返回后才第一次创建操作身份。

该算法用 O(n) 分片元数据与 O(w) 活跃槽描述；逐字节转换为 O(D) 工作。完成状态可以压缩为位图，但判断集合必须源自冻结需求。若两个目标副本各需 D 字节，仅一个副本完成时，成功分片表非空或逻辑内容已去重，都不足以使两个副本就绪。

## CQE、一次性通知与不丢唤醒的推进

CQE 是具体操作的记录；完成通道事件只提示某个 CQ 可能有工作。poll 会移除 CQE；成功 get 到的每个通道事件都必须 ack。ack 可以合并摊薄控制成本，但必须保存准确的待确认事件数，不能用 CQE 数代替。

固定 poll 文档规定：失败 CQE 只有 wr_id、status、qp_num、vendor_err 有效。因此先检查 status，再解释 byte_len、opcode、immediate 等成功字段。poll 返回负值或 CQ overrun 都进入错误处理；CQ overrun 后该 CQ 不可继续正常使用，不能把丢失完成记录的范围判为空闲。

下面由一个 owner 负责 CQ，使用 solicited_only=0；否则普通成功发送完成可能不触发所等待的事件。

```pseudocode
算法 EVENT_DRIVEN_CQ(cq)
在允许产生完成之前，请求一次新 CQE 通知；失败则停止准入
循环：
    重复批量 poll，直到返回 0：
        返回负值：关闭正常推进，转错误与排空处理
        对每个 CQE：先检查状态，再按账本解释和结算
    若已关闭新工作且全部责任已结算：退出
    等待完成通道事件；超时只触发状态调查，不结算任何 WR
    get 成功后，将事件计入其实际 CQ 的待 ack 账
    对该 CQ 重新请求一次通知，然后再次 poll 至空
    按准确的 get 数量确认事件；退出和销毁前结清 ack 账
```

关键关系是“先重挂通知，再清空 CQ”。反例为：先 poll 得空，随后一个 CQE 到达，此时尚未重挂；再重挂并直接睡眠。通知针对新加入的 CQE，现存 CQE 不保证补发通知，可能出现有完成但永远不醒。

正确顺序也可能收到额外空事件：重挂后 CQE 到达并产生事件，随后本轮 poll 已取走 CQE；下一次 get 仍会拿到那个事件。这是合法轨迹，应 ack 并继续 poll，不应虚构一次完成或额外递减在途计数。

CQ 容量必须覆盖共享该 CQ 的全部尚未取回完成记录，包括发送、接收和错误路径。设某窗口最多产生 A 个记录、处理期间又可能到达 E 个，容量预算至少覆盖该峰值，而不是只等于 poll 的批大小。平均完成到达率超过处理能力时，增大 CQ 只能延后溢出；应减少准入、缩小窗口或改善处理能力。

## GPUDirect 与布局转换的完整数据路径

[S-GPUDIRECT](../sources/S-GPUDIRECT.md) §2.7 要求，外部 DMA 写入必须相对于将发起依赖 CUDA API 的 CPU 线程完成，再通过适用的 CUDA 同步或工作提交关系启动消费者。NIC 完成不能放行任意已在运行的 kernel。注册、SYNC_MEMOPS、地址可达和一个普通 ready 标志，也不能独立代替这条关系。

数据路径两端都要有顺序：源 GPU 生产和必要转换完成，才允许 NIC 读取；目标 NIC 写入完成并建立 CUDA 消费依赖，才允许转换或模型读取。CPU 处理 CQE 与调用依赖 CUDA API 若由不同线程承担，还需要主机线程间的完成信息交接。

以一个明确布局例子展开：一个状态张量有 N=5 个 token、H=2 个 head、C=3 个通道，每元素 b=2 字节。源为 NHD，目标为 HND，总量 5×2×3×2=60 字节。逻辑坐标 (t,h,c) 的地址分别为

源地址 = a_s + 2((t×2+h)×3+c)，
目标地址 = a_d + 2((h×5+t)×3+c)。

以两个 token 为一块，三个 wire 分片对应 [0,2)、[2,4)、[4,5)，长度为 24、24、12 字节。源的这些 NHD 区间连续，可以作为 SEND 的本地范围；目标直接接收到连续槽，再转换到最终 HND。尾块只处理 6 个元素，不把槽的剩余 12 字节发布成数据。

```pseudocode
算法 CONVERT_NHD_CHUNK_TO_HND(lo,hi,N,H,C,slot,final)
输入：本分片连续 NHD wire 数据，已完成到达与消费排序
输出：final 中本分片对应的 HND 元素

E ← (hi-lo)×H×C
选目标设备允许的正整数线程块大小 B，启动 ceil(E/B) 个块
每个线程取得 i ← block_index×B + thread_index
若 i≥E，退出，不读尾部填充
t ← lo + floor(i/(H×C))
h ← floor(i/C) mod H
c ← i mod C
读取 slot 中偏移 b×i 的元素
写入 final 中偏移 b×((h×N+t)×C+c) 的元素
全部转换写入完成后，建立 final 到后续消费者的依赖
```

每个有效 i 对应唯一 (t,h,c)，各分片 token 域不相交，所以目标无重复写且完整覆盖。线程连续读取 wire；写入在通道轴连续，在 token/head 边界发生布局变化。该映射足以恢复地址与执行工作，但不宣称已选择最优 warp tile、向量宽度或真实事务数。

轨迹可以是：先为分片 0、1 post 两个接收槽；0 到达后转换，转换最后读取结束才把槽 0 分给分片 2；分片 1 的处理可以独立推进。最终区需要 60 字节，两个按最大块分配的接收槽共 48 字节，目标 payload 容量为 108 字节；源快照另为 60 字节。注册、协议元数据、工作区和池空闲保留另计。即使源已收到三个发送完成，目标仍需全部转换及消费依赖，不能提前 READY。

若直接把相同 wire 字节解释成 HND，数值可能全部合理但对应坐标错误。例如源元素序号 ((t×2+h)×3+c) 与目标序号 ((h×5+t)×3+c) 通常不同；改 stride 描述不能完成这次转置。

## 小消息、大状态与共享拓扑的条件化成本

消息净荷 D、分片上限 q、每次固定开销 α、有效方向带宽 B_net 下，串行传输服务的初始模型为 nα+D/B_net，n=⌈D/q⌉。D=0 时不产生这些数据 WR，但控制握手、身份核验和应用提交仍可能有成本。α 是否可跨消息重叠取决于实现，不能把这个串行模型当作任意异步库的墙钟时间。

| 成本 | 在同一候选与完成边界中列账 |
|---|---|
| 计算 | packing、校验、布局转换、数据类型转换及 CQ/描述符处理；传输本身不要求执行模型前向 |
| 访存 | 源 NIC 读取、目标写入、staging 读写与转换；逻辑字节不保证等于 HBM/DRAM 事务 |
| 通信 | payload、控制消息、协议开销和重试；按真实路径统计共享链路服务量 |
| 准备 | 分配、锁页、注册、BAR、缓存有效性核验、接收资源和描述符构造 |
| 同步 | 源生产、窗口授权、CQ 处理、目标可见性、转换完成及应用接管 |
| 驻留 | 源恢复副本、发送读保护、接收槽、最终区、工作区、MR 和待排空对象 |

直接路径可为 GPU_A→PCIe_A→NIC_A→网络→NIC_B→PCIe_B→GPU_B。主机 staging 路径还包含 GPU_A→主机_A、NIC 对主机的读取/写入、主机_B→GPU_B；NUMA 放置可能再穿过 CPU 互联。可达性与每个方向的有效带宽是不同事实，改变 GPU/NIC 配对后必须重建路径。

对共享资源 r，设本次各传输经过它的实际服务字节之和为 Q_r，可持续带宽为 B_r，则对应窗口至少需要 Q_r/B_r 的服务时间。只有明确共享同一方向或同一容量组的流量才合计；全双工两个独立方向不能无条件合并为单向时间。TP、P/D、缓存副本和制品加载若共用出口，应在重叠窗口中共同列账。

设定一个 512 MiB 对象，方向有效带宽为 20 GiB/s，纯 payload 服务为 25 ms。取 32 MiB 分片，共 16 块；设每块固定服务开销 5 μs，则传输阶段 b_t=1.5625+0.005=1.5675 ms。再设每块转换 c_t=0.8 ms。它们都是演算输入。

若传输和转换使用足够独立的资源，两个接收槽足够，并且主机及时重挂和授权，理想流水时间为

T = b_t+c_t+(16−1)max(b_t,c_t) = 25.88 ms。

单槽迫使每块转换读完后才能接收下一块，串行为 16(b_t+c_t)=37.88 ms。这里每槽从开始传输到转换读完占用 2.3675 ms，启动周期 1.5675 ms，至少需要 ⌈2.3675/1.5675⌉=2 槽。若控制消息往返或发送端完成更慢，还需分别计算相应窗口，不能只用目标槽的生命周期。

最终区 512 MiB 加两个接收槽 64 MiB，目标 payload 驻留主项为 576 MiB；源完整快照为 512 MiB，两端合计为 1088 MiB。注册同一分配不会再产生一份同样大小的 payload，但映射占用自己的硬件资源。转换读、写各 D，NIC 在源读 D、目标写 D，本设定跨两端的逻辑 GPU 数据流为 4D；最终模型读取、额外 packing、缓存和协议开销尚未计入。

若传输与转换共享 HBM 或 PCIe，上述最大阶段公式可能不可达。应同时满足共享资源下界，再按依赖和容量安排日程；不能把已经包含访存的转换持续时间再加一遍相同字节除带宽。

窗口也受延迟约束：若每 q 字节额度从取得到可再次使用需 L 秒，w 个额度的理想吞吐不超过 wq/L，且不超过链路能力。增加 w 可以隐藏等待，却增加约 wq 的对应槽容量和取消排空负担。接近资源饱和后继续增窗，通常只增加排队。

注册复用 R 次时，固定准备成本 C_reg 可在简化平均账中摊为 C_reg/R，但有效性检查和每次使用成本仍存在。比较直接路径与 host staging，应以相同目标可消费边界计时：前者包含直接注册、拓扑和可见性；后者包含实际 D2H、网络、H2D、主存与 NUMA 成本。更快的孤立链路并不保证完整候选更快。

## 集合通信、空工作与成组提交

RC 分片协议不能替代集合通信的参与合同。[S-NCCL-COLLECTIVE](../sources/S-NCCL-COLLECTIVE.md) 要求所有 ranks 使用匹配的 count 和 datatype；操作、root、归约方式、次序及数据解释也须一致。root 是 communicator rank，AllGather 输出按 rank 排列，不能直接用物理 GPU 序号代替。

局部没有有效 token，不授权该 rank 单独跳过已约定的 collective。求和中只有在数学合同允许“无贡献”为零时，才能构造合法零输入；AllGather 没有通用的缺失贡献单位元。全组零长度是否可调用须按固定接口另核，或者在任何提交前共同删除这个 slot，不能假定数学空数组证明接口合法。

```pseudocode
算法 ISSUE_MATCHED_GROUP(plan)
共同固定 communicator 身份、rank 映射和按序操作描述
各 rank 准备其角色需要的合法输入、输出范围及生产依赖
单线程管理多个设备时，按固定 Group Calls 合同使用 group
进入 group，按共同次序暂存调用
结束最外层 group：
    SUCCESS：确认该发起单元已入相关 CUDA streams
    IN_PROGRESS：持续核对涉及的全部 communicator 状态
        全部成功前，不提交依赖它们的相关 CUDA 操作
    错误或超时：保留所有可能在途对象，转执行组恢复
确认发起后，建立各实际 stream 上的完成票据与后继消费依赖
设备完成和应用发布分别结算；group 结束不表示通信完成
```

group 内单个调用可以在操作尚未入 stream 时返回；提前记录 event 可能记录到通信之前。group 降低部分发起成本，也可能等待最晚输入、延迟最早消费者并延长缓冲生命期。减少调用次数、完成全部数据搬运和完成请求接管，不能混成同一个指标。

## 取消、重试与方案调整

取消先关闭未来提交和发布，再结算已接受工作。超时只说明尚未观察到所需结果，不证明远端没有写入。重试使用同一逻辑传输身份和新的尝试代次；若旧操作尚未排空，要么等待，要么分配与旧访问隔离的新范围，并把两份容量同时入账。

代次检查可以拒绝旧完成发布，却不能阻止已在途 DMA 写入旧地址。如果立即把该地址分给新对象，即使旧 CQE 被忽略，新对象仍可能损坏。注册缓存失效、rkey 更新或控制面 fencing 的具体效果，也必须按适配层证明，不能默认它们追溯撤销全部已接受访问。

| 条件变化 | 保留与调整依据 |
|---|---|
| 小消息比例增加 | 保留身份和完成边界；研究合并提交、批量 poll。若聚合等待增大尾延迟，则缩小聚合 |
| 大状态或窗口增加 | 重算共享资源、接收槽和恢复副本驻留；容量不足时分块或背压，不能提前复用 |
| 注册命中减少 | 保留分配身份核验；重算冷准备成本，必要时改用长期合法 staging 池 |
| GPU/NIC、NUMA 或驱动变化 | 重核注册方式、方向路径、排序和访问终止合同；旧配对成功不能推广到新配对 |
| 使用 relaxed ordering | 固定 MR 文档允许写入乱序，不保留 write-after-write 顺序；完成语义仍有其保证。重叠目的写或依赖 payload 后写 ready 标志的协议需重新证明 |
| 消费者变慢 | 完成不等于槽空闲；降低准入或窗口。增槽不能修复长期服务率不足 |
| 取消或错误增多 | 将排空、隔离和重试副本纳入峰值；必要时减少并发尝试或放弃迁移，保留可信恢复状态 |

relaxed ordering 的反例是把 payload 和 ready 当作两个普通网络写，仅按发出顺序允许并发消费者读取。固定文档已说明写后写顺序不再保证，GPUDirect 又有 GPU 消费排序边界，因而不能用“ready 已写”替代二者的完成证明。该标志即使在某次机器运行正确，也不能证明协议合法。

## 区分实验与反证修正

实验先固定逻辑内容、物理分配代次、实际字节和完成终点。不同代使用容易区分的内容，记录 post 接受结果、CQE、通道事件、CUDA 提交、转换结束、发布和最后访问。以下为目标环境实验设计，不是已完成的设备测量。

| 观察 | 竞争解释 | 区分干预、预测与修正 |
|---|---|---|
| CQ 有记录但线程不推进 | poll/重挂竞态；CPU 调度晚；错误使用 solicited_only | 在 poll 与重挂之间受控插入完成，比较两种顺序；仅错误顺序停滞支持丢唤醒。顺序修正仍晚则查线程运行和配额 |
| CQE 早、目标 READY 晚 | 转换慢；CUDA 可见性处理晚；应用协调等待 | 分别延迟转换、主机处理与发布，观察对应间隙是否移动；若 NIC 时间不变，不归因链路带宽 |
| 并发 GPU 消费读旧值 | 外部写入排序遗漏；提前复用；布局解释错误 | 固定分配长期保活并先停用复用，再建立合法提交依赖，最后逐坐标对照 NHD/HND。只有哪项干预消错才支持相应解释 |
| 取消后新请求损坏 | 旧 DMA 仍写；旧完成误扣新代保护 | 一组保留旧物理范围但注入旧完成，另一组丢弃逻辑旧完成却提前复用地址。前者检验账本，后者检验物理隔离 |
| 批量 post 错误后挂起 | 错把整批当未提交；接收 WR 未匹配；已接受前缀无人结算 | 在不同 bad_wr 位置注入失败，逐项核对接受前缀和两端保护；无法终止的接收项应留在 DRAINING |
| 直接路径冷启动慢 | 注册/BAR；路径差；布局转换；CPU 控制 | 保持相同分配重复使用，再改变 GPU/NIC 放置；仅首次慢支持准备成本，持续随放置变化支持路径解释 |
| 更多槽不提速 | 链路/HBM 饱和；控制线程不足；消费者慢 | 扫窗口并记录各资源字节、完成速率和槽占用；只增加排队时修正瓶颈判断并缩小窗口 |
| 全组偶发挂起 | 局部空工作跳过；操作顺序不匹配；组发起尚未确认 | 记录共同 slot 序号与描述，注入零有效 token rank 和 IN_PROGRESS；先修首次不匹配或错误发起边界 |

CQ 错误、接收资源不足、源退出和目标退出也要保留未完成集合。若全局同步消错，它同时改变生产、可见性和回收多条边，只能说明时序相关，不能唯一定位原因。没有目标设备证据时，不将模型通过解释为硬件可见性或性能保证。

## 随章检查与证据范围

唯一随章检查为 tools/check_k_hw_014_full.py。它使用 Python 标准库，确定、离线、只读，不调用项目、上游实现、子进程、网络或 CUDA。检查以独立逐字节集合核对范围覆盖，以完整张量轴遍历核对分块 NHD→HND 地址映射，以事件在历史中的位置核对操作状态机，并检查身份化使用集合和 CQ 通知插入位置。负对照实际执行提前可见、取消冒充排空、覆盖计数冒充范围覆盖、合并目标副本、遗漏转置、重复完成扣减及 poll 后才重挂等错误。

本轮实际执行了 functions.exec 中的 JavaScript 对应有限模型：40,320 次事件前缀比较、632 个范围覆盖案例、216 个布局案例与独立参考一致；通知的四个到达插入位置及所述已执行负对照完成核对。初版事件参考错误地把尚未出现取消的历史判为不可发布，修正缺失事件的位置为正无穷后重跑通过。这些是 JavaScript 模型结果，交付 Python 脚本本轮尚未执行。

模型把硬件完成和 CUDA 排序当作显式输入事件，不能证明实际 API 正确产生这些事件。未验证真实 RC/QP 错误恢复、访问终止、注册撤销回调、任意跨 QP 顺序、unsignaled 完成压缩、真实 DMA/GPU 可见性、设备事务、性能或 Agent 使用效果。硬件实验仍需在固定版本、真实拓扑和相同消费终点上完成。
