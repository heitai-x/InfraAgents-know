# 知识内容审查：从 Attention 样例推广

本页把 Attention 多轮审查发现的问题整理为内容作者与审阅者可复用的问题。依据是[知识库构建方法](knowledge-method.md)中的六项标准，深度样例是[当前 Attention 模块](attention-module.md)。它不增加 Agent 的角色义务，也不要求每章采用同一结构、同样多的算例或统一的工程路线。

## 知识库承担什么任务

本库支持 InfraAgents 根据模型、workload、硬件和服务目标，从空工程构建、检验与持续优化完整推理系统。知识应提供五种帮助：还原问题的理论基础；区分合法条件与可探索的设计空间；给出足以独立实现的算法与状态关系；支持成本预测、实验和诊断；保存能够被反驳、修正和迁移的经验。

一条有用的阅读链应支持读者形成这样的推理：任务与输入条件 → 正确性要求 → 候选算法与数据流 → 成本预测 → 区分实验 → 实现结果 → 修正后的结论。某一章可以承担其中一部分，但承担核心算法的地方不能只列注意事项或把关键步骤交给源码。

## 六项标准怎样落实到实际问题

| 内容标准 | 审阅时实际追问 | 过去发现的问题及其含义 |
|---|---|---|
| 原因、数学定义、输入输出和状态 | 为什么需要这个机制？每个量的轴、单位、范围和身份是什么？状态代表已知、已算、已确认还是已分配？ | FP8 只写“使用块尺度”不足以恢复分数和 PV 的共同单位；调度中的 token 已生成不等于其 KV 已计算 |
| 合法性与方案选择 | 哪条性质来自函数、数值契约或设备语义，哪条来自某个方案？等价性在实数、浮点还是特定误差范围内成立？ | 精确算术的归约结合性不能直接变成浮点逐位相同；图地址稳定不证明数据身份仍正确；内部 fragment 未公开就不能猜 lane 映射 |
| 算法、数据流和状态变化 | 能否写出初始化、推进、提交和结束？第一块、最后一块、空输入和失败分支怎样处理？每个被消费的量从哪里产生？ | 量化流程需要量化与恢复尺度；缓冲需要生产者、所有消费者及代次；硬件专题需要一条从逻辑 tile 到地址、线程、片上布局、指令输入和写回的完整路径 |
| 六类成本 | 是否在同一候选、相同输入和相同时间范围中列账？哪些量可以相加，哪些受关键路径和共享资源限制？ | 唯一 KV、各 head 请求流量和 DRAM 事务不能混算；共享容量只计一次；预留池与其中存活对象不能重复相加；深流水的驻留和 spill 会改变本来用于估时的吞吐 |
| 条件变化后的选择 | 改变 shape、状态组织、精度、到达轨迹或设备能力，哪条依赖保留，哪项成本改变？何种结果足以推翻原选择？ | 更多分区在并行度不足时有利，在已经饱和时可能只增加合并；更多缓冲不保证更快；缓存命中不保证新请求可立即执行 |
| 区分竞争解释 | 观察支持哪些解释？它们对某个可控改变给出什么不同预测？实验结果不符后怎样修改判断？ | “三级比两级慢”同时允许首尾、spill、驻留和未重叠解释；一次时间测量不能决定原因；软件事件模型不能证明 GPU 的内存可见性 |

这些问题由主题决定使用范围。调度章节需要把就绪性、预算和输出归属连起来；缓存章节需要贯通身份、复制、发布和回收；硬件章节需要贯通布局、执行契约和资源。协议、统计或模型语义章节不必凭空增加矩阵指令实例。

## 从单个机制走到组合案例

分开解释各个机制之后，选择会改变合法性或成本的真实交界，追踪一次完整变化。例如共享前缀和私有尾块在追加、封存、发布、消费与回收期间，内容、scale、页表和读者必须属于一致的状态；调度器选中的工作必须已有上游输入和容量，而执行视图的压紧不能改变请求归属。

审阅者沿一次轨迹检查：发生了什么输入事件；哪些对象仍存活；谁能写；谁已经取得读取权；何时对消费者可见；失败后哪些旧状态仍有效；取消后哪些工作仍在途；何时能把同一物理资源交给下一使用者。对象需要身份或代次时，解释防止的具体错误。只有单次同步执行的算法不必引入多代次协议。

交界还包括“看似已经完成，下一步却没有输入”的状态。本轮调度审阅发现：完整命中 KV 而没有末行 logits 时，只按已知长度减 KV 长度选择工作会得到零，无法生成第一个新 token。修订明确了安全重算最后一个已知 token 的路径及共享写区隔离。沿状态图检查是否存在有合法请求却无后继事件的停滞，比只检查各状态的字段范围更有用。

组合案例应使读者能计算至少一项会影响决定的代价，并解释另一种选择何时反转。重点是让独立机制能够正确拼接，不是枚举所有组合。示例的页长、tile、队列策略和版本字段均为可替换选择。

## 阅读链与事实核对

先检查正文承担的核心知识，再检查直接来源说明与足以支持关键事实的固定论文或文档。保留原始资料的错误、版本身份和字节，在解释中纠正公式或限定结论；自己的推导不能归为论文实测。源码可以用于作者核对，但读者独立实现所需的事实应进入允许读取的算法说明。

审查记录写明读过哪些正文、哪些来源及其范围、发现的具体问题、实际修改与检查。只有读取摘要、术语检索或运行链接检查的专题，继续保留深度复核待完成状态。没有必要为了一个确定问题递归阅读所有引用。

## 内容与使用效果分别验收

内容审查判断六项标准在声明范围内是否有充分解释。作者侧算例验证代数、布局、边界、协议或成本模型；它需要独立参考、不变量或能触发错误的负对照，不能只让测试复述实现。读取测试检查冻结内容能否被取回及身份是否匹配。这三类证据各自有效，不能互相代替。

直接使用检验让 Agent 在没有现成实现的情况下处理正文未直接演示的问题：重新推导合法算法，改变输入或硬件条件后重算，面对错误提出竞争解释，收到反证后修改方案。保存允许资料、任务、模型/上下文、预算、答卷或实现、执行结果及失败归因。交叉审阅兼做推导练习可以发现内容缺口，但有共同上下文、作者经验或未隔离的环境时，只能声称完成这次练习。

如果要声称“知识改善了 Agent 的构建能力”，还需可比的知识版本或对照条件、多个代表任务以及预先说明的判断方法。目标 GPU 的数值、同步、重叠和性能仍需设备结果。没有最佳 tile 或流水级数不构成知识缺陷；没有解释如何推导候选、识别限制、测量与修正，才是内容缺口。

## 怎样给出审查结论

对每个问题给出正文位置、明确结论与证据边界，区分“已完整解释”“仅提及”“缺推导”“缺证据”“缺失”。这些描述可按实际内容组合使用，不转成总分或用测试数量抵消关键算法缺口。

已经修复的问题在新修订中复核后关闭，不沿用旧审查中“仍缺 FP8/硬件映射/组合案例”的判断。新的缺口必须来自当前字节。Attention 当前的两个具体案例已补足内容展开，实际 Agent 独立构建与目标 GPU 效果仍有各自的验证边界。以当前内容和当前证据决定结论，不为了持续审查而不断增加验收条件。

扩展工作优先完成相关专题的一条知识链，再复核跨专题衔接。当前批次与逐篇状态见[扩展状态](expansion-status.json)；历史审查保留当时结论，不覆盖成当前状态。
