  "chapter": "# K-HW-004：数值格式、打包布局与矩阵指令\n\n硬件能表示一种 dtype、库的接口接受该 dtype、目标 shape 在目标二进制中 dispatch 到能利用目标资源的 kernel，是三层不同能力。推理实现还必须把数值格式、分组元数据、物理布局和执行指令放在同一契约里；任一层的“支持”都不能替代其余层。\n\n## 格式、指令与 dispatch 是三层能力\n\n设执行请求为 P=(dtype、M/N/K、stride、对齐、目标架构、库版本、编译选项)。对一个候选格式，应分别记录以下证据层级：\n\n- E0 可表示：格式定义存在，能够写出该值域内的数。\n- E1 API 接受：类型、shape 或编译接口不拒绝该请求。\n- E2 执行契约满足：dtype、布局、对齐、leading dimension、参与线程和完成条件均符合目标指令或库的要求。\n- E3 实际 dispatch：目标二进制、运行时和编译产物确实选择了预期函数、内核或指令路径。\n- E4 目标负载成本：在相同输入、质量约束和计时边界下，记录实际字节、时间线、驻留与同步。\n\nE0 只说明“能存”，E1 只说明“能调用”。例如库可能接受 INT4 权重，却在 tile 内解包到半精度再调用普通算子，也可能走低位指令，或退回高精度 fallback。三条路径都可能数值正确，但临时内存、访存和吞吐不同。只有 E3 的 dispatch 记录和 E4 的负载观测能把它们区分开。\n\n这里的成本结论都是条件化的：减少逻辑权重字节只改变容量和读取候选；实际收益还取决于解包、参数读取、矩阵指令形状、驻留和同步。\n\n## 数值格式与量化契约\n\n一个浮点格式不只是“16 bit”或“8 bit”。至少应说明符号位、指数位、有效数位、特殊值、舍入和转换规则。下表只给出常见格式的结构差异，不代替目标 API 的完整语义：\n\n| 格式 | 结构与输入解释 | 需要单独确认的项 | 不能由此推出 |\n|---|---|---|---|\n| FP16 | 1 符号、5 指数、10 小数位 | 乘法、累加、输出精度；非有限值与次正规数策略 | FP16 输入意味着整个归约按 FP16 执行 |\n| BF16 | 1 符号、8 指数、7 小数位 | 指数范围较宽但有效数位较少；累加路径 | BF16 的指数范围接近 FP32 就等于 FP32 精度 |\n| TF32 | 保留 FP32 指数范围，输入尾数走约 10 位路径 | 转换发生点、舍入方式、是否只影响乘法输入 | 输入以 FP32 存储就完成了完整 FP32 乘法 |\n| FP8 E4M3 / E5M2 | 两种不同的指数/有效数分配 | 缩放粒度、饱和、非有限值、乘法与累加精度 | FP8 是一种唯一格式，或整个模型自动使用 FP8 |\n| signed INT8 | 码域 [-128,127] | zero-point、scale 轴、累加宽度、补偿与输出转换 | 任意 group scale 或任意 zero-point 可直接套入 |\n| packed signed INT4 | 码域 [-8,7]，每字节可放两个 nibble | nibble 顺序、符号扩展、组轴、尾部填充 | 0xF 一定表示 15；它按有符号解释为 -1 |\n\n存储精度、乘法精度、累加精度和输出精度必须分别描述。长归约对累加误差敏感，低精度输入配较高精度累加很常见；但真实路径还可能使用 reduced-precision reduction、TF32 或分批累加。溢出、下溢、次正规数、饱和和非有限值产生的结果不同，不能都归入“舍入误差”。\n\n对量化张量，设标量为 x，步长 s 有限且 s>0，码域为 [q_min,q_max]。两种常见重建是：\n\n- 实数偏移：q = clip(R((x-b)/s), q_min, q_max)，x̂ = b + s·q。\n- 整数零点：q = clip(R(x/s)+z, q_min, q_max)，x̂ = s·(q-z)，其中 z 是码域内整数。\n\nR 的舍入位置和半整数规则属于编码契约。b=-s·z 时两种写法也不一定在重新编码时等价，因为先舍入再加 z 与先加 z 再舍入可能不同。既有码流只依赖解码规则；混合加载器、转换器和 kernel 必须共享同一个模式、轴和版本。\n\n对线性层 y=Wx，量化误差满足 Δy=ΔW·x+W·Δx+ΔW·Δx。权重自身的逐元素误差不是层输出误差的完整目标；校准输入的结构会影响权重误差如何传到输出。GPTQ 类方法因此关注层输出重建，而不是孤立权重的舍入噪声。本库只使用这一目标关系，不把论文的校准设置当成目标模型的质量保证。\n\n## 合法性：格式、分组与执行契约\n\n合法实现必须同时保持数值含义、索引身份和完成依赖。下列条件中，有些来自函数和数值契约，有些只是某个方案的选择。\n\n- s 有限且严格为正；ZERO 模式的 z 是码域内整数；码域、位宽和有符号解释一致。\n- 分组覆盖每个有效元素恰好一次。组大小不必整除 K；尾组有效长度和组身份必须单独保存，不能用相邻组的 scale 填充。\n- 代表实数零的填充码必须按模式定义。ZERO 可用 q=z；REAL 若没有精确零码，必须使用有效掩码或另有定义的中性处理。\n- 打包协议包含低位顺序、符号扩展、行跨度、组表顺序、预转置、对齐、有效长度和格式版本。\n- scale 位于归约轴内部时，必须在对应 K 段的部分结果上分别应用；只有能在归约外提出的尺度才能由一个 epilogue 直接承接。\n- 矩阵指令的 dtype、形状、操作数布局、leading dimension、基址对齐和参与线程都必须满足目标 API。fragment 内部元素映射若未公开，不能把它当普通数组按行列下标访问。\n- 目标架构、编译选项和运行时库版本必须产生实际 dispatch；源码中出现一个 dtype 名称或库宣称支持，不证明本形状走到对应指令。\n\n组大小、对称或非对称、动态或静态尺度、敏感层是否保持高精度，属于选择空间。满足数值契约只是合法条件；实际质量、dispatch 和端到端成本决定方案是否适用。\n\n整数矩阵乘仍有溢出边界。对未经 zero-point 修正的 signed INT8 乘积，绝对上界可用 128²=16,384。K=4,096 时，绝对上界为 67,108,864，小于 INT32 最大值 2,147,483,647。但这个例子不覆盖更长归约、初始 accumulator、bias、zero-point 修正和更窄的中间累加。若 K 增大到 131,072，仅按 128² 的绝对上界就已达到 2³¹，不能再声称普通有符号 32 位累加安全。\n\n## 打包、解包与分组尺度：完整算法\n\n设权重 W 为 d_out×d_in，组沿输入维 K 划分，组长 G，采用有符号 b bit 对称量化，行主序存放。对元素 W[r,j]，其组身份为 g=floor(j/G)，scale 表按 (r,g) 索引。下面给出一个可独立重建的打包与解包流程；它不绑定某个 CUDA 或 CPU 内核。\n\n```pseudocode\n算法 PACK-UNPACK-SYM\n输入：W[d_out,d_in]、组长 G、位宽 b、行主序布局 L、格式版本 v\n输出：packed codes、scale 表 S、有效长度表、布局版本 v\n\n1 校验 b≥2，q_min=-2^(b-1)，q_max=2^(b-1)-1，G>0\n2 对每个输出行 r 和每个非空组 g：\n     取 j 属于 [gG, min((g+1)G, d_in)) 的有效元素\n     a = max_j |W[r,j]|\n     若 a=0：s=1；否则 s=a/q_max\n     若目标只保存低精度 scale：先把 s 舍入到存储精度，再用该值编码\n     若保存后的 s 不是有限正数：拒绝该配置\n     把 (r,g,s) 写入冻结的 scale 表 S\n3 对每个有效元素 W[r,j]：\n     s = S[r, floor(j/G)]\n     q = clip(R(W[r,j]/s), q_min, q_max)\n     记录 q 到逻辑码数组 Q[r,j]\n4 按行主序和格式版本 v 打包 Q：\n     每字节低 nibble 放偶然下标 2h 的码，高 nibble 放 2h+1 的码\n     奇数尾部的最后一字节高 nibble 填 0，但该位置不计入有效长度\n     负码按其 b 位二进制补码写入\n5 写出 packed codes、原样冻结的 S、每行每组的有效长度与 v\n6 解包时按同一 v 读取字节、nibble 顺序和有效长度：\n     对每个有效码 q，若最高位为 1，则解释为 q-2^b\n     由 j 求组号 g，读取 S[r,g]\n     重建 x̂ = s·q\n7 任何缺失组、重复组、越界尾部或版本不匹配都应报错，不能静默补 0\n```\n\n正确性不变量是：冻结 scale 表之后，编码和解码没有“再拟合尺度”的步骤；每个有效元素恰好由一个组参数解释；奇数尾部的高 nibble 不被消费；代码值只在 b 位补码域内解释。若导出时重新舍入 scale，或把 signed nibble 当无符号数，重建值会改变，即使输出 shape 完全正确。\n\n一个最小反例是 signed INT4 的 nibble 0xF：按有符号解释为 -1，按无符号解释为 15。另一个反例是 V 形分组：组长 G=2、scale 分别 0.5 和 2、四个整数码均为 1、激活均为 1。正确归约是 0.5·(1+1)+2·(1+1)=5；把两个组的整数部分先相加再乘最后一个 scale，会得到 8。这个错误不是浮点舍入，而是把归约内尺度错误地提到了单一 epilogue。\n\n## 从逻辑 tile 到矩阵指令：一条可核验路径\n\n矩阵指令处理特定 tile、数据类型与布局。以固定 CUDA 12.8 指南所描述的 WMMA 半精度 16×16×16、FP32 accumulator 为例，一个 warp 协作执行 D=A·B+C。具体 API 的 fragment 内部映射未公开保证，因此这里只交付逻辑 tile、共享存储交接、集体加载、矩阵乘加和写回路径；实际项必须核对目标 API 的 dtype、row/col 布局与编译结果。\n\n本例假定 A、B 均为行主序浮点输入，先转换为 FP16 并暂存到行主序共享 tile，目标 API 支持 matrix_b 的行主序操作数。若目标 API 只支持另一种布局，就必须在共享存储中支付转置或使用对应的 col-major 装载，不能把逻辑行列直接替换。\n\n```pseudocode\n算法 WMMA16-STAGE\n输入：A[M,K]、B[K,N]、C[M,N]、输出 tile 起点 (m0,n0)、FP16 暂存区\n输出：C 的 16×16 有效 tile\n\n1 检查目标 API 支持 16×16×16、FP16 输入和 FP32 accumulator\n   检查 A_s/B_s 基址达到 32 字节对齐\n   检查 half leading dimension 为 8 的倍数，float leading dimension 为 4 的倍数\n2 将 accumulator fragment 初始化为 0\n3 对 k0=0,16,32,... 且 k0<K：\n     全体 warp 成员协作，把 A[m0+i,k0+k] 装入 A_s[i,k]，i,k 属于 [0,16)\n     把 B[k0+k,n0+j] 装入 B_s[k,j]\n     若全局下标越界：对应 A_s 或 B_s 位置写 FP16 的 0，不执行越界读取\n     全体成员以一致参数集体加载 A fragment 与 B fragment\n     等待装载完成，再执行矩阵乘加\n     在目标指令规定的完成条件满足前，不能覆盖 A_s/B_s\n4 全部 K 段完成后，WMMA 的线程集体把 accumulator fragment 写回 C_s[16,16] 的 FP32 row-major 暂存区\n5 写回完成后，按明确的 C_s 行列下标写出到全局 C；越界 (m0+i,n0+j) 不写\n6 所有集体调用必须由整个 warp 以一致路径到达；不能因尾部有效元素少而让部分 lane 提前退出\n```\n\n这里的状态分为三层：逻辑状态是 A/B/C 的 shape、stride 和有效范围；数学状态是跨 K 段保留的 accumulator；执行状态是 A_s/B_s/C_s 暂存区和 warp 的集体完成条件。矩阵指令的同步只覆盖该 API 规定的 fragment 操作，不自动替代前后任意共享内存依赖。如果之后要对输出做逐行归约，不能按未公开的 fragment 内部下标读取；应先按 API 写回共享或全局存储，再建立明确的元素归属。\n\n这条路径的资源账是：两个 FP16 16×16 输入 tile 共 1,024 字节，FP32 16×16 输出暂存为 1,024 字节；accumulator 有 256 个 FP32 元素，若由 32 个 lane 均摊则平均每线程 8 个累加值，尚未计地址、fragment 操作数、双缓冲和对齐填充。它只说明一个 tile 的片上占用，不证明该配置在目标 GPU 上能获得最高占用率或最佳吞吐。\n\n若 M=1 的 decode 直接套用 16 行 tile，矩阵指令的有效行利用率只有 1/16；此时可能要比较 scalar/GEMV、较小 tile、跨请求合批或 split-K 路径。相反，大 prefill 可以在更多 query 行之间复用同一权重 tile，tile 的固定开销更容易摊薄。两者是不同的执行条件，不能把大矩阵上的选择直接搬到单 token decode。\n\n## 条件化成本：字节、归约、准备与驻留\n\n设权重的有效元素数为 d_out·d_in，位宽为 b，每组的 scale 与 zero-point 合计 m 字节，组数为每行 ceil(d_in/G)。不计对齐时：\n\nB_code = ceil(d_out·d_in·b / 8)\nB_meta = d_out·ceil(d_in/G)·m\nB_weight = B_code + B_meta + B_align\n\n有效位宽为 8·B_weight/(d_out·d_in)。对 4,096×4,096、4 bit、G=128、m=4 的设定，B_code=8,388,608 字节，B_meta=524,288 字节，总权重约 8,912,896 字节，即 4.25 bit/weight；元数据占码字节约 6.25%。这个数没有计对齐、索引、重打包副本和运行时工作区。\n\n若一次前向只读取每个权重一次，M 行激活的近似算术强度可写成 16M/(b+8m/G) FLOP/字节，尚未计激活、输出和重复读取。M=1、b=4、G=128、m=4 时约 3.76 FLOP/字节；b 降低但解包和参数读取上升时，这个条件化的强度估计可能不再成立。\n\n解包成本不能从压缩比直接推出。若每次前向都完整恢复一份 FP32 权重，4,096×4,096 的压缩权重约 8.5 MiB，而 FP32 副本为 64 MiB；副本的写读会把逻辑权重读取节省抵消，并且增加峰值驻留。只有在 tile 内解包、复用已经恢复的片段，或把转换与矩阵计算组织成不重复物化完整副本时，压缩才可能持续体现在稳态读取上。\n\nscale 位于 K 维内部时，每个输出元素可能要对 ceil(K/G) 个组的部分和分别加权。K=4,096、G=128 时有 32 个组；若 16×16 输出 tile 的每个输出都保留 32 个独立部分和，仅这部分状态就是 256×32 个 FP32 值，即 32 KiB，可能挤占寄存器或迫使写回共享存储。可以将组部分和立即缩放后累加，或把同组片段合并后再乘尺度，但两种数据流的累加顺序、工作区和同步不同。\n\n准备成本包括校准、量化、打包、布局转换、JIT 编译和图捕获。设一次准备成本 C_prep，单次调用节省 Δt，只有 R·Δt>C_prep 时，准备在声明复用次数内才可能收回；未命中形状、重新打包和运行时转换还要另计。通信方面，若 scale 随权重分片复制到 R 个 rank，则元数据容量和传输量按副本数增长；动态激活 scale 还要一次归约和完成同步，不能把共享 scale 的容量只算一次后再假设所有 rank 免费可见。\n\n驻留必须按对象相加：packed 权重、解包片段、FP32 高精度副本、矩阵工作区、图缓冲和 scale 表分别计入峰值。不能因为文件是 4 bit，就把运行时驻留写成“权重只有 4 bit”。同步包括暂存完成、fragment 集体调用、epilogue、动态 scale 归约和 kernel launch；能重叠的阶段不能把各自理想时间直接相加，不能重叠的阶段也不能漏算。\n\n## 条件变化后的保留、调整与放弃\n\n| 条件变化 | 保留的关系 | 调整对象与成本 | 放弃或改选条件 |\n|---|---|---|---|\n| 小 batch decode，权重带宽主导 | 压缩码减少权重读取候选字节 | 比较 tile 内解包、参数访问、实际 dispatch 和每轮真实读取 | 解包或启动成本超过读取节省时保留较高精度路径 |\n| 大 prefill，矩阵计算主导 | 同一权重可服务更多 query 行 | 比较低位矩阵指令、转换后矩阵乘和较高精度成熟内核 | 低位路径不能有效使用计算单元时不要仅凭位宽下降选择它 |\n| 组长 G 变小 | 更细的局部网格可能减少量化误差 | 重建 scale 表，增加组数、参数流量和对齐成本 | scale 读取或工作区成为主项时增大组或改变布局 |\n| scale 存储精度降低 | 码必须由实际保存的 scale 解释 | 用实际存储值重新编码，重跑独立解码和质量检查 | 尺度下溢为零或无法保持合法正值时拒绝该配置 |\n| 目标架构改变 | 数值契约和分组身份可保留 | 重核指令形状、布局、对齐、驻留和实际 dispatch | 没有合法高效内核时使用成熟高精度路径或更换布局 |\n| 非整除
