# K-WORK-007：多模型放置：共同容量、混合执行与租户公平

多模型服务同时决定哪些版本驻留、各放在哪些设备、请求到达后去哪里，以及有限容量由哪些请求占有。完整权重不同的模型、共享基座的 adapters、同一模型的独立副本，具有不同的共享条件。模型名数量、逻辑资源份额和平均设备利用率都不能替代逐设备的容量与执行账。

放置的输入包括模型及版本、可用执行配置、设备与链路、请求到达和长度轨迹、租户份额、数值要求与服务目标。输出包括逐设备物理对象、模型副本及执行组、冷对象加载规则、请求绑定与准入决定，以及不能满足的条件。离线规划选择长期布局，运行时按实际状态重新检查；预测可以改变选择顺序，不能放宽身份、容量和完成条件。

## 先确定可共享的对象

一个可执行模型身份至少包含基座及版本、adapter 完整对象、数值表示、目标层、分片与布局。adapter 对象包含每个目标矩阵的 A/B、有效因子内维 r、缩放 s 和对象版本。相同模型名、相同形状或相同 r 都不足以证明对象相同。

采用列向量约定：

u＝Ax，y＝W₀x＋sBu，

其中 W₀∈R^{dₒ×dᵢ}、A∈R^{r×dᵢ}、B∈R^{dₒ×r}。r 是因子内维，rank(BA)≤r。固定 adapter 可形成 W′＝W₀＋sBA；运行时分支则在每个目标层共享基座矩阵乘，按请求加回各自增量，再把已加增量的隐藏状态传给下一层。不能先执行完整基座模型，最后才添加一次 adapter 修正。

合并副本减少运行时低秩分支，但复制完整权重或支付串行切换成本。共享基座保留跨 adapter 合批机会，却增加分组、低秩计算、对象加载和版本管理。实数恒等式不保证浮点逐位一致；合并、量化与分组路径必须满足同一声明的误差和质量要求。r＝0 时直接跳过增量，不能计算 α/r。

请求准入时固定绑定 β＝(请求生命期、租户、基座版本、adapter 版本、执行配置、状态身份)。路由别名更新只影响后续绑定。不同 adapter 下相同 token 可能产生不同 KV，即使 adapter 未直接修改 K/V 投影，上游隐藏状态也可能已经改变。默认把影响状态的 adapter 身份及版本纳入前缀身份；只有证明状态独立于某项依赖，才可省略。tokenizer、位置、模态内容和数值表示也需要相容性证明，不能由形状推断共享。

[S-LORA](../sources/S-LORA.md) 给出低秩分支及合并关系；[S-SLORA](../sources/S-SLORA.md) 将共享基座计算与异 adapter 分支分开。[S-VLLM-PREFIX](../sources/S-VLLM-PREFIX.md) 的固定文档将父块哈希、块 token 和额外身份共同用于前缀检索，明确包含 LoRA ID 并只缓存完整块。允许同一 ID 更新权重时，还须补充版本或内容身份。哈希检索、授权与真实计算完成是不同条件。

### 物理容量与逻辑份额

对设备 d，令 U_d(t) 是时刻 t 实际占用或已承诺的唯一物理 backing 集合，容量账为

M_d(t)＝Σ_{o∈U_d(t)} allocated_bytes(o)，max_t M_d(t)≤Cap_d。

对象包括权重、adapter、KV、执行区、图缓冲、加载目的区、在途缓冲、待消费输出，以及分配器已保留但未使用的物理空间。已承诺的空闲页以后变成存活对象时只改变分类，不再加第二份容量。纯虚拟地址预留不计物理驻留；未 backing 的增长需求要作为未来分配承诺检查。

容量键是设备与物理分配身份，不是内容哈希。同一基座 backing 被多个请求引用只计一次；同设备上两份内容相同但分配独立的副本仍计两次。同一物理键若出现不同大小或代次，必须先解决账本冲突，不能静默去重。

上述不等式是总字节约束。即使字节足够，连续区间、对齐、页大小、可写权限、图地址、分片或内核布局也可能不满足。只有实际页映射及生命期也已确定，才能认定这个具体计划可分配。保守上界超预算说明当前预留方案不能被该上界证明可行，不证明其他分块、串行或重算方案都不可能。

逻辑计费另设租户账。共享权重怎样分摊属于服务契约；不能把逻辑份额相加变成另一份物理权重，也不能用减少计费份额使活跃 KV 立即消失。借出的容量只有在请求结束、迁移、换出或重算路线实际释放后才可收回。

## 驻留、并行与路由的候选

独占副本便于归因和限制干扰，但低频模型可能长期闲置。完整模型共同驻留复用设备时间，却减少各模型的 KV 余量。冷模型按需加载以启动等待换容量，等待还包括旧版本排空、存储争用、转换、通信组建立与预热。共享基座的 LoRA 可只交换增量；极热且长期固定的 adapter 则可能适合合并副本。

模型并行提供另一种复用方式。层间流水把不同层放到不同设备，让连续请求同时占据不同阶段；在各层执行效率不变的假设下，它不缩短孤立请求的串行计算，还增加阶段通信。收益来自突发期间的流水吞吐和可用容量。算子内并行可以缩短单请求计算，却增加集合通信和同步。实际分片必须给出逐 rank 权重、复制张量、KV、workspace 和链路账，不能用组内总显存代替逐设备约束。

[AlpaServe v1](../sources/S-ALPASERVE.md) 研究模型并行与多模型统计复用，但主要评估一次前向的非自回归模型，不能把固定服务时间、batch 饱和或模拟器结果直接套到逐 token decode。执行组内一个设备故障可能破坏整个组；组内并行也不能替代不同故障域的独立副本。

### 两设备流水为何可能获益，也可能反转

以下是设定模型。模型 A/B 的完整权重各为 12 GiB；独占方案将 A 放设备 0、B 放设备 1。流水方案把两模型各分成两个 6 GiB 阶段：设备 0 保存 A₀/B₀，设备 1 保存 A₁/B₁，每设备权重仍为 12 GiB，执行区与请求状态另计。两个模型共享同一条 FIFO 流水，每设备一次执行一个阶段。

设单设备一次请求耗时 D＝10 ms；流水每阶段耗时 5.5 ms，已包含这一设定的阶段开销。四条 A 请求同时到达、B 没有请求时，独占方案完成时刻为 10、20、30、40 ms，均值 25 ms。流水在设备 0 依次运行 A₀，设备 1 在对应前阶段完成后运行 A₁，完成时刻为 11、16.5、22、27.5 ms，均值 19.25 ms。首条更慢，突发均值却下降。

若 A/B 同时各到达四条，独占方案的两设备同时工作，八条请求均值仍为 25 ms。共享流水的八个完成时刻从 11 ms 起每隔 5.5 ms 一个，均值变为 30.25 ms。两设备都持续饱和时，独占总服务率为 2/10 请求/ms，流水为 1/5.5 请求/ms，开销使后者更低。

因此应保留模型间突发的时间相关性。只给每模型平均到达率，或分别打乱轨迹，会删除决定复用收益的同时突发关系。真实 decode 还包含长度、KV、批组成和逐轮公平变化，需重新构建事件与资源模型。

## 放置与阶段划分怎样求解

### 先生成合法执行配置

设模型有 K 个保持拓扑顺序的层，候选流水阶段数为 S。对连续层段 [i,j)，预先给出阶段时间估计 ℓ(i,j) 和逐设备物理需求；不满足容量、布局或分片条件的层段标为不可行。在选择加性近似时，ℓ 可由逐层时间相加并加入相应通信；融合、cache 和不同并行配置改变时，必须重新校准，不能假设任意层段都可相加。

令 F(s,k) 表示前 k 层分成 s 个非空阶段时，能够得到的最小最大阶段时间：

F(0,0)＝0，其余未初始化状态为＋∞；

F(s,k)＝min_{s−1≤i<k，段[i,k)可行} max(F(s−1,i),ℓ(i,k))。

记录取得最小值的 i，从 F(S,K) 反向恢复所有阶段边界。不存在有限前驱即表示这个阶段数及配置下无解。空模型只接受零阶段；非空模型不允许零阶段或 S>K。时间复杂度为 O(SK²)，状态为 O(SK)，段成本准备另计。

例如层时间为 [6,1,1,4] ms，分两阶段。按层数均分得到 [6,1] 与 [1,4]，瓶颈 7 ms；动态规划得到 [6] 与 [1,1,4]，瓶颈 6 ms。若后者第二阶段容量不够，必须删去该分割，不能保留时间最优却无法分配的配置。

这个目标优化流水稳态间隔；孤立请求延迟还需加所有阶段及通信。阶段数增加也可能增加同时存活的激活、通信缓冲和状态版本，不能仅靠 F 值决定放置。

### 有限候选上的放置搜索

下面是从 AlpaServe 的配置枚举与模拟筛选思想推导的一种保守规划器，不声称复制其全部实现或找到全局最优。设备组在本候选族中互不重叠，同组允许驻留多个模型。其他共享组织可以另建候选。

目标先明确：在固定 offered 轨迹上，最大化满足数值、TTFT、ITL/完成时间等共同约束的完成请求数；另检查每租户拒绝率和份额约束。成本向量保留设备时间、加载字节、容量峰值与等待；没有指定偏好时不把异单位量直接相加。

```pseudocode
输入：有限模型/版本集合；有限设备分组与执行配置；固定请求轨迹；
      每设备容量、布局与链路条件；租户目标；束宽 B≥1；副本上限 R
输出：满足声明约束的最佳已发现计划，或未找到及逐候选原因

若模型集合为空，返回空计划；若配置集合为空，报告缺少候选
对每个设备分组及配置组合：
    用阶段划分和逐 rank 需求生成合法执行配置
    初始化 beam 为仅含空放置，best 保存当前可接受计划
    对深度 1 到 R：
        extensions ← 空集合
        对 beam 中每个计划 P：
            对每个有限的 (模型版本，设备组，执行配置)：
                构造增加一个副本的 P′，给独立 backing 新物理身份
                共享只在已有兼容 backing 确实被共同引用时去重
                建立权重、KV 承诺、workspace、加载与过渡版本生命期
                若逐设备字节、映射、执行身份或链路硬条件失败，记录并跳过
                按下述事件规则评估固定轨迹，保留所有拒绝与未完成请求
                以完整计划签名去重，把 P′ 加入 extensions
        若 extensions 为空，结束这个组合
        按预先声明的目标排序并保留前 B 个进入 beam
        仅当租户和服务约束满足时，更新 best；中间深度也可成为 best
合并所有组合的 best；返回已发现结果和适用轨迹
```

束搜索丢弃的分支可能包含更好方案；有限候选未找到结果不等于所有放置都不可行。物理需求随驻留和共享集合变化时，要在每个扩展中重算，不能固定一个“每模型大小”做所有装箱。

轨迹评估须展开执行依赖。对于固定 FIFO 流水，令 f(j,k) 是第 j 条请求在阶段 k 的完成时刻，阶段时间为 ℓ(j,k)：第一阶段等待请求到达及前一请求释放设备；后续阶段满足

f(j,k)＝max(f(j,k−1),f(j−1,k))＋ℓ(j,k)。

缺少的前驱视为初始设备空闲；加载和输入传输另作为必须完成的前驱。共享链路也有自己的占用时间，不能让两次传输各自使用独占带宽。真实模型有不同执行组或异构阶段时，使用对应设备和链路的事件依赖，不能继续套同一条 FIFO 递推。

逐 token 服务还要在本轮完成、采样和状态提交之后产生下一轮候选。每个时刻先处理已完成的资源事件，再处理到达并运行准入/轮转；只有真正完成的对象才可释放或供消费者使用。拒绝不从 offered 分母删除，窗口结束仍未完成的请求单列。服务时间是估计时，结果属于该模型的有限回放，不能称为未来总体 SLO 保证。

## 运行时准入、路由与公平

### 可以等待加载，与可以提交执行不同

设备组的基座、通信组和执行路径就绪后，某个冷 adapter 仍可尚未驻留。此时可以接受一个有完整资源承诺的待加载计划，但必须在实际加载完成后才能提交依赖它的执行。不能把“adapter 未 READY”一律当成永远不可路由，也不能把“允许等待加载”当成现在即可读取。

准入状态包含未准入、已绑定待加载、就绪待服务、在途、待输出和终止；对象另记 FETCHING/READY、逻辑引用、实际读写者、发布资格和代次。这些责任可以同时存在，不能用单个枚举替代。

```pseudocode
输入：请求 r；实际设备与链路状态；对象目录；页池；租户账；输出预算
输出：拒绝/等待原因，或不可变绑定及临时资源责任

校验非空输入、长度与生成上限、权限、完整模型/adapter 对象和执行契约
若无须生成且无需执行其他工作，按协议完成，不分配无用设备状态
对每个基座与执行组已就绪的候选 g：
    固定对象版本，取得已复用状态的真实计算边界
    计算本轮新增可写 KV、共享尾页 COW、加载目的页、staging 和输出需求
    只将回收条件已经满足的旧页算作当前可用空间
    若缺少合法加载源、映射、容量、租户份额或执行路径，排除此计划
    构造依赖时间线，估计排队、加载、计算、通信和输出的完成代价 E_g
若合法计划为空，排队或拒绝，并记录具体阻塞原因
选择 E_g 最小的合法计划；并列按预先声明的稳定规则处理
在协调区内重新核对资源与代次，取得已有对象保护并预留全部新增资源
任一步失败，撤销本请求尚未提交的临时改动，保留旧状态
成功后发布请求绑定；冷对象登记复制责任并进入 FETCHING
复制完成且完整对象、布局和分片核对成功，才发布 READY
实际提交前再次确认全部依赖已 READY，登记读取、写入和输出责任
完成后提交全层一致的新状态和允许的输出，再释放本次实际使用责任
```

已提交 DMA 或设备工作的目的页不能在失败/取消时立即归还；应停止新访问，排空已有操作后再回收。完整 KV 命中却没有末行 logits 时，仍需合法的末 token 重算或另有已验证的 logits 缓存；不能因为待计算长度为零就让请求永远停在就绪队列。具体 token 边界与安全写区由[连续批处理](../algorithms/iteration-batching.md)展开。

设定路由候选 A 排队 100 ms、加载 0、计算 10；B 排队 10 ms、冷加载 40、计算 10，且能预留完整加载目的区；C 排队 0，但没有 adapter 目的空间。按串行设定，合法计划 A/B 的代价为 110/60 ms，选 B；B 要等加载完成才可执行，C 不能用最低队列绕过容量。

若把 C 的队列改成 10，与 B 并列，忽略合法性的最短队列实现可能因输入顺序选 B，也可能选 C。因此该负对照不能断言“必选 C”。检查应保留这个并列回归，另用 C 严格最短的设定触发错误，并验证正确路由在候选重排后仍只选择合法最小代价。

### 跨轮轮转与进度边界

优先同 adapter 请求可减少活跃增量和准备开销，却可能使冷租户饥饿。一种明确的基线是维护持续存在的租户环和各租户 FIFO：新非空租户加入环尾，每次给环首一个合法最小服务片，然后仍有请求的租户移到环尾；一轮预算用尽后保留游标。未就绪或本轮容量不可行的请求保留阻塞记录，扫描其他可执行工作。

```pseudocode
初始化：租户环为空；每租户请求队列为空
到达：请求进入本租户队尾；租户此前为空则加入环尾
每轮：
    初始化本轮 token、页、时间与输出预算
    按持久环顺序访问租户
    为其队首或契约允许的首个就绪请求尝试一个最小服务片
    若可行，完成预留并记入不可变执行计划，扣减相应预算
    若失败，撤销这次临时预留，记录原因；不得消耗虚假的服务额度
    仍非空的租户移到环尾；保留跨轮位置
    预算耗尽，或完整一圈没有任何可行进展时结束本轮
完成事件：按请求和代次提交进度，修正实际服务成本，移除已终止请求
```

若持续非空且就绪的租户至多 M 个，每个最小片资源可行，资源最终完成，新租户不插到既有等待者前面，则一个这样的租户至多经过 M 个成功服务机会取得一次进展。若每个机会到下一次调度的时间不超过 T，可得到 M·T 的粗等待上界。它保证租户进度，不自动保证租户队内每条请求同样的界；还需有限前驱和有限准入。

每轮重新按租户名从头扫描不是上述轮转。M＝3、每轮仅一个片且 A/B/C 一直就绪时，持久轮转为 A、B、C、A……；每轮重置为 A 优先会使 B/C 无进展。无限输出背压、不可回收页或不可完成设备操作同样会破坏进度前提，必须限准入或使用有证明的恢复路线。

公平单位也要明确。等 token 不等于等设备时间：相同 query 数在历史 32 与 32768 时有不同 attention 工作。可以按预测设备时间扣欠额，再以实际观测修正，但要限制一次不可抢占片，并保留硬容量检查。

## 共享基座场景的完整成本账

以下均为设计设定，适用于声明的稠密 decoder 和状态表示，不是 GPU 测量。单设备可用 24 GiB，基座 12 GiB，workspace/执行缓存 3 GiB，额外保留 1 GiB，adapter 与 KV 的共同预算为 8 GiB。额外保留与其中实际对象必须避免重复计数。

共有 128 个 adapter，32 层、每层两个 4096×4096 线性层使用 rank 16、FP16 LoRA。一个目标矩阵的增量为

r(dᵢ＋dₒ)b_w＝16×8192×2＝262144 字节＝256 KiB。

64 个目标矩阵使一个 adapter 为 16 MiB，128 个共 2 GiB 主存；主存中的冷对象还与 KV 换出、加载转换和分词竞争。16 条请求使用不同 adapter 时，端侧增量为 256 MiB。同一 adapter 被多请求使用时，只有真实共享 backing 才去重。

普通稠密 GQA 的全层 KV 主项为

b_KV＝2LH_kv d_h b_s 字节/token，

L 为层数，H_kv 为 KV head 数，d_h 为 head 维数，b_s 为状态元素字节。不同 K/V 维数、量化、MLA、滑窗或其他状态表示须重写此式。设本例 b_KV＝128 KiB/token，每条 2048-token 历史需要 256 MiB；16 条共 4 GiB，加 adapter 为 4.25 GiB。若全部再生成 512 个需缓存的 token，KV 另增 1 GiB；页尾、元数据和过渡版本另计。

30 条同类历史且 adapter 各异时，KV 为 7.5 GiB，adapter 为 480 MiB，仅剩 32 MiB。第 31 条新增 256＋16＝272 MiB，应拒绝当前准入计划。即使不再准入，每轮 30 条各增长一个 token 仍增加 3.75 MiB；忽略页舍入时，32 MiB 只够八轮共同增长，第九轮已越界。准入不能用“当前还放得下”代替持续推进的资源策略。

两个独立 12 GiB 合并副本已经用尽设备容量，无法容纳本例执行区与 KV。一个合并槽串行切换则可能合法，但需排空旧读者并计算合并、切换和等待成本。共享基座在这里扩大容量可行域，不单独证明服务目标达标。

### 计算与设备读取

一层总 query 数为 Q 时，基座线性层约需 2Qdᵢdₒ FLOPs；低秩分支约需

F_low＝2Σ_i q_i r_i(dᵢ＋dₒ)。

若统一补到 R≥max r_i，低秩主项变为 2Σ_i q_i R(dᵢ＋dₒ)。8 个 rank 16 与8 个 rank 64、q_i 相同时，实际维度和 640，补齐后 1024，低秩部分倍率为 1.6。它不适用于整个 forward。padding 还必须保持原 scale，不能把 α/r 改成 α/R。

权重逻辑读取主项为基座矩阵及活跃 adapter 的实际存储字节。一个融合批能否只从 HBM 读取一次基座，取决于 cache、分块和重读；不能把参数大小直接称为实测 DRAM 流量。共同前缀减少唯一 KV 驻留，但不同请求仍要取得各自可见历史。没有跨请求广播或片上复用证明，KV 读取不能按物理共享份数直接去重。

### 加载、通信、准备与同步

有效 H2D 带宽为 B、未命中对象总字节为 z 时，z/B 是相应共享链路的纯传输下界，另加存储、CPU 转换、页表、排队与同步。16 MiB 在 16 GiB/s 下为 0.9765625 ms；16 个不同未命中为 15.625 ms。若其他串行工作为 24 ms，关键路径为 39.625 ms，接近 40 ms ITL 上限。带宽降至 8 GiB/s 时变成 55.25 ms；忽略加载会错误保留这个候选。

若预取与当前计算能够重叠，理想阶段时间接近 max(T_compute,T_transfer)，再加不可隐藏的首尾和依赖；不能同时声称完全重叠又把两者全部相加。预取需要额外目的页和可能的 staging，错误预测增加流量并可能挤掉 KV。带宽竞争还可能让两条路径同时变慢。

流水每个边界传输的激活主项为 Qd_cut b_a 字节，其中 d_cut 是边界宽度，b_a 是激活元素字节；启动、链路争用与接收完成另计。TP 的元素量及 LoRA 分片取决于具体轴，须从已验证的执行配置取得，不能把总参数平均除以设备数。单设备候选没有模型内设备间通信，但用户输出传输仍进入端到端指标。

准备成本包括候选扫描、排序/轮转、对象检索、分组和行逆映射、页分配、图桶与描述填充。同步包括加载发布、阶段/collective 依赖、状态提交和最后使用回收。驻留成本既有峰值字节，也有对象长期占住容量的字节时间；后者需要结合被阻塞请求价值才能转换为服务代价。减少小算子可能同时增加等组时间，必须以完整请求时间线比较。

## 版本更新、取消与迟到完成的组合轨迹

继续用本例 16 MiB adapter。r1 已绑定 a:v1、正在读设备页 p1；r2 将绑定 a:v2。旧版本仍在途时，v2 的新 backing 至少再占 16 MiB，可能还需独立 staging。若共同预算仅剩 32 MiB，双版本已经消耗其中一半；不能把 v1 的预期释放提前用于 v2 的承诺。

1. r1 固定 β_r1 和 p1 的页代次，持有逻辑引用；执行提交登记独立操作 ID，取得实际读权。缓存目录是否保留对象另记。
2. 发布路由别名 a→v2，新请求绑定 v2，r1 的绑定保持 v1。预留 p2 与 staging，登记复制操作，v2 为 FETCHING。
3. r2 可以进入有完整承诺的待加载状态；复制成功并核对 A/B、scale、布局与全 rank 对象一致后，v2 才 READY。r2 的实际执行在其后提交。
4. r1 取消后停止新业务提交和交付，释放可结束的逻辑责任，并撤销不再需要的目录资格；旧执行仍保有 p1 的实际读权。
5. 旧执行完成事件按操作 ID 和页代次结算一次。重复事件没有第二次扣减效果，不能减少 p2 或后来复用 p1 的新操作责任。
6. p1 无逻辑引用、无目录保留或已合法撤销目录、无在途读写后才可回收。复用 p1 时增加页代次，旧通知不能作用于新代。
7. 若 r2 在复制期间取消，未提交执行，但复制写者仍须排空；完成后释放失败请求的承诺。对象可否继续留给其他请求由仍存活的引用决定。

反例是将 p1 原地改成 v2，再让已提交的 r1 继续读取同一地址。路由表正确也救不了旧读者，其实际结果已经改变。另一个反例是在复制取消时立即复用 p2，迟到 DMA 会覆盖新对象。独立页、写时复制或其他方案都可以，但必须保留旧读写者的完成关系。

## 条件变化与区分实验

| 观察或条件变化 | 竞争解释或保留条件 | 区分干预与反证后的修正 |
|---|---|---|
| 模型并行在部分轨迹上更快 | 突发互补减少等待；更高带宽或更好分片也可能降低服务时间 | 固定阶段服务时间，只改变模型间到达相关性；同时突发使收益消失时，应收窄统计复用结论 |
| 混合 adapter 吞吐下降 | 冷加载、小 kernel、准备开销、页压力或基座饱和 | 固定 offered 轨迹，分别预驻留、改变分组及增加可用页；预驻留后仍慢则撤回纯加载解释 |
| rank 桶增大后变慢 | padding 算术、图变体或驻留挤掉 KV | 固定有效 rank，仅改桶宽，分记低秩执行、准备、准入和等待；只有排队增加不能归为 FLOPs |
| 缓存命中提高但 TTFT 变差 | 亲和路由集中、热页占容量或冷对象等待 | 固定真实命中边界改变路由，再固定路由改变驻留；按等待发生位置修正解释 |
| 同文本换 adapter 后输出错误 | 身份漏版本、错误可写页或位置/数值表示不符 | 用独立完整输入计算参考，关闭复用，再只改变 adapter；错误随非法命中出现才支持身份解释 |
| 更新或取消后旧结果变化 | 原地覆盖、混合 A/B 发布、提前回收或旧事件扣新引用 | 延迟真实读者/复制完成，比较保留旧 backing 与提前复用的负对照；字段正确但内容变化仍判失败 |
| 聚类均值改善而冷租户恶化 | 等组、重复驱逐或每轮重置公平游标 | 保留相同到达、长度和取消，只改最大等待、驻留或持久游标；冷租户无进展时放弃纯热优先 |
| 全部模型持续饱和或隔离要求加强 | 身份与硬容量仍保留，统计互补或共同故障前提改变 | 重新比较独占副本、设备组拆分与更少并行；不能延用低负载下的选择 |

数值检查应比较每个 adapter 的独立执行与共享执行，覆盖异 rank、同 rank 异对象、零增量和行重排；这些线性与分片细节见[多 LoRA 执行](../algorithms/lora-serving.md)。目标设备实验另需验证真实布局、allocator、异步可见性、kernel、链路争用及数值路径。

随章 tools/check_k_work_007_full.py 是确定性、只读、离线的 Python 标准库模型。它以显式物理槽集合核对容量，以枚举所有切分核对阶段动态规划，以合法集合参考核对路由，以持续就绪窗口核对轮转，并实际制造旧读者内容改变的负对照。它还保留旧路由并列用例，检查严格最短非法候选、容量阈值、增长、传输和回收代次。软件模型通过不能证明 GPU 测量结果、未来总体 SLO 或知识改善了 Agent 的构建效果。
