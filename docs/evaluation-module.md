# 评测与实验设计模块

本模块帮助 Agent 根据模型、硬件、workload 和服务目标定义可比较的性能问题，设计能够区分解释的实验，并根据完整观测作出保留、调整或放弃的决定。指标名称不能代替事件合同，压测器运行成功不能代替有效实验，经验分位数也不能单独证明总体 SLO。内容沿用既有六项标准，不规定系统组件或研发施工顺序。

## 一次评测应能还原的推理

首先说明决定是什么，例如在共同质量和用户等待要求下是否采用一个融合、缓存或调度改变。由此确定要估计的是固定形状的一次执行、一个有限离线任务集的总完成成本、外部到达服务的合格容量，还是交互用户在反馈负载下的体验。这些目标可以同时有价值，各自需要匹配的人口、计时边界和独立重复。

随后将候选作用与其他因素分开：哪些条件保持、哪些因素随机化、哪些 workload 层必须共同覆盖、缓存和编译状态怎样处理、先后次序怎样安排。如果候选效果随并发或缓存状态反转，应保留交互和适用条件，不能只报告等权混合后的单一“提升”。改变混合负载会改变队列与批量形成时，事后重加权不能替代新负载的真实运行。

实验计划连接原始事件、明确估计量、正确性与质量、完整失败账、独立单位、样本/预算、查看规则和最终决定。先保留能够支持目标结论的正常计时，再用有针对性的 profiling、资源或条件干预区分解释。工具扰动下的诊断结果需要回到共同正常路径确认。

最后分别判断效果是否超过值得维护的门槛、SLO/质量是否保持、统计证据是否充分以及资源成本是否值得。未区分、缺观测和不适用有各自含义，不能都填成零或通过。探索阶段挑出的候选应在未用于选择的独立运行或保留负载上确认。

## 口径交界需要怎样连接

TTFT 的起点可以是计划到达、实际发送或服务端接收，终点可以是内部选择 token、接收首响应或收到首个有效内容。必须随名称或字段保留边界；同一客户端的持续时间不需要服务器时钟同步，跨机阶段拆解则另需时钟证据。计划迟发对用户等待可能有贡献，不能通过把计时起点推后消失。

最后内容、协议结束、客户端提交和物理排空也不同。逐 token TPOT 的终点是最后内容；以最终响应构造的归一化时间可能多计尾部协议等待。只有 chunk 时间时，不能补造精确 token 轨迹。请求吞吐、输出 token 吞吐、每用户输出速率和合格完成率使用各自人口与时间窗，不能仅更换单位标签。

完整到达模型还可能记录终止后发生的实际服务端接受决定，以保留服务端责任；业务资格账则不应因此复活已终止请求。前者可称实际接受决定数，后者为有效业务准入数。两个责任账应通过身份和事件关联，不能直接把同名 admitted 字段相加。

服务事件观察截止与离线质量证据截止也应分别保留。质量评定晚于服务完成不应增加用户延迟；截至某时尚未得到质量结论的结果保持待判。后续报告可以绑定新证据重新结算，但不能静默改写已经发布的旧截止快照。

生产侧完整不可变输出已经确定，也不代表客户端已经看到全部内容。绑定这个输出身份的质量证据可以先于客户端最后内容或协议结束到达；资格归约应保留证据，等待其所需业务事实成立。相同证据重复导出可以幂等处理，同一固定规则对同一输出产生矛盾的确定标签则使该资格证据失效，不能按最后标签覆盖。随机评审观测若需要聚合，应先由明确的聚合规则产生证书。增加质量证据截止不能把服务截止之后才完成的请求补进原完成集合。

## 检验读者是否能使用

读者应能从一张含迟发、多 token chunk、最后内容、协议结束、取消和质量评定的事件表重建指标，并指出哪些量不可观测；应能为离线、开环和闭环目标选择不同设计，并解释各自允许的推论；应能用因子交互与负载分层解释条件反转；应能从效果、容许超限率和预算规划有效重复，执行与其统计假设匹配的停止或确认规则。

对“平均更快但 p99 变差”“低并发有效、高并发无效”“完成者延迟下降而拒绝增加”“局部 kernel 改善而用户 TTFT 不变”等观察，应提出不同预测和区分实验。这里没有要求每个实验覆盖所有硬件，也不以一次通过证明所有未来负载。

本模块的检查与实际执行、非作者审查和读取证据由[本轮记录](evidence/evaluation-module-20261029/workflow.json)绑定。合成事件、有限统计模型和离线算例检验其声明范围；真实服务性能、尾部概率、质量与 Agent 使用收益需要各自的证据，不能由本页或检查数量替代。
