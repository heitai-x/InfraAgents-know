CacheGen: Fast Context Loading for Language Model Applications
Yuhan Liu, Hanchen Li, Kuntai Du, Jiayi Yao, Yihua Cheng, Yuyang Huang, Shan Lu†,
Michael Maire, Henry Hoffmann, Ari Holtzman, Ganesh Ananthanarayanan†, Junchen Jiang
The University of Chicago
†Microsoft
Abstract
As large language models (LLMs) take on more complex
tasks, their inputs incorporate longer contexts to respond to
questions that require domain knowledge or user-specific con-
versational histories. Yet, using long contexts poses a chal-
lenge for responsive LLM systems, as nothing can be gener-
ated until all the contexts are fetched to and processed by the
LLM. Existing systems optimize only the computation delay
in context processing (e.g., by caching intermediate key-value
features of the text context) but often cause longer network
delays in context fetching (e.g., key-value features consume
orders of magnitude larger bandwidth than the text context).
This paper presents CacheGen to minimize the delays in
fetching and processing contexts for LLMs. CacheGen re-
duces the bandwidth needed for transmitting long contexts’
key-value (KV) features through a novel encoder that com-
presses KV features into more compact bitstream represen-
tations. The encoder combines adaptive quantization with a
tailored arithmetic coder, taking advantage of the KV features’
distributional properties, such as locality across tokens. Fur-
thermore, CacheGen minimizes the total delay in fetching
and processing a context by using a controller that determines
when to load the context as compressed KV features or raw
text and picks the appropriate compression level if loaded as
KV features. We test CacheGen on three models of various
sizes and three datasets of different context lengths. Com-
pared to recent methods that handle long contexts, CacheGen
reduces bandwidth usage by 3.7-4.3× and the total delay in
fetching and processing contexts by 2.7-3× while maintain-
ing similar LLM performance on various tasks as loading the
text contexts.

Introduction
With their impressive generative capabilities, large language
models (LLMs) are widely used [1,5,7,11] in personal assis-
tance and recommendation, AI healthcare, and marketing, to
mention a few. The widespread use of public LLM APIs (e.g.,
GPT-4 [9]) and application frameworks (e.g., Langchain [10]),
combined with the open-source of industry-quality LLMs
(e.g., Llama [3]), further boosts LLMs’ popularity.
With LLMs increasingly used in complex tasks, many ap-
plications augment their user inputs (i.e., prompts) to LLMs
with long contexts containing at least thousands of tokens.
For example, some context supplements user prompts with
domain-knowledge texts so that LLMs can generate responses

This trend of long contexts is well reflected by the recent

short LLM inputs can still be useful [65, 92], many studies
have shown that longer inputs often help improve response
quality and coherence [25,26,28,38,48,87,97,106].
Although improving response-generation quality, using
long context poses challenges to response-generation latency,
as no response can be generated until all the contexts are
loaded and processed.
To tackle this latency challenge, previous work reduces
the computational delays of context processing by caching
the intermediate processing results: key-value (KV) features.
This way, instead of repeating the self-attention computation
on text context, whose complexity is super-linear to the text
length [25,39,87,98,113], LLM systems can directly use the
KV features and skip the redundant computation.
Unfortunately, previous work reduces the computational
delay at the cost of increased communication delay, as KV
features are multi-dimensional tensors of floating-point num-
bers and can be orders of magnitude larger than their corre-
sponding text contexts. The cost of loading KV features is
particularly concerning, as in practice, they often need to be
fetched remotely from another machine(s). For instance, a
database of background documents might reside in a sepa-
rate server and the supplementary documents assisting LLM
inference are only to be selected and fetched to the LLM

large tensors, still require high bandwidth to transmit.
Therefore, solely optimizing computational delay is not
enough for long-context response generation and may even
degrade the end-to-end performance, as loading the KV fea-
tures increases the network delay. Instead, LLM systems must
optimize not only the computational delay but also the com-
munication (network) delay in handling long contexts.
This paper presents CacheGen, a fast context-loading mod-
ule for LLM systems, designed for (1) reducing the bandwidth
needed to transmit a context’s KV features and (2) minimiz-
ing the total delay in fetching and processing contexts, rather
than each separately.
CacheGen reduces the bandwidth needed for transmitting
long contexts’ KV features by compressing, instead of drop-
ping or rewriting, these feature tensors into more compact
bitstreams using a new KV encoder. The design of our KV
encoder leverages unique properties of KV features across
tokens and layers to achieve high size reduction and little
information loss. It uses a tailored arithmetic coder that takes
advantage of KV features’ distributional properties, such as
locality across tokens; it varies compression strategies across
layers of KV features, leveraging the fact that LLM’s gen-
eration performance has different sensitivities towards the
compression losses at different layers of KV features.
With its KV encoder, CacheGen has the flexibility of trans-
mitting a context in different forms, including KV features in
multiple bitstream representations each with a different com-
pression rate1 and the original raw text, which incurs more
LLM processing cost but no decompression cost or informa-
tion loss. Right before transmitting a context, CacheGen uses
a controller to decide which form to use, flexibly navigating
the tradeoffs among LLM generation quality, the transmission
bandwidth, and the decompression cost. It picks the context
form that optimizes the combined cost of transmission and
decompression, or the form that fits in a given time budget
with the least information loss.

To put CacheGen’s design into perspective, each of its com-
ponents (adaptive compression and KV cache) may have been
studied before. Nonetheless, the exact designs of these com-
ponents in CacheGen embrace domain-specific insights about
KV features and are integrated into an end-to-end system that
explicitly minimizes LLMs’ network and computation delays
regarding context for the first time.
We evaluate CacheGen on three models of different capaci-
ties and three datasets of different tasks that use contexts of
different lengths. Compared to a baseline quantization and
arithmetic coding scheme that does not consider the distribu-
tional properties of KV, CacheGen can save the bandwidth
usage for transferring KV features by 3.7-4.3× and the delays

cuts the latency of processing KV features by 2.8-4.5× with
less than 1% drop in F1 score or a perplexity score increase
of 0.5. Moreover, at similar task performance, CacheGen also
has lower total fetching, processing delays and higher LLM
performance than more sophisticated baselines that modify
contexts or retrain models to shorten the contexts.

2.1
Transformer basics
Transformer models have revolutionized the field of natural
language processing (NLP), becoming the de-facto architec-
ture for most NLP tasks [28, 30, 35, 54, 78, 98, 114]. Today,
most generative NLP services are based on transformer mod-
els, including T5 [84], Llama [96], PaLM [35], OPT [116],
and BLOOM.
A transformer model takes as input a sequence of tokenized
words and generates an output response, which is another

generation process includes two high-level steps. First, the
attention module processes the input tokens to obtain encoded
features. Then, the encoded features of the input are utilized to
generate new tokens in an autoregressive manner. Specifically,
the input tokens and previously generated tokens are fed into
the transformer model to generate the next token.
The key of the transformer architecture is the attention mod-
ule. Each layer of the attention module produces an attention
matrix, which models the connections between each pair of
tokens. The attention matrix at every layer is obtained by ap-
plying a non-linear neural network operation on the attention
matrix of its previous layer. Intuitively, the attention matrices
of deeper layers might embed a more complex understanding
of the tokens under consideration.
While the attention module is crucial, it is known to be
compute-intensive. Given an input of N tokens, the compu-
tation overhead of computing the attention matrices grows
quadratically, O(N2). Though the complexity could be re-
duced to O(NlogN) (e.g., [57,69]), such reduction often de-
grades the generation quality. Once the attention matrices are
obtained, the time to generate (decode) each token is quite
marginal and can be reduced to almost constant on GPUs.
2.2
Long contexts in LLM applications
Traditionally, the input of an LLM is a relatively short prompt,
as illustrated in Figure 3(a). Since the prompt contains limited
information, the LLM generates the response based solely on
the knowledge already embedded in the LLM itself.
However, as LLMs are used in more real-world applica-
tions, it is no longer sufficient to rely on the knowledge em-
bedded in the LLM. Instead, LLM applications often append
additional texts, referred to as the context, to supplement the
prompt input to an LLM3. To make our discussion more con-
crete, we highlight two types of applications, retrieval-based
apps and chat apps.

Retrieval-based apps (Figure 3b) use LLMs to answer
queries that require domain-specific knowledge. Examples
include question-answering systems [28,48,88], code under-
standing systems [61,88] or fact verification systems [48,61].
They use a background database that contains a large num-
ber of background documents. On retrieving a question, they
use embedding-based search algorithms (e.g., DPR [48,50],
BM25 [48, 85]) to quickly identify a subset of background
documents from the database, prepend these documents to
the prompt, and feed them together as input to the LLM. Note
that the search procedure is done by a seperate DNN or a
vector similarity search algorithm, which is not part of the
LLM.
Chat apps (Figure 3c) become popular with the rise of
OpenAI’s ChatGPT and have many similar products [8,37].
To produce high-quality and coherent responses, a user’s con-
versation history with the LLM, or at least part of it, is often
included in the input to the LLM as the context. For instance,
some applications supply a series of prompts to the LLM
(ChatGPT) to create a character in a video game and then
interact with the character by asking questions [56]. Chat app
users themselves are also intentionally using long prompts to
offer more background information (i.e., context) to the LLM.
For example, in few-shot learning, users provide several long
examples and their desired responses to the LLM before ask
the real questions [20,30].
Importantly, LLM applications use increasingly long con-
texts to raise the probability of including the right informa-
tion needed to generate high-quality, coherent responses. For
example, the user may ask “Which of the following coun-
tries generated the most total energy from solar sources in
2019?” [90]. It is hard for the LLM to answer the question
correctly without retrieving enough background documents
for the relevant countries the user is asking for. Though it is a
hypothetical example, many studies have shown that the accu-
racy of the generated answers increases with more retrieved
documents [48–50]. For instance, FiD [48] found that the
accuracy score increased from 40% to 48% when increasing
the number of context tokens from 1K to 10K. Retro [28]
shows that the perplexity (a proxy score of generation quality)
improves significantly when increasing the number of context
tokens from 6K to 24K.

To take in such long contexts, the LLM industry has been
training LLMs with the capability to accept ever longer in-
put sequences. For instance, Vicuna models [120], GPT-4-
32K [78], and MPT models [94] can take up to 32K tokens
as input. Latest models like LongNet [42] can even take up to
1 billion tokens as input.
In essence, long contexts play an increasingly important
role in LLM applications for two reasons. First, modern LLMs
have a superb ability to reason about new texts and potentially
learn new knowledge from them. To exploit this ability, many
works on in-context learning aim at optimizing what should
the LLM input encompass to induce better responses from
LLMs. Second, while LLMs are sometimes fine-tuned in
specific domains, it is not always feasible. For instance, it is
unrealistic to fine-tune an LLM for each user in chat apps.
The background database may be managed separately from
the LLM provider in retrieval-based apps. Due to their huge
number of parameters, fine-tuning LLMs is also slow and can
be very tricky to do right (e.g., catastrophic forgetting, loss of
reasoning ability, etc [43,64] ).
2.3 Saving computation by caching KV features
Recall that the computation overhead of the transformer (at-
tention module) on a context grows superlinearly (quadrat-
ically) with longer contexts (§2.1), so longer contexts will
dramatically increase the computation delay (Figure 4a).
Many recent works have tackled the long contexts’ com-
putation overheads. A common optimization, illustrated in
Figure 4b, is to cache the intermediate outcomes of contexts,
namely the key and value (KV) features, in GPU memory.
For a given text with N tokens, the KV features are two ten-
sors, each with the shape [N,c,l], where c is the number of
channels and l is the number of layers. For instance, with the
LLaMa-7B model, there are 4096 channels and 32 layers.
When the context is used again as part of another LLM in-
put, one can save the computation delay of processing the con-
text by using its KV features to reconstruct the self-attention
matrices of the context. To put it more concretely, the compu-
tation delay can be reduced by about 15-30× for the Llama-
7B model on contexts with more than 5K tokens, assuming
the KV features are already in GPU.
Caching KV features of a context, called a KV cache,4 can
be used in both chat apps and retrieval-based apps. In chat
apps, the context is the past prompts and responses, whose
KV features can be cached when the past prompts were first
processed and responses were first generated [38]. Retrieval-
based apps often preprocess each background document by
the LLM to compute the self-attention matrices and cache
their KV features [29,40,74,75].

Hidden network delays of loading contexts
Current LLM systems assume that the KV cache is already in
the GPU memory (or on the same machine), so they focus on
reducing computation delays. In practice, however, the KV
cache is not always in the memory of the GPUs that run the
LLM inference. Rather, the context of an LLM input often
needs to be fetched remotely from another machine(s).
In retrieval-based apps, the background documents can be
hosted on different servers than the LLMs [28,63]. One reason
is that background documents can be too big (even in raw
texts) to be stored locally on the GPU servers running the
LLM. For example, a recent work [63] uses a background
database that contains 364 Million documents [83], requiring
750 GB to store their texts. In another recent work [28], the
documents contain up to 2 trillion tokens and require 1 TB of
storage. Moreover, the background database may be managed
by a different service than the LLM service for proprietary
considerations [15,63].
In chat apps, a user may resume her conversation with the
LLM a few days after the last interaction. In these cases, the
KV cache of her conversation history may need to be swapped
out of GPU memory to save space for other active conver-
sation sessions [46, 112, 115]. Moreover, a user may issue
her prompts to the LLM from different locations at differ-

network bandwidth of 1Gbps, for example, the transmission
delay of KV feature over the network bandwidth takes more
than 10 seconds. By contrast, processing the text context by
the transformer takes only 5 seconds on an A40 GPU.

4
CacheGen Design
This section presents CacheGen, a fast context-loading mod-
ule for LLM inference systems. CacheGen minimizes the
overall delay for loading and processing a given context while
preserving the performance of the LLM.
Specifically, we define the overall delay as the time be-
tween obtaining the input (the prompt and context) and the
generation (decoding) of the first token. We refer to it as the
time-to-first-token (TTFT), since it measures when the first
token is available for the user. As shown by previous studies,
users’ experience can be heavily affected by the TTFT since it
demonstrates the responsiveness of the application [14,16,60]
Importantly, TTFT includes both the network delay to re-
motely fetch the context or its KV features and the computa-
tion delay to process the context/KV features and the prompt
before decoding the first token. To focus on the impact of
long contexts, TTFT excludes two delays. First, TTFT ex-
cludes the time to decode generated tokens one by one, which
grows with the response length, so we exclude it to better
focus on speeding up the loading and processing of contexts
in the input.5 Second, TTFT excludes the delay of selecting
relevant documents based on prompt because of two reasons:
(1) this procedure is handled by another separate DNN or
algorithm than the LLM itself, which is not the focus of this
paper; (2) this delay has been optimized by recent retrieval-
based pipelines [34,48,49,52] and it is relatively marginally
compared to TTFT [63,117].
4.1
Overview
To balance the overall delay and LLM’s performance on a
given context, CacheGen employs a KV encoder/decoder and
a loading controller, depicted in Figure 6.
Given the cached KV features of a context, CacheGen’s
KV encoder first compresses the KV features into bitstream
representations. While some recent schemes [45, 76] have
proposed to shorten the context or its KV features, they do so
by dropping tokens, with inevitable information loss. More-
over, with the shortened KV features still in the shape of large
tensors in GPU memory and directly consumed by LLMs,
they still require a high bandwidth to be loaded in the first
place. In contrast, our encoder aims to compress KV features,
with the compressed features being a bitstream and will be
decompressed before being consumed by LLMs. No longer
in the shape of KV tensors, this bitstream can take on a more
compact representation with minimum information losses.
To flexibly navigate the tradeoffs between TTFT and gen-
eration performance, CacheGen compresses the KV cache of
a context in multiple bitstream representations with different
compression levels in advance before user query arrives. With
a new prompt and selected context, CacheGen’s loading con-
troller picks the compression level of the context based on the
TTFT budget, fetches it through the network, decompresses it,
and feeds it to the LLM. Notably, depending on the context’s
length, the controller may choose to load the original text of
the context when the estimated time of loading and decom-
pressing the KV features is longer than the time of loading
and processing the text directly. This often happens when the
context is relatively short or the available bandwidth to fetch
the context is relatively low, as will be shown in §5.3.

These steps of compressing KV features to a bitstream are
conceptually similar to video coding (from pixel tensors to a
.mp4 file), with each token’s KV features being a frame. How-
ever, our designs of these steps in CacheGen are inspired by
domain-specific insights on KV features produced by LLMs.
Change-based encoding: Our first insight is that if two
tokens’ positions are near each other in the context, their KV
feature values at the same channel and same layer are similar.
Figure 7 visualizes how the feature value varies across tokens,
at a specific layer and channel. We can see that the values do
change across different tokens in a context but in most cases,
they are similar among tokens of close proximity. We can
summarize this insight as follows:
Insight 1 At the same layer and channel, tokens in closer
proximity have more similar KV feature values compared to
tokens that are further apart.
Why do KV features have such token-wise locality? It does
not necessarily mean nearby tokens themselves are similar
or more correlated (and they are not). Rather, it stems from
how the transformer (the self-attention) computes the KV
features. In essence, the KV features for a given token index
are calculated based on the KV features of previous tokens.
This dependency inherently leads to numerical similarity in
their KV features across nearby tokens in a context.
To utilize this token-wise locality of feature values, we
employ two ideas:
First, instead of compressing the KV feature separately for
each token, we compress the delta between nearby tokens.

Second, we partition the tokens of a context into chunks of
ten contiguous tokens. In each chunk, we compress the KV
features of the first token, called the anchor token, indepen-
dently (i.e., without comparing it with other tokens), and then
compress the delta tensor between each remaining token and
the anchor token’s decompressed features. We do not com-
press the delta between each pair of consecutive tokens, like
in video frame encoding, for two reasons. First, by comparing
all tokens with the same anchor token, we can parallelize the
compression and decompression of multiple tokens. Second,
the tokens within a chunk may not change as smoothly (Fig-
ure 8) as between two consecutive video frames, so the benefit
of compressing the difference with the immediate last tokens
vs. with the anchor token is marginal.
Due to the token-wise locality, the resulting delta tensors
are easier to compress than the KV features themselves. This
corroborates with our component-wise results in §5.4, high-
lighting delta-based compression’s benefits.

ing [103] (AC) to losslessly compress the delta tensors and
anchor tensors of a context to bitstreams. Like other entropy
coding schemes, AC assigns fewer bits to encode more fre-
quent symbols and more bits to encode less frequent symbols.
For it to be efficient, AC needs accurate, low-entropy prob-
ability distributions of the elements in the KV cache. To
motivate our design, we first consider two strawmen:

• Fine-grained symbol distributions: Alternatively, a separate

To strike a better balance between AC’s compression ef-
ficiency and the storage overhead of the symbol probability
distributions, we should group the elements in the tensors
into as few groups as possible while minimizing the entropy
of the distribution at each group. In other words, we should
maximize the information gain of such grouping We consider
three dimensions for grouping elements in KV features: the
channel, the layer, and the position of the token in the con-
text. To examine the impact of each grouping, we pick the
contexts in the Wikitext dataset [73] and use the Llama-7B
model to produce 3.8K KV feature tensors. Figure 9 compares
the entropy across all elements vs. the entropy at individual
groups of certain layers, channels, or token indices, and their
difference indicates the information of a grouping. We can
summarize the observation in the following insight:
Insight 2 In a KV cache, each element is distinguished by
its channel, layer, and token index. The information gain of
grouping by channel and layer is significantly higher than
that of grouping by token position.
Inspired by the insight, our KV encoder offline profiles a
separate probability distribution for each channel-layer com-
bination of delta tensors and another for anchor tensors pro-
duced by an LLM, and uses the same distributions for all KV
features produced by the same LLM. In §5.4, we empirically
show that our method reduces the bitstream size by up to 53%
compared to the strawman of using one global symbol distri-
bution. Compared to the strawman of finest-grained symbol
distributions, our method stores N times fewer distributions

(l ×c), where N can be several thousand. §5.4 will quantify
the size overhead of storing these probability distributions.
Layer-wise quantization: So far, the compression (running
AC on delta tensors) has been lossless. To further reduce the
bandwidth usage of transferring the KV cache, CacheGen also
drops some information from the tokens while minimizing
the impact on LLM’s performance. Recent methods propose
to drop some tokens from the context [68,76,118], but they
must know the query (the prompt) to obtain the self-attention
scores. In contrast, we want to compress the KV feature before
the query arrives.
Instead of dropping tokens from the context, CacheGen
uses quantization to reduce the precision of the elements in
a KV cache so that they can be represented by fewer bits.
For instance, applying 4-bit quantization on a floating-point
tensor linearly rescales the original tensor to fit within the in-
teger range of [−23,23]. Quantization has been used recently
to reduce attention matrices to pack longer contexts in GPU
memory [89], but all elements are uniformly quantized with
the same number of bits without leveraging any distributional
properties of KV features. It remains unclear what a better
quantization strategy is to compress KV features while mini-
mizing the impact on LLM’s performance.
Our insight is that the impact of quantizing KV elements on
LLM’s output varies with the layers of the elements. Specifi-
cally, our insight can be summarized as follows:
Insight 3 The output from the LLM is more sensitive to losses
in the KV feature values of the shallower layers than to those
in the deeper layers.
Intuitively, KV features at the deeper layers of an LLM
extract higher-level structures and knowledge by applying NN
operations on the KV features of the shallower layers, which
embed more primitive information [100]. As a result, the loss
of information by removing precision on the shallow-layer
features can propagate and affect the deeper-layer features
and thus hinder the model’s ability to grasp the higher-level
structures necessary to produce high-quality responses.
Driven by this insight, we apply less aggressive quantiza-
tion (more bits) on the features of shallower layers of delta
tensors. Specifically, we split the transformer layers into three
layer groups, the first (shallowest) 1/3 of layers, the middle
1/3 of layers, the deepest 1/3 of layers, and apply x-bit, y-bit,
and z-bit quantization on the features at each layer group,
respectively. Each combination of (x,y,z), where x ≥y ≥z,
represents a tradeoff between compression size and loss of
the LLM performance and §4.3 will explain the exact settings
of quantization levels used in CacheGen.
Note that we still use 8-bit quantization, a relatively high
precision, on the KV features of the anchor token (the first
token of a token chunk). This is because these anchor tokens
account for a small fraction of all tokens, but their precision
affects the distribution of all delta tensors of the remaining

precision just on these anchor tokens.
4.3
Context-Loading Controller
Like any lossy compression, each compressed result of the KV
encoder represents a single tradeoff point between the com-
pressed size and the LLM’s performance. In practice, however,
the best tradeoff depends on the maximum TTFT the applica-
tion can tolerate. To flexibly navigate the size-performance
tradeoffs, CacheGen uses a context-loading controller.
First, CacheGen offline compresses the KV cache of each
context document at multiple compression levels to cover
a range of size-performance tradeoffs. By default, we pick
three quantization settings of (x,y,z): (8,6,4), (6,4,3), and
(5,4,3), where x, y and z are the number of quantized bits of
delta tensor elements at the shallowest 1/3, the middle 1/3, and
the deepest 1/3 of transformer layers (defined in §4.2). The
quantized tensors are then compressed by AC and stored on
the storage server, together with the probability distributions.
Though these quantization settings empirically work well
across a range of LLM models and datasets (§5.3), we believe
future work can further refine the quantization scheme to
make it more adaptive to LLMs or context distributions.
We should stress that the compression of each KV cache
is offline, so its delay is not part of the TTFT of loading and
processing a context, though decompression of KV features
is still part of TTFT. We will evaluate both compression and
decompression delays in §5.4.
In runtime, the application provides CacheGen with a
prompt (with length Lprompt) and the selected documents as
the context (with length Lcontext), the controller then estimates
the TTFT of each compression level k using Equation 1,
TKV(k) = Sk
B +Cdecompress(Lcontext)+Cprocess(Lprompt)
(1)
The first term represents the network delay in transferring the
compressed KV features: Sk is the size of the compressed bi-
trate of the context at level k and B is the estimated bandwidth.
The second term estimates the decompression of KV features,
which is modeled by a linear function of Lcontext. The third
term is the computation delay of calculating the attention be-
tween context and the prompt, which is empirically modeled
as a quadratic function of the prompt length, Lprompt.
In addition, the controller also estimates the TTFT if the
context is loaded as raw text as follows:
Ttext = RTT +Cprocess(Lcontext +Lprompt)
(2)
The first term is the round-trip-time (RTT) between the stor-
age server and the GPU server. We use it to estimate the net-
work delay because the context test is usually small enough
to fit in one congestion window size. The second term is the
GPU computation to compute the attention from scratch
With these delay estimates, the controller can then decide
whether it is faster to load the text context or some compressed
KV features (and which compression level). If the application
also specifies a TTFT budget, then the controller can pick the
minimum compression level k that fits the budget.
The exact parameters in function Cprocess and Cdecompress
depend on the speed of the inference server, and in our ex-
periments, we record the past compute delays from the same
server and interpolate these parameters. In this work, we as-
sume the estimated bandwidth B and the estimate of RTT
are known beforehand. In practice, they can be obtained by
probing or controlled bandwidth in data center [24, 51, 81].
And this is beyond the focus of this paper.
4.4
Implementation
We implement CacheGen with about 2K lines of code in
Python, based on PyTorch v2.0 and CUDA 12.0.
Quantization, arithmetic coding (AC): Following previ-
ous work [41], we use the vectorwise quantization method,
which has been usually used for quantizing model weights.
We use torchac [72], a CPU-based AC library designed for
Pytorch tensors. Particularly, we use its encoding and decod-
ing functions to perform AC. The probability distributions are
obtained by counting the frequencies of quantized symbols in
the KV feature for the corresponding context.
Interface with LLM: CacheGen interacts with LLM in-
ference via two simple interfaces: (1) CacheGen extracts
the KV features of a given context from an LLM inference,
and (2) CacheGen feeds the KV features (which can be the
decompressed ones) to resume the LLM inference while skip-
ping the attention computation on the context. Many Pytorch-
based LLMs support these APIs. For instance, Huggingface
provides these APIs as part of each LLM model’s forward
method [104].
Speed optimization for CacheGen: To speed up the decom-
pression of KV features, we parallelize the decompression of
delta tensors (explained in §4.2), running multiple instances
of torchac simultaneously. Optionally, we further speed up
the loading of decompressed KV features to GPU by pipelin-
ing the loading of layer i with the DNN inference computation
of layer i+1.

• Given a context, how much can CacheGen’s KV encoder

• Given a network bandwidth, how much can CacheGen re-

• How sensitive is CacheGen’s performance gain across dif-

• Does CacheGen have a better tradeoff between LLM per-

5.1
Setup
Models and testing datasets: We evaluate CacheGen on
three pipelines, summarized in Table 1, that span models with
different sizes and datasets for different tasks.
• Pipeline A tests the Llama-13b model and Llama-7b
model [3], both scaled with Neural Tangent Kernel (NTK),
on the Wikitext [73] dataset. The task is to predict the prob-
ability of the next token in a sequence based on the context
consisting of relevant documents that belong to a specific
Wiki page. The Wikitext dataset covers a wide range of top-
ics, with the context length ranging from 1.8K-24K tokens.
• Pipeline B tests the LongChat-7b-16k model [62] on the
LongChat [62] dataset, recently released to test LLMs on
queries like “What was the first topic we discussed? ” based
on all the previous conversations as the context. Most con-
texts are around 9K-9.6K tokens. We chose LongChat-7b-
16k since it is one of the best models on this dataset.
• Pipeline C tests the T5-large model [84] on Natural Ques-
tion dataset [58], a question-answering dataset developed
by Google. Following previous work (e.g., [49]), it tests the
model to answer user queries from a Q & A dataset with the
context from Wikipedia documents relevant to the queries.
Most contexts are around 8K-12K tokens.
It is worth noting that these pipelines represent the two typical
apps with long contexts (§2.2): chat apps (Pipeline B) and
retrieval-based apps (Pipeline A and C).
LLM task performance: We measure generation quality
using the standard metric of each dataset.
• Perplexity is used to evaluate the model’s performance on
the Wikitext dataset. The perplexity is defined as the ex-
ponentiated average negative log-likelihood of the next
token [23, 33]. A low perplexity means the model likely
generates the right next token. While perplexity does not
equate to text-generation quality, it is widely used as a
decent proxy [17]. This metric has been commonly used
by prior works to test the impact of pruning or quantizing
LLMs on generation performance [41,68,87,107].
• Accuracy is used to evaluate the model’s output on the
LongChat dataset. The task predicts the first topic in the
conversational history between the user and the LLM. The
accuracy is defined as the percentage of generated answers
that exactly includes the ground-truth topic.
• F1 score is used to evaluate the model’s response in the
Natural Questions dataset. It measures the probability that
the generated answer matches the ground truth answer of
the question-answering task.
Baselines: We compare CacheGen with baselines that do not
change the contexts or model (§5.4 evaluates more baselines).
•“Original KV” uses torch.save to serialize the KV fea-
tures in GPU memory to a file. This serves as a reference
for the most straightforward implementation.
•“Default quantization & AC” combines the uniform quanti-
zation of KV features [89] with the default arithmetic cod-
ing (AC) that uses a global probability distribution for all

as well as the ability to choose to load text context when the

These reductions in KV cache sizes and TTFT confirm

Microbenchmarks
Breakdown of online delays: While having better com-
pression efficiency on KV features, CacheGen does incur
(marginally) more overhead than the baselines. To examine
the overheads in delays, Figure 13a breaks down the TTFTs of
CacheGen and the baselines on a context of 8.5K tokens into
data transfer, decompression (or torch.load), CPU-GPU
data movement, and computation by LLM in GPU. We can
see that while CacheGen has slightly more non-transmission
delays, particularly decompression, it is overwhelmingly com-
pensated by its reduction in transmission. This figure confirms
our illustration in Figure 4.
Offline delays and storage overheads: Unlike prior methods
that compress each context only once, CacheGen compresses
multiple versions (§4.3), and Figure 13b and 13c evaluate
the overheads in delays and storage. We can see that despite
needing to encode and store multiple bitstream representa-
tions, the total, CacheGen still requires less storage than the
baselines since each version requires much less space than the
baselines. CacheGen compresses each context almost as fast
as the baselines because the additional compression delays
are much smaller than computing KV features.
CacheGen vs. more intrusive methods: So far, all methods
we have evaluated, including CacheGen, do not modify the
LLM or context. As a complement, Figure 14 tests CacheGen
against recent methods that change the context or LLM.
• Smaller models: Replacing the LLM with smaller mod-
els may speed up the computation. Figure 14a replaces
the Llama-7B model with a smaller Llama-3B and applies
different quantization levels.
• Token selection: Figure 14b uses Scissorhands as an ex-
ample of removing tokens with low self-attention scores
from the LLM input [68]. Since the self-attention scores
are only available during the actual generation, it cannot
reduce TTFT, but we make an effort to create an idealized
version of Scissorhands (Scissorhands*) by running the
self-attention offline to determine which tokens to drop and
provide this information to Scissorhands* online.
• Context selection: Another trick used by some retrieval-
based apps is to select fewer documents as the context. We
test this idea on Pipeline C because the dataset already has
this optimization. By default, it picks the top 20 documents
as context, and Figure 14b tries top-10 and top-4.
• Gisting Finally, we test Gisting as an example of a more
advanced method that shortens contexts into gist tokens
and changes the LLM to accept the gist tokens [76]. In
Figure 14c, we test the pre-trained gisting model, which is
based on Llama-7B. The gisting model retrains the LLM’s
attention model in order to run inference on a compressed
version of the input prompts. Since the gisting model can
compress arbitrary long contexts into one token, we vary the
compression ratio of the gisting model to obtain a trade-off
in size and accuracy. This is done by adapting the frac-
tion of input tokens that are compressed into one token.
We apply CacheGen on the original Llama-7B model on
the PIQA [27] dataset, which is one of the most popular
question-answering datasets. We did not apply CacheGen
on other datasets in our evaluation because the public pre-
trained gisting model can only take up to 512 tokens, and
truncating the dataset into smaller chunks will not be able
to preserve the information in the context.
We can see that CacheGen outperforms these baselines, re-
ducing TTFT or KV cache size while achieving similar or
better LLM’s performance on the respective tasks. In par-
ticular, CacheGen is faster than smaller models (which are
slowed down by transformer operations), and can reduce KV
cache better than context selection or gisting because it com-
presses the KV features to more compact bitstream repre-
sentations. We want to stress that even though CacheGen is
compared head-to-head with these methods, it makes no as-
sumption about the context and the model, so one can combine
CacheGen with these methods to potentially further improve
the performance.

Related work
Faster LLM serving: The landscape of LLM systems re-
search is fast evolving. Besides speeding up LLM training
(e.g., [86,91]), many recent efforts, including ours, focus on
the LLM serving systems. Some try to parallelize the gen-
eration of multiple tokens with smaller approximating mod-
els [59, 74] and accelerate the inference of Mix-of-Expert
LLMs on edge devices [111]. Others quantize LLM model
weights (e.g., [22]), reduce memory I/O of GPU on-chip
SRAM [39], and reduce self-attention computation complex-
ity by k-means [87]. New scheduling strategies are also pro-
posed for LLM services [105,112]. Nonetheless, a common
approach to speeding up without modifying the LLMs is by
caching KV features of repeatedly used input sequences, such
as contexts [38, 63, 67, 74, 80, 82, 89, 104, 105, 118]. How-
ever, caching KV features results in a dramatically increased
amount of cached data, which requires a bandwidth-efficient
KV/context-loading system like CacheGen.
Longer LLM input (context): Though the benefits of longer
contexts are still under scrutiny [66,87,93], many recent ef-
forts aim at enabling LLMs to accept ever longer contexts.
The main challenge is to hold the attention matrices of more
tokens without needing a bigger GPU memory. They enable
longer input sequences by dynamically offloading less used
parts of the attention matrices [89], using external knowledge
via KNN [106], retraining the self-attention module to only
attend to top-k keys to approximate the full attention [21,26],
mapping long inputs into smaller latent space [47], using local
windowed self-attention [25], or using dilated attention [42]
or sparse attention [113] to scale the input length to even 1
billion tokens. However, the longer inputs (contexts) also in-
flate the KV cache, and this work complements these efforts
by focusing on fast remote loading of KV cache.
Context shortening/pruning: More relevant to our work
is the emerging literature on shortening and pruning long
contexts. These efforts select the most important text seg-
ments and prune out the others to reduce context length, based
on the similarity between the user query and the potentially
relevant documents (e.g., [28]), or drop tokens that are less
attended to by the current prompt [67,118]. Different from
them, CacheGen compresses the KV cache into bitstreams,
rather than shortening the context in its original form (i.e.,
text or tensor). Furthermore, unlike [28,67,118], CacheGen’s
KV compression does not need to know the query (prompt).
Recently, some work retrains LLM models to directly
take in contexts that are rewritten by gisting [76] or auto-
encoding [45]. Different from them, CacheGen does not need
to train a new LLM model and also achieves better compres-
sion rate with less information loss by leveraging unique
distributional properties of KV features. Finally, we show
CacheGen achieves better delay-quality tradeoffs than exist-
ing context compressors (§5.4). and can potentially be com-
bined with them to further improve the delay-quality tradeoffs.
Tensor compression: CacheGen’s KV encoder can be seen
as a special tensor compression technique tailored for KV
features produced by LLMs. General tensor compression has
been intensively studied, e.g., relaxing rank and ordering con-
straint [119] or decomposing large tensors into products of
smaller ones [79]. In model training systems, tensor compres-
sion has been used to compress gradient updates of DNN
weights (e.g., [18, 19, 102]). Nonetheless, KV features and
gradients have very different properties. For instance, these
training systems often leverage the sparsity of gradient up-
dates but KV features are typically not as sparse.
Retrieval-augmented generation:
A wide range of
works [28,48,49,53,61,63,88,90,101,108–110] focus on
optimizing retrieval-augmented generation. The workflow of
retrieval-augmented generation includes retrieving relevant
documents to the user’s question, and feeding the retrieved
documents as the context to the LLMs to generate the answers
to the question. Upon receiving a question submitted by the
user, the application decides the relevant documents by com-
12


=== PDF page 13 ===
paring the question with documents in the database via simi-
larity search algorithms, such as dense or sparse vector meth-
ods [31,77,109] and DNN-based schemes [53,61,108,110].
For example, FiD [48] represents the prompt text and the doc-
uments’ text in the form of “bag of words” and ranks the rele-
vance of the documents with the term frequency-inverse doc-
ument frequence (TF-IDF). As another example, Atlas [49]
pre-trains a BERT-based retriever, which encodes the prompt
text and documents’ text into vectors, and searches for top-k
documents whose embeddings are most relevant to the prompt.
The application then concatenates the retrieved documents
with the user query as the context to the LLMs.
Another line of research develops applications that cache
query results from LLMs to reduce repetitive query costs [71,
95]. These applications convert user queries previously sub-
mitted by a user into semantic embeddings, which are DNN
features8 that represent the semantic meaning. The applica-
tions then store them in vector databases [36,44,70,99], which
are designed to store high-dimensional vectors and enable
vector-based queries. When queries with similar semantic
embeddings come, cached answers are retrieved to reduce
latency. These works are complementary to us, as they focus
on enabling the efficient storage and retrieval of the cached
vectors, usually the semantic embeddings of the queries, not
the KV features, while CacheGen focuses on reducing the
bandwidth usage needed to transfer the KV features.
7
Limitations
Due to GPU memory limitations, we have not yet evalu-
ated our ideas on extra-large models, such as OPT-175B. We
also did not extensively evaluate CacheGen’s performance on
“free-text generation”, which we leave as a future work. Our
evaluation uses a simple network model of transmission delay
that will not work under high bandwidth variations. Finally,
not all applications can naturally cache KV features. Search-
based apps, like Google and Bing, use real-time search results
as context, and their volatile contexts will unlikely be reused
unless for very popular search results. We expect future works
can address these issues.
8
Conclusion
We present CacheGen, a context-loading module to minimize
the overall delays in fetching and processing contexts for
LLMs. CacheGen reduces the bandwidth needed for transmit-
ting long contexts’ KV cache through an encoder tailored to
compress KV features into compact bitstreams. Experiments
across three models of various capacities and three datasets
with different context lengths show that CacheGen can reduce
the overall delays while maintaining high task performance.
